SQL NULL vs JSON null

Lesson 36 shipped. Your delete route now writes a snapshot, and I can see it in your database. Then I went to write the first filter the audit page needs — show me the rows that have a snapshot — and it came back with 216 rows that have no snapshot. The filter is correct SQL. The column is correct. Postgres is right. jsonb can hold a value that is the word null, and that is not the same as an empty cell.

In one minute

  • A jsonb column has two kinds of nothing. SQL NULL = the cell is empty. JSON null = the cell holds a real value, and that value is the JSON word null.
  • IS NULL only finds the first one. A row holding JSON null is a row with a value, so it fails IS NULL and passes IS NOT NULL.
  • Measured on your database right now: 216 audit rows hold JSON null in targetSnapshot, and 3,960 hold it in params. Not one params cell in the whole table is actually empty.
  • You wrote them that way yesterday. params: row.params ?? null looks like “leave it empty”. To Prisma, null on a Json? field means “store the JSON word null”.
  • Prisma makes you say which one — Prisma.DbNull for the empty cell, Prisma.JsonNull for the word. It refuses to guess, which is the good design; passing plain null is where it stopped being obvious.
  • Fix: undefined, not null. An omitted field takes the column default, which is SQL NULL. One word per line, then one backfill migration for the 4,176 rows already written.

What the two nothings actually are

SQL NULL — the cell has no value. It is the database saying “nothing here”. It matches IS NULL. It is never equal to anything, not even to another NULL.
JSON null — the cell has a value, and the value is the JSON literal null. It is four bytes of stored data. It matches = 'null'::jsonb. It fails IS NULL.

Postgres is explicit about this, and it is worth reading in their words: PostgreSQL — JSON functions notes that a JSON null value is processed differently from a SQL NULL. The reason there are two is that JSON is a document format with its own null, and the column has to be able to store a document faithfully — including one whose value really is null.

Row with JSON null

params = 'null'::jsonb

IS NULL        -> false
IS NOT NULL    -> true
jsonb_typeof   -> 'null'
params->>'id'  -> NULL

Row with SQL NULL

params = NULL

IS NULL        -> true
IS NOT NULL    -> false
jsonb_typeof   -> NULL
params->>'id'  -> NULL

Look at the last line of each. params->>'id' gives NULL either way. That is why nothing has ever complained: every read you have written so far happens to survive both. The first read that does not survive both is IS NULL, and that is the read the audit page needs.

Where it came from — one word in your code

Here is the line, in src/audit/audit.ts:

params: (row.params ?? null) as never,
targetSnapshot: (row.targetSnapshot ?? null) as never,

Read that as English and it says “if there is nothing, store nothing”. Read it as Prisma and it says something else. For a Json? field, Prisma treats these three inputs as three different instructions:

{ params: undefined }            // ? don't set the column -> stays at its default -> SQL NULL
{ params: Prisma.DbNull }        // ? set the column to SQL NULL, explicitly
{ params: Prisma.JsonNull }      // ? set the column to the JSON word null
{ params: null }                 // ! shorthand for JsonNull. This is the one you wrote.

Prisma documents this and even gives it a name — Working with Json fields — using null values. It invented two sentinel values because plain null is ambiguous here. Two nothings in the database means the client needs two words for them.

And that as never. It is on both lines. Prisma's type for that field is a union that does not include plain null, so TypeScript was going to tell you. as never is the cast that told it to be quiet. This is lesson 34 again, from the other side: there, a declared type was believed without a check. Here, a real check was switched off by hand. The compiler knew.

A cast is a promise you make to the compiler. When you break the promise, nobody tells you — that is the entire point of a cast.

The fix

Two words in src/audit/audit.ts. undefined means “do not set this column”, the column default is SQL NULL, and the casts come off because the types now agree:

params: row.params ?? undefined,
actorEmail: row.actorEmail ?? null,      // ? String? -- plain null is fine and correct here
targetType: row.targetType ?? null,
targetId: row.targetId ?? null,
targetSnapshot: row.targetSnapshot ?? undefined,

Only the two Json fields change. String? and Int? have one kind of nothing, so null was always right for them. The ambiguity is a Json-only problem.

Then the 4,176 rows already written. This is a data migration, and it is the honest kind — it does not invent anything, it corrects a shape:

npx prisma migrate dev --create-only --name audit_json_null_to_sql_null
-- prisma/migrations/*_audit_json_null_to_sql_null/migration.sql
UPDATE "AuditLog" SET params = NULL          WHERE params = 'null'::jsonb;
UPDATE "AuditLog" SET "targetSnapshot" = NULL WHERE "targetSnapshot" = 'null'::jsonb;
Yes, this is an UPDATE on an append-only table. Notice that it is allowed today only because you have not run the REVOKE from lesson 36. Do this correction now, while the table is still writable, and let that be the argument for why the revoke belongs at the end of week 13 rather than the start. It changes no fact in any row — both values already meant “there was nothing”.

Check yourself

A jsonb cell holds the value null. What does IS NULL answer?

IS NULL asks about the cell, not about the contents. The cell holds four bytes of JSON, so it is not empty, so the answer is false. This is exactly why the count came back 218 when only 2 rows had a real snapshot.

In Prisma, what does { params: undefined } do to a Json? column?

undefined means “this field is not part of my write”. Prisma omits it from the INSERT, the column falls back to its default, and the default for a nullable column is SQL NULL. Plain null is the one that writes the JSON word.

Why did no test ever catch these 3,960 rows?

Every read you had written used params->>'id' or read the value in JavaScript, and both give the same answer for the two nothings. A bug in stored data is invisible until a query asks the one question that can tell them apart. Your fixtures do delete rows, but that is not what hid this.

Two nothings in the store means two words in the client. When a library gives you two names for what looks like one thing, that is the library telling you the thing is not one thing.
