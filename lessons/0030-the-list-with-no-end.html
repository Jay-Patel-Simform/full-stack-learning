Cursor pagination

Your GET /teams/:teamId/tasks has no limit. Not a big limit — no limit. Whatever is in the table comes back, every time. Today that is 5 rows, so nothing hurts. I put 5,000 rows in a scratch team and measured what happens next. Then I found a second query nobody asked for, reading a column nobody is allowed to see.

In one minute

  • No limit means the caller decides how much memory you use. 5,000 rows: 15 ms and every row in Node’s memory. Ask for 20 instead: 3 ms.
  • include: { owner: true } in listTasks fires a second query — and that query SELECTs "User"."passwordHash". The response schema throws the owner away before it reaches the wire. So you pay for it, load it into memory, and send none of it.
  • A cursor beats an offset. Prisma turns cursor into a real WHERE id >= ..., so page 250 costs the same as page 2.
  • Measured: the index you already have is enough for ?sort=id and useless for ?sort=createdAt. Adding @@index([teamId, createdAt]) took that query from 0.814 ms to 0.025 ms — and changed the plan from “read 5,000 rows, then sort” to “read 20 rows”.
  • The reply shape has to change, from Task[] to { items, nextCursor }. I applied the whole change: 4 tests break, and one line of the front end.

The word pair

offset — “skip the first 4,980 rows, then give me 20.” The database still has to walk past all 4,980 to know where to stop.
cursor — “give me 20 rows after the row with id 4980.” The database jumps straight there, because the index is sorted.

An offset asks the database to count. A cursor asks it to look up. Counting gets slower every page. A look-up does not.

Measured, on your table, just now

Real Task table, real Postgres, a throwaway team with 5,000 tasks. I deleted the team afterwards; your table is back to 5 rows.

all rows + include owner:  20ms  5000 rows   <- what your code does today
all rows, no include:      15ms  5000 rows
take 20, no include:        3ms    20 rows
page 2 by cursor:           2ms    20 rows
page 250 by cursor/skip:    2ms    20 rows   <- the last page costs the same
Be honest about the size of this. 20 ms is not slow, and 5,000 rows is not big. The number that matters is not the milliseconds — it is that the caller picked it, not you. Every row also becomes a JavaScript object in your one Node process. 5,000 objects is fine. The same code with 500,000 rows is one request that eats the heap, and a second one that arrives while the first is still building the array. A limit is not a speed feature. It is the ceiling on what one request can cost you.

The second query nobody asked for

Turn on Prisma’s query log and call listTasks once. It is not one query:

SQL: SELECT "Task"."id", "Task"."title", "Task"."done", "Task"."createdAt", ...
SQL: SELECT "User"."id", "User"."email", "User"."passwordHash", "User"."createdAt" ...

That second line comes from one word in src/store/task.store.ts:

today

return prisma.task.findMany({
  where: { teamId },
  orderBy: { [sort]: dir },
  include: { owner: true },
});

what the caller receives

[
  { "id": 1, "title": "buy milk", "done": false }
]

// TaskPublic has three fields.
// No owner. Never had one.
overfetching — loading data you will not use. It costs a query, memory, and time, and it returns nothing to the person who asked.

The serializer is doing its job perfectly. TaskPublic lists three fields, so three fields go on the wire — that is the lesson 17 rule still holding. But the response schema guards the wire, not the query. Every password hash in that team already travelled from Postgres into your Node process before the serializer ever saw it.

A field the response schema drops is a field you should not have selected. The schema is the last wall, not the first one.

The name for the sibling bug, so you recognise it later. N+1 is one query for the list, then one more per row — 1 + 5,000 round trips. That is not what your code does: Prisma batches the owners into a single second query, so this is 1+1, not N+1. Same family, different size. You get the real N+1 the day you write for (const task of tasks) { await getOwner(task.ownerId) }. The way you find both is the same: turn on the query log and count the lines.

The index question, answered by measuring

You already have @@index([teamId]) on Task. Is that enough? It depends entirely on ?sort=, and EXPLAIN ANALYZE will tell you rather than guess. Both runs below are the same 5,000-row team.

?sort=createdAt — the index does not cover it

Limit  (actual time=0.804..0.806 rows=20)
  -> Sort  (actual time=0.803..0.804 rows=20)
       Sort Key: "createdAt" DESC
       Sort Method: top-N heapsort  Memory: 26kB
       -> Index Scan using "Task_teamId_idx"  (actual time=0.005..0.435 rows=5000)
            Index Cond: ("teamId" = 573)
Execution Time: 0.814 ms

Read the two rows= numbers. Postgres read 5,000 rows and returned 20. It had to: the index knows the order of teamId, and nothing about createdAt. So it collects every matching row and sorts them, and the LIMIT 20 only applies at the very end.

Same query, after adding @@index([teamId, createdAt])

Limit  (actual time=0.014..0.016 rows=20)
  -> Index Scan Backward using Task_teamId_createdAt_idx  (actual time=0.013..0.015 rows=20)
       Index Cond: ("teamId" = 573)
Execution Time: 0.025 ms

The Sort step is gone. So is rows=5000. The index is already stored in (teamId, createdAt) order, so Postgres walks it backwards, takes 20, and stops. 32× faster, and it stays 32× as the table grows — the sort version gets worse with every row you add, the index version does not.

And now the part that says “do not add the index”

Your default sort is id, not createdAt. I measured that one too, with only the index you have today:

Limit  (actual time=0.007..0.009 rows=21)
  -> Index Scan using "Task_pkey"  (actual time=0.006..0.008 rows=21)
       Filter: ("teamId" = 574)
Execution Time: 0.017 ms

No sort, 21 rows read, faster than the compound-index version. The primary key is an index on id, already in order, so Postgres walks it and filters as it goes. A (teamId, id) index measured slower here (0.025 ms).

Add the index for the query you actually run, after EXPLAIN ANALYZE shows you a Sort you do not want. An index is not free: every INSERT writes to it too.

One caveat on that last plan, because a number without its conditions is a lie. The primary-key scan is fast there because that team owns 5,000 of the 5,005 rows — almost nothing gets filtered out. A team with 30 tasks in a table of 50,000 is a different question, and I measured that too: Postgres switched back to Task_teamId_idx plus a sort of 30 rows, and both versions were under 0.05 ms. EXPLAIN tells you about your data, not about databases in general. Re-run it when your data changes shape.

The change — type it yourself

I applied all of it to your files, ran tsc and the suite, then put your files back byte-for-byte. Numbers below are what I actually saw.

1. server/src/schemas/task.schema.ts — the query gets two more keys

  export const TaskQuery = z.object({
    sort: z.enum(["id", "title", "createdAt"]).default("id"),
    dir: z.enum(["asc", "desc"]).default("asc"),
+   // ! A limit with no ceiling is not a limit. ?limit=1000000 is a caller
+   // ! asking the server to load the whole table into memory, politely.
+   limit: z.coerce.number().int().min(1).max(100).default(20),
+   // ? Where the last page stopped. Absent means "start at the beginning".
+   cursor: z.coerce.number().int().positive().optional(),
  });

Both are caller input, so both go through the wall, same as everything since lesson 2. Note .max(100). Without it, ?limit=999999999 is a legal request and you are exactly where you started.

2. Same file — a page is not an array

+ // * A page, not a bare array. The array alone cannot say "there is more".
+ export const TaskPage = z.object({
+   items: z.array(TaskPublic),
+   // ? null = this was the last page. Do not ask again.
+   nextCursor: z.number().nullable(),
+ });

This is the part that costs you. A bare array has nowhere to put “there is more”. Every caller has to change.

3. server/src/store/task.store.ts — the real work

- export function listTasks(teamId: number, { sort, dir }: TaskQueryInput): Promise<Task[]> {
-   return prisma.task.findMany({
-     where: { teamId },
-     orderBy: { [sort]: dir },
-     include: { owner: true },
-   });
- }
+ export async function listTasks(
+   teamId: number,
+   { sort, dir, limit, cursor }: TaskQueryInput,
+ ): Promise<{ items: Task[]; nextCursor: number | null }> {
+   const rows = await prisma.task.findMany({
+     where: { teamId },
+     // ! Two keys, not one. `title` is not unique, so on its own it leaves ties
+     // ! in an order Postgres never promised -- and a cursor into an unstable
+     // ! order skips rows. `id` is the tiebreak that makes every row unique.
+     orderBy: [{ [sort]: dir }, { id: dir }],
+     // ? One row more than asked. If it comes back, there is a next page.
+     take: limit + 1,
+     // ? skip:1 steps over the cursor row itself, which we already sent.
+     ...(cursor ? { cursor: { id: cursor }, skip: 1 } : {}),
+   });
+   const items = rows.slice(0, limit);
+   return { items, nextCursor: rows.length > limit ? items.at(-1)!.id : null };
+ }

Three ideas in there, and the middle one is the one people get wrong.

  • take: limit + 1 is how you answer “is there more?” without a second COUNT(*) query. Ask for 21, get 21 → there is a page 2. Get 20 or fewer → that was the end. You send 20 either way.
  • The tiebreak. orderBy: { title: "asc" } alone is not a total order: two tasks called “fix bug” can come back in either order, and Postgres is allowed to change its mind between the two requests. A cursor into an order that shifts under you skips rows silently. Adding id as a second key makes the order unique and therefore stable.
  • The include is gone. One query instead of two, no password hashes in memory, and the reply is byte-for-byte identical because TaskPublic never had an owner in it.

Look at the SQL Prisma writes for the cursor

This is worth reading once, because it is the whole idea in one line. With the tiebreak in place:

SELECT ... FROM "Task"
WHERE "teamId" = $1
  AND ( ("title" = (SELECT "title" FROM "Task" WHERE "id" = $2) AND "id" >= (SELECT "id" ...))
     OR  "title" > (SELECT "title" FROM "Task" WHERE "id" = $4) )
ORDER BY "title" ASC, "id" ASC LIMIT $5 OFFSET $6

Read the WHERE out loud: “same title as the cursor and a bigger id, or simply a bigger title.” That is a position in a sorted list, expressed as a comparison. It is the reason page 250 is not slower than page 2 — and the reason the tiebreak is not optional, because without it there is nothing to compare.

4. server/src/routes/tasks.route.ts — one line, plus the import

-         response: { 200: z.array(TaskPublic), 403: ErrorReply },
+         response: { 200: TaskPage, 403: ErrorReply },

The handler body does not change at all. It already returns whatever listTasks returns.

5. web/src/features/tasks/tasks.ts — one line, and the blast radius is bigger than it looks

- await api.get<Task[]>(`/teams/${teamId}/tasks`, { params: ... })
- ).data,
+ await api.get<{ items: Task[]; nextCursor: number | null }>(`/teams/${teamId}/tasks`, { params: ... })

Only useTasks changes. The three mutations below it keep working untouched, because the cache still holds a plain Task[] — you unwrap the page at the edge and the rest of the app never learns about it. That is not luck; it is the lesson 25 shape paying off.

What this change quietly does to your UI, said out loud. The panel now shows the first 20 tasks and silently drops the rest. nextCursor comes back and you throw it away. That is an acceptable place to stop today — you have 5 tasks — but it is a real, invisible bug the moment a team has 21. The fix is React Query’s useInfiniteQuery and a “Load more” button, which is a front-end lesson and not this one. Write yourself a TODO in tasks-panel.tsx, not in your head.

The new test file

server/src/routes/task-page.test.ts, its own file with its own fixture, same rule as every other test file here. The interesting one is the second: it walks the whole list by cursor and proves no row is seen twice and none is missed.

test("the cursor walks the whole list once, with no row seen twice", async () => {
  const seen: number[] = [];
  let cursor: number | null = null;
  let pages = 0;
  do {
    const res = await list(`?limit=10${cursor === null ? "" : `&cursor=${cursor}`}`);
    assert.equal(res.statusCode, 200);
    seen.push(...res.json().items.map((t: { id: number }) => t.id));
    cursor = res.json().nextCursor;
    pages += 1;
    assert.ok(pages < 10, "the cursor is not advancing");
  } while (cursor !== null);

  assert.equal(pages, 3);            // ? 10 + 10 + 5
  assert.equal(seen.length, TOTAL);  // ? nothing missed
  assert.equal(new Set(seen).size, TOTAL); // ? nothing seen twice
});

Two lines there are the whole point of writing this test at all. new Set(seen).size catches the skip: 1 being missing, which sends the cursor row again on every page. And pages < 10 stops a broken cursor from turning your test suite into an infinite loop — a test that hangs tells you nothing and blocks everything.

With the four fixes and this file, I measured 146 passing, 0 failing.

Check yourself

Why ask the database for limit + 1 rows?

You need to answer “is there more?” and there are only two ways: a second SELECT COUNT(*) over the whole table, or one extra row. The extra row is free — it is in the index you are already walking. If 21 come back you send 20 and a nextCursor; if 20 or fewer come back, that was the last page and nextCursor is null. The count version is a second full scan of the team’s rows just to render a page number.

Why add id as a second orderBy key?

Sorting by title alone leaves rows with the same title in whatever order Postgres finds convenient, and it may answer differently on the next request — there is no promise. A cursor is a position in a sorted list, so a list whose order can shift means a cursor that points somewhere else next time: rows get skipped, or repeated, and no error is raised. id is unique, so (title, id) is a total order: every row has exactly one place. Prisma requires nothing here; it will happily generate the broken version.

TaskPublic already hides the owner. Why remove the include?

The serializer is reliable — three fields declared, three fields sent, and that is not the problem. The problem is upstream of it. include: { owner: true } makes Postgres run a second query that selects passwordHash, and those hashes are decoded into JavaScript objects inside your one Node process before the serializer runs. You paid for a query, filled memory with secrets, and shipped none of it. Data you do not select cannot be leaked by the next bug, the next log line, or the next console.log a tired person adds at 2am.

EXPLAIN shows rows=5000 feeding a Sort under a LIMIT 20. What is wrong?

An index was used — Task_teamId_idx is right there in the plan. It just answers the wrong half of the question. It knows how to find this team’s rows, and nothing about their createdAt order, so Postgres must collect all 5,000 before it can know which 20 are newest. The LIMIT cannot help until the sort is finished. A (teamId, createdAt) index stores the answer pre-sorted, so the plan becomes read-20-and-stop. The habit worth keeping: in any plan, compare the rows= going in with the rows= coming out.

Each tick is one row the database touches. Red = walked past and thrown away. Green = actually returned to you.

2. Read a query plan in two numbers

Same query, same 5,000 rows, ORDER BY "createdAt" DESC LIMIT 20. Only the index changed.

  team 7 -> already in
  createdAt order

An index is not “make this table fast”. It is one stored order. It helps the query that asks for that order, and does nothing for the others.
