Lesson 02 · Week 1–2 · API basics

Making validation the default

Lesson 1 asked you to remember the wall. A wall you remember is a wall you forget. Today you declare it instead.

In one minute

  • Move the check into the route definition. Fastify runs it for you, before your handler.
  • Add a second check on the way out. It deletes any field you did not name.
  • Two walls: one stops bad input, one stops leaks.

The picture

The idea

Lesson 1's check lived inside the handler. That means every new route needs you to remember to write it. Twenty routes in, one of them will not have it. That one is the hole.

Fastify lets you attach the schema to the route itself. Now the check is part of the route's definition, not part of your discipline.

Then the second half, which is the new idea: your handler returns a database row. That row has columns the caller must never see. Declare what the reply looks like, and everything else is stripped.

declare — write down what you want and let the framework enforce it. The opposite of doing it by hand each time.

The code

Lesson 1 — remembered

app.post("/tasks", async (req, reply) => {
  const p = CreateTask.safeParse(req.body);
  if (!p.success) return reply.code(400)...
  return store.create(p.data);
});

Lesson 2 — declared

app.post("/tasks", {
  schema: {
    body: CreateTask,
    response: { 201: TaskReply },
  },
}, async (req) => store.create(req.body));

req.body is now safe to use directly, because Fastify already replaced it with the checked copy.

Make the safe thing the default thing. Then forgetting is not possible.

Check yourself

What is the reply schema actually protecting you from?

Input schemas stop bad writes. The reply schema stops leaks — a column added to the table next month does not silently start appearing in your JSON.

Do this

  1. Add a junk column to the reply object in your handler. Confirm it never reaches the client.
  2. Send {"title":"hi","admin":true}. Look at what got stored.
