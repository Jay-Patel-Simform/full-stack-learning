Lesson 25 · Week 10 · Front end

Mutations from the front end

The list gets a checkbox. That is your first write from the page — and a write has two problems a read never had: what to say when the network is slow, and what to believe when the server says no.

In one minute

  • Send the value you want — { done: true }. Never /toggle. A verb is a bet on what the server currently holds; a value is not, so sending it twice is harmless.
  • The reply is the new row. PATCH answers 200 with the whole task, so write it into the cache with setQueryData and pay nothing more.
  • Do not invalidate what you are already holding. That is a second round trip for data in hand.
  • The checkbox has no useState. Its checked comes from the cache. That is not tidiness — it is the rollback.
  • A refused write leaves the cache untouched, so the box un-ticks itself. The cheapest rollback is having nothing to roll back.

The word pair

idempotent — doing it twice lands in the same place as doing it once. { done: true } is. toggle is the opposite: run it twice and you are back where you started.
authoritative reply — a response that is the new state, not a receipt saying a change happened. Worth a status code of its own, because it saves the next request.

A double-click, a retry, a flaky tunnel — all of them send your request twice. Say something that survives being said twice.

Measured, on your API, just now

PATCH /teams/443/tasks/359   {}                        400  "send at least one field to change"
PATCH /teams/443/tasks/359   {"done":"yes"}            400  "done: expected boolean, received string"
PATCH /teams/443/tasks/359   {"done":false,"ownerId":1} 400 "Unrecognized key: \"ownerId\""
PATCH /teams/444/tasks/359   {"done":true}             403  {"error":"forbidden"}
PATCH /teams/443/tasks/999999 {"done":true}            404  {"error":"not found"}

Line 1 and line 2 are the same reply. That is the whole design: the second one changed nothing and still answered success, because you sent a value, and the value was already there. A POST /tasks/359/toggle would have un-ticked it.

Lines 3 to 5 are the wall from lesson 17 still standing — an empty patch, a wrong type, and a field you were never allowed to set, all refused before the handler runs. Lines 6 and 7 are lesson 24's two refusals, unchanged by the fact that this is now a write.

Why no CSRF token. This PATCH is a write from a page, and nothing extra is needed: the browser sends Sec-Fetch-Site: same-site, a header page JavaScript is forbidden to set, and allowWrite checks it against ALLOWED_ORIGINS (lesson 16). The defence you wrote nine lessons ago is why today's lesson is short.

The code — type it yourself

1. web/src/features/tasks/tasks.ts — add to the existing file

import { useMutation, useQuery, useQueryClient } from "@tanstack/react-query";
import { api } from "@/lib/api";

// …Task, tasksKey and useTasks stay exactly as they are…

export function useSetTaskDone(teamId: number) {
  const client = useQueryClient();

  return useMutation({
    // The VALUE we want, never a verb. Send it twice and the answer is the
    // same both times, so a double-click and a retry are the same event.
    mutationFn: async ({ id, done }: { id: number; done: boolean }) =>
      (await api.patch<Task>(`/teams/${teamId}/tasks/${id}`, { done })).data,

    // The reply IS the new row, so put it in the cache and stop. Invalidating
    // here would refetch the whole list to learn what we are already holding.
    onSuccess: (task) =>
      client.setQueryData<Task[]>(tasksKey(teamId), (tasks) =>
        tasks?.map((t) => (t.id === task.id ? task : t)),
      ),
  });
}

Note what is not here: no onError. A failed write never touched the cache, so there is nothing to put back.

2. web/src/features/tasks/tasks-panel.tsx — replace the list

import { errorMessage } from "@/lib/api";
import { useSetTaskDone, useTasks } from "@/features/tasks/tasks";

export function TasksPanel({ teamId }: { teamId: number }) {
  const { data: tasks, isPending, error } = useTasks(teamId);
  const setDone = useSetTaskDone(teamId);

  if (isPending) return <p className="text-muted-foreground text-sm">Asking…</p>;

  if (error !== null)
    return <p className="text-destructive text-sm">{errorMessage(error, "Could not load tasks.")}</p>;

  if (tasks.length === 0)
    return <p className="text-muted-foreground text-sm">No tasks yet.</p>;

  return (
    <div className="grid gap-2">
      <ul className="grid gap-1">
        {tasks.map((task) => (
          <li key={task.id} className="flex items-center gap-2 text-sm">
            <input
              type="checkbox"
              className="size-4 accent-primary"
              checked={task.done}
              // Only this row waits. variables is the payload in flight.
              disabled={setDone.isPending && setDone.variables.id === task.id}
              // e.target.checked is the state the user ASKED for. Send that.
              onChange={(e) => setDone.mutate({ id: task.id, done: e.target.checked })}
            />
            <span className={task.done ? "text-muted-foreground line-through" : ""}>
              {task.title}
            </span>
          </li>
        ))}
      </ul>

      {/* Same rule as the read: say what the server said, and no more. */}
      {setDone.error !== null && (
        <p className="text-destructive text-sm">
          {errorMessage(setDone.error, "Could not save that.")}
        </p>
      )}
    </div>
  );
}

The checkbox is a plain <input>, not npx shadcn add checkbox. It is one line, it is keyboard-accessible for free, and a component you do not install is a component you never update.

Why the box moves at all. checked={task.done} is a controlled input: the browser shows what React last rendered. Click it and the DOM box flips for an instant, React re-renders from the unchanged cache, and it flips straight back — until setQueryData lands and it stays. That flicker is the round trip, honestly displayed.

Check yourself

Why send { done: true } instead of calling a toggle route?

A toggle is a bet about the current value, so a retry, a double-click or a duplicated request lands you in the opposite place. A value says where you want to end up, and repeating it changes nothing. Measured above: the same PATCH twice, the same 200 twice.

The PATCH answers 403. What puts the checkbox back?

checked renders from the cached row, and only onSuccess writes to the cache. A refused write leaves the list exactly as it was, so the next render draws the old value. There is no rollback code because there is no forward code to undo.

Why is setQueryData better here than invalidateQueries?

The server answered with the whole updated task. Invalidating asks for the entire list again to discover something you were handed a millisecond ago — one extra round trip, plus a loading state, per tick. Invalidate is for when the write changed things you were not told about.

What this does NOT do

GapWhy it is still open
No optimistic updateTicking waits for the server. onMutate + rollback is real work and only worth it once you feel the delay. Deliberate, not forgotten.
Nothing creates a taskThe list is edit-only; rows still come from the API by hand. A form is the next lesson.
The error line is per panelOne failed write greys out one line for the whole list, not the row that failed. Fine at five rows.

Do this

  1. Write the two pieces above. cd web && npx tsc -b && npm run lint before you look at the page.
  2. Two terminals: cd server && npm run dev, cd web && npm run dev. Sign in, Show tasks on the team you own, tick a box. The Network tab shows one PATCH and no follow-up GET.
  3. Prove the reply is enough. Tick a box, then hard-refresh. The tick survived, and it was never re-fetched to be shown.
  4. Watch the refusal. Tick a box on your Viewer team's panel (add a task to it with psql, or borrow one). The box snaps back and the red line says forbidden. You wrote no rollback.
  5. Break it on purpose, one. Replace onSuccess with onSuccess: () => client.invalidateQueries({ queryKey: tasksKey(teamId) }). Same result on screen, two requests per tick in the Network tab. Put it back.
  6. Break it on purpose, two. Give the row a const [checked, setChecked] = useState(task.done) and drive the box from that instead. Tick on the Viewer team: the box stays ticked, the server refused, and the screen now lies. Put it back.
  7. npm run log in server/: every tick and every 403 is a row, with the method and route on it (lesson 19).

3. Where checked lives, when the server says no

Tick a box on a team where your role is Viewer. The PATCH answers 403. What happens next depends only on which value the input is drawing.

checked = {task.done}

cache: done false
PATCH → 403
onSuccess never runs
cache: done false
re-render → box empty

Rollback code: none.

checked = {useState}

state: true (set on click)
PATCH → 403
onError must setChecked(false)
forget it → state stays true
re-render → box ticked

Screen lies. Server refused.

The bug on the right is not a bug you fix. It is a bug you avoid having, by never keeping a second copy of a fact the server owns.
