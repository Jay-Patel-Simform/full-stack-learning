The word pair

snapshot — a copy of a value, taken once. config is a snapshot: config.ts read the environment at import time and never looks again.
live read — going back to the source every time you need the value. process.env.NODE_ENV is a live read.

A snapshot and a live read of the same fact can disagree, because process.env is a plain mutable object and anyone in the process can write to it. Once two readers exist, no amount of validation makes them agree. You do not test them into agreement — you delete one reader.

Why a flag mismatch is a logout that fails. The comment above that line in your own file already says it: “the flags must match the cookie being cleared, Secure included, or the browser treats this as a different cookie and the session one survives.” And it is worse than that on plain http. A site served over http may not set a Secure cookie at all — the browser drops the whole Set-Cookie header. So POST /logout answers 200, the server row is deleted, and the browser still holds a cookie. The user sees “logged out”. The next request sends the dead id and gets 401. It looks fine. It is fine by luck, not by design — and the one thing you cannot rely on is that the next bug in this shape will also be lucky.

Be clear about the size of this: on your machine today, nothing writes to process.env, so the bug is not live. That is the honest version. But the reason it is not live is that no code happens to mutate one global object. That is not a guarantee. It is an accident you can remove in one word.

5. A test that would have caught it

Add to the bottom of server/src/auth/session.test.ts, and add clearCookie to the import at the top:

// ! Both cookie helpers must read NODE_ENV from the same place. If one reads
// ! config and the other reads process.env, they can disagree inside one
// ! process - and a clear-cookie whose flags do not match is a logout that
// ! leaves the session cookie alive.
test("the clear cookie carries the same flags as the cookie it clears", () => {
  // A live read of process.env would see this. The config snapshot cannot.
  const real = process.env.NODE_ENV;
  process.env.NODE_ENV = "production";
  try {
    const set = sessionCookie("anything", new Date());
    const clear = clearCookie();

    assert.equal(/Secure/.test(set), /Secure/.test(clear));
  } finally {
    // ! Put it back, or every test after this one runs in a different world.
    process.env.NODE_ENV = real;
  }
});

Measured both ways, on your suite:

without the fix  -> not ok 36 - the clear cookie carries the same flags as the cookie it clears

That is what makes it a real test and not decoration: it fails on the broken code. A test you never saw fail is a test you have no reason to trust.

The try/finally is the interesting part. This test writes to a global, and every test after it shares that global. node:test runs the tests in one file in one process, in order. Without the restore, the test fixes itself and quietly changes the world for test 37. This is the same argument as the whole lesson, one level down: a mutable global with two readers.
