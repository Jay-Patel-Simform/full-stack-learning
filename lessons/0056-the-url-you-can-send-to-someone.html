The URL you can send to someone

Last lesson your rows left the laptop. Today the process does too. At the end of this you have an https:// address that works when your Mac is shut, and three env values finally flip to the values they were always meant to have. Zero TypeScript changes. Suite stays at 172.

In one minute

  • Render deploys from a git repository, and you do not have one. That is the first step, and it is the step where a secret gets committed if you are careless. Two .gitignore lines before git init, not after.
  • Your Dockerfile is the deploy. No build packs, no start command, no new file. Render runs docker build on the same file compose has been building since lesson 52, and your ENTRYPOINT migrates on the way up exactly as it does locally.
  • .env.docker does not come with you. It is .gitignored, so the env has to be retyped in a dashboard. config.ts already handles a world with no env file — the try/catch around loadEnvFile() was written for today.
  • You do not choose the port any more. Render hands you PORT and requires 0.0.0.0. Your HOST default is 127.0.0.1, which on Render means the deploy fails with a message about port scanning.
  • Then the three that have been wrong on purpose since lesson 29: NODE_ENV=production, TRUST_PROXY=true, and ALLOWED_ORIGINS. All three are only correct because there is now real HTTPS and a real proxy.
  • And then your login breaks — on the local front end, not on Render. It is not CORS. Finding out why is the last section, and it is the most valuable thing in this lesson.
  • Streak intact: no new dependency, 56 lessons.

Step 1 — the repository, and the two lines that come first

Order matters here in a way it does almost nowhere else. git init then git add . is one command away from a commit that contains your Neon password, and a commit is not undone by deleting the file — only by rewriting history or rotating the secret. You rotated that password yesterday. Do not do it twice.

Your root .gitignore already gained .env.docker last lesson. Two things are still missing, and both of them will be swept up by git add .:

.neon
.env.local
node_modules/
.env.docker
.env
.DS_Store

server/.env is the file npm test and npm run dev read on your Mac. It holds the owner URL for your local Postgres, which is a real credential for a database on a machine you care about. server/.gitignore lists .env already — but a nested .gitignore only helps if you trust it to exist for every directory you ever add. One line at the root covers the whole tree.

A .gitignore pattern with no slash in it matches at any depth, so .env covers server/.env and web/.env alike, and node_modules/ covers all three of them.

Now check your work before committing, with the one command that answers the only question that matters:

cd ~/learning/full-stack-learning
git init
git add -A
git status --short | grep -i env

What you want back is A server/.env.example and nothing else. If .env.docker or .env appears, you have not committed yet and the fix is free. That is the whole reason for the git add / grep pair — the index is a rehearsal, and this is the moment to read it.

git add is reversible. git commit is forever. Between those two commands there is a free, complete list of exactly what you are about to make permanent. Almost nobody reads it. Read it whenever the thing you are adding is a whole project.

Then commit and push. gh is already installed and does the create, the remote and the push in one line:

git commit -m "Team task tracker: API, front end, docker, lessons"
gh repo create full-stack-learning --private --source=. --push

--private, not because the code is secret, but because a public repo is a thing you have to keep being careful about forever. Make it public the day you want someone to read it.

One repository, two apps

You are committing the whole workspace: server/, web/, deploy/, and every lesson and record. That is deliberate. Render is happy to build a subdirectory of a bigger repo — there is a field for it, which you meet in the next step — and one repository means the front end (lesson 57) needs no second one.

Step 2 — the form, field by field

On dashboard.render.com: New → Web Service, connect GitHub, pick the repo. Then four fields decide everything:

FieldValue, and why
LanguageDocker. This is the whole point. Render builds your Dockerfile with BuildKit and runs the image — so the thing that runs in Singapore is the thing you have been running on your Mac since lesson 52. Every other option here would ask you to re-describe your app in Render’s vocabulary.
Root Directoryserver. Render “runs commands and interacts with files relative to your service’s root directory”, so the Dockerfile is found, and — the part that matters — the build context becomes server/. That is the same context compose gives it (build: . inside server/), which is why COPY package*.json ./ still resolves and why server/.dockerignore is still the one that is read.

Leave Docker Command empty. That field overrides your CMD, and your CMD is already right. Note what it does not override: ENTRYPOINT. That split you learned in lesson 54 is what lets Render start your app without being told about migrations at all.

Two of those lines deserve a paragraph each.

HOST=0.0.0.0, or the deploy fails

Read your own config.ts:

HOST: z.string().min(1).default("127.0.0.1"),

And your own server.ts comment: “Default host is loopback on purpose — binding 0.0.0.0 puts the API on the public internet with no TLS in front of it.” That was correct then and is correct now; what changed is that Render’s router is the TLS, and it reaches your container over the network, not over loopback. Render states the requirement flatly: “Every Render web service must bind to a port on host 0.0.0.0 to serve HTTP requests.”

Miss it and you get a deploy that builds fine and then dies with:

==> Port scan timeout reached, no open ports detected. Bind your service to at
    least one port.

That message names a port problem. The cause is a host problem: the port was open, on an address nothing outside the container can reach.

Your .env.docker has had HOST=0.0.0.0 since lesson 52, for the same reason — compose reaches the container over a bridge network, not over its loopback. So this value is not new to you. It is new to Render, because dashboard env vars start from nothing.

PORT: given, not chosen

Render sets PORT for every web service, defaulting to 10000. Your config reads PORT and defaults to 3000; the platform’s value wins because it is really in the environment. Nothing to do — but do not set PORT yourself, because then you are asserting a number the router may not be scanning for.

Your EXPOSE 3000 line becomes a lie in production. Leave it: the Dockerfile itself says that line is documentation and publishes nothing. A stale comment in a file is cheap; a wrong PORT in an environment is a failed deploy.

On your laptop you pick the address. On a platform you are told the address. That is the actual difference between the two environments, and every “works locally, not deployed” port bug is this sentence. The reason it costs you nothing today is your own config.ts rule: read every value from the environment, and default only what is visibly wrong in one second.

The three that were wrong on purpose

ValueWhat it turns on, and what would have broken had you set it earlier
NODE_ENV=productionAdds Secure to the session cookie (session.ts) and turns on HSTS. A Secure cookie is dropped by the browser over plain http://localhost — so on your Mac this value logs you out and tells you nothing. Here there is real TLS, so it is simply correct.
TRUST_PROXY=trueFastify reads X-Forwarded-For instead of the socket address. Render’s router is a proxy you do not control but do sit behind: without this, every request in your audit log comes from Render’s internal address and your lesson-12 per-IP rate limit is one bucket for the entire internet. With it set while nothing is in front of you, anyone picks their own bucket by sending a header. The value is not “on in production”. It is “on when something you trust writes that header”.
ALLOWED_ORIGINSYour Render URL for now. There is no deployed front end yet, and origin: true is still forbidden for the reason lesson 13 gave. Lesson 57 adds the front end’s real origin here.

Read line three. No pending migrations to apply — because you already migrated this Neon database from your laptop last lesson. Your entrypoint ran, took the advisory lock on the direct connection, found nothing to do, and got out of the way. Line four, the REVOKE, ran again and is equally idempotent.

That is the payoff for lesson 54 being its own lesson. Render was never told that this app has migrations. There is no release command, no pre-deploy step, no checkbox. The container knows how to start itself, so anything that can start a container can deploy it.

Then, from your Mac:

curl -i https://<your-service>.onrender.com/health

First call may take a minute — that is the free instance waking, plus Neon waking. Both are cold. Then log in with curl and look at the cookie you get back:

curl -i -X POST https://<your-service>.onrender.com/auth/login \
  -H 'content-type: application/json' \
  -d '{"email":"jay@example.com","password":"..."}'

In the response headers: set-cookie: session=...; HttpOnly; SameSite=Lax; Path=/; Expires=...; Secure. That Secure has been written in your code since lesson 29 and has never once been emitted. It exists now because NODE_ENV is finally telling the truth.

The failure you should cause on purpose

You will hit this one whether you cause it or not, so cause it deliberately and understand it in five minutes instead of an evening.

Point your local front end at the deployed API — web/.env, one line: VITE_API_URL=https://<service>.onrender.com, which web/src/lib/api.ts reads in place of its http://localhost:3000 fallback. Run npm run dev and log in at http://localhost:5173.

The login request succeeds. The next request is a 401.

Now work out which of the three plausible culprits it is, because they need three different fixes:

SuspectVerdict
CORSNot guilty, and it is the one you will blame. If CORS had blocked it, the login itself would have failed in the console with an origin message — and you would fix it by adding http://localhost:5173 to ALLOWED_ORIGINS. Do add it. It is not why you are logged out.
SecureNot guilty. The cookie arrived over https://, so the browser stored it.
SameSite=LaxGuilty. localhost:5173 and onrender.com are different sites. Lax means: do not send this cookie on a cross-site request — and a fetch() from one site to another is exactly that. The cookie is sitting in the browser, and the browser is refusing to attach it.

The fix is not a flag. SameSite=None would work and would delete the CSRF protection lesson 29 bought with that line. The fix is to stop being cross-site: serve the page and the API from one origin. Which is what deploy/nginx.conf has been waiting to do since lesson 53, and what lesson 57 is.

A deploy does not break your code. It stops your assumptions from being true. Every flag that failed today was correct — correct for one origin, one scheme, one machine. The work of deploying is finding which sentence you stopped being able to say.

Why must HOST be 0.0.0.0 on Render?

Render’s router is a separate machine from your container, so it arrives on the container’s network address, not its loopback. 127.0.0.1 accepts only connections that originate inside the container. The deploy fails with a port scan message for what is really a host mistake — and the port itself was open the whole time.

Why leave the Docker Command field empty?

It overrides CMD only, never ENTRYPOINT. Your CMD is already npm start, so there is nothing to say — and the migrations run regardless, because they live in the ENTRYPOINT. That is the lesson-54 split doing its job on a platform that has never heard of it.

Local page, deployed API, logged out. Cause?

Two different sites, so Lax tells the browser not to attach the cookie. The cookie was stored fine and CORS let the login through. Loosening SameSite would fix the symptom and hand back the CSRF defence; putting the page and the API on one origin fixes the cause.

What you did not build, on purpose

left out
the front end lesson 57: web/ as a second Render service, or nginx serving the built page and proxying /api so that page and API are one origin. The SameSite failure above is that lesson’s reason to exist, and you will have felt it first.
a real build step npm start is tsx src/server.ts — TypeScript compiled on the fly, dev tooling in a production image. It works and it is slower and larger than tsc plus node. Worth doing when the image size or the boot time is a number you actually care about, not before.
render.yaml the same settings as code instead of dashboard clicks. It earns its place at the second service, or the second environment — which is lesson 57 and probably a good reason to write it then.
health checks and zero-downtime deploys Render has a health-check path setting, and your /health route is right there. It matters when a bad deploy would take down something people use. Nobody uses this yet.
keeping it awake a cron pinging /health every ten minutes defeats the spin-down — and burns your 750 instance-hours (a month is 720). The sleep is the price of free, and it is the right price for a tracker you are still building.
