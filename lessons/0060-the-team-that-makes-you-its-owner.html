Lesson 60 · Week 15–16 · Front end + RBAC

The team that makes you its owner

Lesson 59 gave a stranger an account. They sign in and land on “No teams yet” — a dead end, because POST /teams has never been called by anything but a test. Today that empty state grows a form. The trap is a cache one: the 201 body is not a list row, so the thing you just created cannot be pushed into the list you already hold.

In one minute

  • POST /teams is the one route with no permission gate, and that is not an omission. There is no team yet, so there is no role to hold in it. Creating one is what gives you a role: OWNER.
  • The reply is {id, name}. A row in useTeams is {id, name, role, can}. Two different shapes from two different schemas.
  • So this mutation invalidates, it does not setQueryData. Lesson 26’s “write it in by hand when you can do the arithmetic” fails here: you cannot do the server’s arithmetic, because can comes from its permission table.
  • Then navigate — after the list has refetched, not before. await the invalidation, or the page you jump to asks for a team its own cache has never heard of.
  • One hook, one small form, no server change. No new dependency, 60 lessons.

Read the route before you call it

server/src/routes/teams.route.ts, and note what is missing from it:

app.addHook("onRequest", requireAuth);          ← who are you: still required

app.post("/teams",
  { schema: { body: CreateTeam, response: { 201: TeamPublic } } },
  async (request, reply) => {                   ← no preHandler: requirePermission(...)
    const { name } = request.body as CreateTeamInput;
    return reply.code(201).send(await createTeam(name, request.userId!));
  });

Every other team route carries a requirePermission(…) line. This one cannot: can(role, action) needs a role, and getRole(teamId, userId) needs a teamId that does not exist until this handler runs. The store closes the loop in one statement:

prisma.team.create({ data: { name, members: { create: { userId, role: "OWNER" } } } });

Authentication is the gate here; authorisation starts a moment later. A route with no permission check is safe exactly when there is nothing yet to have permission over — and when the row it writes is what creates the permission.

The trap: two shapes, one word

What it isFields
TeamPublicthe 201 reply of POST /teamsid, name
TeamMembershipone row of GET /teamsid, name, role, can

Both are “a team” in English. Only one of them is what useTeams() hands to the sidebar, to PageHeader (which prints team.role) and to every team.can.includes("task:create") that decides whether a button is drawn. Push the 201 body into that array and you get a row whose can is undefined — TypeError: Cannot read properties of undefined (reading 'includes'), thrown in a component, over a team that was created perfectly well.

Same family as lesson 59, one level up. There the two bodies were identical and the difference was a header. Here the bodies differ and the difference is a schema. Both times the question is the same: what exactly did this response promise?

Build it — the hook

Append to web/src/features/teams/teams.ts:

import { useMutation, useQuery, useQueryClient } from "@tanstack/react-query";

/**
 * Start a team. The reply is {id, name} -- NOT a row of useTeams, which also
 * carries role and can. So nothing is written into the cache by hand here:
 * only the server knows what OWNER may do.
 */
export function useCreateTeam() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: async (name: string) =>
      (await api.post<{ id: number; name: string }>("/teams", { name })).data,
    // ! Returning the promise keeps isPending true until the list is back,
    // ! so the caller can navigate into a team the cache already holds.
    onSuccess: () => queryClient.invalidateQueries({ queryKey: TEAMS_KEY }),
  });
}

Two things are doing work in that last line. invalidateQueries refetches instead of guessing — and returning its promise from onSuccess makes React Query wait for the refetch before the mutation settles. Drop the return (write { queryClient.invalidateQueries(…) }) and the mutation resolves first; you navigate to /teams/7/tasks while useTeams still holds the old list, useTeam("7") finds nothing, and the page says the team does not exist — for about 80 ms. A bug that appears only on a slow network is the worst kind to own.

Build it — the form

New file, web/src/features/teams/new-team-form.tsx:

export function NewTeamForm() {
  const [name, setName] = useState("");
  const createTeam = useCreateTeam();
  const navigate = useNavigate();

  function onSubmit(event: React.FormEvent<HTMLFormElement>) {
    event.preventDefault();
    createTeam.mutate(name.trim(), {
      onSuccess: (team) => navigate(`/teams/${team.id}/tasks`),
    });
  }

  return (
    <form onSubmit={onSubmit} className="grid w-full max-w-sm gap-2">
      <Label htmlFor="team-name">Team name</Label>
      <Input id="team-name" value={name} required maxLength={100}
             onChange={(e) => setName(e.target.value)} />
      {createTeam.error !== null ? (
        <ErrorLine>{errorMessage(createTeam.error, "Could not create team")}</ErrorLine>
      ) : null}
      <Button type="submit" disabled={createTeam.isPending || name.trim() === ""}>
        {createTeam.isPending ? "Creating…" : "Create team"}
      </Button>
    </form>
  );
}

maxLength={100} mirrors z.string().min(1).max(100) in team.schema.ts — a hint, not a gate, same as lesson 59. And the mutate here takes a second argument: per-call callbacks. The hook’s own onSuccess (cache) runs first and is about the data; this one (navigation) is about this click. Cache work belongs to the hook, because it is true wherever the hook is used; navigation belongs to the component, because it is not.

Practice — three

Why can the 201 body not be pushed into the teams list?

TeamPublic is {id, name}; a row of GET /teams is TeamMembership, which adds role and can. can is computed by allowedActions(role) from the server’s own permission table — the whole point of sending it is that the front end has no copy to let drift. So the front end cannot invent it either.

Why return the invalidation promise from onSuccess?

React Query keeps the mutation pending while a promise returned from onSuccess is unsettled. Without the return, your navigate fires against a cache that still holds the old array, and useTeam(teamId) — which reads the list rather than fetching one team — briefly finds nothing.

Why does POST /teams carry no requirePermission?

requirePermission asks getRole(teamId, userId), and there is no teamId before the handler runs. The route is still behind requireAuth, so a stranger cannot reach it — and the row it writes makes the caller OWNER, which is what every later gate on that team will read.
