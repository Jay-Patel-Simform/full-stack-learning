Lesson 62 · Week 15–16 · Deploy

The header that says no

Every defence you have written so far runs on your server: the session check, can(), the rate limiter, the CSRF check. They all assume the browser is asking questions on your behalf. A Content Security Policy is the other kind of defence — it is you telling the browser what your page is allowed to do, and the browser enforcing it against code you did not write. Today it goes into render.yaml, in the headers: key lesson 61 left empty. The YAML is four lines. The hard part is the policy, and the hard part of the policy is your own app.

In one minute

  • CSP is an allowlist of sources, sent as a response header. The browser refuses anything not on it — a script, a stylesheet, a connection — and says so in the console.
  • It is a defence against injected code. If an attacker gets a <script src="evil.com"> onto your page, CSP is what stops the browser fetching it.
  • Write the policy from the app you actually built, not from a blog post. Your built page has one external script and no inline one — so script-src 'self' costs you nothing.
  • Your styles are the exception, and you must be honest about it. Radix and motion write style="…" onto elements, so style-src needs 'unsafe-inline'. Name the hole rather than pretending it is not there.
  • Ship it in Report-Only first. Same policy, no enforcement, violations printed in the console. That is today’s feedback loop.

What CSP actually prevents

Imagine the bug you have not written yet: somewhere, a task title gets rendered as HTML instead of text, and a title reads <script src="https://evil.example/x.js"></script>. React makes this hard, which is not the same as impossible — one dangerouslySetInnerHTML, or one compromised npm package in your 15 dependencies, and it is on the page.

Without a policy, the browser fetches that script and runs it with your origin’s full authority: it can read your DOM, and because lesson 57 put the API on the same origin, every request it makes carries your session cookie. With a policy, the browser looks at script-src 'self', sees evil.example is not 'self', and refuses to fetch it at all. The bug is still there. The exploit is not.

Every other defence you wrote trusts the browser. This one instructs it. That is why CSP is the last header and not the first: it is worth nothing on its own, and it is the only thing that helps once something has already gone wrong on the page.

The policy

Each directive names a resource kind and the sources allowed for it. 'self' means “my own origin”; 'none' means nothing at all.

default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data:;
font-src 'self';
connect-src 'self';
frame-ancestors 'none';
base-uri 'none';
form-action 'self';
object-src 'none'
DirectiveWhy that value, for this app
default-src 'self'The fallback for anything not listed below. Start closed; open one door at a time.
script-src 'self'The whole point. Your build emits one file from your own origin, so this costs nothing and blocks every injected src. It also blocks inline <script> and eval — and you have neither.
style-src 'self' 'unsafe-inline'The compromise. Radix positions menus and motion animates by writing style="…" onto elements. Without 'unsafe-inline' your dropdowns land in the wrong place. See the honesty box below.
img-src 'self' data:Vite inlines small assets as data: URIs at build time. Drop data: and an icon silently disappears one day.
font-src 'self'Geist ships in your bundle. If you ever add Google Fonts, this line is what breaks — and that is the line telling you that you just added a third party.
connect-src 'self'Covers fetch/XHR — every axios call React Query makes. Same-origin /api means 'self' is enough. This is the one that stops stolen data being posted somewhere.
frame-ancestors 'none'Nobody may put your app in an <iframe>. This is clickjacking, and this directive is the modern replacement for X-Frame-Options.
base-uri 'none'An injected <base href> can repoint every relative URL on the page — including /api. Cheap to forbid, nasty to forget.
form-action 'self'A form may only submit to you. Your forms are all JavaScript anyway, so this is free.
object-src 'none'<object>/<embed>. Legacy plugin surface, zero use to you.
be honest about this one
'unsafe-inline' in style-src is a real weakening, and the name is the warning. It permits style="…" attributes, which allow tricks like restyling an element to overlay a button. It is much less dangerous than the same word in script-src — CSS cannot read your session or call your API — but it is not nothing. The clean fix is a nonce, and a nonce needs a server that generates one per request and stamps it into the HTML. Your page is a static file on a CDN: there is no per-request server to do that. So the honest answer is “this needs server-rendered HTML, which you do not have”, and the dishonest answer is to leave it out of script-src and quietly pretend the page is stricter than it is. Never put 'unsafe-inline' in script-src to make an error go away. That directive is the one doing the work.

Into the file

In render.yaml, on the tasks-web service only, as a sibling of routes:. Send the Report-Only name first:

  - type: web
    name: tasks-web
    runtime: static
    # … rootDir, buildCommand, staticPublishPath, envVars as in lesson 61 …
    headers:
      # Report-Only: the browser reports violations and blocks nothing.
      # Rename to Content-Security-Policy once the console is clean.
      - path: /*
        name: Content-Security-Policy-Report-Only
        value: "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'; object-src 'none'"
    routes:
      # … unchanged …

Three things about that YAML, and each one has bitten somebody:

1. The whole policy is one string on one line. Directives are separated by ; inside the value — they are not a YAML list. And the value must be quoted, because it contains : and '; double quotes outside, CSP’s own single quotes inside.

2. path: /* is a match, not a directory. It applies the header to every response the static site serves, which is what you want — index.html and every hashed asset.

3. It goes on the static site, not the API. CSP governs a page. Your API returns JSON, which renders nothing and executes nothing. Putting a policy there is theatre.

The loop: watch it complain, then make it bite

Validate, deploy, then open the app and open the browser console. A Report-Only violation reads roughly:

[Report Only] Refused to load the font 'https://fonts.gstatic.com/…'
because it violates the following Content Security Policy directive:
"font-src 'self'".

That message names the resource and the directive that would have stopped it — which is the entire diagnosis. Now do the round trip properly:

  1. render blueprints validate, commit, let it deploy.
  2. Open the site and use it: log in, open a team, open a dropdown, create a team, load the activity page. A policy is only tested by the screens you actually visit.
  3. Read every [Report Only] line. Each one is either a real dependency you forgot (widen that directive) or something you do not want (leave it blocked, and go find out what it is).
  4. Console clean? Delete -Report-Only from the header name. Deploy. Now it blocks.
  5. Prove it bites. In the console on your live site, run var s=document.createElement('script'); s.src='https://example.com/x.js'; document.body.appendChild(s). You should get a Refused to load error and no network request. If it loads, your header is not arriving — check it with curl -sI https://…/ | grep -i content-security.

Report-Only is how you ship a risky change to production without risking production. The same shape as the expand/backfill/contract migration in lesson 10: make the new thing observable before you make it authoritative.

Practice — three

Which directive stops stolen data being sent to an attacker?

Both matter, but they stop different halves. script-src blocks code you did not ship from running. connect-src assumes something already runs — an inline handler, a compromised dependency inside your own bundle — and blocks the fetch that carries your data off the origin. That is why connect-src 'self' is worth writing even though it looks redundant next to default-src 'self': it is the last line, after everything else has failed.

Why does this app need 'unsafe-inline' for styles?

Tailwind is fine — it compiles to a real .css file served from your own origin, which 'self' already covers. The problem is runtime: Radix positions a dropdown by setting style="transform:…" on the element, motion animates the same way, and skeleton.tsx sets a width. Those are inline styles, and a static file on a CDN has no per-request server to issue a nonce for them.

What does Content-Security-Policy-Report-Only actually do?

It is the dry run. The browser evaluates the policy in full and prints every violation to the console, but loads the resource anyway. That is what makes it safe to deploy an untested policy to a live site: the worst case is a noisy console, not a blank page. You find the exceptions with real usage, fix the policy, then remove -Report-Only to turn the same string into enforcement.
