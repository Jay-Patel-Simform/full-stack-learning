React Query cache and pages

Last lesson you taught the server to hand out one page at a time. The page asks for a page, reads .items, and drops nextCursor on the floor. So the app now shows the first twenty tasks and quietly pretends the rest do not exist. No error, no empty state, no clue. Today you fix that with one hook — and the fix changes the shape of the cache, which breaks three lines the type checker will not warn you about.

In one minute

  • The bug is silent, which is what makes it bad. Task 21 exists, is returned by no request, and nothing on screen says so. Compare it to the crash in lesson 21: a crash tells you it happened.
  • useInfiniteQuery keeps many replies under one key. getNextPageParam turns your nextCursor into the next request’s cursor. That is the whole wiring.
  • The cache entry stops being an array. Measured: it holds exactly two keys, pages and pageParams. typeof data.map is undefined.
  • So your three setQueryData<Task[]> lines are now wrong — and tsc stays silent. Measured: the component broke with 3 type errors, the three cache writes broke with 0. At runtime: TypeError: tasks?.map is not a function.
  • Create can no longer append. A new task belongs after the last row of the last page, and you may not be holding the last page. It becomes an invalidateQueries — measured cost: one request per page you are holding.

See the bug before you fix it

Your server is correct. Your page is the part that stopped being correct the moment the reply shape changed:

what the server sends

{
  "items": [ /* 20 tasks */ ],
  "nextCursor": 4321
}

“Here are twenty, and there is more — start from 4321.”

what your hook keeps

await api.get(...)
  .data.items

// nextCursor: never read.
// Nobody ever asks again.

“Twenty tasks. That’s all of them.” It is not.

A field in a reply that no caller reads is not a spare. It is a promise the server kept and the client broke.

Why this class of bug deserves its own name in your head. You have now met three silent failures in a row: dead ?? defaults (lesson 29), a missing querystring schema (lesson 20), and this. All three pass every test and every type check. The pattern is the same every time: the code that would have complained is the code nobody wrote. A test that loads 25 tasks and expects to see 25 would have caught this the day lesson 30 shipped. You have no front-end test at all — that is now the loudest gap in the project, and it is lesson 32.

The word pair

query — one key, one answer. useQuery replaces the answer each time it refetches. data is the reply.
infinite query — one key, an ordered list of answers. useInfiniteQuery appends. data is a box holding every reply you have collected, plus the parameter each one was fetched with.

Twelfth pair. The test it gives: does this key hold one reply, or a growing pile of replies? Everything that reads or writes that key has to know the answer, and the type checker will only tell you about some of them.

Measured: the cache shape, and what it costs

I built a real QueryClient, walked it to three pages of two rows, and looked inside. Your version, @tanstack/react-query 5.102.8.

pages held: 3   queryFn calls: 4
cache shape keys: [ 'pages', 'pageParams' ]
typeof data.map: undefined
OLD setQueryData<Task[]> line throws: TypeError: tasks?.map is not a function
refetch (what an active invalidate does) queryFn calls: 3

Read those five lines slowly, they are the whole lesson:

  1. Three pages, four calls. Fetching a page never refetches the ones before it. Each “Load more” is exactly one request.
  2. Two keys, and neither is a task. The tasks are at data.pages[n].items. Nothing at the top level is an array of anything you care about.
  3. data.map does not exist. So every line you wrote in lessons 25, 26 and 28 that says tasks?.map or tasks?.filter is calling a method on an object that does not have it.
  4. It throws, at runtime, inside onSuccess. The write is lost. The server already changed the row, so the screen and the database now disagree until something refetches.
  5. An invalidate on a 3-page query is 3 requests, run one after another to rebuild the pages in order. Not free, and the more the user scrolls, the less free it gets.

The part that should scare you

I made useTasks infinite and changed nothing else, then ran the type checker. Here is every word it said:

src/features/tasks/tasks-panel.tsx(32,13): error TS2339: Property 'length' does not exist on type 'InfiniteData<TaskPage, unknown>'.
src/features/tasks/tasks-panel.tsx(38,16): error TS2339: Property 'map' does not exist on type 'InfiniteData<TaskPage, unknown>'.
src/features/tasks/tasks-panel.tsx(38,21): error TS7006: Parameter 'task' implicitly has an 'any' type.

Three errors, all in the component, none in tasks.ts. The three setQueryData calls — the ones that are now guaranteed to throw — passed clean. Why?

the component: TypeScript knows

const { data } = useTasks(teamId);
data.map(...)

// data's type came FROM the hook.
// TypeScript worked it out.

the cache write: you told it

client.setQueryData<Task[]>(key, (tasks) =>
  tasks?.map(...)
);

// You wrote Task[] in the angle
// brackets. It believed you.

Third time this rule has come up, so it is a rule: a type parameter is a claim you made, not a fact TypeScript checked. Lesson 28 was api.delete<Task>() on a 204. Lesson 17 was as CreateTaskInput. This is the same move in a third costume. <> and as are both you promising, and a promise is only as good as the file that keeps it.

The fix is to stop repeating the claim. Three call sites each writing setQueryData<...> is three chances to write a different wrong shape. Below, the shape is written once, in a small helper, and the three mutations pass it a plain Task[] => Task[] function. Same instinct as lesson 17’s one validator compiler instead of seven .strict() calls: one place beats N places, and the fourth mutation next month gets it for free.

The change — type it yourself

I applied all of it to your files, ran npx tsc -b, then restored your files byte-for-byte. It type-checks clean. Two files, four edits.

1. web/src/features/tasks/tasks.ts — the hook

- import { useMutation, useQuery, useQueryClient } from "@tanstack/react-query";
+ import type { InfiniteData } from "@tanstack/react-query";
+ import {
+   useInfiniteQuery,
+   useMutation,
+   useQueryClient,
+ } from "@tanstack/react-query";

  export const tasksKey = (teamId: number) => ["teams", teamId, "tasks"] as const;

+ // * The server's reply shape, named once. A page, not an array.
+ export type TaskPage = { items: Task[]; nextCursor: number | null };

  export function useTasks(teamId: number) {
-   return useQuery({
+   return useInfiniteQuery({
      queryKey: tasksKey(teamId),
      // sort names a COLUMN, so the server only accepts three strings (lesson 20).
-     queryFn: async () => (await api.get(...)).data.items,
+     queryFn: async ({ pageParam }) =>
+       (
+         await api.get<TaskPage>(`/teams/${teamId}/tasks`, {
+           params: { sort: "id", dir: "asc", cursor: pageParam },
+         })
+       ).data,
+     // ? No cursor on the first request. Absent means "start at the beginning",
+     // ? which is exactly what the server's optional cursor already meant.
+     initialPageParam: undefined as number | undefined,
+     // * The server decides whether there is more. nextCursor null -> undefined,
+     // * and undefined is how React Query says "no next page".
+     getNextPageParam: (last) => last.nextCursor ?? undefined,
    });
  }

Three new lines carry the whole idea. queryFn now receives { pageParam } and returns the whole page, not .items — because the page is the thing worth keeping. getNextPageParam is the only place that reads nextCursor, and its return value becomes the next call’s pageParam. Return undefined and hasNextPage goes false. That is the entire protocol.

Why ?? undefined and not just last.nextCursor. Your server sends null for “no more” (nextCursor: z.number().nullable(), from lesson 30 — a nullable field is honest JSON, an absent one is ambiguous). React Query’s signal for “no more” is undefined or null. They agree here, but writing the conversion makes the boundary visible, and it is where you would put a decoder the day the server says "end": true instead.

2. Same file — the shape, written once

+ // * The cache entry is no longer an array. It is { pages, pageParams }, and
+ // * every write has to walk the pages. One helper, so the three mutations
+ // * below cannot each get the shape wrong in its own way.
+ function editPages(
+   client: ReturnType<typeof useQueryClient>,
+   teamId: number,
+   edit: (items: Task[]) => Task[],
+ ) {
+   client.setQueryData<InfiniteData<TaskPage>>(tasksKey(teamId), (data) =>
+     data === undefined
+       ? data
+       : {
+           ...data,
+           pages: data.pages.map((page) => ({
+             ...page,
+             items: edit(page.items),
+           })),
+         },
+   );
+ }

Read the middle of it: a new box, with a new array of new pages, each with a new items. Nothing is mutated in place. React Query hands you the cached value and expects a new value back — the same rule as any React state. Edit data.pages[0].items directly and React sees the same object reference, so nothing re-renders and you spend an hour wondering why.

The data === undefined branch is not politeness. The updater runs even when there is nothing cached — a mutation can finish after the user navigated away and the entry was collected. Return undefined and the entry stays empty, which is correct: you have no pages to edit.

3. Same file — the three mutations

  // useSetTaskDone
    onSuccess: (task) =>
-     client.setQueryData<Task[]>(tasksKey(teamId), (tasks) =>
-       tasks?.map((t) => (t.id === task.id ? task : t)),
-     ),
+     editPages(client, teamId, (items) =>
+       items.map((t) => (t.id === task.id ? task : t)),
+     ),

  // useDeleteTask
    onSuccess: (_nothing, id) =>
-     client.setQueryData<Task[]>(tasksKey(teamId), (tasks) =>
-       tasks?.filter((t) => t.id !== id),
-     ),
+     editPages(client, teamId, (items) => items.filter((t) => t.id !== id)),

  // useCreateTask
- // Append, and only because useTasks asks for sort=id&dir=asc: a new id is
- // the biggest id, so "last" is arithmetic, not a hope.
- onSuccess: (task) =>
-   client.setQueryData<Task[]>(tasksKey(teamId), (tasks) => [...(tasks ?? []), task]),
+ // ! Appending is now a guess. A new id is the biggest id, so the row
+ // ! belongs after the last row of the LAST page - and we may not be
+ // ! holding the last page. Ask again instead of placing it wrongly.
+ onSuccess: () => client.invalidateQueries({ queryKey: tasksKey(teamId) }),

Toggle and delete keep their setQueryData. They act on a row that is already on screen, so you know which page it is on — you do not even have to work it out, the map over pages finds it. The reply is still the authoritative new row, so there is still nothing to ask about.

Create loses its setQueryData, and this is the honest half of the lesson. Lesson 26 appended, and said in a comment that it worked only because sort=id&dir=asc makes the newest row the last row. That reasoning still holds — and it is no longer enough. “Last” now means last row of the last page, and if you are holding page 1 of 5, the new task belongs to a page you have never fetched. Append it to page 1 and you have invented a row order the server would never send; the next refetch silently moves it.

The lesson-26 rule, now with its edge named: put the reply in the cache when you know where it goes. Paging is exactly the case where you stop knowing. So you ask again — and you pay one request per page held, measured above.

The cheaper version you should not build yet. You could refetch only the last page, or append only when hasNextPage is false. Both are real optimisations and both are extra state to get wrong, for a list of five tasks. Write the invalidate, keep the measurement (1 request per page), and revisit it when a real user holds ten pages. Lesson 30 ended by not adding an index for the same reason: measure, then decide, and “not yet” is a decision.

4. web/src/features/tasks/tasks-panel.tsx — flatten, and one button

- const { data: tasks, isPending, error } = useTasks(teamId);
+ const {

One line of flatMap, placed after the two early returns. That order is not style: before them, data may be undefined, and after them TypeScript knows it is not. Every line of JSX below is untouched — tasks is the same flat array of the same Task objects it has always been.

+ {/* No button when the server said there is nothing after this row.
+     hasNextPage is that answer, not a guess about the count. */}
+ {hasNextPage && (
+   <Button
+     variant="outline"
+     size="sm"
+     className="justify-self-start"
+     disabled={isFetchingNextPage}
+     onClick={() => fetchNextPage()}
+   >
+     {isFetchingNextPage ? "Loading…" : "Load more"}
+   </Button>
+ )}

  <NewTaskForm teamId={teamId} />

hasNextPage is not a count and not a guess. It is getNextPageParam’s answer about the page you are actually holding, which came from the take: limit + 1 row the server fetched in lesson 30. The chain runs unbroken from one extra row in Postgres to whether a button exists.

And disabled={isFetchingNextPage} is the same guard as the Add button in lesson 26, for a different reason: two clicks would fire the same cursor twice and append the same twenty rows twice. Duplicate keys, duplicate rows on screen, no error.

Why a button and not scroll-to-load. Infinite scroll needs an IntersectionObserver, and it takes the end of the list away from the user — no footer, no “I have seen everything”. A button is one line, keyboard-reachable, announced by a screen reader, and tells you plainly that there is more. fetchNextPage is the same call either way; the observer is a trigger you can add later without touching the hook.

Check yourself

Why did tsc catch the component but not the cache writes?

Both files were checked by the same compiler in the same run. The difference is where the type came from. In the component, data’s type was inferred from the hook’s return, so changing the hook changed the type and the errors appeared. In setQueryData<Task[]>, you wrote the type in the angle brackets — the compiler has no independent knowledge of what that cache key holds, so it took your word. Same as api.delete<Task>() on a 204 in lesson 28. Inferred types are checked; declared ones are believed.

Why does creating a task now invalidate instead of appending?

The reply is unchanged — the server still answers 201 with the full new task, so the data is right there. What changed is that you no longer know where to put it. Sorted by id ascending, the newest row belongs after the very last row of the very last page, and if hasNextPage is true you are not holding that page. Appending to the page you happen to have puts the row in a position the server would never send, and the next refetch moves it with no explanation. Invalidating costs one request per page held (measured: 3 pages, 3 calls) and is always right.

What does getNextPageParam returning undefined mean?

undefined is the terminator, not a default. Return it and hasNextPage becomes false, the button disappears, and fetchNextPage does nothing. Note the asymmetry that catches people: initialPageParam: undefined means “first request, no cursor” — the same value with the opposite meaning, because it is read at the start rather than returned at the end. Your server maps onto this cleanly: nextCursor: null is the last page, and ?? undefined is the one line that translates its word into React Query’s.

Why build a new box in editPages instead of editing the pages?

Nothing is frozen — mutating it works, silently, which is the trap. React decides whether to re-render by comparing the old value to the new one by reference. Push into data.pages[0].items and the reference is identical, so React sees no change and the screen keeps the old list even though the cache holds the new one. That is why the helper spreads at all three levels: the box, the pages array, and each page. This is the same rule as never doing state.push() in React — a cache is just state that outlives the component.
