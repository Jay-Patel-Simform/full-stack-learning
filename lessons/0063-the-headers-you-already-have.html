Lesson 63 · Week 15–16 · Deploy

The headers you already have

Lesson 62 ended with a list of other security headers and one instruction: check what you are already being sent before adding any. This lesson is that check, run for real against your live site. It turns out three parties are sending you headers and none of them knows about the others — and one of the three is sending nothing at all, which is not what you thought. The skill today is not writing headers. It is measuring before writing, which is the only way to avoid the two failure modes: the header you send twice, and the header you were sure you sent.

In one minute

  • curl -sI <url> is the whole tool. It fetches only the response headers. It is the fastest feedback loop you have on a deployed site — no browser, no cache, no guessing.
  • Your two services get headers from different places. The API gets them from @fastify/helmet, which is your code. The static site gets them from Render, which is not.
  • Your CSP is not live yet. I checked. The site sends no Content-Security-Policy of any kind, so last lesson’s clean console was clean for the wrong reason.
  • Add only what is missing and not already covered. Two headers, that is all. A header you send twice is a bug; a header that duplicates a CSP directive is noise.
  • Lesson 62’s open question is answered, by measurement: a proxied /api/* response keeps the API’s own headers. The static site does not overwrite them.

Before anything else: a claim of yours did not survive the check

You told me the console was clean and the policy was enforcing. I ran curl against your live site before writing this lesson, because a claim gets checked like any other. Here is the entire header set your site returns today:

$ curl -sI https://tracker-web-mxol.onrender.com/

cache-control: public, max-age=0, s-maxage=300

There is no content-security-policy line and no content-security-policy-report-only line. The block went into render.yaml on your laptop, and that file has not been committed and deployed yet. So the browser was never sent a policy, never evaluated one, and had nothing to complain about.

A clean console is only evidence if the header arrived. “No errors” and “no policy” look identical from the console. They look completely different from curl. This is why the check comes before the conclusion — and it is the same lesson as lesson 61, where three of my own notes claimed a page did not exist while it sat on disk.

and a second thing the check found
Your live services are named tracker-web-mxol and full-stack-learning-mmty. Your render.yaml names them tasks-web and tasks-api. A Render service’s URL comes from its name, so those are not the same services. Whatever is deployed right now was not deployed from that file. This is exactly the lesson 61 question, and now you have the evidence rather than the worry: applying that Blueprint as written would create a second pair alongside these, not adopt them. The fix is one word each — rename the services in the file to match what is live. Do that before you deploy anything today.

Three senders, no coordination

Run curl -sI against the API too and you get a much longer list. That difference is the lesson:

Who sends itWhat it isYou change it by
@fastify/helmetYour own middleware, registered in server/src/app.ts. Every header on your API responses comes from here.Editing TypeScript and deploying the API.
Render + CloudflareThe platform. It adds strict-transport-security and x-content-type-options to the static site for free, without being asked.Nothing — you do not control these.
Your headers: blockThe render.yaml key from lesson 62. Applies to the static site only.Editing YAML and deploying the Blueprint.

Nothing reconciles the three. If Render sends strict-transport-security and you also add one, the browser receives the header twice. That is not an error the platform will warn you about, and which value wins depends on the header — some are first-wins, some last-wins, some are treated as invalid and dropped entirely. The safe assumption is that you cannot predict it.

What your static site is missing

This is the measured gap, from the real output above — not a checklist from a blog post:

HeaderStatus on your siteVerdict
Strict-Transport-SecuritySent by Render, with preload and a ten-year max-ageDo not add. Yours would be weaker and duplicated.
X-Content-Type-OptionsSent by Render: nosniffDo not add. Already correct.
X-Frame-OptionsAbsentDo not add. frame-ancestors 'none' in your CSP is its replacement and is strictly better.
Content-Security-PolicyAbsent — the lesson 62 block is not deployedDeploy it. This is today’s real task.
Referrer-PolicyAbsentAdd it. See the honesty note below — it is cheap, not urgent.
Permissions-PolicyAbsentAdd it. The only genuinely missing protection.

Referrer-Policy controls what goes in the Referer header when someone clicks a link off your site. Without it, a link out could carry the full URL of the page they were on — and your URLs contain team ids. strict-origin-when-cross-origin sends the full path to yourself and only the bare origin to anyone else.

Permissions-Policy switches off browser features your page will never use: camera, microphone, geolocation. Your app is a task tracker. If injected code ever tries to open the camera, this is the header that makes the browser refuse before the permission prompt ever appears — the same posture as CSP, applied to device APIs instead of resources.

be honest about this one
Referrer-Policy is already the browser default. Chrome, Firefox and Safari all default to strict-origin-when-cross-origin when no header is sent, so adding it changes nothing today. It is still worth one line, and the reason is a general one: a default is a decision someone else can change. Sending the header makes your requirement explicit, survives a browser that defaults differently, and tells the next reader that the value was chosen rather than inherited. That is a much weaker argument than the one for Permissions-Policy, and you should know which of the two lines is actually buying you something.

Into the file

Same headers: block on tasks-web, two entries added below the CSP. Each entry is a path, a name and a value:

    headers:
      - path: /*
        name: Content-Security-Policy-Report-Only
        value: "default-src 'self'; script-src 'self'; …"
      # the Referer sent to other sites: origin only, never the path
      - path: /*
        name: Referrer-Policy
        value: strict-origin-when-cross-origin
      # an allowlist of device APIs. Empty () means "nobody, not even me"
      - path: /*
        name: Permissions-Policy
        value: camera=(), microphone=(), geolocation=()

Two things about that syntax. 1. Permissions-Policy uses a structured syntax, not CSP’s: features are comma-separated, each takes a parenthesised allowlist, and () is the empty list — deny to everyone including your own page. (self) would be “my origin may”. 2. Neither value needs quoting in YAML, because neither contains a : — but quoting them anyway costs nothing and is one less rule to remember.

The loop: curl, deploy, curl, compare

This is the whole feedback loop, and it takes about a minute:

  1. Before. curl -sI https://tracker-web-mxol.onrender.com/ > /tmp/before.txt
  2. Fix the names. In render.yaml, rename tasks-web → tracker-web-mxol and tasks-api → full-stack-learning-mmty, so the file describes the services you actually have.
  3. Deploy. render blueprints validate, then commit and push.
  4. After. curl -sI https://tracker-web-mxol.onrender.com/ > /tmp/after.txt then diff /tmp/before.txt /tmp/after.txt
  5. Read the diff. Three new lines, no duplicated ones. If a header appears twice, delete yours — the platform wins.
  6. Now the console check from lesson 62 is worth running, because there is finally a policy to violate.

diff of two curl outputs is a test you did not have to write. It has the property every good check has: it fails loudly when you are wrong, and it costs nothing when you are right. Reuse this shape for any change whose entire visible effect is on the wire.

Practice — three

Why not add your own Strict-Transport-Security line?

Render’s value is max-age=315360000; includeSubdomains; preload — ten years, subdomains included, and preload-eligible. Any hand-written line would be a second copy of a header that is already correct, and the browser’s handling of a duplicated Strict-Transport-Security is not something you should be relying on. The rule generalises: measure, then add only the gap.

What does camera=() in Permissions-Policy mean?

The parentheses hold an allowlist of origins, and an empty list allows nobody — not even the page sending the header. camera=(self) would be the “only me” version. Since your task tracker never opens a camera, the empty list is correct and costs you nothing, which is the same trade as object-src 'none' in your CSP.

Your console showed zero CSP violations. What did that prove?

A page with no policy and a page with a perfect policy produce exactly the same console: silence. The console can only report violations of a policy the browser actually received, so it cannot distinguish “nothing was wrong” from “nothing was checked”. curl -sI can, because it shows you the header itself. Always confirm the mechanism is running before you read its output as a result.

See it drawn

measured — lesson 62’s open box is now closed
curl -sI https://tracker-web-mxol.onrender.com/api/health returns content-security-policy: default-src 'none';frame-ancestors 'none' — which is helmet’s policy from your API, not the static site’s. So a path: /* header is not applied on top of a rewritten-proxy response; the origin’s own headers pass through intact. That is the behaviour you wanted, and now it is a fact rather than a hope. It also means your API’s security headers are carried all the way to the browser through the proxy, which is the thing that would have been quietly broken if it were not true.

What you did not build, on purpose

left out
Redis, and the answer to your question You asked whether an app this small needs Redis, and the answer is no, not yet. Your rate limiter counts in memory. That is wrong only when there are two processes, because then each keeps half the count and your limit of 100 is really 200. You have one instance on a free plan, so today the count is correct. The trigger to revisit is not app size — it is the second instance: scaling up, or enabling autoscaling. When that day comes, check whether Postgres can hold the counter first; you already have it, and a counter with a 60-second window is a small table and one atomic UPDATE. Redis is faster and purpose-built, and it is also a service to run, pay for and handle the failure of. 63 lessons, no new dependency. Keep it.
report-uri / report-to still waiting on a public unauthenticated route with its own rate limit and size cap. Its own lesson.
Cross-Origin-Opener-Policy and friends the COOP/COEP/CORP family. Real headers, but they exist to isolate pages that use SharedArrayBuffer or embed cross-origin content. You do neither. Adding them would be cargo cult.
a cache-control pass your static site sends s-maxage=300 on the HTML, which is a correctness question rather than a security one — how stale a deploy can look. Worth a lesson, not today’s.
