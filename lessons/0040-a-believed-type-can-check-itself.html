A believed type can check itself

Lesson 39 named a gap and did not close it: AuditRow is a believed type — a claim about JSON, with nothing checking it. Today you close it, for real code, with a number attached: I measured what a full validator library costs your bundle (91.5 KB gzip, for one small schema) against what fifteen lines of your own code cost (0 KB, no install). Both catch the same bug. You are taking the second one.

In one minute

The question, measured both ways

A schema validator is a library that turns a believed type into a checked one: you describe the shape once, and it inspects the actual value at runtime and tells you if it disagrees. Zod is the one your server already uses. The question is not whether validation works — it does, I ran it:

AuditPage.safeParse({ ..., status: "200" })
-> { success: false, error: { path: ["items",0,"status"], message: "expected number, received string" } }

The question is what it costs to have that in the browser. I bundled one nine-field zod schema, alone, with nothing else in the file, through the same minifier Vite uses:

That number is not zod being bloated for no reason — a real validator handles unions, refinements, async checks, error formatting, dozens of things AuditPage never uses. You would pay for machinery your one schema does not need. This is the same shape as lesson 22's lucide-react finding: 44 MB installed, 0 imports. Except this time the import would be real, and the cost would ship to every visitor.

Works. Also: a new dependency, 91.5 KB gzip for this one schema, and a second copy of “what the reply looks like” to keep in sync with the server's own zod schema — the exact staleness problem from lesson 39, just moved one level up.

Write the check you actually need

// audit-row.ts, still 0 imports
function isAuditRow(v: unknown): v is AuditRow {
  const r = v as Partial<AuditRow>;
  return typeof r?.id === "number"
    && typeof r.at === "string"
    && typeof r.status === "number";
    // the three fields a wrong type would hide silently
}

15 lines total (full version below). 0 KB. Runs in the same file that already has no imports, so lesson 32's import-graph rule keeps it testable.

The library and the hand-check catch the same bug. The library also validates shapes you do not have. You are not rejecting validation — you are rejecting the 96% of it this page does not use. Ninth dependency decision in this workspace, and it fits the fourth rule from lesson 16's table: take a dependency only when the problem has no decisions left in it. This one still has all its decisions left — nine fields, three that matter.

Where the check belongs

Not in the component. Lesson 39 put the pure function in audit-row.ts because it has no @/ imports and node --test can load it. The guard belongs there too, and it runs at the one place a believed value turns into a used one — inside queryFn, before the page ever holds it:

// audit.ts
queryFn: async ({ pageParam }) => {
  const page = (
    await api.get<unknown>(`/teams/${teamId}/audit`, {
      params: { cursor: pageParam, ...filter },
    })
  ).data;
  return assertAuditPage(page); // throws here, or you get an AuditPage back
},

That single change is why api.get<unknown> replaces api.get<AuditPage> — the type parameter was always a claim, never a check. Now the claim is backed by code on the next line.

believed — a type on a value from outside, with nothing comparing them. What lesson 39 found.
checked, by hand — the same value, run through code that actually looks at it before anything downstream trusts it. What today adds.

A wrong shape now throws inside queryFn. React Query already has a place for a thrown error — it is the same error the page has shown since lesson 39's if (error !== null) line. No new UI branch, no new state. The three states from lesson 22 already cover “the server sent something the page cannot use.”

Check yourself

What does the 91.5 KB measurement actually prove?

Zod handles unions, refinements, async parsing, and detailed error trees — real work for a general tool. AuditPage uses none of that. The cost is proportional to the tool's generality, not to this one schema's needs.

Where does assertAuditPage have to run?

By the time the component has the data, code has already trusted it — the query already cached it, data.pages already exists. The check has to sit at the boundary where an unknown value first becomes a typed one, which is the line that turns the raw response into what queryFn returns.

export function assertAuditPage(v: unknown): AuditPage {
  const p = v as Partial<AuditPage>;
  if (!p || !Array.isArray(p.items) || !p.items.every(isAuditRow)) {
    throw new Error("audit page did not match the shape the page expects");
  }
  return v as AuditPage;
}
