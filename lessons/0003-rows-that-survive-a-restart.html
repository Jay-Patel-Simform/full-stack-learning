Lesson 03 · Week 1–2 · Database

Prisma: schema, migration, client

Your tasks live in an array. Stop the server and they are gone. Today they move into Postgres.

In one minute

  • An array dies with the process. A table lives on disk.
  • Three new words: schema (the shape), migration (the change), client (typed code to talk to it).
  • Only the store file changes. Your routes barely move — that is the point of having a store file.

The picture

The idea

Right now const tasks = [] holds everything. That array is inside the Node process. Kill the process, kill the data.

Postgres is a separate program that writes to disk. It is already running on this Mac (about 15 MB), so you install nothing new.

schema — the shape you want. One file, schema.prisma.
migration — the change from the old shape to the new one, saved as SQL in git. It runs once, everywhere.
client — generated TypeScript functions that match your schema, so a typo is a compile error.

The code

// prisma/schema.prisma — the shape
model Task {
  id     Int     @id @default(autoincrement())
  title  String
  done   Boolean @default(false)
  owner  String
}
npx prisma migrate dev --name task   # writes the SQL, runs it

// src/tasks/task.store.ts — the only file that changed
export const store = {
  list:   ()      => prisma.task.findMany(),
  create: (data)  => prisma.task.create({ data }),
};

A boundary earns its keep the day the thing behind it is replaced.

Check yourself

Why keep the migration SQL file in git?

The migration is a record of the change. Your laptop, a colleague's laptop and the server all run the same file in the same order, so all three end up with the same table.

Do this

  1. POST two tasks. Restart the server. GET /tasks. They are still there.
  2. Open prisma/migrations/ and read the SQL. It is short.
  3. In psql: select * from "Task";
