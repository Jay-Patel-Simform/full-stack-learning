Lesson 20 · Week 7–8 · API security

SQL injection and sort columns

Last item in week 7–8. You have written no SQL, so you have written no SQL injection. Today: why you are safe, and the one input that safety does not cover.

In one minute

  • A parameter sends your value to Postgres beside the query, never inside it. Quotes stop being punctuation.
  • Prisma parameterises everything — the builder and $queryRaw. Only $queryRawUnsafe with glued-in text can be injected.
  • Parameters protect values. They cannot carry a column name. So a caller-chosen column has no escaping trick — only a fixed list.
  • You shipped one: ?sort= is a zod enum. And the honest reason it matters is not injection. Keep reading.

The word pair

value — the data a query asks about. WHERE title = 'Buy milk'. Postgres accepts any value, so it lets you send it separately.
identifier — the name of a thing: a table, a column, ASC. Postgres must know these to plan the query at all.

A value can travel beside the query. An identifier has to be part of it.

The picture

Measured, on your five rows

1  builder,         where: { title: hostile }     -> 0 rows
2  $queryRaw,       WHERE title = ${hostile}      -> 0 rows
3  $queryRawUnsafe, WHERE title = '${hostile}'    -> 5 rows   <-- all of them

Lines 1 and 2 are the same defence, not two. $queryRaw is a tagged template: it receives the fixed text and the ${} values as separate arrays and cannot mix them up. Line 3 is the only injectable shape in all of Prisma, and it is spelled Unsafe for a reason.

Read line 3 out loud. The SQL sent was WHERE title = '' OR 1=1 --'. The caller's quote closed the string early, OR 1=1 became logic, and -- commented out the leftover quote. That is the entire trick: data crossed the line into syntax.

Now try it with a column

You want ?sort=title — a caller choosing a column. In raw SQL, parameterise it and watch:

4a  real     ORDER BY title              -> ["Add zod validation","Buy milk","Learn Prisma migrations"]
4b  param    ORDER BY ${"title"}         -> ["Add zod validation","Write the tasks routes","Buy milk"]
4c  param    ORDER BY ${"nonsense!!"}    -> ["Add zod validation","Write the tasks routes","Buy milk"]

4b and 4c are identical, and neither is sorted. A parameter is a value, so Postgres ordered every row by the same constant — which is no order at all. No error. "title" and "nonsense!!" behave exactly the same: both do nothing, quietly.

A parameter in the wrong slot does not fail loudly. It fails silently, which is worse.

What you shipped

No escaping, no parameter — so the column comes from a list you wrote. You already have the place for that: the wall at the door, from lesson 2.

never write this

sort: z.string()

// then, in the store:
orderBy: { [sort]: dir }

src/schemas/task.schema.ts

sort: z.enum([
  "id", "title", "createdAt",
]).default("id"),
dir: z.enum(["asc","desc"])
  .default("asc"),

The enum is the allowlist. Nothing re-checks sort in the store, and nothing should. By the time listTasks runs it is one of three strings, or the request was a 400.

The honest part

Here is what I found by actually widening it to z.string() and asking for ?sort=passwordHash. Prisma does not build that SQL. It refuses the unknown key before any query exists:

Unknown argument `passwordHash`. Available options are marked with ?.

So the builder is a second wall you did not write, and on this route the enum is not what stands between you and a stolen password hash. What the enum actually buys you is this — the reply that widened version sends to the caller:

HTTP 500
{"statusCode":500,"error":"Internal Server Error","message":"\nInvalid
`prisma.task.findMany()` invocation in\n/Users/jay/learning/full-stack-
learning/server/src/store/task.store.ts:18:22\n\n  15 // ! only because
TaskQuery already narrowed it to one of three strings...

Your absolute file paths, your line numbers, and your source comments, handed to anyone who can type a query string. That is A05: security misconfiguration, not injection — and it is a real hole, in your app, today.

The allowlist version answers this instead, and it names your list on purpose — that is the API contract, not an internal:

HTTP 400
{"message":"sort: Invalid option: expected one of \"id\"|\"title\"|\"createdAt\""}
One more thing I got wrong and fixed. My first version declared 400: ErrorReply in the route's response map. A 400 is Fastify's own reply, shaped { statusCode, error, message } — so the response serializer from lesson 2 dutifully dropped message, and every validation error became a bare {"error":"Bad Request"}. The serializer that keeps passwordHash private will just as happily throw away the one line telling you what you typed wrong. Declare response schemas for the replies you write, not for the ones the framework writes.

The allowlist turns a 500 that describes your code into a 400 that describes nothing. And it is still the right wall the day someone swaps the builder for raw SQL.

Fastify gotcha, and it cost me twenty minutes. Add querystring: TaskQuery to the route schema or the whole thing is ignored: ?sort=nope answers 200, unsorted. No throw — one FSTWRN001 line in the log. Third silent failure on this page.

Check yourself

Why can a column name not be sent as a parameter?

Postgres parses and plans first, then binds values. A column name decides what the plan is, so it must be in the SQL text. Types are irrelevant — a string value parameterises fine.

With Prisma's builder, what does sort: z.string() actually cost?

Prisma refuses an unknown orderBy key before building SQL, so there is no injection on this route. The cost is the unhandled error: Fastify sends Prisma's message, and it carries your file paths, line numbers and comments.

Show me · Lesson 20

The frontend is never the vulnerability. It is just a keyboard. Injection happens at the server, inside a SQL string — so the real question is only ever what the server does with your input, not where you typed it.

Step 1 — get your payload to the server

Three routes, all equal. An attacker picks whichever is easiest — and they are never stopped by your React form’s validation, because two of the three don’t touch it.

  • route A · the form field <input> a search box, a title — type ' OR 1=1 -- and submit.

    The obvious one. Also the least useful to an attacker: your client-side checks can block it, so it proves nothing about the server.

  • route B · the address bar Edit the URL directly: /teams/1/tasks?sort=title;DROP TABLE "Task"--

    No form, no JavaScript, no validation ran. The query string is caller-controlled text that lands straight in your route. This is the ?sort= slot from the lesson.

  • route C · skip the frontend entirely DevTools → Network → Copy as fetch, edit, replay. Or just curl.

    The important one. The attacker throws your UI away and talks to the API raw. Every check that lived in the browser is now invisible. Only server-side walls exist.

all three arrive as the same bytes at POST /… or GET /…?…

Step 2 — the server decides everything

Same hostile string. Its fate is set entirely by how the handler builds the SQL.

parameterised — your whole app

Nothing happens

where: { title: input }
// or  ${input} in $queryRaw

The value travels beside the query. ' OR 1=1 -- is compared as literal text to a title. 0 rows. There is no attack surface here to find.

concatenated — $queryRawUnsafe

Injection

`WHERE title = '${input}'`

The quote in your input closes the string early; the rest becomes syntax. This is the only injectable shape in Prisma, and it is spelled Unsafe. Your app contains zero of them.

So “how do I inject from the frontend” has an honest answer for your app: you can’t — every value is a parameter. Injection needs a raw string you glue input into. The frontend can only deliver the payload; the server has to volunteer the hole.

Step 3 — try it against your own ?sort=

This is the one caller-chosen identifier, so no parameter can carry it — the place you’d actually probe. Paste each into the address bar:

See it drawn — SQL injection and sort columns

One query. Caller input can land in two kinds of slot, and each kind gets a completely different defence.

SELECT * FROM identifier"Task" WHERE title = value'Buy milk' ORDER BY identifiertitle identifierASC LIMIT value20

Green slots: values

The data the query asks about. Postgres will accept any value here, so it lets you send it separately — beside the SQL, never inside it.

defence: a parameter. free, automatic.

Red slots: identifiers

The name of a thing. Postgres has to know these to plan the query at all, so they must be part of the SQL text. No parameter can carry one.

defence: a list you wrote. nothing else.

A value can travel beside the query. An identifier has to be part of it.

Which Prisma call parameterises

Two silent failures, one page apart

Neither of these throws. Both look like working code.

  • 1 · a parameter in an identifier slot — accepted, then ignored
    ORDER BY ${"title"}       -> ["Add zod validation","Write the tasks routes","Buy milk"]
ORDER BY ${"nonsense!!"}  -> ["Add zod validation","Write the tasks routes","Buy milk"]

    Byte-identical, and neither is sorted. A parameter is a value, so Postgres ordered every row by the same constant — which is no order at all. A real column name and pure gibberish behave exactly the same.

  • 2 · a route schema with no querystring key — validation skipped
    schema: { params: TeamParams }                      -> ?sort=nope answers 200
schema: { params: TeamParams, querystring: TaskQuery }  -> ?sort=nope answers 400

    Fastify does not throw for the missing key. You get one FSTWRN001 line in the log, and a wall that is present in the file and absent at runtime.

A parameter in the wrong slot, and a schema the router never reads, both fail quietly. Test for a reordering, never for a 200.

Where the list lives

src/schemas/task.schema.ts   sort: z.enum(["id","title","createdAt"])   <-- the allowlist

Three files, one wall. The enum is the allowlist — there is no second check, because a second check is a place to forget.
