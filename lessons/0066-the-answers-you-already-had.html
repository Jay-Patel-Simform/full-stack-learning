One: the body size limit, asked four times

It is in server/src/app.ts, and it has been for as long as the repository has existed:

const app = Fastify({
  logger: { … },
  bodyLimit: 64 * 1024,
  trustProxy: config.TRUST_PROXY,
});

Fastify’s own default is 1 MiB. Yours is 64 KB, sixteen times tighter, and it was a deliberate line somebody wrote. git log -S'bodyLimit' puts it in commit 5f73323 — the squashed first commit. It never appeared in a lesson, so it never got ticked off, so it stayed on the list.

An item can be open on a list and closed in the code. A plan is a claim about the repository, and claims go stale. This is the third time in six lessons that reading the file first changed the lesson — 61’s audit page, 63’s live headers, now this.

But there was a real question underneath it

Lesson 65 added a custom content-type parser for application/csp-report. A custom parser can carry its own bodyLimit, and yours does not pass one. So: does it inherit the app’s 64 KB, or does it quietly get no limit at all? That is a genuinely worth-asking question, and it is the reason the item deserved a look rather than a tick.

Measured, with your installed Fastify and lesson 65’s parser copied exactly:

A limit with no test is a limit you will delete by accident. The line is right, and nothing in the 174 tests you already had would notice if someone removed it. That is your exercise below — three assertions, no new dependency.

Two: does the CSRF hook block a CSP report?

Lesson 65 shipped with an honesty box: “unmeasured — whether the CSRF hook 403s a report POST”. You cannot answer this by reading, because the answer is a fact about what headers a browser puts on a report, and no amount of staring at csrf.ts reveals that.

So: a throwaway page served with a policy that blocks an image, a report endpoint that prints every header it receives, and a real headless Chrome pointed at it. Here is what Chrome actually sent:

=== REPORT ARRIVED ===
method:          POST
content-type:    application/csp-report
sec-fetch-site:  same-origin
sec-fetch-mode:  no-cors
sec-fetch-dest:  report
origin:          http://127.0.0.1:7788
cookie:          undefined
content-length:  386

Now walk that through your own allowWrite(), line by line:

if (SAFE_METHODS.has(method)) return true;      // POST — no
if (site === "same-origin") return true;         // ← returns HERE

The answer is 204, not 403. The report sails through on the second line of the function — the line whose comment says “the good case in production”. And it is the good case, genuinely: since lesson 57 your page and your API are one origin, so a report posted to /api/csp-report is same-origin by construction.

The second measurement, which is the interesting one

What if the report endpoint were not same-origin — if report-uri pointed straight at full-stack-learning-mmty.onrender.com instead of at the /api rewrite? Same probe, page on one host, endpoint on another:

=== CROSS-SITE REPORT ARRIVED ===
method:          POST
content-type:    application/csp-report
sec-fetch-site:  cross-site
sec-fetch-dest:  report
origin:          http://localhost:7790   ← the PAGE's origin

That falls past the same-origin line and lands on the allow-list line:

if (origin) return allowedOrigins.includes(origin);

The Origin the browser attaches is the page’s origin — and your page’s origin is in ALLOWED_ORIGINS, because that is exactly what ALLOWED_ORIGINS is for. So it passes too. Both ways round, reports get through.

Passing and passing for the right reason are two different results. The cross-site report is allowed because your page is on the CORS allow-list — a list that exists to answer a completely different question. The day someone trims that list, reports start vanishing with a 403 that nothing logs and nobody is waiting for. It would look like “CSP stopped finding violations”.

The header you would actually want

Look again at the probe output. Chrome sent Sec-Fetch-Dest: report. Not empty, not document — report. That value means “this request is a browser-generated report” and a page cannot forge it, for the same reason it cannot forge Sec-Fetch-Site: the Sec- prefix makes it a forbidden header name.

So there is a precise discriminator available, and it is one line. Whether you want it is a real decision, and the honest answer is not yet:

Leave it aloneAdd a Sec-Fetch-Dest exception
Works todayYes, measured, both waysYes
Survives trimming ALLOWED_ORIGINSNoYes
Lines of code0~3, in a function you have not touched in 50 lessons
New failure mode—A second reason a write can be allowed

Recommendation: leave it. Write the finding in the honesty box and move on. You have one page, one origin, and a measured pass. Adding a second door to the CSRF gate to protect a telemetry route from a hypothetical config change is the kind of code that looks wise and costs you at 3am. Revisit it the day ALLOWED_ORIGINS has more than one entry that matters.

Three: did the old assets survive? Still cannot tell

Lesson 64 set you homework: save one asset URL, deploy again, curl the saved URL, see whether Render keeps the old deploy’s files alive. I went to run it for you. Here is the live page today:

$ curl -sS https://tracker-web-mxol.onrender.com/ | grep -o '/assets/[^"]*'
/assets/index-D1HMFRqX.js
/assets/index-ChPRm71S.css

That is the same hash lesson 64 wrote down. The bundle has not changed, so there is no “old” version to ask about. The site has redeployed since — last-modified is today, and lesson 63’s headers are live — but a headers change does not change a byte of JavaScript, so Vite produced the identical filename.

A content hash that did not move is telling you the truth: nothing changed. That is the whole point of the name. It also means this experiment needs a real source edit to run at all — which lesson 68 is about to give you.

The check, for when you have one:

# BEFORE you push a change to web/
curl -sS https://tracker-web-mxol.onrender.com/ | grep -o '/assets/[^"]*\.js'
# write that filename down. then push, wait for the deploy, and:
curl -sS -o /dev/null -w '%{http_code}\n' \
  https://tracker-web-mxol.onrender.com/assets/index-THE-OLD-ONE.js

200 means a tab someone had open before your deploy can still load its chunks. 404 means that tab breaks on its next lazy import, and s-maxage=300 from lesson 64 is the only thing hiding it.

Practice — three

Why did reading csrf.ts not answer lesson 65’s question?

allowWrite() is a pure function and entirely readable — you can see exactly what it does with every combination of Sec-Fetch-Site and Origin. What you cannot see is which combination a browser actually sends when it posts a violation report, and that is the input the whole answer depends on. No amount of staring at your own code produces a fact about Chrome. That needed a probe: a page, a policy, a violation and a header dump.

Why is the same live asset hash a useful result?

A content hash is derived from the file’s bytes, so an unchanged name is positive evidence that the JavaScript is identical — which is the exact guarantee lesson 64 leaned on when it put immutable on /assets/*. The site did redeploy: last-modified is today and lesson 63’s headers are live. Headers are served by the platform and are not part of the bundle, so they changed while the filename did not. That is the system working, not a failure.

Why not add a Sec-Fetch-Dest exception today?

The header is genuinely unforgeable — the Sec- prefix makes it a forbidden header name, exactly like Sec-Fetch-Site, so page JavaScript cannot set it. The reason to skip it is different: reports already pass, measured both ways, and the exception only earns its keep if somebody later trims ALLOWED_ORIGINS. Adding a second way to be allowed through the CSRF gate, in a function untouched for fifty lessons, to insure against an edit nobody has made, is cost now for a benefit that may never arrive. Write the finding down instead.
