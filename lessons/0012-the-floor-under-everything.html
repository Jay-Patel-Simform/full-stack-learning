Lesson 12 · Week 7–8 · API security

Choosing security libraries

Lesson 11 put a wall in front of one route. The other twenty will still answer as fast as your laptop can ask.

In one minute

  • Lesson 11 stopped guessing. This one stops noise.
  • A junk cookie has no email in it, so the only key left is the IP. Here that is fine.
  • Install @fastify/rate-limit — first new dependency in eleven lessons, because this job has no decisions left in it.
  • Register it with global: false, then one app-level hook, so the cheap check runs before the session query.

The picture

The idea

Lesson 11's key was the email, because the attacker was guessing a password. Now the attacker is not guessing anything — they are just hammering GET /tasks with a junk cookie. There is no email in that request. The only thing left to count is the IP, and for pure volume that is the right key.

The library rule, both halves

Lesson 11Lesson 12
Rejected the libraryTook the library
Because its default key was wrong for a loginBecause "100 per IP per minute" has no decisions left in it

Reject a library when its defaults are wrong. Take it when the problem has no decisions left in it.

The code

// src/app.ts
await app.register(rateLimit, { global: false, max: 100, timeWindow: "1 minute" });

// then YOUR hook, at app level, so it runs first of everything
app.addHook("onRequest", app.rateLimit());

buildApp() is async now, because register is.

x-forwarded-for — a header a proxy adds to say the real client IP. Believe it only when something you control writes it. trustProxy stays off until you deploy.

Check yourself

Why not just use the plugin's own global: true?

Global mode attaches per route, and per-route hooks run after app-level ones. So requireAuth's Postgres query would happen before the rate limit rejected the request — a check you never reach in time.
