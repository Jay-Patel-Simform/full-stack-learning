The route nobody is logged into

Every route you have written so far has a user behind it. requireAuth runs, a session is found, and everything after that — the rate-limit bucket, the audit row, can() — hangs off knowing who asked. Today you write the first route where nobody is logged in and nobody ever will be: the endpoint that collects CSP violation reports. The reports are the excuse. The skill is the shape, because your invite-accept route will have exactly the same problem in two weeks.

In one minute

  • An unauthenticated route loses three defences at once — the session check, the per-user rate limit, and the audit row that says who did it. You have to replace each one deliberately.
  • Your app will reject the browser’s report with a 415, and it is not a bug. Browsers post application/csp-report; Fastify only parses application/json.
  • Your audit hook will write one row per violation. A single broken page can emit dozens per load. That is a table you delete in a month.
  • The endpoint must be allowed to drop data. It is telemetry, not a transaction. Nobody is waiting for the reply.
  • Honest framing first: with one user and a console open, this buys you very little today. The reason to build it is the shape, not the reports.

First, the argument against building this

Lesson 62 left report-uri out with the note “needs a public unauthenticated route, so its own lesson”. It has now been carried for three lessons, so here it is — but it starts with the case for skipping it.

A reports endpoint pays for itself when you cannot see the console: real users, real browsers, extensions you do not have, an old Safari on someone’s phone breaking on a directive you never tested. You have one user. You have the console open. Today the endpoint tells you nothing that F12 does not tell you faster.

Build it for the shape, not for the reports. Your invite flow needs a route that a person who is not logged in can POST to — that is what accepting an invite is. Every problem below reappears there, except there the request matters and cannot be dropped. This is the cheap place to meet them.

What you lose when there is no session

Read down the “replaced by” column. That column is the lesson:

The fourth row is the one that catches people. Everywhere else in your API, an unknown key is a 400 on purpose — lesson 30’s strict mode, so a front-end typo is loud. Here the sender is Chrome, and Chrome may add a field next year. Strictness is for input you control. For a body somebody else’s browser composes, you read the fields you want and ignore the rest.

The three things that will break it

1. The content type — a 415, not a bug

Fastify parses application/json. It does not parse application/csp-report, which is what browsers actually send, and an unknown content type is answered 415 Unsupported Media Type before your handler exists. One line fixes it:

// the browser posts application/csp-report, not application/json.
// Same bytes, different label — so reuse the JSON parser.
app.addContentTypeParser(
  "application/csp-report",
  { parseAs: "string" },
  (_req, body, done) => {
    // ! a malformed report is the reporter's problem, not ours.
    // ! done(err) here would answer 400; we would rather drop it.
    try { done(null, JSON.parse(body as string)); }
    catch { done(null, {}); }
  },
);

Note what that catch does: it turns bad JSON into an empty object instead of an error. On a telemetry route, a malformed message is something to drop, not something to complain about — nobody is reading your complaint.

2. The audit hook — a row per violation

Your hook in app.ts calls shouldAudit(method, status), which returns true for every non-safe method. A POST is a write, so every report becomes an audit row — with userId: undefined, because there is no user. One broken screen emitting fifteen violations per load is fifteen rows with no actor, and your audit log stops being the thing you can read.

// in the onResponse audit hook, first line:
if (request.routeOptions.url === "/csp-report") return;

Check the route pattern, never request.url — the same rule the hook already follows for the route column, and for the same reason: a URL is caller input.

3. The rate limit — the bucket you share

The global limit already covers this route: 100 per IP per minute. But those hundred are shared with the user’s real requests, so a page spraying reports would spend the allowance and then get 429s on the actual app. Give the route its own, much tighter limit:

app.post("/csp-report", {
  config: { rateLimit: { max: 20, timeWindow: "1 minute" } },
}, async (request, reply) => {
  // 204: received, nothing to say. The browser ignores the body anyway.
  reply.code(204);

  const r = (request.body as any)?.["csp-report"] ?? {};
  request.log.warn({
    // ! the fields you chose, never the whole object — server/CLAUDE.md.
    // ! this body came from the internet; logging it whole is log injection.
    blocked: String(r["blocked-uri"] ?? "").slice(0, 200),
    directive: String(r["violated-directive"] ?? "").slice(0, 100),
    doc: String(r["document-uri"] ?? "").slice(0, 200),
  }, "csp violation");
});

Three deliberate choices in that handler. 204, because there is no body worth sending to a reporter that does not read it. slice() on every field, because the values are attacker-influenced and a log line is a place attackers like to write. Named fields, never the whole report — the rule your own server/CLAUDE.md already states, and this is the route where it matters most.

and one I have not measured
Your CSRF hook might refuse the report before any of this runs. Lesson 46’s allowWrite() denies a POST unless Sec-Fetch-Site is same-origin or the Origin is allow-listed. A violation report is sent by the browser itself rather than by your page, and I do not know for certain what it puts in those two headers — I would be guessing, and lesson 63 is about what guessing costs. Measure it: deploy, trigger a violation, and look at the response. A 403 in the network tab means the hook caught it, and the fix is one early return in the hook for this one route pattern. A 204 means it passed. Tell me which.

Wiring it up

The route goes on the API, and the policy has to point at it. Since lesson 57 your front end and API share an origin, so the path is simply /api/csp-report, and the headers: block gains one directive inside the existing policy value:

value: "default-src 'self'; … object-src 'none'; report-uri /api/csp-report"

report-uri is formally deprecated in favour of report-to and the Reporting API, which needs a second header and a JSON endpoint-group document. It is also the one every browser actually implements today. Ship report-uri alone; when report-to is universal, this is a one-line change and your endpoint does not move.

The loop

  1. Prove the 415 first, so you have seen the failure before the fix: curl -X POST -H 'content-type: application/csp-report' -d '{}' …/api/csp-report
  2. Add the parser, the route, the audit skip. Add the directive to render.yaml.
  3. Deploy both. Same curl — expect 204.
  4. Open the app, and in the console run document.body.appendChild(document.createElement('script')).src='https://evil.example/x.js'
  5. Read your server log, not the browser console. One csp violation line with directive: script-src. That line arriving is the whole point: the browser told your server what it blocked.

Practice — three

Why can this route not use a strict zod schema?

Strict mode exists to catch your typos — a front end sending isDone when the API wants done should be a loud 400 rather than a silent no-op. Here the sender is the browser, the field set differs between Chrome, Firefox and Safari, and a new field next year is normal rather than a mistake. So you read the few fields you care about and ignore everything else. Strictness is for input you control.

Why exclude this route from the audit log?

Every audit row answers “who did what”, and here there is no who — userId is always undefined because nobody is logged in. Worse, the volume is set by a broken page rather than by a person: one bad screen can emit dozens of reports per load, and each becomes a row. A table that grows without an actor and without a ceiling is one you stop reading, and an audit log nobody reads is not an audit log.

Why answer 204 instead of 200 with a body?

The browser sends a violation report and discards whatever comes back — there is no caller to inform, no UI to update and no retry that depends on the answer. 204 No Content states exactly that, and saves composing a body nobody parses. It is the same instinct as dropping a malformed report instead of answering 400: on a telemetry route your job is to receive cheaply, not to converse.

What you did not build, on purpose

left out
storing reports in Postgres a log line is enough to learn from, and a table filled by the public internet needs retention, an index and a page to read it — three things before the first useful answer. If you ever want the table, add it when the log lines have proved what you would query.
report-to and the Reporting API the standards-track replacement. A second header, a JSON group document, and no browser that needs it yet. One line to add later.
de-duplication one violation per element, so a bad page repeats itself. The 20/min cap is the crude version and costs nothing; real de-dup needs state, and state is the thing you have gone 65 lessons without adding.
alerting on a report you have no alerting at all yet. Wanting to be paged for this is a reason to build alerting, not a reason to build it here.
