Lesson 57 · Week 15–16 · Docker + deploy

One origin, and the cookie comes back

Lesson 56 ended with a 401 you could not blame on your code. Today the front end joins the API on one origin and that 401 disappears — not by loosening a cookie flag, but by removing the second site. One new Render service, two rewrite rules, one env value on each side. Zero TypeScript changes. Suite stays at 172.

In one minute

  • There are two fixes and only one of them is right. SameSite=None makes the 401 go away and gives back the CSRF defence you bought in lesson 29. Putting the page and the API on one origin makes the cross-site request stop existing.
  • A Render static site can proxy. A rewrite rule sends /api/* on to your API service. The browser only ever talks to one host, so there is no cross-site anything to defend against.
  • Your cookie has no Domain= attribute, which is exactly why this works with no server change. A host-only cookie belongs to whatever host the browser asked — and now that host is the page’s own.
  • VITE_API_URL becomes /api — a path, not a URL. And Vite bakes it into the bundle at build time, which is the opposite of how every server variable you have works.
  • ALLOWED_ORIGINS shrinks to one entry, the static site’s URL. CORS goes quiet: same-origin requests never ask it anything.
  • One thing to go and check afterwards, not to take on trust: what request.ip now says, because your 100-per-minute floor is keyed on it and there is a new machine in the path.
  • Streak intact: no new dependency, 57 lessons.

Five fields, two rules, two variables — and not one line of code. Everything below is about why each of those is what it is — and the why is worth more than the how, because the how is different on every platform and the why is the same everywhere.

Why — 1. name the failure exactly, before fixing it

The 401 has a precise cause and it is worth being able to say it in one sentence, because the wrong sentence leads to the wrong fix.

SentenceTrue?Why it matters
CORS blocked the requestNoThe login returned 200 and you read the body. CORS had already said yes.
The cookie was never storedNoIt was stored. Secure is fine — the API is real HTTPS now.
The cookie was not sentYesSameSite=Lax. localhost and onrender.com are different sites, so the browser holds it back.

Open DevTools → Network → the failing request → Request Headers, and confirm it for yourself: there is no Cookie header. Then look at Application → Cookies and see the session sitting there, stored, unsent. That gap between “stored” and “sent” is the whole lesson.

Same site is not same origin. An origin is scheme + host + port. A site is roughly the registrable domain: a.example.com and b.example.com are two origins but one site. localhost and onrender.com are neither.

SameSite=None is not forbidden — it is the correct answer when the page and the API genuinely are different companies, and then you pay for it with a real CSRF token. You are not in that situation. You have one app whose two halves happen to be on two hosts, and that is a deployment accident, not a design.

Do not loosen a defence to accommodate an accident. Ask first whether the situation the defence is complaining about should exist at all. Here it should not: there is no reason on earth for your own page to be a third party to your own API.

Why — 4. the two rules in step B

This is the whole lesson in one form. On the static site: Redirects/Rewrites → Add Rule. Order matters, and the API rule must be first.

Source  /api/*
Destination  https://<your-api>.onrender.com/*
Action  Rewrite

Source  /*
Destination  /index.html
Action  Rewrite

Two things are happening, and they are unrelated to each other.

The first rule is the fix. * in the source captures everything from that point on; * in the destination pastes it back. So /api/auth/login arrives at your API as /auth/login — the path your routes already use. Rewrite, not Redirect: a redirect sends a 301 back and the browser goes to the API host itself, which is the cross-site problem you started with, now with an extra round trip. A rewrite is invisible to the browser. Render fetches your API server-side and hands the answer back under its own hostname. Render’s own words: the destination “can be either a path or a full, publicly accessible URL”.

The second rule is ordinary SPA housekeeping. Your React app routes in the browser, so a hard reload on any path other than / asks the CDN for a file that does not exist. /* → /index.html hands every unknown path to the app. It has to come second, or it would swallow /api too. Rules are matched top down.

Why — 5. the two variables in steps C and D

On the static site, one environment variable:

VITE_API_URL=/api

Not a URL. A path. web/src/lib/api.ts passes it to axios as baseURL, and a relative baseURL resolves against whatever page it is running on — so the request goes to https://tracker-web.onrender.com/api/auth/login, which is the page’s own origin.

A VITE_ variable is not an environment variable. It is a compile-time find-and-replace. Vite substitutes import.meta.env.VITE_API_URL for the literal string while building, and ships the result. Changing it in the dashboard does nothing until you redeploy. And anyone can read it, because it is sitting in the JavaScript you sent them. Vite’s docs say it outright: never put a secret in one.

On the API service, shrink one value:

ALLOWED_ORIGINS=https://tracker-web.onrender.com

Drop the API’s own URL and http://localhost:5173 if they are still in there. Keep it exact — scheme included, no trailing slash. Then hit the static site’s URL, log in, and watch the request that used to 401.

Why no server change was needed — the missing attribute

A proxy in front of an API usually breaks cookies, and there is a whole genre of blog post about rewriting the Domain on the way through. You skip all of it, for a reason worth knowing:

server/src/auth/session.ts

session=<id>; HttpOnly; SameSite=Lax; Path=/; Expires=…; Secure
                                    ^ no Domain= anywhere

A Set-Cookie with no Domain makes a host-only cookie: the browser files it under the exact host it asked, and sends it back only to that host (MDN). The browser asked tracker-web.onrender.com, so that is where the cookie lands and that is where it goes back — it never learns the API host exists. Had you written Domain=<your-api>.onrender.com at any point, today would have needed a proxy that rewrites it.

The narrowest default is the one that survives being moved. Host-only was never chosen for this situation; it was chosen because it was the tightest thing that worked. Tight defaults keep paying out in situations you had not imagined.

The one thing to go and check

There is now a machine between the browser and your API that was not there yesterday. Your global floor from lesson 12 is 100 requests per IP per minute, and the whole question is whose IP that counts.

browser → Render CDN (rewrite) → Render router → your container

If the forwarded client address survives that hop, request.ip is the visitor and the limit works per visitor. If it does not, every visitor in the world shares one bucket and the 101st request of the minute is a 429 for somebody innocent. TRUST_PROXY=true makes Fastify read X-Forwarded-For instead of the socket, so the machinery is in place — but whether the CDN hop appends to that header is a fact about Render, not about your code, and I have not measured it.

Check it, do not assume it. Your logger already prints reqId and the request line; load the page, then read the API service’s Logs tab in the dashboard and compare the address against what your own IP actually is. Two outcomes, both fine to discover:

what you find
your real IP the chain forwards correctly. Nothing to do. Say so in the next session and it becomes a measured fact instead of an open question.
one address for everyone the per-IP floor is meaningless behind the CDN, and the answer is not a bigger number — it is to key the limit on something that identifies a caller. The login throttle from lesson 11 is already keyed on the account, and it is unaffected either way.

Why Rewrite and not Redirect for /api/*?

A redirect answers 301 with the API’s own URL, and the browser goes there itself — two sites again, cookie withheld again, plus a wasted round trip. A rewrite is server-side: Render fetches the API and replies under its own hostname, so the browser only ever sees one origin. Both forms can forward the path.

Why does the proxy not break the session cookie?

No Domain= attribute means the browser files the cookie under the host it actually asked — the static site — and sends it back there. The API host is never named in the cookie and the browser never learns it. HttpOnly is about JavaScript access and has nothing to do with which host receives it.

You change VITE_API_URL. What happens?

Vite replaces import.meta.env.VITE_API_URL with the literal string while building and ships that. The deployed bundle has no idea the variable exists. Server env is read at boot; VITE_ env is read at build. Same word, two different moments — and the built one is public.
