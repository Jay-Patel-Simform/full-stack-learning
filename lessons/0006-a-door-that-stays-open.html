Lesson 06 · Week 3–4 · Auth

Sessions and cookies

Lesson 5 checked a password once. Today the API remembers who you are on every request after that.

In one minute

  • HTTP forgets. Every request arrives as a stranger.
  • Give the browser a random session id in a cookie. The browser re-sends it for free.
  • Store only sha256(id). Steal the table, get nothing usable.
  • Delete the row and the person is logged out now. A plain JWT cannot do that.

The picture

The idea

HTTP has no memory. Request two knows nothing about request one. So after a successful login you have to hand the browser something it will show you again next time.

Two choices exist. A session: a random id, with the real facts in your database. Or a JWT: the facts themselves, signed, held by the client.

Session — chosen

cookie: sid=Xk9...   (random)
DB row: { hash, userId, expiresAt }

logout  -> DELETE the row
         -> dead immediately

Plain JWT

cookie: eyJhbGci...  (the facts)
DB row: none

logout  -> ask nicely
         -> valid until it expires

We picked sessions because revocation is the whole point. "Log this person out now" has to be a real button.

HttpOnly — JavaScript cannot read the cookie. Stops a script on your page stealing the session.
Secure — HTTPS only, never plain HTTP.
SameSite=Lax — the browser will not attach it to a cross-site POST. Comes back in lesson 16.

The code

// src/auth/session.ts
const id = randomBytes(32).toString("base64url");   // give this to the browser
const hash = createHash("sha256").update(id).digest("hex"); // store this
await prisma.session.create({ data: { hash, userId, expiresAt } });

// src/auth/require-auth.ts — one hook, every task route
export async function requireAuth(request, reply) {
  const user = await sessionUser(request.cookies.sid);
  if (!user) return reply.code(401).send({ error: "not logged in" });
  request.user = user;
}

Hand out a ticket, keep the facts. Then logging someone out is one DELETE.

Check yourself

Why store sha256(id) instead of the id itself?

Same reasoning as the password hash. If someone reads your Session table they get hashes, and a hash cannot be sent as a cookie.

Do this

  1. Log in with curl -c jar.txt. Then curl -b jar.txt localhost:3000/tasks.
  2. Delete the session row in psql. Retry. You want a 401.
  3. Send a made-up cookie value. Also a 401, and no crash.
