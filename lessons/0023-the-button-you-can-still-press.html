Lesson 23 · Week 10 · Front end

Client UI is not a permission

Your page now knows your role, and hides what your role may not do. That is a courtesy to the user. It is not a wall, and today you watch it fail on purpose.

In one minute

  • New route: GET /teams. It has no permission gate, and that is not an omission — the where clause is the scope.
  • It answers with { id, name, role, can }. can is the list of actions your role may do, straight out of the server's own table.
  • The page draws a button only if the action is in can. Hidden, not disabled.
  • Un-hide the button and the server still says 403. Two independent facts. Only the second one is security.
  • So the teams query keeps a 30-second cache while the session query has none. A stale hint cannot open anything.

The word pair

hiding — the page chooses not to offer something. Happens in your JavaScript, which the user owns, can read, and can edit. Costs nothing and can be undone in ten seconds.
refusing — the server declines to do it. Happens on a machine the user does not own. Costs a round trip, and cannot be undone from the browser.

Every access-control bug that ships is somebody who did the first one and believed they had done the second.

The last line is the whole lesson. The page changed its mind about what a Viewer may do. The server did not. Full output, and the two-lens picture, are in See it drawn below.

Why 409 and not 201. The probe invites you to a team you are already in. The gate refuses (403), or the gate agrees and the store finds your row already there (409). No third answer, so the button can never change anything.

The route with no gate

Every route since lesson 8 names a team in the URL, so requirePermission() can ask “what is your role there”. This one asks the opposite question, and there is no :teamId to scope it with:

app.get("/teams", { schema: { response: { 200: TeamList } } }, async (request) => {
  const rows = await listMemberships(request.userId!);
  return rows.map(({ role, team }) => ({ ...team, role, can: allowedActions(role) }));
});
where: { userId },   <-- in listMemberships. this line is the authorisation.

There is no “all teams” query to forget a where clause on, so there is nothing to refuse. Somebody in no team gets [] and a 200, not a 403, and so never learns your team exists — same reasoning as lesson 18.

A permission check needs a scope. When the scope is the query, the query is the check.

One table, two consumers

can is not a new decision. It is three words in src/auth/can.ts:

export const allowedActions = (role: Role): readonly Action[] => PERMISSIONS[role] ?? [];

The obvious alternative was to write the role→actions table again in React. Don't: two copies drift, and the copy that drifts is the one nobody tests. Send the answer instead. The front end then holds no policy at all — only labels:

const BUTTONS: readonly [Action, string][] = [
  ["task:create", "New task"],
  ["member:invite", "Invite member"],
  ["team:delete", "Delete team"],
];

BUTTONS.filter(([action]) => team.can.includes(action)).map(...)   <-- the line you deleted

Hidden, not disabled. A greyed-out Delete team still tells a Viewer that deleting the team is a thing that happens on this screen, and invites them to go looking. If they may not do it, do not mention it.

The knob that proves it is only a hint

Lesson 22 ended with a rule: auth is the one query with no grace period, staleTime: 0. The teams query breaks that rule on purpose and keeps the 30-second default.

QuerystaleTimeBecause a stale answer means
["session"]0a signed-out user still seeing an app
["teams"]30_000a button drawn that the server will refuse

If can were the check, this cache would be a thirty-second hole. It is not the check, so it is a thirty-second cosmetic wobble. The safety of a cache depends entirely on what the cached value is allowed to decide.

And can is approximate even when it is fresh

Your can() takes three arguments since lesson 9: role, action, and the target. The rank rule — act only on somebody strictly below you — needs to know who you are aiming at. A flat list has no target in it. So an Admin's can contains member:remove, and the answer for “remove the Owner” is still no.

The UI can be told what a role may generally do. It can never be told what it may do to this person. That gap is a permanent argument for deciding on the server.

Check yourself

What does the can list in the reply actually decide?

Only the drawing. Every write still passes requirePermission(), which asks can() again with the target loaded. Delete the filter in the React file and the buttons come back — the 403 does not go away. Measured above.

Why does GET /teams need no requirePermission gate?

A permission is scoped, and this route has no :teamId to scope to. where: { userId } returns only your own membership rows, so there is no row to refuse. “It only reads” is the wrong reason — reading somebody else's team would be exactly the leak lesson 18 closed.

Why may the teams query cache 30s when the session query may not?

A stale session leaves a signed-out person looking at an app. A stale can leaves a button on screen that the server refuses. One is a hole, the other is a cosmetic wobble — and the difference is not the cache, it is what the value is allowed to decide.

2. One table, two consumers

Both answers come out of the same twelve lines in src/auth/can.ts. They leave by different doors and end in different kinds of thing.

Look at the third argument on the right. The gate knows who you are aiming at; the list cannot — so an Admin's can holds member:remove while removing the Owner is still refused. The hint is approximate by construction, not by accident.

Write the role→actions table twice and you have two policies. Send the answer instead and you have one, with a copy of its output on screen.
