Lesson 54 · Week 15–16 · Docker + deploy

The box that starts itself

Lesson 53 promised one command and then gave you five. You ran migrate deploy by hand, db seed by hand, and piped a SQL file in by hand. You also hit a trap I did not warn you about: docker compose up ran an old copy of your seed file and the seed crashed. Today those three manual steps become part of starting the container, and you learn why the old copy was there. Zero TypeScript changes. Suite stays at 172.

In one minute

  • An image is a snapshot, not a window. COPY . . copied your files at build time. Editing them afterwards changes nothing inside the image. up does not rebuild — up --build does.
  • An entrypoint (a script the container runs before your app) is where "set the database up, then serve" lives. One small shell file, four lines.
  • migrate deploy is safe to run on every single boot. It applies what is pending and says No pending migrations to apply. when there is nothing. That property has a name: idempotent (running it twice does the same as running it once).
  • Two containers starting at once do not corrupt anything. Prisma takes a Postgres advisory lock (a lock you ask for by name, on no table at all). One migrates, the other waits. I ran two at once against an empty database to check this.
  • Migrations start automatically. The seed does not, ever. A migration is part of the code. Fake rows are not.
  • Streak intact: no new dependency, 54 lessons.

First: why your seed crashed

You ran the seed and Prisma threw P2025 on this line:

const bulkOwner = await prisma.user.findUniqueOrThrow({
  where: { email: "jay@example.com" },
});
An operation failed because it depends on one or more records that were
required but not found.

The user was missing. But jay@example.com is in your seed.ts, at the top, in the tasks object. You could open the file and read it.

It was not in the file the container ran. Your Dockerfile says COPY . ., and that copy happened once, when the image was built — before you added that line. The container was running a seed file from the past, and the log proves it: two seeded lines, not three.

An image is a photograph of your source, not a window onto it. Every edit you make after the build is invisible inside the container until you build again. docker compose up reuses an existing image and never checks whether it is stale. You want docker compose up --build while you are changing code.

You will meet this again the first time a deploy “ignores” a fix. It did not ignore it. It was never given it.

The new file: server/docker-entrypoint.sh

Four lines. Read them before the explanation.

#!/bin/sh
set -e
npx prisma migrate deploy
npx prisma db execute --file prisma/sql/audit-lockdown.sql
exec "$@"
LineWhat it does, and why it matters
set -eStop at the first command that fails. Without it the script would carry on to exec and serve requests against a half-migrated database. With it, the container exits and Docker marks it Exited (1). A dead container is a much better outcome than a lying one.
migrate deployThe same command you typed by hand, now on every boot. It reads DATABASE_URL from .env.docker — the tasks owner role. Migrations still run as the owner, exactly as lesson 42 decided. Your app still serves as tasks_app.
db execute --fileThis is the homeless step from last lesson. audit-lockdown.sql could not run at db init, because it names a table. Here it can: migrations just finished, so "AuditLog" exists. REVOKE is idempotent, so running it every boot is free. And prisma db execute means the API image needs no psql installed.
exec "$@""$@" is whatever the CMD is — npm start. exec replaces this shell with that command instead of starting a child. Without exec the shell stays alive as the container's main process, and SIGTERM on shutdown stops at the shell — the same signal problem lesson 52 solved with the JSON CMD.

The two new lines in server/Dockerfile

Put them at the end, after the existing CMD:

RUN chmod +x docker-entrypoint.sh

ENTRYPOINT ["./docker-entrypoint.sh"]
CMD ["npm", "start"]

The file already arrives in the image — COPY . . takes the whole server/ directory. chmod +x is there because a file copied without the execute bit cannot be run, and whether it has one depends on your Mac.

ENTRYPOINT and CMD are not rivals. Docker joins them: ENTRYPOINT is the command, CMD is its arguments. So the container runs ./docker-entrypoint.sh npm start, and "$@" on the last line is npm start.

ENTRYPOINT is what the container always does; CMD is what it does by default. That split is why docker compose run --rm api npx prisma db seed still works: it replaces the CMD, so the migrations still run first and then your seed runs instead of the server.

That line is the whole reason this is safe to leave in. The second boot costs a query and changes nothing.

Still by hand: the seed

A fresh volume has no users, so you still cannot log in. Run it once, deliberately:

docker compose run --rm api npx prisma db seed

This stays manual on purpose, and the reason is not laziness. A migration is part of your code — the same 15 files run on your Mac, in CI and on the server, and the schema is worthless without them. A seed is 500 fake tasks. Wire that into container start and the day you deploy, your production database gets Fake task 1 through Fake task 500 and a user whose password is in a public repository.

Automate the step that must happen everywhere. Keep your hand on the step that must happen nowhere but here.

Two containers, one empty database

The obvious worry: at deploy you often start more than one copy of the API. If every copy runs migrate deploy at the same second against an empty database, do they collide?

I ran exactly that — two containers, started together, empty volume:

docker compose down -v && docker compose up -d db
docker compose run --rm --no-deps api sh -c 'npx prisma migrate deploy' &
docker compose run --rm --no-deps api sh -c 'npx prisma migrate deploy' &
wait

Both exited 0. One applied the 15 migrations; the other printed No pending migrations to apply. Nothing ran twice.

The reason is a Postgres advisory lock. That is a lock with a number you choose, attached to no table — Postgres just promises that only one connection holds it at a time. Prisma takes one before it touches _prisma_migrations. The second container blocks on that lock, and by the time it gets in, the work is done and there is nothing pending.

This is worth knowing beyond Prisma. Any time two processes must not do the same job at once, and the job is not one row you can lock, an advisory lock is the tool.

The failure you should cause on purpose

My first version of the entrypoint had a wrong flag. Prisma 7 removed --schema from db execute:

api-1  | unknown or unexpected option: --schema
$ docker compose ps -a
server-api-1   ...   Exited (1)
server-db-1    ...   Up (healthy)

Look at what did not happen. The API never started. /health did not answer. No request ever reached a database in an unknown state. That is set -e doing its one job, and it is why a startup script without it is dangerous: it would have printed the error, ignored it, and served.

Break it yourself. Add a line that fails, such as false, rebuild, and watch the container die. Then take it out.

Why did the container run a seed file you had already fixed?

The image holds a copy of your source made when it was built. docker compose up reuses that image and never compares it to your disk. Use up --build, or docker compose build api, whenever you have edited code the image contains.

Why is exec "$@" the last line, and not just "$@"?

Without exec, the shell stays as the container's main process and the app is its child. Docker sends SIGTERM to the main process, so shutdown would stop at a shell that ignores it. exec hands the process over — the same reason lesson 52 used the JSON form of CMD.

Migrations run on every boot. Why not the seed too?

Migrations are part of the code and must run on every machine. A seed writes 500 fake tasks and a user with a known password. Automating it would put both into production on your first deploy. Automate what must happen everywhere; keep your hand on what must happen only on your laptop.

What you did not build, on purpose

left out
a rollback there is no migrate undo, and there should not be. A migration that breaks the old code is fixed by a new migration, forward. This becomes real when the deploy has users on it.
waiting for the database in the script no wait-for-it loop. Compose's condition: service_healthy from lesson 53 already does it. On Fly.io there is no compose, and the loop comes back.
a separate migration job the grown-up version: one container migrates, then the app containers start. Compose cannot express it well. Fly.io has release_command for exactly this, and that is where you will meet it.
the front end still not a service. Still next, or after the deploy.

Read this: Docker — ENTRYPOINT, especially the table showing how ENTRYPOINT and CMD combine. Then Prisma — development and production, which is the official version of “never migrate dev near a deploy”.

Then this: two experiments, five minutes. First, add false to the entrypoint, rebuild, and confirm the container exits and /health does not answer. Second, change one word in a console.log in src/, run docker compose up -d without --build, and confirm your change is not there. Then add --build. Feel that one once and you will never debug it again.

Reference card: Environment — the entrypoint uses DATABASE_URL (owner) and the app uses APP_DATABASE_URL (restricted). Two roles, one container, and the boot is the only moment the owner one is needed.
