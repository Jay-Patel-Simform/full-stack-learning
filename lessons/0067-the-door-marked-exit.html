Lesson 67 · Week 13–14 · RBAC

The door marked exit

Since lesson 9, your permission gate has had one rule about people: you may only act on somebody strictly below you. It closed a real hole — an Admin cannot remove the Owner. It also closed a door you never meant to close. Right now, in your API, nobody can leave a team. Not the owner, not an admin, not a viewer. The plan has carried this as “an owner cannot leave their own team” for forty lessons, and the note undersold it.

In one minute

  • The bug is wider than the note says. Every role is trapped, for two different reasons, and the reasons need two different fixes.
  • Leaving is not removing. Same row deleted, different act — so it is a different action, not a special case bolted onto member:remove.
  • The rank rule has nothing to say about you and yourself. Comparing your rank to your own rank is always a tie, and a tie is a no. So the leave action carries no target.
  • One real refusal survives: the last owner may not leave, or the team is orphaned forever. That is a 409, not a 403.
  • A transaction will not save you here. Two owners leaving at the same instant both see two owners. You need a lock, and it is one line.

First, reproduce it

Before any code, prove the trap. You have a team where you are OWNER. Try to remove yourself with the route that already exists:

DELETE /teams/1/members/<your own user id>
→ 403 {"error":"forbidden"}

Now walk the gate and see why. requirePermission("member:remove", targetMember) loads the victim’s role — the victim is you — and calls:

// can.ts, the rank rule
const target = resource?.targetRole;
if (target !== undefined && rank(role) <= rank(target)) return false;
//                          rank(OWNER) <= rank(OWNER)  →  3 <= 3  →  true  →  no

Equal rank is a no. That was deliberate in lesson 9 — it stops two admins from deleting each other — and you are always exactly equal to yourself. So the owner is stuck.

Now check the other three roles, because the note only mentioned one

RoleHas member:remove?Rank rule vs selfCan leave today?

Four roles, one outcome, two unrelated causes. Viewers and members are refused by the permissions table — they were never given the power to remove anybody. Admins and owners get past the table and are refused by the rank rule. A fix aimed at the rank rule alone would free two roles and leave two trapped.

When one symptom has two causes, you have two bugs. The 403 looked like a single problem because your gate deliberately answers the same way for every kind of no — lesson 8’s “one reply for two different noes”. Good for attackers, quietly misleading for you. The reply is identical; the reasoning is not.

The wrong fix, and why it is wrong

The tempting patch is three lines in the gate:

// ! do not do this
if (request.params.userId === request.userId) return; // leaving is fine

It works. It is also the shape lesson 9 taught you to distrust: a special case in the gate that the permissions table knows nothing about. Three specific costs:

  • can() stops being the answer. Today one function decides everything, and you can read it in sixty seconds. After this patch, “may I?” is answered by can() plus a condition in a hook, and the second one is invisible from the first.
  • The front end cannot see it. allowedActions(role) is where the UI gets its list of buttons. An exception living in the gate is not in that list, so the page can never learn that Leave exists.
  • It cannot express the one refusal you actually want. The last owner still must not leave. A blanket “self is fine” has nowhere to put that.

Leaving and removing are different acts that happen to delete the same row. Removing is something you do to someone; leaving is something you do about yourself, and nobody outranks themselves. Count the nouns: member:remove has an actor and a target, member:leave has only an actor. Different number of nouns, different action.

The fix, in four files

1. server/src/auth/can.ts — a new action, and who has it

Two edits. Add the action to the list, and grant it at the bottom rung so every role inherits it:

export const ACTIONS = [
  "task:read",
  "project:read",
  "task:create",
  "task:update",
  "task:delete",
  "project:create",
  "project:delete",
  "member:invite",
  "member:remove",
  "member:leave",
  "team:delete",
  "audit:read",
] as const;
// ! member:leave sits on VIEWER, the lowest rung, so all four roles inherit
// ! it. Nobody is held in a team against their will -- not even the owner,
// ! who is stopped by the state of the team below, never by their role.
const VIEWER = ["task:read", "project:read", "member:leave"] as const;

That is the whole permissions change. Note what you did not touch: the rank rule. It stays exactly as lesson 9 wrote it, because it is still right about what it is for.

2. server/src/store/team.store.ts — the leave itself

Append this. Read the comments twice; the lock is the part that is easy to leave out and impossible to notice.

// * Leaving is its own store function, not removeMember with a different
// * argument, because it has a rule removeMember does not: the last OWNER
// * may not go. A team with no owner cannot be deleted, cannot invite, and
// * cannot be handed to anybody -- it is stuck for good.
export async function leaveTeam(
  teamId: number,
  userId: number,
): Promise<"gone" | "missing" | "last-owner"> {
  return prisma.$transaction(async (tx) => {
    // ! Lock the team row FIRST, before reading anything about it.
    // !
    // ! A transaction alone does NOT fix the race here. Postgres runs at READ
    // ! COMMITTED by default, so two owners leaving at the same instant would
    // ! BOTH count two owners, BOTH delete a different row, and both commit.
    // ! Atomicity is not isolation. This SELECT ... FOR UPDATE makes the
    // ! second leave wait for the first to finish, so it counts one and is
    // ! refused. A tagged template, so teamId travels as a parameter --
    // ! lesson 20's one mechanism.
    await tx.$queryRaw`SELECT id FROM "Team" WHERE id = ${teamId} FOR UPDATE`;

    const me = await tx.membership.findUnique({
      where: { teamId_userId: { teamId, userId } },
      select: { role: true },
    });
    // ? Not a member. The gate already answered 403 for strangers, so this
    // ? is the narrow case of a membership deleted since the gate looked.
    if (!me) return "missing";

    if (me.role === "OWNER") {
      const owners = await tx.membership.count({ where: { teamId, role: "OWNER" } });
      // ! < 2, not === 1. Same answer today; survives the day a bug leaves
      // ! a team with zero owners, where === 1 would happily delete nothing.
      if (owners < 2) return "last-owner";
    }

    await tx.membership.delete({ where: { teamId_userId: { teamId, userId } } });
    return "gone";
  });
}

Three return values, not a boolean. The route has three different things to say, and a boolean would force the route to re-derive which one — a second read, racing the first.

3. server/src/routes/teams.route.ts — the route

Add this above the DELETE /teams/:teamId/members/:userId route. It does not have to be above — see the box after — but read order should match the specific-before-general rule you are relying on.

// * Leaving, not removing. No Load function and therefore no targetRole, so
// * the rank rule stays out of it entirely -- which is correct: you do not
// * outrank yourself, and you never will. The only refusal left is about the
// * TEAM's state, and that lives in the store, not in the gate.
app.delete(
  "/teams/:teamId/members/me",
  {
    schema: {
      params: TeamParams,
      response: { 204: z.null(), 403: ErrorReply, 404: ErrorReply, 409: ErrorReply },
    },
    preHandler: requirePermission("member:leave"),
  },
  async (request, reply) => {
    const { teamId } = request.params as TeamParamsInput;
    const result = await leaveTeam(teamId, request.userId!);

    // ! 409, not 403. 403 means "you may not" -- and you may, that is what
    // ! member:leave says. What refuses you is the state of the world: you
    // ! are the only owner. Change the world and the same request succeeds.
    // ! A 403 tells the user to find an admin; a 409 tells them what to do.
    if (result === "last-owner")
      return reply
        .code(409)
        .send({ error: "the last owner cannot leave; make somebody else an owner first" });

    if (result === "missing") return reply.code(404).send({ error: "not found" });

    return reply.code(204).send();
  },
);

And add leaveTeam to the import from ../store/team.store.ts.

the routing question you should have asked
Does /members/me collide with /members/:userId? No, and not because of the order you wrote them in. Fastify’s router is a radix tree and a static segment always beats a parametric one, whichever was registered first. So /members/me wins, always. Worth knowing precisely, because the same fact means /members/me can never be reached by a user whose id is literally the string me — and MemberParams would have answered 400 for that anyway, since z.coerce.number() makes "me" a NaN. Two independent reasons this is safe; check them yourself with one curl each.

4. The front end gets it for free

Nothing to write. GET /teams already sends can: allowedActions(role), and TeamMembership types can as z.array(z.enum(ACTIONS)) — so the moment member:leave joins ACTIONS, every team row in the API response carries it. One table, two consumers, still.

The hint is approximate, for the third time. can will contain member:leave for a sole owner, and their leave request will still be a 409. Lesson 9 said it (the rank rule needs a target a flat list has not got); lesson 23 said it about a flat list of teams; here it is a fact about the team rather than about ranks. Same shape every time: the list says what to offer, the server says what happens.

// 1. a VIEWER leaves                         → 204, and GET /teams no longer lists it

Practice — three

Why does member:leave pass no target to can()?

The rank rule exists to stop you acting on a peer or a superior, and it does that by refusing whenever your rank is less than or equal to the target’s. Against yourself that comparison is a tie by definition, at every role, forever — so passing a target would make the action permanently impossible. The rule is not wrong; it simply has nothing to say about an act with only one person in it. An action with no target skips the comparison entirely, which is exactly what team:delete already does.

Why is the sole owner refused with 409 and not 403?

403 is a statement about the caller: you are not permitted to do this, and doing it again will not help. But a sole owner is permitted to leave — member:leave sits on VIEWER, so every role has it. What refuses them is a fact about the team: removing the last owner would strand it. That is a conflict with the current state, which is what 409 means, and it is actionable — promote somebody and the identical request succeeds. Status codes are for the caller to act on, so this one tells them what to change.

Why will a transaction alone not stop two owners leaving together?

A transaction guarantees that your statements land together or not at all — atomicity. It does not, at Postgres’s default READ COMMITTED level, guarantee that two concurrent transactions cannot make decisions on the same stale reading. Both owners count two, both conclude they are not the last, both delete a different row, and both commit happily. The team ends with zero owners and no error anywhere. SELECT … FOR UPDATE on the team row is what serialises them: the second transaction blocks until the first commits, then counts one and is refused.

What you did not build, on purpose

left out
a Leave button on the page the API is the lesson, and can already carries member:leave to the front end, so the button is a small piece of work with no new ideas in it. It also wants a confirm step, and lesson 28 argued that a confirm dialog without real undo is a speed bump — so it belongs with soft delete.
transferring ownership the obvious partner to this, and a bigger lesson than it looks: promoting somebody to OWNER means an owner handing out their own rank, which the rank rule forbids. That is a second deliberate exception and deserves its own hour, not a footnote in this one.
deleting the team when the last owner leaves the tempting “helpful” version, and it is a data-loss trap: one click on Leave silently destroys every task the team ever had. Owners already have team:delete if that is what they want. Make the destructive thing deliberate — the same rule as lesson 3.
reusing removeMember with an isSelf flag a boolean parameter that changes which rules apply is two functions wearing one name. The store function is nine lines; a second one is cheaper than a flag you have to remember the meaning of.

Read this: PostgreSQL — Transaction Isolation. Read only §13.2.1, Read Committed, and find the sentence about a statement seeing a snapshot taken at statement start. That sentence is why the lock line exists.
