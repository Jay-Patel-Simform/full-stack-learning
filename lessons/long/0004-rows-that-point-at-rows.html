Rows that point at rows

Right now every task carries the text "jay@example.com". That is a sticky note, not an owner. Today a task points at a real User row. One win: you can ask the database “whose task is this?” and it cannot lie.

In one minute

  • A task should point at a user row, not at a copy of their email.
  • The pointer is called a foreign key. Postgres refuses ids that do not exist.
  • One line, where: { ownerId }, is the first real security in this app.
  • Leave it out and every user reads everyone else's tasks. That bug is called IDOR.

The one new idea: a foreign key. It is a column that must hold an id that really exists in another table. Postgres checks it on every write. Same argument as lesson 3 — put the rule where forgetting is impossible. PostgreSQL: Foreign keys.

Step 1 — two models, one link

server/prisma/schema.prisma:

model User {
  id        Int      @id @default(autoincrement())
  email     String   @unique
  createdAt DateTime @default(now())
  tasks     Task[]
}

model Task {
  id        Int      @id @default(autoincrement())
  title     String   @db.VarChar(200)
  done      Boolean  @default(false)
  createdAt DateTime @default(now())

  owner     User     @relation(fields: [ownerId], references: [id])
  ownerId   Int
}

Read the two relation lines as one sentence: the column ownerId holds a User.id, and in TypeScript I will call that user owner.

LineLives in the database?
ownerId IntYes. A real column, plus a foreign-key rule.
owner User @relation(...)No. A name for Prisma, so you can write include: { owner: true }.
tasks Task[] on UserNo. The same link, read from the other side.

@unique on email is the thing that stops two accounts sharing one email in week 3. You get it now, free.

Step 2 — the migration will refuse you

Your Task table already has rows. You are adding a column that may not be empty and must point at a real user. Prisma cannot invent owners, so it will offer to wipe the table.

You are in week 2 with test data. Take the wipe. It is the honest answer here:

cd /Users/jay/learning/full-stack-learning/server
npx prisma migrate reset          # drops, re-runs every migration
npx prisma migrate dev --name task-owner
In production you never do this. The real move is three migrations: add ownerId as nullable, backfill it with an UPDATE, then make it required. Remember the shape; you will need it at week 11–12. Prisma: data migration.

Now open prisma/migrations/*_task_owner/migration.sql. Find the line that starts ALTER TABLE "Task" ADD CONSTRAINT. That sentence is the wall.

Step 3 — one user to own things

Login does not exist until week 3. So make one user by hand and keep using it:

psql "$(grep '^DATABASE_URL' .env | cut -d'\"' -f2)" \
  -c 'insert into "User"(email) values (''jay@example.com'') returning id;'

Put that id in server/.env as DEV_USER_ID=1. It is a placeholder with an expiry date: week 3 deletes it and reads the real user from the session.

Step 4 — the store learns the join

src/store/task.store.ts:

export function listTasks(ownerId: number): Promise<Task[]> {
  return prisma.task.findMany({
    where: { ownerId },              // only this person's tasks
    orderBy: { id: "asc" },
    include: { owner: true },        // pull the User row along
  });
}

export function createTask(input: CreateTaskInput, ownerId: number): Promise<Task> {
  return prisma.task.create({
    data: { ...input, ownerId },
    include: { owner: true },
  });
}

And the route passes the placeholder instead of the email string:

const ownerId = Number(process.env.DEV_USER_ID);
const task = await createTask(body, ownerId);

Update the type in src/schemas/task.schema.ts, since ownerEmail is gone:

export type Task = z.infer<typeof TaskPublic> & {
  ownerId: number;
  owner?: { email: string };
};

TaskPublic does not change, so the reply still shows only id, title, done. The owner came out of the database and never left the server. The response schema is still filtering.

The same query in raw SQL

include is not magic. It is a join: read two tables as one, matched on a column.

select t.id, t.title, u.email
from "Task" t
join "User" u on u.id = t."ownerId"
where t."ownerId" = 1;

Run it in psql. Compare it to what listTasks(1) gives back. Knowing this SQL is how you will spot an N+1 query in week 13.

The line to remember

where: { ownerId } is not a filter for tidiness. It is the first piece of security in this app. Drop it, and GET /tasks hands every user everybody else's tasks. That bug has a name: IDOR — broken object level authorization, number one on the OWASP API Security Top 10. Weeks 5–8 are mostly about never forgetting this line.

Check yourself

What does owner User @relation(...) add to the actual Postgres table?

Right: only ownerId is a real column. The relation field is a name for your code.

You insert a task with ownerId = 999 and no user 999 exists.

Right: that refusal is the whole point of a foreign key. A string email column could never do it.

You delete where: { ownerId } from listTasks. What breaks?

Right: hiding fields is not the same as hiding rows. The response schema trims columns, never rows.

Why keep ownerId instead of matching on the owner's email text?

Right: a key should be something that never needs to change. Email is data about a person, not their identity.
