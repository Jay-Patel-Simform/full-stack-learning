Lesson 17 · Week 7–8 · API security — seventh one

The key you did not name

Your create handler does data: { ...input, teamId, ownerId }. It spreads the caller’s JSON straight into a database write. That is the exact shape of a named vulnerability — and you are safe from it today for three reasons, none of which you chose.

Your homework, marked

The questionYou saidMark
A forged write from a rate-limited IP gets 429, not 403. What does the attacker learn, and should the hook order change?—Not said.

So I am answering it, one lesson early. Here is the answer, and then the thing I want you to notice about it.

What they learn: almost nothing, and that is the point. A 429 says “this IP is over its quota”. It does not say whether the cookie was valid, whether the route exists, or whether the CSRF check would have passed. The order should not change. Two reasons: the rate limiter is cheaper than the CSRF check, and a 429 reveals strictly less than a 403. When the cheap check also leaks less, there is no trade to make.

In lesson 16 I labelled the knobless question as knobless, hoping the label would be enough. It was not. So this lesson has one question at the end instead of two. In one minute

  • Mass assignment: the caller sends a key you never named, and your code passes it to the database anyway.
  • You are already safe, because z.object strips unknown keys. You did not decide that. It is a default.
  • Stripping is safe but silent. A front-end typo gets a 200 and changes nothing — the worst kind of bug to debug.

The attack has a name

Read your own handler in src/routes/tasks.route.ts:

const body = request.body as CreateTaskInput;
const task = await createTask(body, teamId, request.userId!);

and the store it calls:

return prisma.task.create({
  data: { ...input, teamId, ownerId },   // <-- the caller's JSON, spread
  include: { owner: true },
});

OWASP calls this mass assignment: “Software frameworks sometimes allow developers to automatically bind HTTP request parameters into program code variables or objects to make using that framework easier on developers. This can sometimes cause harm.” Rails calls it mass assignment, Spring calls it autobinding, PHP calls it object injection. Same bug, three names, CWE-915.

In the 2023 OWASP API Security Top 10 it is no longer its own entry. It was merged into API3:2023 Broken Object Property Level Authorization, defined as an endpoint that “allows a user to change, add/or delete the value of a sensitive object’s property which the user should not be able to access.”

Read that definition next to the last four lessons. Lesson 8 gave you authorization per route. Lesson 9 gave you authorization per target. Lesson 10 gave you authorization per team. This is authorization per property — the same word, one level further down.

Two words: strip and reject

Both refuse the unnamed key. They are not the same thing.

Row two is the one that will actually happen to you, in week 9–10, when you wire the React front end. A silent strip means your server lies to your front end about success. That is worth more to you day-to-day than the attack is.

This is your fourth word pair, after permission/scoping (10), same-origin/same-site (13) and reading-is-CORS/writing-is-CSRF (16). Strip is safe. Reject is safe and honest.

Where to put it — two options

Zod gives you z.strictObject() and .strict(). The only question is where they go. You have seven request bodies: Register, Login, CreateTask, UpdateTask, CreateTeam, AddMember, CreateProject.

OptionWhat it costs you
A. Write .strict() on all seven schemasVisible in the file you are reading. But it is seven places, and body number eight next month will not have it. A rule you must remember is a rule you will forget.
B. One check in the validator compiler in app.tsFour lines, one place, every future body included. But the rule is no longer visible in the schema file, so it needs a comment saying so.

Take B. Same reason as lesson 7’s can() and lesson 15’s no-store hook: a rule with no exceptions does not belong in each caller. And it is the fifth outing for the frame you already own — make the safe thing the default and the unsafe thing deliberate. Under option A, strict is something you opt into. Under B, loose is something you would have to opt out of, in writing.

The code

src/app.ts, inside the validator compiler you wrote in lesson 2:

app.setValidatorCompiler(({ schema, httpPart }) => {
  const s = httpPart === "body" && schema instanceof ZodObject
    ? schema.strict()
    : (schema as ZodType);

  return (data) => {
    const r = s.safeParse(data);
    // ...unchanged from here down
  };
});

Three things in there are load-bearing:

  • httpPart === "body" — Fastify hands the compiler which part it is validating: "body", "params", "querystring" or "headers". Only bodies get this, and the reason is the query string. A body is a thing your client composed on purpose. A query string collects junk it never asked for: ?utm_source=newsletter from a marketing link, ?fbclid=… added by Facebook, a cache-buster from a proxy. Make the query strict and a shared link becomes a 400. I checked what strict params would break in your app today: nothing — your params objects hold exactly the URL segments you declared. So this line is not fixing a live break. It is scoping the rule to the one input that is fully under a client’s control, before week 13–14 gives you your first querystring schema for pagination.
  • schema instanceof ZodObject — .strict() only exists on an object schema. A body that is an array or a string has no unknown keys to speak of, so it passes through.
  • schema.strict() returns a new schema; it does not mutate yours. And it happens once, at route-registration time, not per request. The per-request cost is zero.

Then one line in src/schemas/task.schema.ts, for the other half of “silent success”:

export const UpdateTask = z
  .object({ title: CreateTask.shape.title, done: z.boolean() })
  .partial()
  .refine((patch) => Object.keys(patch).length > 0, {
    message: "send at least one field to change",
  });

.partial() made every field optional, which is right for a PATCH. It also made no field acceptable, which is not: PATCH with {} used to answer 200 and change nothing. Same failure as the typo, different cause.

And one comment in src/store/task.store.ts, on a line I did not change:

// ! This cast is a promise, and app.ts is what keeps it. Bodies are parsed
// ! strictly, so `patch` cannot hold a key we never declared. Loosen that
// ! and this line hands Prisma whatever the caller typed -- ownerId included.
const data = patch as { title?: string; done?: boolean };

Row four of the counting table. An as cast is a claim about runtime that TypeScript cannot check. It is now true because of a rule four files away, so the comment says which rule. Same habit as the ponytail: comments in lesson 11: a written-down assumption is a decision, an unwritten one is a future bug.

Check yourself

You reorder the store call to data: { teamId, ownerId, ...input }, so the spread comes last. Bodies are strict now. What changes?

Danger later. Today nothing changes, because ownerId never survives validation, so there is nothing for the spread to overwrite. But you have just moved from two independent things stopping the attack to one. The day anyone loosens a schema, that reorder is the difference between a dropped key and a forged owner. Defence in depth is not about today.

Your React form has a stale field and posts { "title": "x", "createdAt": "2026-01-01" } to create a task. What does the API answer?

400. The message is (root): Unrecognized key: "createdAt" — it names the key, so you fix the front end instead of hunting the server. Before this lesson it was the second answer: a 201, a task created, and createdAt quietly ignored. Note that createdAt is a real column, so this is the harmless-looking version of the same bug as ownerId.

Sixth security lesson with this table. The honest line this time is row one: strict is a check on your schema, not on your judgement. It stops keys you forgot to think about. It has nothing to say about keys you thought about and got wrong.

Read this

Primary source: OWASP — Mass Assignment Cheat Sheet. Two pages, and it lists exactly three mitigations: allow-list the bindable fields, block-list the sensitive ones, or use a DTO. Read it and then notice something: you have been doing all three since lesson 2. Your zod schema is the allow-list. TaskPublic is the DTO. What you were missing was not a technique — it was making the allow-list say no out loud.
