Lesson 07 · Week 5–6 · RBAC

One place that says no

Your API knows who is asking. It does not know what they are allowed to do. Today you build the function that decides — and ten tests that prove Viewer cannot edit and Member cannot delete a team. Straight out of MISSION.md.

In one minute

  • Gate 1 asks who are you (401). Gate 2 asks may you (403). You only have gate 1.
  • Do not scatter if (role === "ADMIN") through forty routes.
  • Put the decision in one plain function: can(role, action).
  • Roles are data (rows). Permissions are code (a file in git).
  • Unknown role? Answer no. Never crash.

Two gates, not one

Lesson 6 built the first gate. It asks one question: who are you? If the cookie is bad, 401.

That gate is now shut and working. And it protects nothing.

Every logged-in person can do every single thing. Log in as an intern, delete the team. The first gate has no opinion, because "logged in" is not "allowed".

The two words look alike and mean different things. Say them out loud as who and may, and you will never mix them up again.

The bad version first

Nearly everybody writes this. Look at it, then we will kill it.

// somewhere in tasks.route.ts
if (user.role !== "ADMIN" && user.role !== "OWNER") {
  return reply.code(403).send({ error: "forbidden" });
}

It works. It is also a trap, for three reasons.

  1. You must remember it. Forty routes, forty chances to forget. The one you forget is the hole. Same problem as lesson 3's "declare the wall, do not remember it".
  2. It names the role, not the job. Next year Admin stops being allowed to invite people. Now you are grepping for "ADMIN" across forty files, hoping you got them all.
  3. You cannot test it without a server, a database, a user, a login and a cookie. So nobody tests it.

Split the decision from the enforcing

One idea fixes all three. Pull the decision out into a plain function, and leave only the enforcing in the route.

if (!can(role, "task:update")) return reply.code(403).send(...);

Now the route reads like English, the rule lives in one file, and can is a function of two strings — so a test costs two lines and no database.

"This takes in an actor, an action and a resource and returns a True/False." — Oso, Authorization Academy, on the central authorization function.

Note what changed in the wording: you no longer ask "is this person an admin?". You ask "may this person update a task?". Ask about the job, never about the badge.

Roles are data. Permissions are code.

This is the sentence to keep from today. Two halves.

A role is data. "Jay is ADMIN of team 3" is a row in the database. It changes all day — people join, get promoted, leave. It must be a row.

A permission is code. "ADMIN may invite members" is a line in a file. It changes when you decide to ship a change. So it lives in the repo, in git, with a test next to it.

Keeping them apart buys you something real: nobody can grant themselves a new power by editing a row, because the powers are not in rows. The worst a database attacker can do is promote themselves to a role you already designed.

When does the table move into the database? Only when your users need to invent their own roles ("create role: Billing Reader"). Oso calls that stage custom roles, and says the map "needs to be dynamic" then — and not before. Your four fixed roles are stage one. Start small: "start out with a small number of roles".

Deny by default

One more rule before the code. When your function gets something it does not recognise — a role it has never heard of, a person with no membership at all — it must answer no. Not maybe, not a crash.

"Even when no access control rules are explicitly matched, the application cannot remain neutral… The application must always make a decision, whether implicitly or explicitly, to either deny or permit." — OWASP, Authorization Cheat Sheet

A crash is not a decision. A crash is a 500, and a 500 in the wrong place is a door left open. So: undefined role → false. Junk role → false.

The code you now have

server/src/auth/can.ts. The whole authorization brain of your API, and it touches nothing.

export const ROLES = ["VIEWER", "MEMBER", "ADMIN", "OWNER"] as const;
export type Role = (typeof ROLES)[number];

export const ACTIONS = [
  "task:read", "task:create", "task:update", "task:delete",
  "project:create", "project:delete",
  "member:invite", "member:remove",
  "team:delete",
] as const;
export type Action = (typeof ACTIONS)[number];

// "the role below, plus these". Our four roles nest, so say it once.
const VIEWER = ["task:read"] as const;
const MEMBER = [...VIEWER, "task:create", "task:update", "task:delete",
                "project:create"] as const;
const ADMIN  = [...MEMBER, "project:delete", "member:invite",
                "member:remove"] as const;
const OWNER  = [...ADMIN, "team:delete"] as const;

const PERMISSIONS: Record<Role, readonly Action[]> = {
  VIEWER, MEMBER, ADMIN, OWNER,
};

export function can(role: Role | undefined, action: Action): boolean {
  if (role === undefined) return false;
  return PERMISSIONS[role]?.includes(action) ?? false;
}

Three small things worth pausing on.

as const plus typeof. You write the list of roles once, and TypeScript makes the type from it. No separate type Role = "VIEWER" | ... to keep in sync. Same trick as z.infer in lesson 2: one source, type derived.

Record<Role, readonly Action[]>. This is the wall from lesson 3, in the type system. Add a fifth role to ROLES and the build breaks until you decide what it may do. You cannot ship a role with accidental powers, because you cannot ship a role with no entry.

?? false looks dead. It is. Record covers every Role, so the lookup cannot miss. It stays because a role read out of Postgres is a string that we promised is a Role. If that promise ever breaks, this line says no instead of throwing. Deny by default means at the type boundary too.

Ten tests, no database

server/src/auth/can.test.ts, still node:test, still no framework.

test("a viewer cannot edit", () => {
  assert.equal(can("VIEWER", "task:update"), false);
});

test("a member cannot delete the team", () => {
  assert.equal(can("MEMBER", "team:delete"), false);
});

test("no role is no permission", () => {
  for (const action of ACTIONS) assert.equal(can(undefined, action), false);
});

Those first two are literally lines from your mission, now machine-checked. Two more are worth stealing for any table you ever write:

test("every action is granted to somebody", () => {
  // An action no role can do is dead code -- and a route that checks
  // it would be locked shut forever. Catches a typo in the table.
  for (const action of ACTIONS)
    assert.ok(ROLES.some((role) => can(role, action)), `no role can ${action}`);
});

test("more senior roles never lose a power", () => {
  // ROLES is ordered least to most powerful, so each role must allow
  // everything the one before it allowed. Catches a bad edit years later.
});

That last one is a property test: it does not check one fact, it checks a shape that must hold for every role and every action. Nine actions times four roles, in one test you wrote once.

What this shape cannot say

Your mission has a third rule: "Admin cannot remove Owner". Try to write it in the table above.

You cannot. The table only knows about the person asking. That rule needs the role of the person being removed — the resource. Same with "you may edit a task you own": that needs the task's ownerId.

Which is why the mission says can(user, action, resource), with three arguments. Today's two-argument version is the first gate and it stays; the resource rules layer on top of it. Lesson 9.

Notice you have already met a resource rule, by accident. where: { id, ownerId } in task.store.ts — the IDOR fix from lesson 6 — is an ownership check, hidden inside a query. Lesson 9 pulls it out where you can see it and test it.

Check yourself

Your session gate returns 401. Why is a second gate needed at all?

Right: authn is who, authz is may. A logged-in intern is still logged in.

Why is can(role, "member:invite") better than isAdmin(user)?

Right: name the job, not the badge. Routes ask for a power; the table decides who holds it.

Why do permissions live in code while roles live in the database?

Right: and nobody grants themselves a power by editing a row, because powers are not rows.

A role string from the database is not in your table. What must happen?

Right: deny by default. A throw is a 500, and a 500 in the wrong place opens the door.

Which mission rule does a role→action table fail to express?

Right: the table only sees the asker. Resource rules need the third argument.

Lesson 6 fixed an IDOR with where: { id, ownerId }. What was that, really?

Right: it decided may you. It just did it in a place you cannot test on its own.

Front end hides the Delete button from Viewers. What did that buy you?

Right: OWASP — checks "must be performed server-side". Hiding is UX, not a gate.

Adding a fifth role to ROLES breaks the build. Why is that good?

Right: same move as the NOT NULL wall in lesson 3. Let the tool remember for you.
