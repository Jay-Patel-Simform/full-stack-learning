Lesson 03 · Week 1–2 · API Basics

Rows that survive a restart

Your tasks live in an array. Stop the server and they are gone. Today they move into Postgres. One win: restart the API, and the data is still there.

In one minute

  • An array dies with the process. A table lives on disk.
  • Three new words: schema (the shape), migration (the change), client (typed code to talk to it).
  • Only the store file changes. Your routes barely move — that is the point of the boundary.
  • Postgres is already on this Mac. You install nothing.

What a database gives you

An array holds data while the process lives. A database holds data on disk, for many processes at once, and enforces rules you write down once.

JobArray todayPostgres from today
Survives restartNoYes
Two servers share itNoYes
Rule “title max 200 chars”Only in ZodAlso in the table
Unique idstasks.length + 1, breaks after a deleteautoincrement(), never repeats

That third row matters later. Zod guards the door of your API. The database guards the data itself, even from a script you run at 2am. Two walls, not one. This is the same idea as lesson 2: put the rule where forgetting is impossible.

The three new words

WordPlain meaning
Schema (prisma/schema.prisma)Your tables, written as a short list. One file, the truth about the shape.
MigrationA saved SQL file that changes the database from the old shape to the new one. Prisma writes it for you. You commit it.
ClientGenerated TypeScript code that matches your schema, so prisma.task.findMany() is typed. If you rename a column, your editor shows the broken lines.

Never edit a migration that has already run. Make a new one. Prisma: Migrate workflows.

Step 1 — make a database in the Postgres you already have

Postgres 18 is already installed on this Mac and already running. It costs about 15 MB of memory. You install nothing today.

You only need your own role and your own database, so this project never touches anything else. Run these once, with the password you set when Postgres was installed:

psql -U postgres -h localhost \
  -c "CREATE ROLE tasks LOGIN CREATEDB PASSWORD 'tasks';"

psql -U postgres -h localhost \
  -c "CREATE DATABASE tasks OWNER tasks;"

A role is a database user. CREATEDB is needed because prisma migrate dev makes a short-lived second database (a shadow database) to check your migration before running it for real.

Then server/.env holds one line:

DATABASE_URL="postgresql://tasks:tasks@localhost:5432/tasks?schema=public"

Read the URL as five parts: user, password, host, port, database name. .env is in .gitignore. It never goes to git.

Why not Docker, and why not npx prisma dev? Docker is week 11–12, on purpose, as its own lesson. npx prisma dev also works and needs no setup, but it keeps a Node process alive using about 210 MB. Your native Postgres does the same job for a tenth of that. Use the machine you have.

Step 2 — describe the table

server/prisma/schema.prisma:

generator client {
  provider = "prisma-client"
  output   = "../../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
}

model Task {
  id         Int      @id @default(autoincrement())
  title      String   @db.VarChar(200)
  done       Boolean  @default(false)
  ownerEmail String
  createdAt  DateTime @default(now())
}

Read it as one line per column: name, type, then rules. @id is the primary key. @db.VarChar(200) pushes your Zod max(200) rule down into Postgres too.

Note what is not here: no url. In Prisma 7 the connection string lives in prisma7.config.ts and is read from .env. Secrets stay out of the schema file you commit.

Step 3 — make the table

npx prisma migrate dev --name init

This does three things: writes prisma/migrations/<time>_init/migration.sql, runs it against your database, then regenerates the typed client. Open that SQL file and read it. It is only CREATE TABLE. Nothing magic.

Step 4 — one client for the app

New file src/db.ts:

import { PrismaPg } from "@prisma/adapter-pg";
import { PrismaClient } from "./generated/prisma/client.ts";

// Read .env into process.env. Built into Node, so no dotenv package at runtime.
process.loadEnvFile();

// Prisma 7 talks to Postgres through a driver adapter. `pg` is that driver.
const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL });

// One client for the whole app. It holds a pool of connections.
export const prisma = new PrismaClient({ adapter });

Make it once, export it, import it everywhere. A new client per request would open a new pool of connections per request, and Postgres would run out. Prisma: connection management.

Step 5 — swap the store

This is the good part. src/store/task.store.ts keeps the same four function names. Only the insides change. The routes barely notice.

import type { CreateTaskInput, Task, UpdateTaskInput } from "../../schemas/task.schema.ts";
import { prisma } from "../../db.ts";

export function listTasks(): Promise<Task[]> {
  return prisma.task.findMany({ orderBy: { id: "asc" } });
}

export function createTask(input: CreateTaskInput, ownerEmail: string): Promise<Task> {
  return prisma.task.create({ data: { ...input, ownerEmail } });
}

export async function updateTask(id: number, patch: UpdateTaskInput): Promise<Task | undefined> {
  // updateMany does not throw on a missing id. It just reports 0 rows changed.
  const data = patch as { title?: string; done?: boolean };
  const { count } = await prisma.task.updateMany({ where: { id }, data });
  if (count === 0) return undefined;
  return (await prisma.task.findUnique({ where: { id } })) ?? undefined;
}

export async function deleteTask(id: number): Promise<boolean> {
  const { count } = await prisma.task.deleteMany({ where: { id } });
  return count > 0;
}

Every function now returns a Promise, because a database call goes over a socket. So the routes gain three awaits:

const task = await createTask(body, "jay@example.com");
const task = await updateTask(id, request.body as UpdateTaskInput);
if (!(await deleteTask(id))) return reply.code(404).send({ error: "not found" });

That is the whole change to src/routes/tasks.route.ts. The boring file boundary from lesson 2 just paid for itself: the routes never knew where the data lived.

Why updateMany and deleteMany for one row? update and delete throw when the id is missing, so you would need try/catch to answer 404. The *Many versions return a count instead. Fewer lines, same answer.

Now prove it

Postgres is already running in the background. So one terminal only: npm run dev. Then:

# 1. make a task
curl -s -X POST localhost:3000/tasks \
  -H 'content-type: application/json' -d '{"title":"buy milk"}'

# 2. STOP the server (ctrl-c), start it again, then read
curl -s localhost:3000/tasks

# 3. look at the actual row, email and all
psql "$(grep '^DATABASE_URL' .env | cut -d'"' -f2)" \
  -c 'select id,title,done,"ownerEmail" from "Task";'

Test 2 is the win: the task is still there. Test 3 is the second lesson: the row in Postgres does hold ownerEmail, but the API reply from test 2 does not. Your TaskPublic response schema is still filtering the way out. Storage and exposure are different questions.

Check yourself

You already validate title with Zod. Why also set @db.VarChar(200)?

Right: Zod guards one door. The table guards the data from every door, including a migration script or a psql session at 2am.

A migration file has already run on your machine. You need a column change.

Right: applied migrations are history. Editing one makes your database and the recorded history disagree, and every teammate drifts apart.

Why is one exported PrismaClient better than a new one per request?

Right: a client owns a connection pool. Postgres allows a limited number of connections, and pools are meant to be shared and reused.

Your routes needed almost no edits when the array became Postgres. Why?

Right: the routes only knew createTask, listTasks, updateTask, deleteTask. Swapping what is behind a boundary is cheap. That boundary is where auth will sit too.
