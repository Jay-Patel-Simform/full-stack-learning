Lesson 10 · Week 5–6 · RBAC — last one

A task belongs to a team

Half of your permission table has no route behind it. task:read, task:create, task:update, task:delete — four rules nothing calls. Today you wire them, and to do it you have to add a required column to a table that already has rows.

In one minute

  • PATCH /tasks/5 has no team in it, so the gate has no role to look up.
  • Put the scope in the URL: PATCH /teams/7/tasks/5.
  • A task now needs a teamId. Postgres refuses a required column on rows that have none.
  • The safe dance is expand, backfill, contract — add nullable, fill it in, then put the wall up.
  • where: { id, ownerId } was a hidden permission. where: { id, teamId } is a fence. Different jobs.

Why nothing calls them

Look at the two URLs you have:

DELETE /teams/7/members/3   ← the gate can answer this
PATCH  /tasks/5             ← the gate cannot

Say the gate's job out loud: "what role does this person hold, in this team?" The first URL contains a team. The second does not. There is no role to look up, so there is no answer to give.

That is not a routing detail. It is the same counting problem as lesson 9: your rule needs a fact your code has no room for. Last time the missing fact was the target. This time it is the scope.

A permission is never "may Jay delete tasks". It is "may Jay delete tasks here". Drop the here and the question has no answer.

So the task has to know its team. Which is a database change, and the database is about to say no.

Postgres refuses, and it is right to

Add teamId Int to the Task model, run the migration, and read this carefully:

⚠ We found changes that cannot be executed:

  • Added the required column `teamId` to the `Task` table
    without a default value. There are 5 rows in this table,
    it is not possible to execute this step.

Nothing is broken. You asked for a column where every row must have a value, on a table with 5 rows that have none. Postgres cannot invent one, and it will not guess. Same wall as lesson 3, from the other side.

This was your homework question. Three ways out:

waywhat you getthe cost
Make it nullableIt applies straight awayThe rule is now "a task usually has a team". Every gate needs a null branch, forever.
Drop the rowsAlso applies straight awayFine on your laptop. On a real database it is data loss, and it is not undoable.
Expand, backfill, contractColumn required, rows kept, no downtimeThree statements instead of one, and you have to say what the old rows belong to.

Take the third. Not because your five rows matter — they are junk from lesson 3 — but because this is the one that still works when there are users on the other end, and you want the muscle memory now, not at 3am.

Why is "make it nullable" the worst of the three, even though it is the easiest?

Right. A NOT NULL is one wall in one place. A nullable column is a ? in every gate, store and handler that ever touches it — and you only have to forget one.

Expand, backfill, contract

Three steps, in this order. On a live server they are three separate deploys; here they run back to back.

  1. Expand — add the column nullable. Old rows are allowed to be empty for a moment. Nothing breaks.
  2. Backfill — give every empty row a real value.
  3. Contract — now that nothing is empty, put the wall up.

Prisma will write the SQL for you, but not this SQL. So take the pen: --create-only makes the migration file and stops, so you can edit it before it runs.

npx prisma migrate dev --create-only --name task_team
# edit prisma/migrations/<stamp>_task_team/migration.sql
npx prisma migrate dev

The middle step needs an answer to a question only you can answer: which team do the old tasks belong to? You had zero teams, so there was no honest answer — the migration makes one, called Legacy, and puts everybody who ever wrote a task into it:

-- 1. EXPAND. Nullable, so the existing rows may be empty for now.
ALTER TABLE "Task" ADD COLUMN "teamId" INTEGER;

-- 2. BACKFILL. Every old row gets the legacy team.
UPDATE "Task" SET "teamId" = (SELECT MAX("id") FROM "Team")
  WHERE "teamId" IS NULL;

-- 3. CONTRACT. Nothing is empty now, so the wall can go up.
ALTER TABLE "Task" ALTER COLUMN "teamId" SET NOT NULL;

All five rows survived. Open the migration file and read the whole thing — the membership rows it invents are the interesting part, because they are you deciding what the old data meant.

A backfill is never a technical step. It is you writing down an assumption about the past, in SQL, permanently.

Now the routes move

The URL has to carry the scope, so every task route grows a prefix:

beforeaftergate
GET /tasksGET /teams/:teamId/taskstask:read
POST /tasksPOST /teams/:teamId/taskstask:create
PATCH /tasks/:idPATCH /teams/:teamId/tasks/:idtask:update
DELETE /tasks/:idDELETE /teams/:teamId/tasks/:idtask:delete

One line per route, and you have written it three times now:

preHandler: requirePermission("task:update"),

No loader. There is no target role here — a task does not hold a role — so the third argument sits out, exactly as it does for team:delete. You changed the shape of can() last lesson and it cost you nothing today. That was the point of the test that looped every role against every action.

The homework you were dreading

Question 5 last lesson: open task.store.ts and look at this.

await prisma.task.updateMany({ where: { id, ownerId }, data });

That is a permission rule. It says "you may only change a task you wrote". It lives in a database query, it is not in can(), no gate calls it, and no test covers it. It is lesson 7's mistake wearing a different hat: a rule you cannot find is a rule you cannot check.

So ownerId comes out of the where. It stays as a column — who typed it is a useful fact — it just stops deciding anything.

Read what replaces it very carefully, because it looks identical and is not:

await prisma.task.updateMany({ where: { id, teamId }, data });
where: { id, ownerId }where: { id, teamId }

The gate has already said "yes, a MEMBER of team 7 may update tasks". The teamId in the query is what stops PATCH /teams/7/tasks/999 reaching into team 4. Not a second opinion on the permission — a fence around which rows the permitted action can see.

That attack has a name, and it is on the OWASP top ten: IDOR — Insecure Direct Object Reference. Guess an id, get somebody else's row. There is a test for it now.

A MEMBER of team 7 sends PATCH /teams/7/tasks/999, where task 999 is team 4's. Why 404 and not 403?

Right. They really may update tasks in team 7 — that question is settled and the answer was yes. Task 999 is simply not one of team 7's tasks, so it is not found. 403 would leak that some other team owns it.

One rule quietly changed

Before today, only the author could edit a task. Now any MEMBER of the team can. That is not a slip — it is what "roles are scoped to a team" means, and it is why the app is a team task tracker. If you ever want "only the author may edit", that is a new fact about the resource and a new comparison in can(), the same shape as targetRole. Not a where clause.

npm test is now 50 passing, up from 40. The ten new ones are all enforcement: a viewer reading but not writing, an outsider getting 403, the IDOR 404, and the cascade that takes a team's tasks with it.
