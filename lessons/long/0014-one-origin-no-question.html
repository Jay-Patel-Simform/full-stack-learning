  • Same origin means no Origin header, no preflight, no allowlist, no cookie question.
  • You delete configuration instead of writing it. That is why most teams ship it.

Look at the fetch row. On the same origin the URL is relative. No hostname in your front-end code at all — so no environment variable for the API URL, no build-time base URL, no staging-vs-production mixup. That saving is bigger than the CORS one.

The best answer to “which cross-origin setting do I change?” is to stop being cross-origin.

Why no CORS at all

Say the rule out loud: the browser attaches an Origin header, and applies CORS rules, only when the request goes to a different origin than the page. /api/auth/me from https://app.example goes to https://app.example. Same scheme, same host, same port. There is nothing to check.

So in production you can set ALLOWED_ORIGINS= to nothing and the app still works. Your @fastify/cors registration stays in the code for local development, where the Vite dev server really is on :5173. Two environments, one behaviour difference, and the risky one is the one you can see on your own laptop.

Your page at https://app.example calls fetch("/api/tasks"). What does the browser put in the Origin header?

Same-origin requests are not cross-origin, so no Origin header is attached and no CORS check runs. Your allowlist is never consulted. (There is one wrinkle: same-origin POST requests do send Origin, which is useful for CSRF checks — but no CORS rule applies to it.)

The nginx file, line by line

I wrote it for you at deploy/nginx.conf. The two parts that matter:

location /api/ {
  proxy_pass http://127.0.0.1:3000/;
}

root /var/www/app;
location / {
  try_files $uri $uri/ /index.html;
}

The trailing slash on proxy_pass http://127.0.0.1:3000/ is the whole trick. It strips the /api prefix, so the browser asks for /api/auth/me and Fastify sees /auth/me. Your routes do not change. Drop that slash and Fastify gets /api/auth/me and answers 404, and you will lose twenty minutes.

Fastify listens on 127.0.0.1:3000, not 0.0.0.0. Only nginx can reach it. The API has no public port at all.

The cost, said plainly

Every request now arrives from 127.0.0.1. That means request.ip is nginx, not the user — and your 100-per-minute IP limit from lesson 12 becomes one shared bucket for the entire internet. The hundred-and-first person to load the page gets a 429.

The fix is one option, in week 11–12, not today:

const app = Fastify({ logger: true, bodyLimit: 64 * 1024, trustProxy: true });

trustProxy: true makes request.ip read the X-Forwarded-For header that nginx sets. Only ever turn it on when a proxy you control is in front. Turn it on with the API directly exposed and anyone can forge that header and walk past your rate limit.

Same family as lesson 11: the rate limit is only as good as the key. A proxy changes the key underneath you.

You move to the same-origin setup and forget trustProxy. What breaks first?

Cookies and CORS are fine — that is the point of same-origin. What breaks is the limiter: every request looks like it came from 127.0.0.1, so all users share one 100-per-minute bucket. Silent, and it only shows up under load.

Make development match production

In week 9–10 you build the React app. Give Vite the same shape, so the code you write locally is the code that ships:

// vite.config.ts
export default defineConfig({
  server: {
    proxy: { "/api": { target: "http://localhost:3000", rewrite: p => p.replace(/^\/api/, "") } },
  },
});

Now fetch("/api/auth/me") works on your laptop and in production, with no if (import.meta.env.PROD) anywhere. Keep @fastify/cors registered anyway — it costs nothing and it saves you the day you run the front end from a different machine.

So when is a subdomain right?

Two honest cases. First, the API has other clients — a mobile app, a partner, a webhook consumer — and needs a stable public hostname of its own. Second, front end and API scale or deploy separately enough that one nginx in front of both is a bottleneck you can measure. Neither is true for the Team Task Tracker. Take the same origin.

If you do take a subdomain later: your cookie still needs Domain=app.example to be sent to api.app.example, and that is a widening of where the cookie travels. Worth a lesson of its own if you go there.

Read row two twice. Going same-origin is a real trade, not a free win. Cross-origin writes needed a preflight, and a hostile page could not get one. Same-origin writes need none, so SameSite=Lax is now doing that job alone. It is enough — Lax withholds the cookie from a cross-site POST — but it is now the only thing doing it.
