The route nobody audited

Six lessons have hardened POST /auth/login. One message for two failures, a per-account backoff, a CSRF check, strict bodies. POST /auth/register sits four lines above it in the same file and got none of it. Today you audit one route against rules you already wrote — and you find two real bugs, one of which I only found by measuring.

The three channels

“Can a stranger learn whether jay@work.com has an account?” is one question with three separate answers, because a reply carries three separate signals.

OWASP’s testing guide calls this WSTG-IDNT-04, Testing for Account Enumeration, and lists exactly these channels: “different error message… different HTTP status code… different response time”. Your login closes all three, and it is worth seeing which line closes each:

ChannelWhat closes it on loginMeasured
MessageOne string, "invalid email or password", for both no-such-user and wrong-passwordByte-identical bodies
Status code401 either way — and the throttle is keyed on the typed email, so an unknown address flips to 429 on the sixth try just like a real oneLesson 11’s test asserts this
ClockDUMMY_HASH in auth/password.ts. With no user row you still run scrypt, against a hash of nothing237 ms vs 236 ms

That third one is the interesting defence, so look at it properly:

const user = await findUserByEmail(email);

// ! Always hash, even with no user, so both paths take the same time.
const ok = await verifyPassword(password, user?.passwordHash ?? DUMMY_HASH);

The obvious code is if (!user) return reply.code(401).... It is one line shorter, it is what most tutorials write, and it answers in 2 ms instead of 237. That 235 ms gap is a machine-readable answer to “does this account exist?”, repeatable from any network, with no login attempt ever succeeding. You avoided it in lesson 5. Nothing else you have written is defended against a clock.

Your register spends 250 ms hashing a password before it discovers the email is taken. Fixing the wasted work would mean checking the email first. What does that change?

It opens a timing oracle. Check-then-hash means a taken email returns in about 2 ms and a free one in 250 ms — so even if you deleted the 409 and answered 201 to everybody, the clock would give the answer back. The wasted hash is load-bearing. This is the exact inverse of lesson 12’s “the cheap check goes in front of the expensive work”: there the cheap check leaked less than the expensive one, so putting it first was free. Here it leaks more. Same shape, opposite answer — which is why the rule was never “always reorder”.

The decision: what should register answer?

You cannot close the status-code channel and keep an instant signup form. Those are the same fact stated twice. So there are two honest designs, and only two.

A — Answer the same thing alwaysB — Keep the 409, make it cost
The reply202 "check your email" whether the address was free or taken201 or 409, as today
LeakNone. The two cases are indistinguishable.Full. One request, one bit of truth.
NeedsAn email sender, a token table, and an account that is not usable until the link is clickedNine lines. Everything already exists.
Costs youEvery signup now depends on mail delivery. A stranger can also spam a real person’s inbox by “registering” them.An attacker with 10 000 emails and patience still gets a list.

Take B today, and A in week 13–14 when the invite emails land (BullMQ is already in the plan for that week). Two reasons. Design A is not optional there anyway — the moment you email invites, unverified accounts have to exist. And doing A now would mean building a mail pipeline in an auth lesson, which buries the actual idea under infrastructure.

Be clear-eyed about what B buys, because it is less than it looks. It does not stop enumeration; it makes it slow and loud. Five probes per email are free forever. What dies is the bulk attack: checking a leaked list of 100 000 addresses against your signup form. And — this is the part that matters more — the 429s land in your logs, so the attempt becomes something you can see. OWASP is equally blunt about it: registration and forgot-password flows are where enumeration usually survives, even in apps whose login is careful.

Found while measuring: two rows, one person

I wrote a script to time the four replies for the table above. It registered Mixed1788@e.com, then logged in with mixed1788@e.com. Here is what came back:

register Mixed       { ms: 231, code: 201, body: '{"id":720,"email":"Mixed1788@e.com"}' }
login lowercased     { ms: 250, code: 401, body: '{"error":"invalid email or password"}' }
login exact case     { ms: 238, code: 200, body: '{"id":720,"email":"Mixed1788@e.com"}' }
register dup lower   { ms: 233, code: 201, body: '{"id":721,"email":"mixed1788@e.com"}' }

Read the last line twice. Id 720 and id 721 are the same human being. And a user who signs up with a capital letter — which iOS does for you, in the keyboard, by default — gets a 401 forever if they later type their address in lower case. They will report that as “your site lost my password”.

Now the part I want you to be annoyed by. This test has been passing since lesson 11:

test("case does not open a side door", async () => {
  const upper = `UPPER-${stamp}@example.com`;
  for (let i = 0; i < 6; i++) await login({ email: upper.toLowerCase(), password: "wrong" });
  assert.equal((await login({ email: upper, password: "wrong" })).statusCode, 429);
});

It passed because the throttle key was lower-cased in the handler: const key = email.toLowerCase(). The database lookup two lines below it used the raw string. One normalised, one not, and a green test standing on top saying case is handled. Half a normalisation is worse than none — with none, you find the bug the first time you type a capital letter; with half, a passing test tells you not to look.

The fix is not another .toLowerCase() next to the query. Count the places a raw address can enter: login, register, and every route you write after this one. The address has exactly one door, and lesson 2 built it — the zod schema:

// ! Normalise BEFORE the format check, or a pasted "  Jay@x.com " is a 400.
// ! Order matters: each step in a zod chain sees the output of the one to its
// ! left, so .trim() after .email() trims a string that already passed.
const emailField = z.string().trim().toLowerCase();

export const Register = z.object({
  email: emailField.pipe(z.email().max(254)),
  password: z.string().min(8).max(256),
});

The comment is a real trap I walked into while writing this. z.email().trim().toLowerCase() type-checks and looks right, and it rejects " Jay@x.com " with a 400 — because zod runs the chain left to right, so .email() judged the string before .trim() ever touched it. Transforms are not preprocessing. To clean a value then validate it, the validation goes on the right, behind .pipe().

With the door fixed, the handler gets simpler, and it says why it is allowed to be:

// ? Already trimmed and lower-cased -- by Login in schemas/auth.schema.ts,
// ? which is the only way a body reaches this handler.
const key = email;

That is the third use of the rule from lesson 17: a promise kept in another file is written down, with the file named. Otherwise the next person deletes the normalisation and this line is silently wrong.

The rows already in your database

Code fixes the future. Jay@x.com is still sitting in Postgres, and it is now unreachable — the door lower-cases the login attempt, and no row matches. This is lesson 10’s hand-written migration again, and it is data-only:

-- prisma/migrations/20260907062418_lowercase_emails/migration.sql

-- Two rows that differ only in case are two accounts for one person. Only a
-- human can say which one is real, so refuse to guess: the UPDATE below hits
-- the @unique on email and this whole migration rolls back.
-- Find them first with:
--   SELECT lower(email), count(*) FROM "User" GROUP BY 1 HAVING count(*) > 1;
UPDATE "User" SET email = lower(email) WHERE email <> lower(email);

Letting it fail is the design, not laziness. A migration that resolved duplicates for you — keeping the oldest, say — would silently delete a person’s account and their tasks along with it. A migration that stops and shows you the collision costs you a query and a decision, once. Your database had one duplicate pair when I ran it, both created by my own timing script, so I deleted those four rows before applying it. Yours is clean; a real one might not be.

The tests

Eight new, all enforcement, in src/routes/enumeration.test.ts. Every one asks the same question: can the caller tell whether the account exists? Two of them are worth pointing at.

test("a real email and a made-up one get the same 401 and the same words", async () => {
  const real = await login(known);
  const ghost = await login(`ghost-${stamp}@example.com`);
  assert.equal(real.statusCode, ghost.statusCode);
  assert.equal(real.body, ghost.body);     // <-- byte-for-byte, not "similar"
});

And the timing one, which is written the awkward way on purpose:

assert.ok(real > 100, `a login should cost a hash, took ${Math.round(real)}ms`);
assert.ok(ghost > 100, `a missing user must cost one too, took ${Math.round(ghost)}ms`);

The tempting assertion is Math.abs(real - ghost) < 50. Do not write it. Your laptop under load will make two identical code paths differ by 200 ms and fail the build for no reason — and a flaky security test gets deleted within a month, which leaves you with no test at all. What it cannot do is make scrypt free. So assert the thing that only breaks when the code breaks: both paths paid for a hash. A test is only worth writing if the only way to fail it is the bug.

You add POST /teams/:teamId/members next week. It answers 404 when the user id does not exist. Which rule from today applies?

It is the same bug with a different noun. A 404 for “no such user” and a 409 for “already a member” let any team admin map your entire user table by id. The question is never “is this about email?” — it is “does this reply describe a thing the caller was not already allowed to see?” That is why lesson 9’s gate loads the target and answers 403 for both the wrong role and a total stranger. Same reply, two different noes, one more time.

The one sentence. A rule I put in one hook protected a route I was not thinking about; a rule I put in a handler protected only that handler — and my newest route inherited every rule of the first kind and none of the second.

One for the community, because it is a judgement call and I have seen senior people land on both sides. Ask Security StackExchange or r/node: “For a small B2B API, is hiding account existence at signup worth the cost of an email-verification round trip — given that the login form is already careful and the customer list is basically public?” Design A is the textbook answer. Whether it is the right answer for a tool with forty corporate users is exactly the kind of thing a cheat sheet cannot tell you, and a practitioner can.
