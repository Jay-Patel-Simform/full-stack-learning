Same-site is not same-origin

In week 9–10 your React app starts calling this API. It will be on a different port. Today you find out what the browser does about that — and why the fix everybody copies off Stack Overflow hands your users' sessions to strangers.

Still owed from lesson 12. The body-size limit is not in src/app.ts yet. It is still one option on Fastify({ ... }). Do it this week; it is the smallest win left in week 7–8.

In one minute

  • A CORS error does not mean your server said no. Your server answered in full; the browser binned the reply.
  • Same-origin counts the port. Same-site does not. Two different words, two different jobs.
  • Anything that could change data gets a preflight OPTIONS first.
  • origin: true reflects whatever origin asked. With credentials: true that hands your sessions away.
  • Write an exact allowlist. CORS is never your access control.

The thing that is about to happen to you

Your front end runs on http://localhost:5173. Your API runs on http://localhost:3000. You write the fetch call, and the browser prints this:

Access to fetch at 'http://localhost:3000/auth/me' from origin
'http://localhost:5173' has been blocked by CORS policy: No
'Access-Control-Allow-Origin' header is present on the requested resource.

Read that error slowly, because it says the opposite of what people think it says. Your server answered. The request arrived, the handler ran, the reply came back. The browser then threw the reply in the bin before your JavaScript could see it.

CORS is not a lock on your server. It is the browser refusing to hand one page the contents of another site's replies. CORS is how you open that door a crack.

You now need two definitions that differ, and the difference is the whole lesson.

So your SameSite=Lax cookie from lesson 6 keeps working in local development, because a port is not a site. It is not doing nothing — it is still the thing stopping evil.com from riding your session. But it is not what is blocking your fetch. CORS is, and CORS counts the port.

The browser blocked the reply. What did your Fastify server do?

Right, and this is the whole mental model. curl localhost:3000/health works today with no CORS setup, because curl is not a browser and has no other site to protect. Every CORS header is advice to a browser. A server-side attacker ignores all of it — which is why CORS is never your access control. Lesson 7 is your access control.

The preflight

Simple reads go straight out and get judged on the way back. But anything that could change data — a DELETE, or a POST with Content-Type: application/json — gets asked about first. The browser sends an OPTIONS request of its own:

OPTIONS /teams/1/tasks
Origin: http://localhost:5173
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type

It is the browser asking “before I let this page delete something on you, do you know who it is?” Your reply lists the origins, methods and headers you accept. If your answer does not cover the real request, the real request is never sent. This is why a broken CORS setup often shows an OPTIONS in your server log and no POST.

The line that gives your sessions away

Here is the fix people paste. Show the bad version first, as usual:

await app.register(cors, { origin: true, credentials: true });

origin: true does not mean “allow everyone”. The spec forbids the wildcard * together with credentials, so the plugin does the next thing: it reflects whatever Origin header arrived. Every origin is now on the allowlist, including one nobody has registered yet.

Now add credentials: true, which tells the browser to send your session cookie on cross-origin calls. Put the two together and read it as an attacker would:

  1. A logged-in user opens evil.example in another tab.
  2. Its JavaScript calls fetch("https://your.api/teams/1/tasks", { credentials: "include" }).
  3. The cookie goes along. Your server answers 200 with the team's data.
  4. Your server echoes Access-Control-Allow-Origin: https://evil.example, because that is what reflection means.
  5. The browser sees its own origin in the header, so it hands the page the data. It is now on someone else's server.

SameSite=Lax saves you from most of this today — but the day you move the front end to a real domain and set SameSite=None for it, this becomes a full account-data leak with no other guard behind it. Write the allowlist now, while it costs nothing.

Why is origin: "*" the safer of the two bad options here?

Right. The wildcard is a public API's answer: anyone may read this, and it is fine, because no credentials will ever ride along — the browser enforces that pairing. Reflection breaks the pairing while looking almost the same in the config file. That is what makes it the dangerous one: it is the version that works when you test it.

What you wrote

In src/app.ts, above buildApp():

const ALLOWED_ORIGINS = (process.env.ALLOWED_ORIGINS ?? "http://localhost:5173")
  .split(",")
  .map((o) => o.trim())
  .filter(Boolean);

And after the rate limiter:

await app.register(cors, {
  origin: ALLOWED_ORIGINS,
  credentials: true,
  methods: ["GET", "POST", "PATCH", "DELETE"],
});

An array of exact strings. Not a regular expression — a regex without anchors matched localhost:5173.evil.example in real, shipped code more than once, and there is a test below that proves your version does not. The environment variable is there so the deploy in week 11–12 changes one string, not one line of source.

This is your second dependency, @fastify/cors (172 KB), and it earns its place by the rule you already own from lesson 12: the CORS protocol is a fixed spec with preflights, Vary headers and cache rules, and exactly one decision left in it — which origins. You made that decision. The plugin does the typing.

Five tests, and what they are for

src/routes/cors.test.ts, 75 tests total now. Same rule as last time: test what you decided, not what you installed.

  • An allowed origin comes back echoed, with allow-credentials: true.
  • A stranger's origin gets 200 and no allow header. Read that test twice. It is the shape of the whole lesson: the server does not say no, it just stays quiet, and the browser does the refusing.
  • http://localhost:5173.evil.example gets nothing. That is the anchoring bug, nailed down.
  • The preflight for POST /auth/login is answered.
  • PUT is never offered, because it is not in your list.
