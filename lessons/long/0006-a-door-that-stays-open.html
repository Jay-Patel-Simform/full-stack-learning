Lesson 06 · Week 3–4 · Auth You Write Yourself

A door that stays open

Lesson 5 checked a password once. Today the API remembers. The win: DEV_OWNER_ID = 1 is deleted, and /tasks finally shows your tasks because the server knows who is asking.

In one minute

  • HTTP forgets. Every request arrives as a stranger.
  • Give the browser a random session id in a cookie. The browser re-sends it for free.
  • Store only sha256(id). Steal the table, get nothing usable.
  • Delete the row and the person is logged out now. A plain JWT cannot do that.
  • One hook, requireAuth, guards every task route by default.

The problem: HTTP forgets

Every request to your API arrives as a stranger. The server reads it, answers, and throws away everything it knew. The next request starts from nothing.

So verifyPassword returning true is worth almost nothing on its own. It proves a password for one request. Then the memory is gone.

You need to hand the browser a small piece of paper that says "this one is Jay". The browser shows the paper every time. That paper is a session.

Two ways to make the paper

Server-side sessionJWT (signed token)
What the browser holdsA random id. Means nothing by itself.The user data, signed so it cannot be edited.
Server looks it up?Yes, one row read.No. It just checks the signature.
Log out right now?Delete the row. Done.Cannot. It stays valid until it expires.

People reach for JWT because "no database lookup" sounds fast. Then they discover they cannot log anyone out, and they bolt a refresh token in a database table onto it — which is a session, wearing a hat.

Your PLAN.md said access token + refresh token. We are doing plain sessions instead, and the reason is in the third row: you asked for revocation. A session gives it for free. Your app is one server talking to one Postgres, so the "no lookup" win does not apply to you.

"Sessions provide a way to persist state in stateless protocols like HTTP… They are especially useful when you need to be able to invalidate them." — The Copenhagen Book

Same shape as the scrypt choice in lesson 5: take the simpler approved option, and know exactly when it stops fitting.

Making the id

The session id is the whole key to the account. Two rules.

Rule 1: unguessable. Not a counter, not the user id, not a UUID from Math.random. The Copenhagen Book asks for at least 112 bits of entropy from a cryptographically secure generator. 15 random bytes gives 120 bits. Source.

Rule 2: hash it before you store it. Exactly the trick from lesson 5. The browser gets the raw id. The database gets only sha256(id). Steal the database, and you have a table of useless fingerprints — no live logins.

Why sha256 here, when lesson 5 said sha256 was wrong? Both are true. sha256 is wrong for passwords because a human password is short and guessable, so a fast hash lets a GPU try billions of guesses. A session id is 120 random bits. There is nothing to guess. Nobody brute-forces that, at any speed. So the fast hash is correct.

The lesson underneath: slow hashing protects low-entropy secrets. That is the rule, not "always use scrypt".

The cookie, and its four flags

The paper travels in a cookie — a small string the browser stores and re-sends automatically on every request to your site. You never write code to attach it. That is the point.

Set-Cookie: session=MnVUGd07fkrR-j60sZul; HttpOnly; SameSite=Lax; Path=/; Expires=...
FlagWhat it stops
HttpOnlyPage JavaScript cannot read the cookie. So an XSS bug on your site cannot steal the session.
SameSite=LaxAnother site's form cannot POST to your API with your cookie attached. Blocks the easy CSRF.
Path=/Sent to every route, not just the one that set it.
SecureHTTPS only. Left out today, on purpose: localhost is plain http, and a Secure cookie would simply never be stored. Add it in week 11-12.

Two notes worth writing down. Lax not Strict: Strict cookies are not sent when a user arrives from an external link, so they land logged out. And SameSite alone is not full CSRF protection — that is still a week 7-8 job. Copenhagen — CSRF.

  // The SHA-256 of the id we handed the browser. Never the id itself.

  userId Int
}

Notice what did not happen: no reset, no data loss. Lessons 4 and 5 both made you reset, because both added a required column to a table that already had rows. A brand-new table asks nothing of the old rows. Adding is cheap. Requiring is expensive. Keep that in mind when you design a change.

Step 2 — the session module

New file server/src/auth/session.ts. Same shape as password.ts: the rest of the app never learns how any of this works.

import { createHash, randomBytes } from "node:crypto";
import { prisma } from "../../db.ts";

// 15 random bytes = 120 bits of entropy. Copenhagen asks for 112+.
// base64url so the string is safe in a cookie with no escaping.
const ID_BYTES = 15;

// 30 days, and every use pushes it back out to 30 days again.
const LIFETIME_MS = 30 * 24 * 60 * 60 * 1000;
// Only rewrite the row when less than half the life is left. Saves a write
// on every single request.
const RENEW_AFTER_MS = LIFETIME_MS / 2;

// SHA-256 is fine here (not scrypt) because the id is already long and
// random, so there is nothing to guess.
function hashId(id: string): string {
  return createHash("sha256").update(id).digest("base64url");
}

export async function createSession(userId: number) {
  const id = randomBytes(ID_BYTES).toString("base64url");
  const expiresAt = new Date(Date.now() + LIFETIME_MS);
  await prisma.session.create({ data: { idHash: hashId(id), expiresAt, userId } });
  return { id, expiresAt };
}

// The user id when the session is real and alive, otherwise undefined.
export async function readSession(id: string): Promise<number | undefined> {
  const row = await prisma.session.findUnique({ where: { idHash: hashId(id) } });
  if (!row) return undefined;

  // Expiry is checked here, in code. The row may still sit in the table.
  if (row.expiresAt.getTime() <= Date.now()) {
    await prisma.session.delete({ where: { idHash: row.idHash } });
    return undefined;
  }

  // Sliding window: an active user is never logged out mid-work.
  if (row.expiresAt.getTime() - Date.now() < RENEW_AFTER_MS) {
    await prisma.session.update({
      where: { idHash: row.idHash },
      data: { expiresAt: new Date(Date.now() + LIFETIME_MS) },
    });
  }
  return row.userId;
}

// deleteMany, not delete: an already-gone session is not an error.
export async function endSession(id: string): Promise<void> {
  await prisma.session.deleteMany({ where: { idHash: hashId(id) } });
}

Then the cookie helpers, in the same file. Written by hand, so the flags stay where you can see them:

export const COOKIE_NAME = "session";

export function sessionCookie(id: string, expiresAt: Date): string {
  return [
    `${COOKIE_NAME}=${id}`,
    "HttpOnly",
    "SameSite=Lax",
    "Path=/",
    `Expires=${expiresAt.toUTCString()}`,
    // ponytail: add "Secure" once this is served over HTTPS (week 11-12).
  ].join("; ");
}

export function clearCookie(): string {
  return `${COOKIE_NAME}=; HttpOnly; SameSite=Lax; Path=/; Max-Age=0`;
}

// Cookies arrive as one header: "a=1; session=xyz; b=2".
export function readCookie(header: string | undefined, name: string) {
  if (!header) return undefined;
  for (const part of header.split(";")) {
    const eq = part.indexOf("=");
    if (eq === -1) continue;
    if (part.slice(0, eq).trim() === name) return part.slice(eq + 1).trim();
  }
  return undefined;
}

There is a @fastify/cookie plugin that does those last twenty lines. Skip it for now. Cookie flags are the whole security story here, and a plugin would hide them behind an options object you would copy without reading.

Step 3 — the gate

New file server/src/auth/require-auth.ts. This is a Fastify hook: a function that runs before the handler. If it sends a reply, the handler never runs at all.

import type { FastifyReply, FastifyRequest } from "fastify";
import { COOKIE_NAME, readCookie, readSession } from "./session.ts";

// Tell TypeScript a request can carry a userId, or the assignment below
// is a type error.
declare module "fastify" {
  interface FastifyRequest {
    userId?: number;
  }
}

export async function requireAuth(request: FastifyRequest, reply: FastifyReply) {
  const id = readCookie(request.headers.cookie, COOKIE_NAME);
  const userId = id ? await readSession(id) : undefined;

  // 401 = "I do not know who you are". (403 would be "I know, and no".)
  if (userId === undefined) return reply.code(401).send({ error: "not logged in" });

  request.userId = userId;
}

Learn that pair now, because you will use it for the rest of the project:

  • 401 Unauthorized — who are you? (Really it means unauthenticated. The name is a 1990s mistake.)
  • 403 Forbidden — I know who you are, and you still cannot. That is week 5-6, RBAC.

Step 4 — login, logout, me

Add to server/src/schemas/auth.schema.ts:

// Login is not Register. No .min(8) here: an old account may have a shorter
// password, and telling a guesser "too short" is a free hint.
export const Login = z.object({
  email: z.string().max(254),
  password: z.string().max(256),
});
export type LoginInput = z.infer<typeof Login>;

Two more store functions in server/src/store/user.store.ts:

export function findUserByEmail(email: string) {
  return prisma.user.findUnique({ where: { email } });
}
export function findUserById(id: number) {
  return prisma.user.findUnique({ where: { id } });
}

Then the three routes in server/src/routes/auth.route.ts:

app.post("/auth/login", {
  schema: { body: Login, response: { 200: UserPublic, 401: ErrorReply } },
  handler: async (request, reply) => {
    const { email, password } = request.body as LoginInput;
    const user = await findUserByEmail(email);

    // Always hash, even with no user, so both paths take the same time.
    const ok = await verifyPassword(password, user?.passwordHash ?? DUMMY_HASH);

    // One message for both failures. "wrong password" would confirm the
    // email exists, which hands an attacker your user list.
    if (!user || !ok)
      return reply.code(401).send({ error: "invalid email or password" });

    const session = await createSession(user.id);
    reply.header("set-cookie", sessionCookie(session.id, session.expiresAt));
    return reply.send(user);
  },
});

app.post("/auth/logout", {
  schema: { response: { 204: z.null() } },
  handler: async (request, reply) => {
    const id = readCookie(request.headers.cookie, COOKIE_NAME);
    if (id) await endSession(id); // the row dies -> the cookie is now junk
    reply.header("set-cookie", clearCookie());
    return reply.code(204).send();
  },
});

// "Who am I?" The front end calls this on load to decide what to render.
app.get("/auth/me", {
  onRequest: requireAuth,
  schema: { response: { 200: UserPublic, 401: ErrorReply } },
  handler: async (request, reply) => {
    const user = await findUserById(request.userId!);
    if (!user) return reply.code(401).send({ error: "not logged in" });
    return user;
  },
});

Logout deletes the row and clears the cookie. The row deletion is the real one. Clearing the cookie is only tidiness — a copied cookie is now worthless either way. That is revocation, and it is the thing a plain JWT cannot do.

And in password.ts, the stand-in hash that keeps the two failure paths the same speed:

// Without it, a fast "no" means "no such user", and an attacker can list
// who has an account.
export const DUMMY_HASH =
  `scrypt$${N}$${r}$${p}$${Buffer.alloc(16).toString("base64")}$${Buffer.alloc(64).toString("base64")}`;

Step 5 — kill DEV_OWNER_ID

In server/src/routes/tasks.route.ts, delete the constant and add one line at the top of the plugin:

export default async function tasksRoutes(app: FastifyInstance) {
  // One line, every route below it. The gate runs before any handler, and
  // sets request.userId. No route can forget to check, because none opts in.
  app.addHook("onRequest", requireAuth);

Then swap every DEV_OWNER_ID for request.userId!.

Read that comment again, because it is the real design idea. A gate you opt into gets forgotten on the one route added at 5pm on a Friday. A gate on the whole plugin is on by default, and skipping it has to be deliberate. Same move as naming the column passwordHash: make the safe thing automatic and the unsafe thing awkward.

The bug you just created

Until today there was one user, so where: { id } was fine. Now there are many, and this line is a hole:

const { count } = await prisma.task.updateMany({ where: { id }, data });

Logged in as anybody, PATCH /tasks/7 edits task 7 — even if task 7 is mine. Being logged in is not the same as being allowed. This is IDOR (Insecure Direct Object Reference), and it is number one on the OWASP API Security Top 10.

Fix in server/src/store/task.store.ts: take the owner too, and put it in the where.

export async function updateTask(id: number, ownerId: number, patch: UpdateTaskInput) {
  // { id, ownerId }, never { id } alone. Someone else's task simply is not
  // found, so the reply is the same 404 as a task that does not exist.
  const { count } = await prisma.task.updateMany({ where: { id, ownerId }, data });
  // ...
}

export async function deleteTask(id: number, ownerId: number): Promise<boolean> {
  const { count } = await prisma.task.deleteMany({ where: { id, ownerId } });
  return count > 0;
}

404, not 403. A 403 would confirm task 7 exists and belongs to someone else. 404 says nothing.

Check yourself

Why is a password hash alone not enough to keep you logged in?

Right: HTTP forgets between requests. The session is the thing that carries the proof.

Lesson 5 said sha256 was wrong. Why is it right for a session id?

Right: slow hashing protects guessable secrets. Random 120-bit ids are not guessable at any speed.

An XSS bug lands on your page. What does HttpOnly buy you?

Right: HttpOnly hides the cookie from page JavaScript. The XSS is still a bug, just not a session theft.

Login says "invalid email or password" for both failures. Why not be clearer?

Right: that is user enumeration. The generic message and the dummy hash both close it.

You are logged in as user 2. DELETE /tasks/7 belongs to user 1. Which is true?

Right: logged in is not allowed. Authentication and authorization are two separate gates.

Adding Session needed no migrate reset. Why did lessons 4 and 5?

Right: a new table asks nothing of old rows. A new required column asks every row for a value.
