Lesson 09 · Week 5–6 · RBAC

The third argument

Your API has a hole, and you already know about it. An ADMIN can remove the OWNER. Today you close it — by teaching can() to look at the thing being acted on, not only at the person acting.

In one minute

  • “An admin may remove a member, but not the owner” has three parts. Your function had room for two.
  • Add the third: the thing being acted on. can(role, action, resource).
  • The rule is one comparison: you may only act on somebody strictly below you.
  • The gate fetches the target, never the handler. A check in a handler is a check you can forget.
  • Same rule closed a second hole for free: an admin can no longer invite a new OWNER.

Why the hole exists

Look at the shape of the question you have been asking:

can(role, action)

Two facts go in. Who you are, and what you want to do. The answer comes from a fixed table (lesson 7).

Now say the rule you want, out loud: "an admin may remove a member, but not the owner."

Count the things in that sentence. Three. The admin, the removing, and the owner. Your function has room for two. That is the whole bug. Not a missing if — a missing argument.

"An access control policy… decides whether a subject may perform an operation on an object." — NIST, glossary

Subject, operation, object. Everybody who has ever built this ends up with three. You are about to add the third.

Where does the third fact get fetched?

This was your homework question, and it is the real content of the lesson. The target's role is in the database. Somebody has to go and get it. Route, gate, or store?

Here is the answer most people write, and it is wrong:

// in the route handler
const target = await getRole(teamId, userId);
if (target === "OWNER") return reply.code(403).send(...);
await removeMember(teamId, userId);

It works. Ship it and the test passes. It is still wrong, for one reason:

A handler only runs after the gate has already said yes. So a check inside a handler is a gate you can forget to write.

That is lesson 7's argument again, one level up. You did not put the role check in the handler, so do not put the rank check there either. Same rule, same reason: make the safe thing the default and the unsafe thing deliberate. A route with no gate is obviously naked. A route with a gate and a hidden second rule in the body is the dangerous one, because it looks guarded.

So: the gate fetches it. Which means the gate can no longer be a plain (action) => hook factory. It needs to be told how to find the target.

Why not fetch the target's role inside can() itself?

Right: can.test.ts runs with no Postgres at all. Keep the decision pure; let the gate do the fetching.

The rule, in one comparison

You could write a special case: "if the action is member:remove and the target is OWNER, no." Don't. One special case becomes nine.

Your four roles already sit in a line, least to most powerful. ROLES in can.ts is that line. So the rule is just a position on it:

You may only act on somebody strictly below you.

Strictly. Equal rank is a no too — an admin cannot remove a fellow admin. One comparison, and look how much it covers:

actortargetanswerwhy
ADMINOWNERnotarget is above
ADMINADMINnoequal is not below
ADMINMEMBERyestarget is below
OWNERADMINyestarget is below
VIEWERVIEWERnothe table said no first

Read that last row twice. The rank rule never ran. The table already refused, because VIEWER was never granted member:remove. Two questions, in order:

  1. Does the table grant this role the action at all?
  2. If there is a target, does this role outrank it?

Question one still guards everything it guarded yesterday. The rank rule can only take permission away, never add it.

The code

server/src/auth/can.ts. A type for the target, and one more comparison:

// The *thing being acted on*. Lesson 9's third argument.
export type Resource = { targetRole?: Role | undefined };

// Derived from ROLES so there is no second list to drift.
const rank = (role: Role): number => ROLES.indexOf(role);

export function can(role: Role | undefined, action: Action, resource?: Resource): boolean {
  if (role === undefined) return false;
  if (!(PERMISSIONS[role]?.includes(action) ?? false)) return false;

  const target = resource?.targetRole;
  if (target !== undefined && rank(role) <= rank(target)) return false;

  return true;
}

Three small decisions in there, each worth naming.

rank is derived, not written. You already have the order in ROLES. A second hand-typed list ({ VIEWER: 0, MEMBER: 1… }) would be a thing to keep in sync, and one day it would not be. Same move as importing Role from the Prisma enum instead of retyping the names (lesson 8).

The third argument is optional. can(role, action) still compiles and still answers exactly what it answered before. Most actions have no target: team:delete aims at the team, task:create aims at nothing yet. There is a test that proves every old call is unchanged — look for it below.

A junk target loses to everyone. ROLES.indexOf("SUPERUSER") is -1, so the actor always outranks it. That is deliberate, and it is the opposite of deny-by-default — on purpose. Deny-by-default protects you from an actor you cannot read. A target you cannot read must not be allowed to lock a real owner out of their own team.

Teaching the gate to fetch

server/src/auth/require-permission.ts. The factory takes a second, optional argument: a small function that knows where the target lives.

export type Load = (request: FastifyRequest) => Promise<Resource>;

// The person named in the URL: DELETE /teams/:teamId/members/:userId
export const targetMember: Load = async (request) => {
  const { teamId, userId } = request.params as { teamId: number; userId: number };
  return { targetRole: await getRole(teamId, userId) };
};

export function requirePermission(action: Action, load?: Load) {
  return async function gate(request, reply) {
    const { teamId } = request.params as { teamId: number };
    const role = await getRole(teamId, request.userId!);

    const resource = load ? await load(request) : undefined;

    if (!can(role, action, resource)) return reply.code(403).send({ error: "forbidden" });
    request.role = role;
  };
}

And the route says what it needs, still without naming a single role:

preHandler: requirePermission("member:remove", targetMember),

The ponytail: comment that admitted the hole is gone from teams.route.ts. Go and look — a shipped hole should leave a visible scar when it closes.

The same rule, for free, on another route

Here is the payoff of writing a rule instead of a special case. Your invite route had the same hole, and you had not noticed: an ADMIN could invite a stranger as OWNER. Remove the owner in one request, promote yourself in the next.

The target there is not a person in the database. It is the role in the request body. Different place, same shape:

export const grantedRole: Load = async (request) => {
  const { role } = request.body as { role: Role };
  return { targetRole: role };
};
preHandler: requirePermission("member:invite", grantedRole),

No change to can(). The rule already said "you may only act on somebody strictly below you", and handing out a role counts.

Why preHandler matters more now. grantedRole reads request.body. In an onRequest hook the body has not been parsed or validated yet, so it would be undefined. Lesson 8's rule holds: pick the hook by what it needs, not by habit.

The tests

Two kinds again, and the split is the same as last lesson. Pure decision tests in can.test.ts, real HTTP in teams.test.ts.

The most valuable one is the boring one:

test("a missing target leaves the old answer alone", () => {
  for (const role of ROLES) {
    for (const action of ACTIONS) {
      assert.equal(can(role, action, {}), can(role, action));
    }
  }
});

Thirty-six comparisons, written once. It says: I changed the shape of the most security-critical function in this codebase, and I did not change any answer it used to give. When you touch a rule everything depends on, prove the old behaviour survived.

Then the enforcement test, over a real request, asserting status and state:

test("an admin cannot remove the owner", async () => {
  const r = await removeMemberAs("admin", ids.owner!);
  assert.equal(r.statusCode, 403);
  assert.ok(await prisma.membership.findUnique({
    where: { teamId_userId: { teamId, userId: ids.owner! } },
  }));
});

npm test is now 40 passing, up from 28.

Removing somebody who is in no team at all now answers 404, not 403. Why?

Right: targetRole is undefined, the rank rule sits out, and the handler answers for itself. The owner was allowed to ask — there was simply nobody there.

Which change would break the rank rule without breaking a single test?

Right: rank reads positions out of ROLES. The order is now load-bearing, not documentation. Your homework adds the guard.
