Lesson 08 · Week 5–6 · RBAC

A role is a row

Last lesson you built can(), and nothing called it. Today you give it a role to judge — a real row in Postgres, one per person per team — and you make four routes answer 403. Your mission line "Member cannot delete a team" now passes over HTTP, not just in a unit test.

In one minute

  • A role is not a column on User. One person can be OWNER here and VIEWER there.
  • The role belongs to the pair: this user, in this team. That pair is a row.
  • Make role a Postgres enum, so "ADMINN" cannot be stored.
  • One hook, requirePermission("member:invite"), reads the row and answers 403.
  • Routes ask for a job, never for a badge.

Where does the role come from?

That was your homework question, and it has a short answer. can(role, action) needs a role. request.userId exists. request.role does not, because nothing in your database has ever stored one.

So the first job is a place to keep it. And the shape of that place is the whole lesson.

Here is the wrong shape. Nearly every tutorial ships it:

model User {
  role String   // "ADMIN"
}

It reads fine. It breaks the moment you have two teams. Jay is OWNER of the design team and VIEWER of the finance team. One column on User cannot hold two answers.

Oso calls this the jump from organizational roles to cross-organization roles — stage two of four. "Users have different roles in different organizations." — Oso, Authorization Academy

So the role does not belong to the person. The role belongs to the pair: this person, in this team.

A pair is a row

A row about two things is a join row. You already have one, and you did not notice: Task.ownerId joins a task to a user (lesson 4). This one joins a user to a team, and carries the role along with it.

teamIduserIdrole
31OWNER
32ADMIN
37VIEWER
91VIEWER

Read the last two lines out loud. User 1 is OWNER in team 3 and VIEWER in team 9. The one-column version could not say that. This one says it with no new machinery at all.

Prisma has two ways to write a many-to-many. Use the explicit one whenever the join carries a field of its own:

"Use implicit m-n unless you need to store additional metadata in the relation table." — Prisma, Many-to-many relations

role is exactly that metadata. So: explicit.

The role names go in the database too

role could be a String. Then "ADMINN" is a legal value, and the day a typo lands, can() gets a role it does not know. It answers no — correctly, per lesson 7's deny-by-default — and a real admin is locked out, and nothing anywhere says why.

Postgres has a better answer: a type of your own, with a fixed list of allowed values.

CREATE TYPE "Role" AS ENUM ('VIEWER', 'MEMBER', 'ADMIN', 'OWNER');

Now the typo cannot be stored:

ERROR:  invalid input value for enum Role: "ADMINN"

That message is from the Postgres manual, and it is the same teaching move as lesson 3's NOT NULL: declare the wall, do not remember it. Three walls now guard the same four names — zod at the door, TypeScript at compile time, the enum in the table. Each one catches what the others cannot see.

The schema you now have

server/prisma/schema.prisma. Two models and an enum.

enum Role {
  VIEWER
  MEMBER
  ADMIN
  OWNER
}

model Team {
  id      Int    @id @default(autoincrement())
  name    String @db.VarChar(100)
  members Membership[]
}

model Membership {
  role Role @default(MEMBER)

  team   Team @relation(fields: [teamId], references: [id], onDelete: Cascade)
  teamId Int
  user   User @relation(fields: [userId], references: [id], onDelete: Cascade)
  userId Int

  // One membership per person per team. Nobody is VIEWER and OWNER at once.
  @@id([teamId, userId])
}

Two details worth your attention.

@@id([teamId, userId]) is a composite primary key — the key is the two columns together. It means the duplicate row simply cannot exist. Not "we check first"; cannot exist. The database refuses it, and your invite route turns that refusal into a 409.

onDelete: Cascade, twice. Delete the team, the memberships go. Delete the user, their memberships go. No orphan row claiming a role in a team that is gone.

The role names now live in one place, not two. src/auth/can.ts no longer types out the four names — it imports the type Prisma generated from the enum. Add BILLING to schema.prisma and the PERMISSIONS table stops compiling until you say what BILLING may do. Your lesson 7 homework did this by hand; now the database drives it.

Now make a route say no

You have a decision function and a role to feed it. One small piece joins them: a hook that looks up the role for this team and enforces the answer.

export function requirePermission(action: Action) {
  return async function gate(request, reply) {
    const { teamId } = request.params as { teamId: number };
    const role = await getRole(teamId, request.userId!);

    if (!can(role, action)) return reply.code(403).send({ error: "forbidden" });

    request.role = role;
  };
}

It is a factory: you hand it an action, it hands you back a hook. That is why the route can read like this — server/src/routes/teams.route.ts:

app.post("/teams/:teamId/members", {
  schema: { params: TeamParams, body: AddMember, response: { ... } },
  preHandler: requirePermission("member:invite"),
}, handler);

The route asks for a job. It never mentions ADMIN or OWNER. Change your mind next year about who may invite, and you edit one line of can.ts — no route changes at all. That is the promise from lesson 7, now cashed.

Why preHandler and not onRequest?

Your session gate uses onRequest. This one cannot. Fastify runs the lifecycle in a fixed order, and validation sits between the two:

onRequestrequireAuthparams are raw text
validationzod runs"3" becomes 3
preHandlerrequirePermissionteamId is a number

The gate needs a real teamId to query with. So it runs after the wall that makes one. Pick the hook by what it needs, not by habit.

One reply for two different noes

Look again at the 403. A VIEWER trying to delete team 3 gets it. So does a total stranger who is in no team at all. Same code, same body, no hint of which.

That is deliberate. If the stranger got 404 no such team, they could walk the ids and map out every team you host. Same idea as lesson 6's login: one message for a wrong password and an unknown email, so nobody can farm your user list.

"Ensure lookup IDs are not accessible even when guessed" — OWASP, Authorization Cheat Sheet

And one route has no permission gate: POST /teams. Before the team exists there is no role to hold, so any logged-in person may start one — and creating it makes them its OWNER, in one transaction. A team with no owner is a team nobody can ever delete.

It runs

Ten of those are new, in src/routes/teams.test.ts, and they are a different animal from lesson 7's. Those tested the decision. These test the enforcing — a real request, through a real route, against a real Postgres. A perfect rule that no route calls protects nothing at all.

test("a member cannot delete the team", async () => {
  assert.equal((await removeTeam("member")).statusCode, 403);
  // and the team is still there
  assert.ok(await prisma.team.findUnique({ where: { id: teamId } }));
});

Note the second line. A 403 alone would also pass if the route deleted the team and then complained. Check the status and the state.

Check yourself

Why can a role not be a column on the User table?

Right: the role belongs to the pair, not the person. Oso stage two.

What does @@id([teamId, userId]) stop from ever happening?

Right: the pair is the key, so a second row for that pair cannot exist.

Why is role a Postgres enum rather than a plain text column?

Right: declare the wall. A junk role is denied by default, and denied quietly.

Why does the permission gate run on preHandler, not onRequest?

Right: onRequest sees raw text. Pick the hook by what it needs.

A stranger asks to delete team 3. Why 403 and not 404?

Right: one reply for both noes. Same move as the login error message.

Why does POST /teams have no requirePermission line on it?

Right: and creating the team makes you OWNER, in the same transaction.

Why does the test assert the team still exists, not only the 403?

Right: check the status and the state. A status is a claim, not proof.

Adding BILLING to the Prisma enum breaks the build. Where, and why?

Right: a new role cannot ship until you have said what it may do.
