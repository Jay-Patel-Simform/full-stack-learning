Lesson 05 · Week 3–4 · Auth You Write Yourself

Passwords you cannot read back

Your User table has an email and nothing else. Today it gets a password. The win: you can run select * from "User", stare at the row, and still not know the password. Not even you. That is the whole job.

In one minute

  • A password goes in a shredder, not a locked box. You never need it back.
  • Add a random salt per user, so two people with the same password get different shreds.
  • Pick a hash that is slow on purpose. scrypt is already inside Node.
  • Store the recipe next to the shreds, so you can turn the dial up later.

Hashing is not encryption

Encryption is a locked box. It has a key, so it opens both ways. Hashing is a paper shredder. It only goes one way.

You never need the password back. You only need to answer one question: is this the same password as before? So shred the password, keep the shreds, and shred again next time to compare. If a thief steals your database, they get shreds.

Way to store a passwordThief steals the database
Plain textEvery account is theirs, right now
EncryptedTheirs as soon as they find the key, which sits nearby
Fast hash (sha256)A GPU guesses billions per second. Common passwords fall in minutes.
Slow hash (scrypt / argon2)Guessing costs real time and real memory. Most accounts hold.

Note the third row. sha256 is a hash, and it is still wrong here. It was built to be fast. For passwords, fast is the bug. You want a hash that is slow and memory-hungry on purpose. OWASP — Password Storage.

Two words to own

Salt. A random string, different for every user, mixed in before shredding. Without it, two people with the password hunter2 get the same shreds — so cracking one cracks both, and a pre-built lookup table cracks everyone at once. The salt is not a secret. It is stored right next to the hash. Its job is only to make every hash one-of-a-kind.

Work factor. The dial that says how slow. Turn it up, and each guess costs the attacker more. It costs you too, on every login. That trade is the point.

Which algorithm — and why we skip the recommended one

OWASP ranks them: argon2id first, then scrypt, then bcrypt (legacy only), then PBKDF2 (only if a rule forces it).

argon2id needs a package. scrypt is already inside Node, in node:crypto. Zero install, zero megabytes, and it is OWASP's own second choice — not a compromise, an approved option. Same reasoning that picked your native Postgres over prisma dev in lesson 3: use what is already on the machine.

Real cost, said out loud: OWASP's scrypt minimum is N=2^17, r=8, p=1. That asks for about 128 MiB of RAM for a fraction of a second, per hash. Your laptop is fine with one login at a time. A real server with many logins at once is not — that is when you move to argon2id, which gets the same strength for ~19 MiB. Week 13 revisits this.

Measured on this machine before writing the lesson: 252 ms per hash. That is the number an attacker pays for every single guess.

The name matters. Call it passwordHash, never password. A field called password invites someone to put a password in it one tired evening.

Step 2 — the hashing module

New file, server/src/auth/password.ts. It exports exactly two functions, and nothing else in the app knows how hashing works:

import { randomBytes, scrypt, timingSafeEqual } from "node:crypto";
import { promisify } from "node:util";

// scrypt uses a callback. promisify gives us the await version.
const scryptAsync = promisify(scrypt);

// OWASP minimum for scrypt: N=2^17, r=8, p=1. N is the "how slow" dial.
// Costs about 128 MiB of RAM per hash. That cost is the feature.
const N = 2 ** 17;
const r = 8;
const p = 1;
const KEY_LEN = 64;

// scrypt in Node needs maxmem raised by hand, or it refuses this N.
const MAX_MEM = 256 * 1024 * 1024;

// Store the settings alongside the hash. Future-you can raise N without
// breaking old rows, because every row says which settings made it.
export async function hashPassword(plain: string): Promise<string> {
  const salt = randomBytes(16); // new random salt for every single user
  const key = (await scryptAsync(plain, salt, KEY_LEN, {
    N, r, p, maxmem: MAX_MEM,
  })) as Buffer;
  return `scrypt$${N}$${r}$${p}$${salt.toString("base64")}$${key.toString("base64")}`;
}

export async function verifyPassword(plain: string, stored: string): Promise<boolean> {
  const [scheme, sN, sR, sP, saltB64, keyB64] = stored.split("$");
  if (scheme !== "scrypt") return false;

  const salt = Buffer.from(saltB64, "base64");
  const expected = Buffer.from(keyB64, "base64");

  // Re-hash the attempt with the SAME salt and the SAME settings as the row.
  const actual = (await scryptAsync(plain, salt, expected.length, {
    N: Number(sN), r: Number(sR), p: Number(sP), maxmem: MAX_MEM,
  })) as Buffer;

  // Not ===. A normal compare stops at the first wrong byte, so how long it
  // took leaks how much was right. timingSafeEqual always takes the same time.
  return timingSafeEqual(actual, expected);
}

Three ideas hiding in that file, worth naming:

  1. The stored string carries its own recipe (scrypt$131072$8$1$salt$hash). No lookup table of "which users used the old settings".
  2. verifyPassword does not decrypt anything. It shreds again and compares shreds.
  3. timingSafeEqual exists because how fast you said no is information. That is a timing attack, and it is on your week 7-8 list already.

Step 3 — the register route

Schemas first, as always. New file server/src/schemas/auth.schema.ts:

import { z } from "zod";

export const Register = z.object({
  email: z.email().max(254), // zod 4 style; z.string().email() is deprecated
  // 8 min and 256 max, per OWASP. Do not cap low. Do not strip characters.
  password: z.string().min(8).max(256),
});

// What we send back. No passwordHash. Not ever.
export const UserPublic = z.object({
  id: z.number(),
  email: z.string(),
});

export type RegisterInput = z.infer<typeof Register>;

Then server/src/routes/auth.route.ts:

import type { FastifyInstance } from "fastify";
import { Register, UserPublic, type RegisterInput } from "../../schemas/auth.schema.ts";
import { ErrorReply } from "../../schemas/task.schema.ts";
import { hashPassword } from "../../auth/password.ts";
import { createUser } from "../../store/user.store.ts";

export default async function authRoutes(app: FastifyInstance) {
  app.post(
    "/auth/register",
    { schema: { body: Register, response: { 201: UserPublic, 409: ErrorReply } } },
    async (request, reply) => {
      const { email, password } = request.body as RegisterInput;
      const user = await createUser(email, await hashPassword(password));
      if (!user) return reply.code(409).send({ error: "email already registered" });
      return reply.code(201).send(user);
    },
  );
}

And server/src/store/user.store.ts:

import { prisma } from "../../db.ts";

// undefined when that email is taken. The route turns that into 409.
export async function createUser(email: string, passwordHash: string) {
  try {
    return await prisma.user.create({ data: { email, passwordHash } });
  } catch {
    // @unique on email did the checking. We only translate the refusal.
    return undefined;
  }
}

Register it in server/src/app.ts, next to the others:

import authRoutes from "./routes/auth.route.ts";
// ...
app.register(authRoutes);

Step 4 — prove it

# make an account
curl -s -X POST localhost:3000/auth/register \
  -H 'content-type: application/json' \
  -d '{"email":"jay@example.com","password":"correct horse battery"}'
# -> {"id":1,"email":"jay@example.com"}     no hash in the reply

# same email again
# -> 409 {"error":"email already registered"}

# too short
curl -s -X POST localhost:3000/auth/register \
  -H 'content-type: application/json' -d '{"email":"a@b.com","password":"short"}'
# -> 400, and the handler never ran

# now look in the database
psql -U tasks -d tasks -c 'select id, email, "passwordHash" from "User";'

Read that last output slowly. Your password is not there, and there is no way to get it from what is there. That is today's win.

Check yourself

Why is sha256 the wrong hash for a password?

Right: sha256 is one-way, but speed is the problem. Password hashes must be slow on purpose.

The salt is stored in the database in plain sight. Is that broken?

Right: the salt kills shared hashes and pre-built lookup tables. It never needed to be secret.

Why store scrypt$131072$8$1$... instead of just the hash bytes?

Right: the recipe travels with the row, so old and new settings live side by side.

You swap timingSafeEqual for ===. What leaks?

Right: a normal compare quits at the first wrong byte. The clock becomes a hint.

Registering works. Can you now log in and drop DEV_OWNER_ID?

Right: a hash proves a password once. Carrying that proof between requests is a session — lesson 6.
