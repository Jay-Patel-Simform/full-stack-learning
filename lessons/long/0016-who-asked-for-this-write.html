Who asked for this write

CORS decides who may read your reply. An attacker’s page does not want to read it. It wants your browser to send one DELETE, with your cookie, and it does not care what comes back. Nothing in your API decides that yet.

The two missing thirds

What your server does: nothing. Not “refuses”. Nothing. The preflight arrives, @fastify/cors sees https://evil.example is not in ALLOWED_ORIGINS, and replies 200 with no Access-Control-Allow-Origin header. That is the test you already wrote in src/routes/cors.test.ts — the one that asserts a 200 for a denied origin.

What stops it: the browser. The one thing. The preflight came back without permission, so the browser never sends the real DELETE. Your server never sees a DELETE at all. It was not defended — it was never attacked.

Now change one word in the attacker’s page. Not fetch — a form:

An HTML form has been able to POST across sites since 1995, so it needs no preflight. Every defence you named just evaporated. That is CSRF: cross-site request forgery — another site’s page making your browser send a write, using your cookie, without ever reading the reply.

In one minute

  • CORS protects reading. CSRF does not read. Different problem, different defence.
  • SameSite=Lax on your cookie already blocks the form POST. It does not block a state-changing GET.
  • New defence: Sec-Fetch-Site. The browser writes it, and a page is forbidden to set it.
  • Nine lines in src/auth/csrf.ts, one onRequest hook. No token, no store, no second cookie. No new dependency.
  • npm test = 93. Eleven new, split decision (src/auth/csrf.test.ts) and enforcement (src/routes/csrf.test.ts).

Why SameSite=Lax is not the answer on its own

Read your own cookie, in src/auth/session.ts:

"SameSite=Lax", // ! not sent from another site's form -> blocks basic CSRF

That comment is true. Lax sends the cookie cross-site only for a top-level navigation using a safe method — GET, HEAD, OPTIONS. Not fetch, not a subresource, not POST.

But OWASP lists SameSite as a defence-in-depth layer, not a primary defence, and it names the gaps. Two of them are yours to worry about:

  • Lax only blocks unsafe methods. Row four of that table.
  • When Lax is a browser default rather than something you wrote, it is looser: the cookie also rides on a cross-site POST if it was set less than two minutes ago. You wrote SameSite=Lax explicitly, so this one does not bite you — but it is the reason “the default is Lax now, so CSRF is solved” is wrong.

And the thing that should actually worry you: SameSite=Lax is one word in one string. The day somebody needs a mobile app or a third-party embed and changes it to None, your only CSRF defence for writes leaves with it, silently, and no test fails.

The header the page cannot forge

Since March 2023, every browser sends Sec-Fetch-Site on every request. Four values, and they answer exactly the question you need:

ValueMeansFor your API
same-originSame scheme, host and port as the targetOur own page. Allow the write.
same-siteSame site, so a different port or subdomainMaybe. Your dev front end on :5173, or a sibling subdomain you do not control.
cross-siteA different site entirelyRefuse the write.
noneThe user started it — address bar, bookmarkYou cannot POST from an address bar. Refuse.

Here is the part that makes it a defence and not a suggestion. The Sec- prefix makes it a forbidden header name. Page JavaScript cannot set it, cannot change it, cannot delete it. If an attacker’s fetch tries, the browser silently drops their value and writes the true one. Compare that to Origin, which is also written by the browser but is simply absent on plenty of legitimate requests — absence is what makes Origin alone awkward.

This is the same shape as lesson 13’s rule, inverted. CORS is advice to a browser, so it stops nobody with curl. Sec-Fetch-Site is a report from a browser — and since CSRF requires a browser holding a victim’s cookie, a report from the only party that can carry out the attack is exactly the right witness.

The code

server/src/auth/csrf.ts, new file, the whole decision:

const SAFE_METHODS = new Set(["GET", "HEAD", "OPTIONS"]);

export function allowWrite(
  method: string,
  site: string | undefined,     // Sec-Fetch-Site
  origin: string | undefined,   // Origin
  allowedOrigins: string[],
): boolean {
  if (SAFE_METHODS.has(method)) return true;
  if (site === "same-origin") return true;
  if (origin) return allowedOrigins.includes(origin);
  if (site) return false;
  return true;
}

Four decisions, one line each. Note what it is not: no token, no token endpoint, no second cookie, no server-side state, no front-end change. Nothing to keep in sync, nothing to expire, nothing to move to Redis in week 11–12.

Two lines that look small and are not:

  • if (origin) return allowedOrigins.includes(origin) — this is why same-site alone is not enough. blog.app.example is same-site with app.example. Whoever runs the blog is not you. Your existing allow-list already knows the difference, so reuse it rather than trusting the word “site”. That is lesson 13’s pair of words earning its keep a second time.
  • if (SAFE_METHODS.has(method)) return true — this line is a promise that your GETs do not write. Row four of the table lives here. If you ever add a GET that mutates, this line is the bug, and the comment in the file says so.

The hook, in src/app.ts, as step 4 — after the rate limiter, before anything that touches the database:

app.addHook("onRequest", async (request, reply) => {
  const site = request.headers["sec-fetch-site"];
  if (!allowWrite(request.method, typeof site === "string" ? site : undefined,
                  request.headers.origin, ALLOWED_ORIGINS)) {
    return reply.code(403).send({ error: "cross-site write refused" });
  }
});

Fourth use of the frame you already own: the cheap check goes in front of the expensive work. Two string comparisons, then a refusal — a forged write never pays for requireAuth’s session query. And it is one place that says no, per lesson 7: an app-level onRequest hook, not a line in each route, because there is no route this rule should skip.

403, not 401. Sixth use of one reply for two different noes, and this time the point is the opposite — here the two noes must be different. A 401 means “log in and try again”, and the victim already has. The cookie was perfect. The caller was not.

The library you are not installing

The token pattern — generate a secret, put half in a cookie, make the front end echo the other half in a header, compare them — exists because for twenty years the server had no trustworthy way to ask who sent this. In 2023 the platform grew one. The token plumbing is a workaround for a missing header, and the header is no longer missing. OWASP itself now calls Sec-Fetch-Site “the primary signal for CSRF protection”.

This is the fourth dependency rule, and it is the one that will keep paying: before you install anything, ask what year its problem was solved in.

Where I disagree with OWASP, and why I am telling you

Look at the last line of allowWrite. Both headers absent, and we allow the write. OWASP says the opposite: “If neither of these headers are present, you can either accept or block the request. We recommend blocking.”

My reasoning, so you can disagree with it:

  • A CSRF attack needs a browser carrying a victim’s cookie. Nothing else can do it.
  • Every browser since March 2023 sends Sec-Fetch-Site. Every browser since roughly 2016 sends Origin on a POST. A write with neither is not a browser.
  • So blocking that case buys no security, and costs you every curl, Postman call and cron job that writes.

The honest cost: it is one assumption about your clients, and assumptions rot. So it is written down as a ponytail: comment with the exact one-line fix — change that return true to return false, and every curl write then needs -H "Origin: http://localhost:5173". There is a test asserting the current choice, so the day you flip it, one named test tells you what you decided.

Same habit as lesson 11: a written-down shortcut is a decision, an unwritten one is a future bug.

Dropped. Sec- makes it a forbidden header name, so the browser refuses the page’s value and writes the true one, cross-site. That single rule is the entire reason this defence works and a plain X-Requested-With header does not.
