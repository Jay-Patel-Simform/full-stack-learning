Headers for JSON, not pages

You install Helmet and get thirteen headers. Your API sends JSON. Only four of the thirteen mean anything, one of them is set wrong for you, and one can lock your own laptop out of http://localhost for a year.

Your login backoff gives an attacker ten free tries instead of five, and your 100‑per‑minute IP floor becomes 200. In one minute

  • Third dependency: @fastify/helmet@13.1.1. New rule — take the library, then turn it down.

  • Four earn their place: nosniff, a CSP of default-src 'none', X-Frame-Options: DENY, and HSTS in production only.

Your third library decision, and it is a new shape

You now own two rules about dependencies. This lesson adds the third, and the three together are the whole skill:

LessonLibraryRule
11@fastify/rate-limit, rejectedReject it when its default is the wrong decision. Its key was request.ip; a login must key on the account.
12, 13@fastify/rate-limit, @fastify/cors, takenTake it when the problem has no decisions left in it.
15@fastify/helmet, taken and turned downTake it, then switch off what it assumed. Helmet assumed you serve pages. The header strings are worth having; the assumption is not.

Why take it at all, if you switch most of it off? Because the value in Helmet is not the logic — there is barely any. It is the exact spellings, the version history of headers browsers have since dropped, and thirteen names you would otherwise have to keep in your head. Helmet is a list, maintained by people who read the specs. Take the list. Make your own decisions on it.

A library can be right about the facts and wrong about your situation. Those are two separate judgements.

The bad version first

await app.register(helmet);   // <- what everybody ships

It works. Nothing breaks. Now read what it actually sent you (helmet’s own defaults page), and mark each row against a JSON API:

Four yeses, two wrong values, seven that do nothing. Ship the defaults and 60% of every response you send is bytes for a browser feature you do not use — and the two rows that do matter are set for somebody else’s app.

Count the rows that apply to your kind of response. Same counting move as lessons 9, 10 and 11 — it keeps finding things.

The dangerous row, said plainly

Strict-Transport-Security tells a browser: never speak plain http to this host again, for the next year. The browser writes that down and obeys it before it makes a request — your server is not consulted.

Send it from localhost:3000 and your browser pins localhost to HTTPS. Every other project you run on localhost, in any port, now fails to load. You cannot fix it by deleting the header, because the browser has already stopped asking. You clear it by hand in the browser’s internal settings, per browser, and includeSubDomains widens the blast radius further.

So: on in production, where TLS is real. Off everywhere else. That is what the NODE_ENV check in the code below is for, and it is the only environment check in the whole registration.

The code

In server/src/app.ts, after the CORS block:

await app.register(helmet, {
  // A JSON API should be allowed to load nothing at all.
  contentSecurityPolicy: {
    useDefaults: false,
    directives: { "default-src": ["'none'"], "frame-ancestors": ["'none'"] },
  },
  xFrameOptions: { action: "deny" },          // helmet says sameorigin; we frame nothing
  hsts: process.env.NODE_ENV === "production"
    ? { maxAge: 31_536_000, includeSubDomains: true }
    : false,                                   // never from localhost
  // Off: these only mean something to a page, and we do not serve pages.
  crossOriginOpenerPolicy: false,
  originAgentCluster: false,
  xDnsPrefetchControl: false,
  xDownloadOptions: false,
  xPermittedCrossDomainPolicies: false,
  // Kept: nosniff, referrer-policy, cross-origin-resource-policy.
});

useDefaults: false is the important word. Without it your two directives are added to Helmet’s page policy, and default-src stays 'self'. With it, the policy is exactly the two things you wrote.

Read the result out loud: default-src 'none'; frame-ancestors 'none'. No scripts, no images, no fonts, no frames, no anything — and nobody may put this reply inside a frame. That is a correct description of a JSON endpoint.

You keep Helmet’s CSP default of default-src 'self' on your JSON API. What is wrong with it?

CSP restricts what a rendered page may load. It never affects a fetch() from someone else’s page — that is CORS, from lesson 13. 'self' is simply a weaker answer than 'none' for a response that should render nothing. Content-type guessing is nosniff, a different header.

The one no plugin sets

Helmet does not touch caching. OWASP’s REST cheat sheet names it anyway: “Providing no-store indicates that any caches of any kind (private or shared) should not store the response.”

Every route in this API answers with somebody’s private data, behind a session cookie. There is no per-route decision to make, so it is global:

app.addHook("onSend", async (_req, reply) => {
  reply.header("cache-control", "no-store");
});

Why onSend and not onRequest? onSend is the last hook before bytes leave, so it runs for every reply — your 200s, your 400s from zod, your 403s from can(), your 429s from the limiter. A header set at request time can still be overwritten by a handler. This one cannot.

Without it, a shared cache — a corporate proxy, a CDN you add in week 11–12, the browser’s own back-button store — is allowed to keep one user’s /teams/1/tasks and hand it to the next person who asks. Your can() checks are perfect and never consulted.

Access control you never reach is access control you do not have. Same family as lesson 12’s hook-order bug.

Why is Cache-Control: no-store set in an onSend hook rather than in each route?

A 429 from the rate limiter, a 400 from zod validation and a 404 never reach your handler at all. Per-route code cannot cover them. One onSend hook covers every reply the app produces, which is exactly the guarantee you want from a rule with no exceptions.

The tests

Seven new tests in server/src/routes/headers.test.ts. Same rule as cors.test.ts: test what you decided, not what you installed. Every assertion matches a line you wrote in app.ts.

assert.equal(
  res.headers["content-security-policy"],
  "default-src 'none';frame-ancestors 'none'",
);
assert.equal(res.headers["x-frame-options"], "DENY");        // not SAMEORIGIN
assert.equal(res.headers["strict-transport-security"], undefined);  // not in dev

The last one is a guard, not a check of Helmet. If it ever fails on your laptop, something has started sending HSTS from localhost, and you want to know that before your browser does.

The seventh test asks for /nope and asserts nosniff and no-store on the 404. Error replies are where header middleware usually gets skipped. One assertion, and you never wonder.

Read row three. This lesson protected your API’s responses. Your front end is a separate program with a separate policy, and its CSP is the one that stops real XSS. Do not walk away thinking you have shipped a CSP. You have shipped the easy one.
