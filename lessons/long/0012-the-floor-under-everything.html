Lesson 12 · Week 7–8 · API security — second one

The floor under everything

Lesson 11 put a wall in front of one route. The other twenty-odd routes will still answer you as fast as your laptop can ask. Today you add the second layer — and you break an eleven-lesson streak on purpose.

Checked before we started. Everything from lesson 11 is in the repo and working: src/auth/throttle.ts, the three calls in src/routes/auth.route.ts, the ponytail: note, and npm test at 66 pass. Nothing was missing. It is now 70.

In one minute

  • Lesson 11 stopped guessing. This one stops noise.
  • A junk cookie has no email in it, so the only key left is the IP address. Here that is fine.
  • Install @fastify/rate-limit — first new dependency in eleven lessons. The job has no decisions left in it.
  • Register it with global: false, then add your own app-level hook, so the cheap check runs before the session query.

The hole you left

Login is guarded. Now count what is not. Every other route runs behind requireAuth, and requireAuth does a database lookup on the session cookie before it can say no. So a stranger with a junk cookie can do this:

while true; do curl -s localhost:3000/teams/1/tasks -H 'cookie: sid=junk'; done

Each request is one Postgres round trip that you pay for and they do not. Lesson 11's counter cannot help: it is keyed on an email address, and there is no email address in that request. Nothing here is being guessed. It is just noise, and noise is its own problem.

Lesson 11 was about guessing. This one is about volume. Different attack, different key, different layer.

What do you count when there is no account?

Use the same question that worked last time: what does the caller have only one of? A stuffing kit has one email per victim, so login counts the email. But a request with a junk cookie has no account attached at all. Work down what is left in the request — and the honest answer is the connection it arrived on.

So this layer is per-IP. The key that was wrong for login is the only key available here.

Per-IP counting failed in lesson 11. Why is it acceptable now?

Right. A proxy network beat the per-IP login counter because the attacker only needed two requests per address. Flooding is the opposite shape: the whole point is many requests, so spreading them thin defeats the flood, not the counter. Rotating 5,000 proxies gets a rude client 500,000 requests a minute — but now it is a paid, coordinated botnet, not a laptop.

Take the library this time

Eleven lessons, zero new dependencies. This one installs @fastify/rate-limit. Here is the reasoning, because “write it yourself” was right ten times and is wrong now.

You already own three of the functions. You could key throttle.ts on request.ip and reuse it in a hook. But read what the two jobs actually need:

login counter (yours)global limit (the plugin)
countsfailures onlyevery request
forgetson a correct passwordon a clock, every 60s
answer to morea wait that doublesa flat no until the window ends

Only the shape of the storage is shared. Everything that decides is different, so reuse would mean a second set of options threaded through the same file — a config flag for a value that never changes, on both sides. And the last row is real work: sliding windows, three headers, an eviction policy, allowList, a Redis mode for later. That is a maintained 292 KB package doing a job with no interesting decisions left in it.

Reject a library when its defaults are wrong for your problem. Take it when the problem has no decisions left in it. Lesson 11 was the first. This is the second.
cd server && npm i @fastify/rate-limit
# @fastify/rate-limit@11.2.0, 292 KB, 4 small deps

The wiring, and the one line that is not obvious

In src/app.ts, before the routes:

await app.register(rateLimit, {
  global: false,
  max: 100,
  timeWindow: "1 minute",
  cache: 5_000,
});
app.addHook("onRequest", app.rateLimit());

global: false followed by a hook that turns it back on globally looks like nonsense. It is the whole reason this lesson is not two lines long.

The plugin's own global mode attaches its check to each route, appended after that route's hooks. Read the plugin's source and you can see it happen:

// node_modules/@fastify/rate-limit/index.js
} else if (typeof routeOptions[hook] === 'function') {
  routeOptions[hook] = [routeOptions[hook], hookHandler]   // yours first
}

So on GET /auth/me, which sets onRequest: requireAuth, the order would be: check the session in Postgres, answer 401, then count. A blocked request would still cost you a query. I found this by writing a test that expected 429 and getting 401.

An app-wide addHook is different: Fastify runs every app-level onRequest hook before any route's own. So the counter goes first, and a rejected request costs a cache lookup. That is lesson 11's rule again — the cheap check goes in front of the expensive work — except this time the expensive work is a query, not a hash.

Why does hook order matter more here than the limit number does?

Right, and this is the third time that idea has decided where code goes: before the scrypt hash in lesson 11, before the session query here. A limiter that only runs after the expensive part still shrinks your bill — but it turns a flood into a slow flood instead of a cheap no.

One consequence to notice: buildApp() is now async, because app.rateLimit does not exist until the plugin has finished loading. Every caller grew an await — six lines, all of them const app = await buildApp();. Test files can do that at the top level; ESM allows it.

Two layers, and what each one catches

Neither row covers the other. That is what “defence in depth” means in practice, and it is why OWASP's Denial of Service cheat sheet asks for limits at more than one level.

trustProxy is worth one more sentence, because getting it wrong is worse than not having it. It tells Fastify to believe the x-forwarded-for header. If you turn that on while the API is reachable directly, anyone can send a fake header and get a fresh budget per made-up address. Believe a header only when something you control is the one writing it.

The tests

npm test is now 70, up from 66. New file, src/routes/rate-limit.test.ts — and this one is all enforcement, no decision tests. The counting logic belongs to the plugin, so what is worth testing is your wiring:

  • The 101st request from one address is 429, and carries retry-after.
  • One address running out does not block another. (This one matters: get the key wrong and your security feature is a global outage button.)
  • The count is shared across routes — 100 hits on /health, then /auth/me gets 429, not 401. That is the hook-order bug, written down so it cannot come back.
  • A normal reply says how much budget is left.

app.inject() takes a remoteAddress, which is what makes the per-key test possible without a network.

Gotcha that cost me ten minutes. npm test runs tsx --test src/**/*.test.ts, and npm runs scripts in sh, not zsh. In sh, ** is just * — so the pattern means exactly one directory deep. A test file at src/anything.test.ts is silently skipped. Mine was. The test count not moving is the only warning you get.
