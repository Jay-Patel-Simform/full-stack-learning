Lesson 01 · Week 1 · API Basics

Your first validated route

You already write TypeScript. Today you point it at a port instead of a browser. One win: a running API that refuses bad input at the door.

In one minute

  • A server is just a function that runs when a request arrives.
  • Check the request before your code touches it. This line is the trust boundary.
  • Use the checked copy of the data. Never the raw one.
  • You will build: POST /tasks that says 400 to bad input.

Why this first

Every later thing in this workspace — login, roles, audit logs — is a function that runs on a request before your real code does. So the very first thing to learn is the shape of a request handler, and the very first habit to build is validate at the trust boundary.

A trust boundary is the line where data you control meets data a stranger sent you. Inside your server, you trust your own variables. At the boundary, you trust nothing. Validation is the only wall there. OWASP puts it the same way: validate on the server, always, even if the browser already did.

The front end validates to be kind to the user. The back end validates to stay alive.

Three packages, three jobs:

PackageJob
fastifyListens on a port. Turns HTTP into a function call.
zodDescribes the shape input must have. Rejects anything else.
tsxRuns TypeScript directly, no build step while learning.

The code

Create api/src/server.ts:

import Fastify from "fastify";
import { z } from "zod";

const app = Fastify({ logger: true });

// The wall. Anything not matching this never reaches the handler.
const CreateTask = z.object({
  title: z.string().min(1).max(200),
  done: z.boolean().default(false),
});

const tasks: Array<z.infer<typeof CreateTask> & { id: number }> = [];

app.get("/health", async () => ({ ok: true }));

app.post("/tasks", async (request, reply) => {
  const parsed = CreateTask.safeParse(request.body);
  if (!parsed.success) {
    return reply.code(400).send({ error: "invalid body" });
  }
  const task = { id: tasks.length + 1, ...parsed.data };
  tasks.push(task);
  return reply.code(201).send(task);
});

app.get("/tasks", async () => tasks);

app.listen({ port: 3000 }).catch((err) => {
  app.log.error(err);
  process.exit(1);
});

Start it:

npx tsx watch src/server.ts

Now attack it

This is the part that teaches. Run each command and predict the status code before you press enter.

# 1. should work
curl -i -X POST localhost:3000/tasks \
  -H 'content-type: application/json' \
  -d '{"title":"buy milk"}'

# 2. empty title
curl -i -X POST localhost:3000/tasks \
  -H 'content-type: application/json' \
  -d '{"title":""}'

# 3. wrong type
curl -i -X POST localhost:3000/tasks \
  -H 'content-type: application/json' \
  -d '{"title":"x","done":"yes please"}'

# 4. extra field you never asked for
curl -i -X POST localhost:3000/tasks \
  -H 'content-type: application/json' \
  -d '{"title":"x","isAdmin":true}'

Number 4 is the important one. Look at what came back. The isAdmin field is gone — because you built the task from parsed.data, not from request.body. That accident-proofing has a name: it stops mass assignment, where an attacker sets a field you never meant to expose. Had you written { id, ...request.body }, the extra field would have sailed straight in.

Habit to keep for 16 weeks: never read request.body after validating. Read the parsed result. Same for request.query and request.params.

Check yourself

The React form already blocks an empty title. Why validate on the server too?

Right: curl, Postman, or a script never load your front end. Client validation is a nicety; server validation is the actual boundary.

Which line lets an attacker smuggle an unexpected field into your object?

Right: spreading the raw body copies every key the sender chose. Spreading the parsed result copies only keys your schema named.

Test 3 sent "done": "yes please". What should the server answer?

Right: silent coercion hides bugs. Reject at the boundary and say so with a 400.
