Lesson 11 · Week 7–8 · API security — first one

Five tries, then wait

Every route in your API is behind a gate now. Except the one that hands out the keys. POST /auth/login will answer a stranger as many times as they like, as fast as they like, forever. Today you put a floor under it — and the interesting part is what you count.

Housekeeping. Project got built between sessions, so week 5–6 is closed. project:create and project:delete now have routes: POST /teams/:teamId/projects and DELETE /teams/:teamId/projects/:projectId, both behind requirePermission, no loader. Nothing in can() is unwired any more. Skim server/src/routes/projects.route.ts — it is 50 lines and it should read as boring. If it does not, that is a question for me.

In one minute

  • Login is the one route with no gate, and it does 252 ms of expensive work per try.
  • Counting per IP does not work — an attacker rents thousands of them.
  • Count the thing they have one of: the email.
  • Do not lock the account. That is a free denial-of-service button aimed at your users.
  • Double the wait each failure. Check before the hash, so a blocked try costs you nothing.

Count the cost of one wrong password

Your login handler does this, in this order:

const user = await findUserByEmail(email);           // 1 query
const ok = await verifyPassword(password, hash);      // 252 ms, 128 MiB

That second line is lesson 5's scrypt, and those are the real numbers you measured on this Mac. Deliberately slow, deliberately memory-hungry, so that a stolen database is not worth cracking.

Now read it as an attacker. Every request they send costs them nothing and costs you 252 ms of CPU and 128 MiB of RAM. A hundred at once is 12.8 GB. They do not even need to guess your password — they can just knock.

An unauthenticated route that does expensive work is two holes, not one: a guessing hole and a bill.

So the check has to happen before the hash. Hold that thought, it decides where the code goes.

The bad version, which is also the default

Here is what almost everybody reaches for. @fastify/rate-limit, one line, done:

// its default key, straight from the docs
keyGenerator: (request) => request.ip

Count requests per IP address, block the noisy ones. It sounds obviously right. Kill it with two named attacks.

attackwhat they doper-IP counter says
Credential stuffingTake 10 million leaked email+password pairs. Try each once, spread over a proxy network.Nothing. Two requests per IP.
Password sprayingTake one popular password. Try it against every email you have.Nothing. Same shape.

A stuffing kit ships with proxy support built in. OWASP is blunt about it: IP blocking “should not be used as the sole or primary defense due to the ease in circumvention… per IP request volume may remain relatively low, even on high volume attacks.”

Now flip the question. What does the attacker have only one of?

They have thousands of IP addresses. They have one email per victim. So count the email.

That is the whole lesson, and it is OWASP's rule word for word: “The counter of failed logins should be associated with the account itself, rather than the source IP address.”

Notice what just happened. The plugin was not wrong. Its default key was wrong for this one route, and a plugin you install in one line is a plugin whose default you never read. Same reason you hand-wrote the cookie flags in lesson 6: here, the key is the security content.

An attacker has 40,000 email+password pairs and 5,000 proxy IPs. Why does a per-account counter stop them when a per-IP one does not?

Right. Rate limiting works when you count the thing the attacker cannot get more of. They can rent another IP for pennies. They cannot rent a second email address for your user.

Do not lock the account

The obvious next step is a lockout: five wrong, account frozen for ten minutes. Do not. Read it from the other side.

I know your email. I type it with a wrong password five times. You are now locked out of your own account, and it cost me five requests. Your security feature is my denial-of-service button, aimed at anyone whose email I can guess.

OWASP's alternative, and what you built: exponential backoff. The wait doubles with each failure, so a human who fumbles pays nothing and a script hits a wall almost immediately.

wrong passwordsthen you wait
1–4nothing
51 second
62 seconds
74 seconds
15 and up15 minutes (the cap)

Doubling is the point. Ten more guesses and the attacker is down to about 96 tries a day; you were still typing normally at guess four. Nobody is ever locked out — there is only ever a wait, and one correct password clears it completely.

Two small mercies in the design. The wait is capped at 15 minutes, so a bad day still ends. And a blocked request does not count as another failure, so hammering refresh while locked out does not dig you deeper.

The code: three functions and a Map

New file, server/src/auth/throttle.ts. No table, no migration, no dependency — a Map in memory.

const FREE_TRIES = 5;
const BASE_MS = 1_000;
const MAX_MS = 15 * 60 * 1_000;
const MAX_KEYS = 10_000;

type Entry = { fails: number; until: number };
const attempts = new Map<string, Entry>();

// ms this key must still wait. 0 means go ahead.
export function throttleCheck(key: string): number {
  const wait = (attempts.get(key)?.until ?? 0) - Date.now();
  return wait > 0 ? wait : 0;
}

export function throttleFail(key: string): void {
  const entry = attempts.get(key) ?? { fails: 0, until: 0 };
  entry.fails += 1;
  const over = entry.fails - FREE_TRIES + 1;
  entry.until = over > 0
    ? Date.now() + Math.min(BASE_MS * 2 ** (over - 1), MAX_MS)
    : 0;
  attempts.delete(key);   // delete then set, so this key is now the newest
  attempts.set(key, entry);
  if (attempts.size > MAX_KEYS) attempts.delete(attempts.keys().next().value!);
}

export function throttleReset(key: string): void {
  attempts.delete(key);
}

Two lines deserve a second look.

attempts.delete(key) immediately before set looks pointless. It is not. A JavaScript Map remembers insertion order, so re-inserting moves this key to the back of the queue. That makes the last line a working eviction rule: when the map is full, attempts.keys().next().value is the coldest key, and out it goes.

Why bother? Because the map only ever grows on failure, and failures come from strangers. Without a cap, for email in wordlist: login(email, "x") is a memory leak you built for them. Twenty-five lines of security code, and one of them is there purely because the other twenty-four are attacker-fed.

Any store keyed on something the caller types is a store the caller can fill. Cap it in the same breath as you create it.

Where it goes in the handler

const key = email.toLowerCase();

const waitMs = throttleCheck(key);
if (waitMs > 0) {
  reply.header("retry-after", Math.ceil(waitMs / 1000));
  return reply.code(429).send({ error: "too many attempts, try again later" });
}

const user = await findUserByEmail(email);
const ok = await verifyPassword(password, user?.passwordHash ?? DUMMY_HASH);

if (!user || !ok) {
  throttleFail(key);
  return reply.code(401).send({ error: "invalid email or password" });
}

throttleReset(key);   // a right answer wipes the slate

Three decisions are hiding in there.

The check is first. Before the query, before the hash. That is the CPU bill from the top of the lesson — a blocked request must cost you a Map lookup, not 252 ms. It also closes a subtler hole: a locked-out key cannot be unlocked by finally guessing right, because the password is never even read.

The key is .toLowerCase(). Skip that and Jay@x.com, jay@X.com and JAY@x.com are three different counters. Five free tries each, and there are 213 ways to capitalise a thirteen-letter address. There is a test for this one.

The key is the email the caller typed, not a user id. Often there is no user — and that matters more than it looks, which is the next quiz.

Why must an email that was never registered get throttled exactly like a real one?

Right, and it is lesson 6's rule wearing a status code. You were careful to send one message for both failures — then a shortcut here would leak the same fact through the shape of the response instead. Every new reply is a new chance to answer two different questions differently.

What it cost, and what it does not fix

Zero new dependencies. Eleven lessons running. @fastify/rate-limit would have been a dependency, a 5,000-entry LRU cache, and a default key that does not stop the attack you actually face. You wrote 25 lines and you can say what every one does.

Now the honest limits, because a defence you cannot describe the edge of is a defence you will over-trust:

holewhy it is still openwhen you close it
Restart forgets everythingThe Map lives in one Node process.Homework, below.
Two processes, two countersEach keeps its own map, so the real limit doubles.Week 11–12, at deploy.
Junk emails can evict a victim's counterThe 10,000-key cap has to drop something.Same fix as the row above.
Slow, patient guessingFour tries an hour never trips anything.Only MFA really answers this.
Nothing else in the API is limitedThis is one route, not a policy.Week 7–8, a global per-IP layer on top.

That first one is marked in the file with a ponytail: comment naming the ceiling and the upgrade path. Get in the habit: a deliberate shortcut you wrote down is a decision, and the same shortcut undocumented is a bug waiting to surprise you.

And keep the ranking straight. OWASP says MFA “is by far the best defense against the majority of password-related attacks” — one analysis puts it at 99.9% of account compromises stopped. Throttling is the floor, not the ceiling.

The tests

npm test is now 66 passing, up from 56. The new file keeps lesson 8's split:

  • Decisions — no server, no database. Four failures are free; the fifth starts the wait; it doubles; it is capped; one key never blocks another.
  • Enforcement — the real route via app.inject(). Five 401s then a 429 with retry-after; the wall ignores a correct password; an unregistered email throttles identically; capitalisation is not a side door.

Read the four enforcement names out loud. Each one is an attack, written down.

Then two questions to bring me:

  1. Restart the server and try to log in wrong six times. You get six 401s, because the Map died with the process. So where does the counter have to live instead? You already own two things it could live in. Name both, and say what each one costs on every single login, not just the failed ones. One of the two answers is going to bother you.
  2. Opinion, and I do not think there is a clean answer: after backoff, the usual next rungs are a CAPTCHA, an email “someone tried to log in” alert, or forcing MFA. Pick the order you would add them in for a small work app and defend it. Then post it to Security StackExchange or r/node and see who disagrees. This one is a real design argument, not a fact to look up — which is exactly why it goes to practitioners and not to me.
