Lesson 33 · Week 11 · Real world

Query keys as questions

Today the task list stops being “the tasks” and becomes the tasks that match what you asked for. Two filters: ?done= and ?q=. The server part is six lines. The front-end part is one line — and if you write that one line wrong, ticking a filter sends no request at all, and the “Load more” button quietly mixes two different lists into one. I measured it. That is the lesson.

In one minute

  • A filter is an input to the answer, so it belongs in the query key. Measured with the filter left out: the user asks for done-only, 0 requests go out, the old list stays on screen. Then “Load more” sends the filtered request with the unfiltered cursor and appends rows to a list they do not belong to.
  • Put it in the key and paging resets for free. Measured: a new key means a new cache entry, so the request goes out with no cursor. You wrote no code to reset anything.
  • done has three answers, not two. true, false, and absent. Three buttons, not a checkbox. This is the same shape as the session in lesson 22.
  • Trap, measured: z.coerce.boolean() reads the string "false" as true. It is JavaScript’s Boolean(), and a five-letter string is not empty. z.stringbool() knows the words.
  • Trap, measured: Postgres LIKE is case sensitive. contains: "buy" found 2 of 4 rows a person would call a match. mode: "insensitive" is the fix.
  • And the second-order cost: one team now has many cache entries. A write that changes whether a row still belongs in the list can no longer be patched in by hand. One of your three mutations keeps its surgical edit; two go back to asking.

The order matters, and it is the rule from lesson 18. A zod chain runs left to right. Measured, on the string "   ":

Same two words, opposite outcomes. The second order checks the untrimmed string, passes it, then destroys it.

Part one: the server. Six lines, two traps.

I applied this side. It is mechanical, and it is safe to apply first — nothing calls the new filters yet, so the app kept working. Two new fields on the query schema:

// server/src/schemas/task.schema.ts, inside TaskQuery
done: z.stringbool().optional(),
q: z.string().trim().min(1).max(100).optional(),

And the where clause in the store:

// server/src/store/task.store.ts, inside listTasks
where: {
  teamId,
  ...(done === undefined ? {} : { done }),
  ...(q === undefined
    ? {}
    : { title: { contains: q, mode: "insensitive" as const } }),
},

That is the whole feature. Now the two things in it that would have shipped as bugs.

Trap one: coerce is not parse

The obvious way to read a boolean out of a URL is z.coerce.boolean(). It looks right and it is a disaster. Measured, with zod 4.5.4:

z.coerce.boolean()

.parse("false")  -> true
.parse("")       -> false
.parse("maybe")  -> true

coerce calls JavaScript’s Boolean(). Every non-empty string is true. So ?done=false means done, and your “Open” filter shows the finished tasks.

z.stringbool()

.parse("false")  -> false
.parse("0")      -> false
.parse("maybe")  -> 400

It knows the words: true/1/yes/on/y/enabled and false/0/no/off/n/disabled. Anything else is rejected at the door, with the list in the message.

Coercion converts; parsing decides. coerce.number() is fine, because Number("abc") gives NaN and zod then refuses it — the conversion can still fail. Boolean() can never fail. A conversion with no failing state is not a check, and lesson 29 already taught you what code with no failing state does: it never turns a light red.

Trap two: LIKE reads capital letters

Twelve rows, four of them with some form of “buy” in the title. Measured against the real Postgres:

contains: "buy"                        -> [ 'buy bread', 'buy coffee' ]
contains: "buy", mode: "insensitive"   -> [ 'Buy MILK', 'buy bread', 'buy coffee', 'Buy tickets' ]

The first one is a search box that finds tasks only if you typed them in lower case. Nobody would report that as a bug; they would just stop using the search. mode: "insensitive" makes Prisma emit ILIKE instead of LIKE. Confirmed in the query plan: Filter: ((title)::text ~~* '%buy%') — and ~~* is Postgres’ internal name for ILIKE.

q is a value. sort was not. Back in lesson 20 you learned that a column name has to be part of the SQL text, so ?sort= needed an allowlist and there was no escaping move available. ?q= is the opposite case and it is worth feeling the difference: a search word is a value. It travels beside the query as a parameter, Prisma sends it separately, and there is nothing to allowlist. That is why q is a free-text z.string() and sort is an enum. Same file, two inputs, two completely different reasons.
Honest note: the compiler corrected my comment. I first wrote where: { teamId, done } with a comment saying the spread was only for tidiness, since done: undefined is how Prisma spells “no filter”. tsc refused it: TS2375 ... with 'exactOptionalPropertyTypes: true'. That flag in your tsconfig says an optional property may be absent or a boolean, but never present-and-undefined. So the spread is load-bearing, not decoration. And it has to test === undefined: the shorter ...(done && { done }) silently drops done: false, which is the filter people use most.

Part two: the front end. The one line that matters.

The hook takes the filter now, and the key includes it:

export type TaskFilter = { done?: boolean; q?: string };

// the PREFIX - what a mutation talks to
export const tasksScope = (teamId: number) => ["teams", teamId, "tasks"] as const;

// the WHOLE key - what a read talks to
export const tasksKey = (teamId: number, filter: TaskFilter) =>
  [...tasksScope(teamId), filter] as const;

That filter at the end of the array is the entire lesson. Here is what happens without it. I ran a real React Query client with a real observer, twelve fake tasks, four of them done, four rows per page. The user loads the list, then clicks “Done”, then clicks “Load more”.

filter NOT in the key

on screen:      100,101,102,103
clicks "Done"
on screen:      100,101,102,103
requests sent:  [ done=undefined ]

clicks "Load more"
requests sent:  [ done=undefined,
                  done=true cursor=103 ]
on screen:      100,101,102,103,106,109

filter IS in the key

on screen:      100,101,102,103
clicks "Done"
on screen:      100,103,106,109
requests sent:  [ done=undefined,
                  done=true cursor=undefined ]

clicks "Load more"
on screen:      100,103,106,109
(no next page - the server said so)

Read the left column twice, because it fails in three separate ways and only the third one is visible.

  1. The click sends nothing. The key did not change, so React Query is looking at the same cache entry, and that entry is fresh for 30 seconds. Nothing is stale, so nothing refetches. Your filter is a no-op.
  2. The cursor survives across questions. When something finally does fetch, it sends cursor=103 — a position in the unfiltered list — while asking the filtered question. On the server that is not even an error. Measured against real Postgres: it returned one row where the correct filtered list has four, because ids 100 and 103 sit before the cursor and were skipped. A cursor is a bookmark in one specific list. Hand it to a different list and it points at a page that does not exist.
  3. Two answers to two different questions end up in one array. data.pages is a list of pages, and page 2 came from a different query than page 1. Your flatMap cannot tell. The screen shows six rows: four of everything, then two done ones.

Everything the answer depends on goes in the key. The team id has been in there since lesson 24 for exactly this reason. The filter is the same kind of thing. If two different requests can produce two different answers, they are two different keys — and the cache will happily serve you the wrong one, quickly and with no error.

The reward: paging resets and you wrote nothing

Look at the right-hand column again: done=true cursor=undefined. Because the key is new, the entry is empty, so there are no pages, so initialPageParam is used and the request starts at the beginning. You did not write a “reset the cursor when the filter changes” line. There is nothing to reset. This is the derive, never store rule paying out again: the cursor was never a variable you owned.

And switching back is free. Measured: going from “Done” back to “All” cost 0 new requests — the old answer is still in its own entry, still fresh. Two entries now exist:

["teams",7,"tasks",{}]
["teams",7,"tasks",{"done":true}]

Note the first one. The filter object was { done: undefined }, and it hashed to {}. React Query drops undefined values when it hashes a key, so “no filter” and “a filter set to nothing” are the same entry. That is why onChange({ ...filter, q: undefined }) is safe in the filter bar.

The word pair

key prefix — the first part of a key. ["teams", 7, "tasks"]. It is not an entry itself; it matches every entry that starts with it. This is what invalidateQueries and setQueriesData take.
whole key — one exact entry, filter included. ["teams", 7, "tasks", { done: true }]. This is what a useQuery reads and what setQueryData writes.

Fourteenth pair, and the test it gives you: am I talking about one answer, or about every answer to a family of questions? A read always means one. A write almost always means every.

The part nobody warns you about: one write, many keys

Before today, one team had one cache entry, so lesson 25’s trick worked perfectly: the PATCH reply is the new row, so write it straight into the cache and pay no second round trip. Now one team has an entry per filter the user has looked at. Watch what that does. Measured, with two entries cached and lesson 25’s write applied to the one on screen:

before             ["teams",7,"tasks",{}]            -> 100:true,101:false,102:false,103:true
before             ["teams",7,"tasks",{"done":false}] -> 101:false,102:false

  user ticks task 101 while looking at the "Open" list
  setQueryData maps the row in that one entry

after setQueryData ["teams",7,"tasks",{}]            -> 100:true,101:false,102:false,103:true
after setQueryData ["teams",7,"tasks",{"done":false}] -> 101:true,102:false

Two things are now wrong. The “Open” list contains a done task — row 101 is sitting in a list of things that are not done, with its box ticked. And the “All” entry still says 101 is open, so switching filters shows the old value.

The fix is not a bigger write. It is noticing what you stopped knowing:

what you know

The row’s new contents. The server told you: { id: 101, title: "...", done: true }. That has not changed since lesson 25.

what you no longer know

The row’s membership. Does it still answer the question this list is asking? A task that just became done does not belong in a ?done=false list at all — and only the server can say what the list is now.

This is lesson 26’s rule, second use: put the reply in the cache when you know where it goes, and ask again when you do not. Last time it was a create, and the “where” you did not know was the position. This time it is an update, and the “where” you do not know is whether it is in the list at all.

So: two mutations ask, one still patches

useSetTaskDone  onSuccess: () => client.invalidateQueries({ queryKey: tasksScope(teamId) })
useCreateTask   onSuccess: () => client.invalidateQueries({ queryKey: tasksScope(teamId) })
useDeleteTask   onSuccess: (_nothing, id) =>
                    editPages(client, tasksScope(teamId), (items) =>
                      items.filter((t) => t.id !== id))

Delete is the exception, and the reason is worth saying out loud: a deleted row leaves every question at once. No filter can still want it. There is no membership left to be unsure about, so the surgical edit is not a guess — it is a fact, and it costs zero requests.

To make that work, editPages changed by one word. It takes the prefix now and uses setQueriesData, plural:

client.setQueriesData<InfiniteData<TaskPage>>({ queryKey: key }, (data) => ...

One call, every filter the user has looked at, the row gone from all of them. Your four tests from lesson 32 still pass unchanged, because an exact key is also a prefix of itself.

The honest price of the invalidate. Prefix matching marks every entry stale — measured, 2 of 2. But invalidateQueries only refetches the queries something is currently watching. Measured, with two filter entries cached, one on screen, two pages held: 2 requests, both for the mounted key, one per page. The unmounted entry is left stale and unfetched, and refetches only if the user goes back to it. So the cost is “the pages of the list you are looking at”, which is the same price lesson 31 already quoted you for a create.

Two small things I put in, and one I did not

In: one line for the blank screen. A new key means an empty entry, which means isPending is true, which means the panel is replaced by “Asking…” — including the filter bar, so there is briefly no way back. Measured, then fixed with one line:

                          isPending   data
no placeholder            true        undefined     <- the screen empties
placeholderData:
  keepPreviousData        false       100,101,102,103   isPlaceholderData: true

The old rows stay on screen while the new ones load. One line, a real visible bug, and it costs nothing.

In: three buttons, and an empty state that tells the truth. “No tasks yet” is a lie when a filter is on — there may be plenty of tasks and none of them done. The panel now says “No tasks match that” instead, and the filter bar stays above it, or you are stuck.

Not in: a debounce. Every keystroke in a search box would be a new key and a new request. The usual answer is a timer and a useEffect, and this app has had zero useEffect since lesson 22. So the search box is a <form>: the words being typed live in useState, and they only join the query key when you press Enter. One request per Enter, not per letter. A form is the debounce. Work hangs off the event that caused it — the same rule, for the fifth time.

Check yourself

The filter is not in the query key. The user clicks “Done”. What goes out?

Measured: [ done=undefined ] and nothing else. React Query decides whether to fetch by looking at the key. Same key, same entry — and that entry is fresh for 30 seconds, so there is nothing to do. The queryFn did change, but nobody asked it anything. This is the failure that is hardest to debug, because there is no error, no network row, and no wrong data: the screen just does not react.

zod: what does z.coerce.boolean() make of the string "false"?

Measured: true. coerce means “run JavaScript’s Boolean() over it”, and every non-empty string is truthy. So ?done=false would filter for done tasks, and your “Open” button would show the finished ones. z.stringbool() is the parser that knows the words true/1/yes/on and false/0/no/off, and answers 400 to anything else. Coercion converts; parsing decides.

Now that filters exist, which write may still edit the cache by hand?

The delete. The reply’s freshness was never the question — the toggle’s PATCH hands back the whole new row, and it is still not enough. What you lose with filters is membership: whether the row still answers the question this list asks. Ticking done can move a row out of a ?done=false list, and only the server knows the new list. A delete has no such doubt: the row leaves every possible question at once, so setQueriesData can drop it from all of them and pay nothing.

Prefix invalidate: two filter entries cached, one on screen holding two pages. Requests?

Measured: 2, both for the key on screen, one per page held. Invalidating marks every matching entry stale — 2 of 2 — but it only refetches queries that something is currently watching. The unmounted entry stays stale and unfetched until the user goes back to it, and then it costs one request. This is the same distinction that fooled me while writing lesson 31: a measurement can be perfectly correct and be answering a different question than the one you asked.
