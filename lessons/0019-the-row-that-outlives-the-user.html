Lesson 19 · Week 7–8 · API security

Audit rows that survive deletion

Lesson 18 promised that the 429s would “land in the logs, so the attempt becomes visible”. Nothing writes them down. Today that becomes true.

In one minute

  • Your request log (logger: true) cannot answer “who deleted task 41?” An audit log is a table: one row per write and per refusal.
  • It goes in one onResponse hook — the only place that knows both who asked and what the answer was.
  • A 403 is the row you most want, and no handler ever runs to write it.
  • AuditLog is the one model with no relation to User. Cascade would delete the evidence.

The picture — why the hook, and why this hook

You have logs. Why a table?

Word pair for today. A request log is a text stream about the server: this URL, this status, this many milliseconds. An audit log is a table about a person: this human, this team, this action, this answer.

Request logAudit log
Knows whono — written before auth resolvesyes — request.userId
Queryablegrepwhere "userId" = 7
Keptdays, then rotatedas long as you decide

The code — one hook, three lines of decision

// src/audit/audit.ts — the decision
const SAFE_METHODS = new Set(["GET", "HEAD", "OPTIONS"]);
const REFUSALS = new Set([401, 403, 429]);

export function shouldAudit(method: string, status: number): boolean {
  return !SAFE_METHODS.has(method) || REFUSALS.has(status);
}

Every write, whatever the outcome. Plus every refusal, even on a read — a stranger walking /teams/1 to /teams/500 makes no writes at all, and that walk is only visible here.

And not every read. That is the cap, and it is deliberate:

And not every read. That is the cap, and it is deliberate. Log every request and you get 40 million rows a month, 99% of them “someone looked at a list” — a table so expensive and so useless that it gets truncated by March, leaving you with no audit log at all. Log writes and refusals and every row answers a question somebody actually asks.

A store keyed on caller input is a store the caller can fill. Cap it as you create it — lesson 11's rule, third use.

Two details that are the whole craft

1. Store the route pattern, never request.url. /teams/:teamId/tasks is one of a short fixed list. A URL is caller input: it can be 8 KB long, and it can carry a token somebody pasted into a query string. You would be writing an attacker's text into your evidence table.

route: request.routeOptions.url ?? "(no route)",   // the pattern
params: request.params,                            // the ids, separately

2. AuditLog has no @relation to User. Every other model in your schema cascades — delete the team, the tasks go. Here that is exactly wrong:

// prisma/schema.prisma
// Null = nobody was logged in. A 401 is a row worth having.
userId Int?     // ← a plain Int. No relation, so no cascade.

An audit row that vanishes with the person it accuses is not evidence.

What it looks like when it runs

Four requests, measured just now:

GET  tasks (read)        200   20.0 ms
POST task (write)        201   14.3 ms
POST task, no cookie     401    1.3 ms
POST task, wrong team    403   15.2 ms

rows: 3
userId  teamId    method  route                     status  params
911     249       POST    /teams/:teamId/tasks      201     {"teamId":249}
null    249       POST    /teams/:teamId/tasks      401     {"teamId":"249"}
911     999999    POST    /teams/:teamId/tasks      403     {"teamId":999999}

Three things to notice. The 200 wrote nothing. The 401 answered in 1.3 ms and still left a row — because onResponse runs after the reply is already on the wire, so the caller waits for none of it. And teamId is the string "249" on that row: the 401 was answered before zod ever coerced the URL. Params are raw strings until validation runs.

Check yourself

Why can a log line inside the handler not record a 403?

The gate replies and the request ends there. Anything written in the handler records only the requests that were allowed — which is the opposite of what an audit log is for.

Why does AuditLog.userId avoid a relation?

A foreign key with onDelete: Cascade would delete every audit row belonging to an account the moment that account is deleted. The rows about the worst behaviour are exactly the ones you would lose.

See it drawn

Three requests, three paths. Only one of them reaches the handler.

requireAuthcan()handleronResponse
stranger 401 → reply never runs never runs row
viewer userId = 42 403 → reply never runs row
owner userId = 7 MEMBER, allowed writes the task row

Read the handler column. It is empty on two of the three rows — and those two rows are the ones an audit log exists for. A console.log in the handler cannot record a refusal, because there is no handler to put it in.

A log line in a handler records only the requests that were allowed. That is the opposite of an audit log.

Why this hook and no other

The row needs two facts, and they are known at two different moments.

The one model that must not cascade

You have written onDelete: Cascade six times, and it was right six times. Delete the user, their rows go with them:

  • Sessiongoes — a ticket for a person who no longer exists
  • Membershipgoes — a role in a team for nobody
  • Task.ownerRESTRICT — the delete is refused while tasks exist
  • AuditLogstays — no relation at all
The instinct 
user   User @relation(
  fields: [userId],
  references: [id],
  onDelete: Cascade)
userId Int

Delete the account, and every row describing what that account did is deleted in the same statement. The worse the behaviour, the more certain the account gets deleted.

Correct 
// a plain Int.
// No relation, so no cascade.
userId Int?

It keeps pointing at an id that may no longer exist. Nullable as well — a 401 has no user at all, and that is still a row worth having.
