Lesson 04 · Week 1–2 · Database

Foreign keys and relations

Every task carries the text "jay@example.com". That is a sticky note, not an owner. Today a task points at a real row.

In one minute

  • A task should point at a user row, not at a copy of their email.
  • The pointer is a foreign key. Postgres refuses ids that do not exist.
  • One line — where: { ownerId } — is the first real security in this app.

The picture

The idea

A copied email goes stale. Change your address and every old task still says the old one. Worse, nothing stops a task from claiming an owner who does not exist.

A foreign key fixes both. The task holds a number. That number must name a real User row, or the write fails.

And now the security part. Once the database knows whose task it is, you can filter by it:

Everyone sees everything

prisma.task.findMany()

You see yours

prisma.task.findMany({
  where: { ownerId },
})
IDOR — Insecure Direct Object Reference. You ask for /tasks/5, task 5 is not yours, and the server hands it over anyway. Leaving out the where clause is how it happens.

The code

model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  tasks Task[]
}

model Task {
  id      Int    @id @default(autoincrement())
  title   String
  owner   User   @relation(fields: [ownerId], references: [id])
  ownerId Int
}

Store the pointer, not the copy. Then filter by the pointer, every single query.

Check yourself

You forget where: { ownerId } on one route. What happens?

Nothing errors. The route works perfectly and leaks everything. This is why lesson 7 moves the decision out of individual queries and into one place.

Do this

  1. Try to insert a task with ownerId: 999. Read the error Postgres gives you.
  2. Delete where: { ownerId } from list. Log in as user 2. See user 1's tasks. Put it back.
