Lesson 52 · Week 15–16 · Docker and deploy

The machine you can throw away

You parked Docker on 10 September and said you wanted it at the end. This is the end. Today your API runs inside a container — and the first two times it will not work, for two reasons that are both interesting. One is a single line in server.ts that has been correct for fifty lessons and is wrong the moment you put it in a box.

In one minute

  • An image is a file. A container is that file running. You build the image once, then start, stop and throw away containers all day.
  • HOST=127.0.0.1 inside a container means “only this container”. Your API will start, log “listening”, and refuse every request from outside. Nothing is broken. The word localhost just changed meaning.
  • localhost in DATABASE_URL has the same problem. Postgres is on your Mac, not in the box.
  • .dockerignore is the security step, not the speed step. Without it your .env — both database passwords — is copied into a file you can email to someone.
  • You already handle SIGTERM. Lesson-for-free: that is exactly the signal docker stop sends, and the shutdown you wrote in server.ts is why your pool closes cleanly.
  • Still no new dependency in the app. Docker is a tool, not an npm install.

Why a container at all

You have one honest answer and you should not accept a bigger one. Your API needs Node 22, a set of npm packages, a generated Prisma client and six environment variables. Today all of that lives on your Mac, arranged by hand over sixteen weeks. Fly.io and Render do not have your Mac.

A container is that arrangement written down as a recipe, so the same arrangement can be built anywhere. That is the whole idea. It is not about isolation, security or microservices — those are other people’s reasons.

Step 0: install it

No Homebrew needed — Docker Desktop is an ordinary .dmg. Download Docker.dmg (Apple Silicon), drag Docker into Applications, open it once and wait for the whale icon to stop animating. (If you do have Homebrew: brew install --cask docker fetches the same file.)

docker --version
docker run --rm hello-world

If hello-world prints a paragraph, you are done with setup. That command pulled an image from the internet, ran it as a container, and deleted the container when it exited (--rm). You have now done the whole lifecycle once.

The recipe

New file, server/Dockerfile. No extension. Read every line — there are only nine that do anything:

FROM node:22-slim
# Pinned, and "slim" not "latest". `latest` means "whatever they built this
# morning" -- your build would change without you changing anything.
# Your Mac runs 22.23.1, so the container runs 22 too.

WORKDIR /app

COPY package*.json ./
RUN npm ci
# These two lines come BEFORE copying your code, on purpose. See below.

COPY . .

RUN npx prisma generate
# src/generated/prisma is not in git and not in the image. db.ts imports it,
# so without this line the container starts and crashes on the first import.

# Documentation only. It publishes nothing -- `-p` does that.
EXPOSE 3000

CMD ["npm", "start"]

The two lines before COPY . .

Docker builds an image as a stack of layers, one per instruction, and it reuses a layer when nothing that feeds it has changed. npm ci takes about a minute. If you copy your source code first, then every edit to a .ts file invalidates the install layer and you wait a minute for every rebuild.

Copying package*.json alone means the install layer is reused until you actually add a package. This is the one Docker idiom worth memorising, and it is the reason nearly every Node Dockerfile you will ever read has that odd double copy.

Order the recipe from the thing that changes least to the thing that changes most. Dependencies change monthly, your code changes hourly.

No build step, and that is honest

Your npm start is tsx src/server.ts. tsx runs TypeScript directly, so there is nothing to compile and no second stage. Most Node Dockerfiles you will find online have a builder stage and a runtime stage; yours does not need one because you never produce a dist/. Do not add a stage to look professional.

The file that keeps your passwords out

COPY . . means everything. That includes .env, which holds both Postgres passwords, and node_modules, which was built for macOS and is useless in Linux. New file, server/.dockerignore:

node_modules
.env
.env.*
!.env.example
src/generated
*.log
.git

Say this part out loud, because it is the one thing in today’s lesson that can actually hurt you: an image is a file you hand to other people. You push it to a registry, a CI server pulls it, a colleague runs it. Anyone holding it can read every file inside it — there is no such thing as a private file in an image.

# this is all it takes to read a secret out of somebody's image
docker run --rm my-api cat /app/.env

A secret never goes in the image. It is handed to the container at start time. That is what --env-file below is doing, and it is why config.ts from lesson 27 already reads the environment rather than a file it insists on.

Now build it and watch it fail twice

cd server
docker build -t tasks-api .
docker run --rm -p 3000:3000 --env-file .env tasks-api

-p 3000:3000 reads host port : container port. Without it the container’s 3000 is not reachable from your Mac at all.

Failure one: it says it is listening, and it is not there

{"level":30,"msg":"Server listening at http://127.0.0.1:3000"}

# other terminal
curl http://localhost:3000/health
curl: (52) Empty reply from server

Nothing crashed. Open src/server.ts and read the comment you wrote:

// ! Default host is loopback on purpose. In deploy/nginx.conf nginx is the
// ! only thing that may reach this port; binding 0.0.0.0 puts the API on the
// ! public internet with no TLS in front of it.
await app.listen({ port: Number(config.PORT), host: config.HOST });

That reasoning was right and is still right — on a machine. A bind address of 127.0.0.1 means “accept connections that came from this machine only”. Inside a container, “this machine” is the container. Your Mac is now the outside world, and so is nginx if it is in a second container.

The fix is one line in the .env you pass in, not in your code:

HOST=0.0.0.0

And the security argument survives intact, which is the part worth understanding. 0.0.0.0 inside a container does not mean “on the internet”. It means “anything that can reach this container’s network” — and the only thing that can is what you publish with -p. The boundary moved from the bind address to the port publish. Change where the wall is, not whether there is one.

Failure two: it cannot find Postgres

Error: connect ECONNREFUSED 127.0.0.1:5432

Exactly the same mistake in a different costume. Your DATABASE_URL says @localhost:5432, and there is no Postgres inside the box. For today, point it at the Mac:

# server/.env.docker -- a second env file, for container runs only
DATABASE_URL=postgres://tasks:...@host.docker.internal:5432/tasks
APP_DATABASE_URL=postgres://tasks_app:...@host.docker.internal:5432/tasks
NODE_ENV=development
ALLOWED_ORIGINS=http://localhost:5173
TRUST_PROXY=false
HOST=0.0.0.0

Add .env.docker to .dockerignore’s .env.* line — it is already covered. Then:

docker run --rm -p 3000:3000 --env-file .env.docker tasks-api
curl http://localhost:3000/health   # {"status":"ok"}

Your API is running on a Linux machine that did not exist five minutes ago, talking to the Postgres on your Mac. host.docker.internal is a Docker Desktop convenience and will not exist on Fly.io — there, Postgres gets its own name. That is next lesson.

The part you already built

Press Ctrl-C. Watch the log. docker stop sends SIGTERM, and your server.ts has caught SIGTERM since the day you wrote it — so the app stops accepting, finishes what is in flight, and hands the Postgres pool back. Most first Dockerfiles get killed after ten seconds instead. Yours does not, and you did not do anything today to earn it.

Why does HOST=127.0.0.1 break inside a container?

A bind address of 127.0.0.1 accepts connections originating on the same machine. The container is its own machine, so your Mac — and any other container — is outside it. Nothing is broken; the word local points somewhere new.

Why must .env be listed in .dockerignore?

An image is a file that gets pushed, pulled and shared. Every file copied into it is readable by anyone who can run it: docker run my-api cat /app/.env. Secrets are handed to the container at start time with --env-file, so they live on the host that starts it and nowhere else.

Why is npm ci above COPY . . and not below it?

Each instruction is a cached layer, and editing any copied file invalidates that layer and everything after it. Copying only package*.json before installing means the slow install is reused on every rebuild until you actually change a dependency. Least-changing first.

See it drawn

The same word, localhost, pointing at two different machines. That is both of today’s failures.

What you did not build, on purpose

left out
Postgres in Docker next lesson, with compose. One command to start both, and a real network name instead of host.docker.internal.
a non-root user a real hardening step, and it belongs with deploy, not with your first build.
the front end a static build behind the nginx config already sitting in deploy/. Its own lesson.
multi-stage build you have no compile step. Adding a stage that copies nothing is cargo cult.

Read this: Docker — Containerize a Node.js application. The official guide, and short. It generates a fancier Dockerfile than yours; read it to see which parts you genuinely do not need.
