The shape of the change

Here is the whole thing. Three files, twelve lines.

// .env
DATABASE_URL="postgres://tasks:tasks@localhost:5432/tasks"
APP_DATABASE_URL="postgres://tasks_app:tasks_app@localhost:5432/tasks"

// src/config.ts
  DATABASE_URL: z.url(),
  APP_DATABASE_URL: z.url(),

// src/db.ts
const connectionString =
  config.NODE_ENV === "test" ? config.DATABASE_URL : config.APP_DATABASE_URL;
const adapter = new PrismaPg({ connectionString });

// package.json
"test": "NODE_ENV=test LOG_LEVEL=silent tsx --test \"src/**/*.test.ts\""

Read the ternary again. It is the one design decision in this lesson, and it is worth a sentence: the login is chosen by the job, not by the file. Serving a request is one job. Running the test suite is a different job. They are allowed different powers.

connection string — the URL that says which login, which password, which host and which database. postgres://user:password@host:port/database.

Why tests keep the owner

Lesson 41 measured this: five lines in your tests call prisma.auditLog.deleteMany to tidy up, and zero route handlers do. If tests ran as tasks_app, those five cleanups would fail with 42501 and you would rewrite them for no gain.

JobLoginWhy
npm run dev / npm starttasks_appthis is the one the internet can reach
npx prisma migrate devtasksCREATE and ALTER belong to the owner
npm testtaskscleanup deletes audit rows; a test is not a web request

A rule worth keeping: least privilege applies to the exposed path, not to your terminal. Locking down your own laptop commands buys nothing and costs you an hour a week. Lock down the thing a stranger can send bytes to.

The one thing I was not sure would work

The test script now sets NODE_ENV=test in the shell. But src/config.ts calls process.loadEnvFile(), and your .env file says NODE_ENV=development. Which one wins? I did not know, so I checked instead of guessing:

printf 'FOO=fromfile\n' > .env
FOO=fromshell node -e 'process.loadEnvFile(); console.log(process.env.FOO)'
fromshell

The shell wins. loadEnvFile() fills in variables that are missing; it never overwrites one that is already there. This is also why LOG_LEVEL=silent in your test script has been working since lesson 6 — you just never had a reason to ask why.

The test that proves the refusal

A privilege with no test is a rule nobody enforces. New file, src/db.test.ts. It is the first test file in this project that does not import prisma, and the reason is the whole point:

// tests run as the OWNER, so the shared client would prove nothing
const client = new pg.Client({ connectionString: config.APP_DATABASE_URL });

It opens one connection as the restricted login and asks the database four questions. pg is already a dependency — Prisma's adapter uses it — so nothing new was installed.

TestExpectedGot
INSERT an audit rowallowedid returned, then ROLLBACK
SELECT count from the logallowed6,664
DELETE / UPDATE / TRUNCATE the logrefused42501 × 3
CREATE TABLErefused42501
42501 — the Postgres error code for “insufficient privilege”. The test asserts this code, never the English message. A message is text that can change between versions; a code is a contract.

Two details in that file are deliberate, and both are habits worth copying. The INSERT test wraps itself in BEGIN / ROLLBACK, because a test that protects the audit log must not leave a row in it. And the refusal helper returns the error instead of using assert.rejects, so the assertion can be about the code and nothing else.

I checked that the new test can fail

Same check you did in lesson 41, step 0, and it is now the standard for every test I hand you. I changed one word in src/db.test.ts — APP_DATABASE_URL to DATABASE_URL, so the test connects as the owner instead:

Hint versus gate — I have asked three times, so here it is

You have skipped this homework three times, so I will teach it instead, using today's code where it is easiest to see.

HintGate
What it doestells someone what is allowedmakes the other thing impossible
Who obeys itwhoever reads it and agreeseveryone, including a bug
Today's examplethe line in server/CLAUDE.md: “never delete audit rows”REVOKE DELETE in the database
Earlier examplea greyed-out Delete button in the UIrequirePermission("task:delete") on the route

Hints are not useless. A greyed-out button is kind, and a comment is how the next person learns the reason. But a hint is advice and a gate is physics. Every hint needs a gate behind it, and the gate belongs as far down the stack as you can push it — UI, then route, then database. Today you pushed one all the way down.

Check yourself

Why does npm test still use the owner login?

Five lines in your tests call prisma.auditLog.deleteMany to tidy up after themselves. The app role is not allowed to do that, on purpose. Tests run from your terminal, not from the internet, so they keep the owner. Prisma connects as any role you give it — src/db.test.ts proves that.

What happens when tasks_app tries to grant itself DELETE?

Measured on your database: WARNING: no privileges were granted for "AuditLog". Not an error. A role can only grant what it owns or holds, and tasks_app owns nothing. This is the hole lesson 41 found with the owner role, and this is why a second role closes it.
