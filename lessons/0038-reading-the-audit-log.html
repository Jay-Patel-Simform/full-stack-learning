Reading the audit log

For twenty lessons the audit log has only been written to. Today it gets a reader: GET /teams/:teamId/audit. Two things make this route different from every list route you have built. First, looking is a power of its own — a MEMBER may delete a task and still have no business seeing who else deleted what. Second, the route audits itself: I built it, ran it, and the row count came back one higher than I seeded. That extra row is the refused read.

In one minute

  • Reading is an action. "audit:read" is a new entry in ACTIONS, granted to ADMIN and OWNER. Not a new if anywhere.
  • Doing ≠ seeing. A MEMBER holds task:delete and does not hold audit:read. The two powers are unrelated, so they are two rows in the table.
  • The writer picked the reader's filters. Lesson 18 wrote @@index([teamId, at]). That index is exactly “one team, newest first”, and that is the query you are allowed to write cheaply.
  • Order by at DESC, id DESC. at is not unique. A cursor into a tied order skips rows. id is the tiebreak.
  • The response schema is the allowlist again. ip, params and targetSnapshot are not in AuditPublic, so they never reach the browser.
  • One trap I hit for you: z.iso.datetime() on the at field is a 500. Your serializer parses before it stringifies, and Prisma hands you a real Date. Use z.date().

The question the route answers

Not “show me the log”. That is not a question a database can answer well. The real question is the one your index was built for:

What the index serves

@@index([teamId, at])

where:   { teamId }
orderBy: [{ at: "desc" }, { id: "desc" }]
take:    limit + 1

One team. Newest first. A page at a time. Postgres walks the index backwards and stops.

What it does not serve

where: { route: { contains: "tasks" } }
where: { actorEmail: "..." }
orderBy: { status: "asc" }

No index starts with those columns, so each one is a full scan of the biggest table you own. Fine at 7,400 rows. Not fine at 7 million.

The filters a list route may offer are decided by the indexes that already exist. A query builder that accepts anything is a promise the table cannot keep.

So today's route takes exactly three query keys: limit, cursor, and status. status is the one extra, and it is honest — it is a cheap filter on top of a range the index already narrowed to one team. Everything else waits for an index that justifies it. Use The Index, Luke — concatenated keys is the short, exact explanation of why the column order in [teamId, at] is the whole story.

A power you have not named yet

Open src/auth/can.ts and read the action list aloud. Every entry is something a person does: create, update, delete, invite, remove. Not one of them is something a person sees.

That is the gap. The rule you want is:

A MEMBER may delete a task.
A MEMBER may not see that somebody else deleted a task.

Count the nouns, the way you did in lessons 9 and 10. There are two different powers in those two lines, so there must be two entries in the table. Writing this as if (role === "ADMIN") inside the handler would be the fourth time you avoided the table, and the table is the only place that can be audited itself.

Why ADMIN and not OWNER only. An audit log nobody reads is decoration. The people who investigate an incident are the people who run the team day to day. OWNER-only sounds safer and in practice means the log is never opened. OWASP's logging cheat sheet is blunt about this: logs exist to be monitored, and an unmonitored log is a cost with no benefit.

The self-audit

Here is the thing I did not plan for. I seeded 25 rows into a test team, then wrote this test first:

test("a MEMBER may delete a task but may not read the log", async () => {
  const res = await list("", memberCookie);
  assert.equal(res.statusCode, 403);
});

Then the next test asked for all the rows and asserted 25. It got 26.

The 403 above is a refusal, and shouldAudit() has said since lesson 18 that every refusal earns a row. So the refused read wrote itself into the very log it was refused. The newest row in that team is now:

{ "route": "/teams/:teamId/audit", "status": 403, "method": "GET",
  "actorEmail": "audit-member-...@example.com" }

Somebody trying to read the log is the single most interesting line in the log. You did not write a rule for that. The rule you wrote in lesson 18 — “every refusal, even on a read” — already covered a route that did not exist yet.

That is what a cross-cutting hook buys you, and it is lesson 18 paying a dividend. A per-handler audit call could not have logged this, because no handler ever ran.

The trap in the reply schema

I wrote at: z.iso.datetime(), which is the obviously correct thing, and got a 500 on every request. Your own serializer, from src/app.ts:

app.setSerializerCompiler(({ schema }) => (data) => JSON.stringify((schema as ZodType).parse(data)));

It parses, then stringifies. Prisma gives you a JavaScript Date. A Date is not a string, so zod throws, and your error handler turns a thrown error into a 500 with a requestId. The fix is one word:

at: z.date(),   // ? JSON.stringify turns it into the same ISO text anyway

This is a small thing with a general shape worth keeping: a response schema describes the value your handler returns, not the JSON the caller receives. Those two are not the same object, and Date is where they first disagree.

Check yourself

Why is audit:read a new action rather than a role check?

Deleting a task and seeing who deleted it are two unrelated jobs, so they are two entries in the table. A role check in the handler puts a permission somewhere that can.ts cannot see, which is the one thing lesson 7 forbade.

Why does the order need id DESC after at DESC?

at is not unique. Two rows written in the same millisecond tie, Postgres may return ties in any order, and a cursor into an unstable order skips or repeats rows. id is unique, so it breaks every tie. Same rule you learned for ?sort=title.

A MEMBER is refused at GET /teams/3/audit. What happens?

shouldAudit() returns true for 401, 403 and 429 even on a GET. The refusal is written by the onResponse hook in app.ts, long after the gate said no and without any handler running. An attempted read of the log is exactly the row you want most.

See it drawn

One index. The page it serves. And the row that wrote itself when somebody was told no.

The index is the shape of the page

@@index([teamId, at]) — Postgres walks it backwards and stops
teamId at -> id
......
7 2026-09-11 09:14:02 7433 <- page 1 starts here (newest)
7 2026-09-11 09:13:58 7431
7 2026-09-11 09:13:58 7430 <- same millisecond: id breaks the tie
7 2026-09-11 09:11:40 7428 <- limit=4, so stop. nextCursor = 7428
7 2026-09-11 09:02:19 7425 <- read anyway (take: limit+1) to answer "is there more?"
8 2026-09-11 09:14:44 7434 <- another team. Never reached.

The query is not clever. It is the index, read in order, from one end. That is the whole reason it stays fast at seven million rows.

A filter the index serves

where: { teamId: 7 }
order: at desc, id desc
4 rows read

A filter it does not

where: { actorEmail: "x@y" }
order: at desc
7,433 rows read

Two powers, two entries

src/auth/can.ts — the only place this is decided
role task:delete audit:read
VIEWER no no
MEMBER yes no <- may do it, may not see who did it
ADMIN yes yes
OWNER yes yes
