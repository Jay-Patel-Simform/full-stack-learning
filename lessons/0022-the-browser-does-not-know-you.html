Lesson 22 · Week 9 · Front end

Auth state in the browser

Twenty-one lessons of server. Today the first page. And the very first thing it does is discover that it cannot answer the only question it needs answered.

In one minute

  • You made the session cookie HttpOnly in lesson 6. So document.cookie is empty.
  • There is no isLoggedIn variable to read. “Logged in” is not a fact the page holds — it is a question the page asks.
  • So the app boots into three states, not two: unknown → in or out.
  • A cross-origin request sends no cookie unless you ask: withCredentials: true on the axios instance.
  • One axios interceptor handles the 401, because a session can die while the tab is open.

The word pair

a fact you hold — something in the page's own memory. A theme, a draft, an open tab. Read it, trust it, render it. Costs nothing.
a question you ask — something only the server can answer. Who you are. What you may do. Costs a round trip, and can change its answer at any moment.

Auth is the second kind. Every design mistake in front-end auth is treating it like the first.

Measured, in real Chrome, this morning

                 httpOnly: true, sameSite: "Lax", secure: false }

withCredentials: false → 401      withCredentials: true → 200

Chrome has the cookie and Chrome sends it. Your JavaScript cannot see it. That is not a limitation to work around — it is the feature you asked for. An XSS bug cannot steal a session it cannot read.

The two 401/200 lines are the same URL, same tab, same logged-in user. The only difference is one option. Browsers default to no credentials across origins — fetch calls it credentials: "same-origin", axios calls it withCredentials: false — and :5173 is not the same origin as :3000. Forget it and your app looks logged out while the cookie sits in the jar. This is the single most common bug in this week's work.

And the reload survived two different ports. That is lesson 13, now visible instead of tabular. SameSite=Lax counts the site and a site ignores the port, so the cookie is sent. CORS counts the origin and a port makes a new one, so credentials is needed. Both true, about the same two URLs. That is why the pair exists.

Three states, not two

Boot into out and every reload flashes a login form at someone already signed in. Boot into in and you render an app for someone who is not. unknown deserves real markup.

Where the 401 lives

The app is React + Vite + Tailwind + shadcn/ui, with React Query holding the server state and axios doing the talking. Two pieces carry this whole lesson.

One. src/lib/api.ts — the axios instance, and the option that decides everything:

export const api = axios.create({
  baseURL: import.meta.env.VITE_API_URL ?? "http://localhost:3000",
  withCredentials: true,   <-- the whole lesson
  headers: { "content-type": "application/json" },
});

Two small things came in with it. The origin is VITE_API_URL with the dev port as a fallback, because lesson 14 says production is same-origin — the value that changes between dev and nginx belongs in the environment, not in the source. And content-type: application/json is set once here rather than at each call site, which is the same “one place” move as the interceptor below.

Two. src/features/auth/session.ts — the boot question, as a query:

async function getSession(): Promise<User | null> {
  try {
    return (await api.get<User>("/auth/me")).data;
  } catch (error) {
    // A 401 here is an ANSWER, not a failure.
    if (error.response?.status === 401) return null;
    throw error;
  }
}

export function useSession() {
  const { data: user, isPending } = useQuery({
    queryKey: SESSION_KEY, queryFn: getSession, staleTime: 0,
  });
  return { user, isPending, signedIn: user != null };
}

Turning the 401 into null instead of an error is what makes the three states fall out for free. undefined is asking, null is out, a user is in. One line in App.tsx reads them:

{isPending ? <Asking /> : user != null ? <SignedInCard user={user} /> : <LoginForm />}

No useState mirroring the session, and no useEffect anywhere in the app. React Query is the state.

The 401 that arrives later

A session row can die while the tab sits idle. So one axios interceptor owns that case, for every request the app will ever make:

const CREDENTIAL_ROUTES = new Set(["/auth/login", "/auth/register"]);

api.interceptors.response.use(undefined, (error: AxiosError) => {
  const url = error.config?.url;
  if (error.response?.status === 401 &&
      url !== undefined && !CREDENTIAL_ROUTES.has(url))
    queryClient.setQueryData(SESSION_KEY, null);
  return Promise.reject(error);
});

The url !== undefined is not ceremony. error.config?.url is optional, and a Set asked about undefined answers false — so a 401 from a request with no recorded URL would take the “session gone” branch by accident. Name the unknown case instead of letting a falsy value decide.

One place sees the 401. Same rule as lesson 19's audit hook and lesson 7's can(): a rule with no exceptions does not belong in each caller. Third time now — it is a rule, not a coincidence.

And CREDENTIAL_ROUTES is the deliberate exception — both credential routes, because the same status means two things:

A 401 frommeansso show
any ordinary requestyour session is gonethe form, silently
/auth/login, /auth/registerthese credentials are wrongthe form, with the error

Route login through the generic handler and the user gets an empty form and no idea why.

Measured: the session that died elsewhere

I signed in, then deleted every Session row straight out of Postgres, then just gave the tab focus — no reload, no click:

deleted every Session row server-side. cookie still in the jar.
document.cookie is still:  ""
after a focus poke:        state: out   ← login form, by itself

That is React Query re-asking on window focus. It only works because useSession sets staleTime: 0: with the 30-second default I first wrote, this tab showed a signed-in UI for half a minute after the session was destroyed. Auth is the one query with no grace period.

A correction to the plan

PLAN.md promised “token refresh on 401” this week. There is nothing to refresh. You chose server-side sessions over JWTs in lesson 6, and readSession() already pushes the expiry out to thirty days whenever half the life is gone. The refresh happens in Postgres, and the front end never hears about it.

A good server decision shows up later as front-end code you never write.

Check yourself

Why can the page not just read the cookie and skip the request?

HttpOnly is your own flag from lesson 6: the browser stores and sends the cookie, but document.cookie never shows it. That is what stops an XSS bug stealing a session. The cost is that the page must ask the server instead — a cost worth paying.

A user sits on the page for an hour, then clicks. A 401 comes back. Why?

Logging out in another tab, an admin ending sessions, expiry — all delete the row, and the cookie in the jar is unchanged. Nothing in the browser can detect it. That is why the axios interceptor handles a 401 on every response and not only at boot.

Why does the session query set staleTime: 0?

React Query only revalidates on focus if it thinks the answer is stale. With the 30-second default, a session destroyed elsewhere left this tab rendering a signed-in UI for half a minute — measured, on your app. Auth is the one query with no grace period.

Most front ends have two states because they read a token from localStorage. Yours has three because it asks. Three is the honest number.

2. Two ports, looked at twice

The same two URLs. Two different rules read them, and each reaches a different answer.

CORS asks: same ORIGIN?

http://localhost:5173
http://localhost:3000

No. A port makes a new origin.

→ the reply needs Access-Control-Allow-Origin, and the request needs withCredentials: true (axios) or no cookie is sent at all.

SameSite asks: same SITE?

http://localhost:5173
http://localhost:3000

Yes. A site ignores the port.

→ SameSite=Lax is satisfied, so the browser is willing to send the cookie — if you asked it to.

Both boxes are true at the same time. withCredentials: true is you satisfying the left box; SameSite=Lax already satisfied the right one.
