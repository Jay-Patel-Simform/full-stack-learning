Lesson 07 · Week 5–6 · RBAC

Deny-by-default permissions

Your API knows who is asking. It does not know what they may do. Today you build the one function that decides.

In one minute

  • Gate 1 asks who are you (401). Gate 2 asks may you (403). You only have gate 1.
  • Do not scatter if (role === "ADMIN") through forty routes.
  • Put the decision in one plain function: can(role, action).
  • Roles are data (rows). Permissions are code (a file in git).

The picture

The idea

The obvious version puts the check where the work happens:

Scattered

// in every handler, forever
if (user.role !== "ADMIN") {
  return reply.code(403).send(...);
}
// ...forty routes later, one of
// them does not have this line

One place

// src/auth/can.ts — the whole policy
export function can(role, action) {
  return PERMS[role]?.includes(action) ?? false;
}

The scattered version is not wrong on any single line. It is wrong because it is forty chances to forget. One table in one file can be read top to bottom and reviewed by a person.

roles are data — who is an admin changes at runtime, by users clicking. That belongs in Postgres.
permissions are code — what an admin may do changes when you ship. That belongs in git, with a diff and a review.

The code

// src/auth/can.ts
export const ROLES = ["VIEWER", "MEMBER", "ADMIN", "OWNER"] as const;

const PERMS: Record<Role, readonly Action[]> = {
  VIEWER: ["task:read"],
  MEMBER: ["task:read", "task:create", "task:update"],
  ADMIN:  [...MEMBER, "task:delete", "member:invite", "member:remove"],
  OWNER:  [...ADMIN, "team:delete"],
};

export function can(role: string, action: Action): boolean {
  return PERMS[role as Role]?.includes(action) ?? false;  // unknown role -> no
}

?? false is the important character. A role you have never heard of gets no, not a crash.

Deny by default. Then a bug is a missing permission, never an accidental one.

Check yourself

Why do permissions live in code, not in a database table?

Speed is irrelevant here. The point is process: adding team:delete to MEMBER should show up in a pull request, not in somebody's afternoon of clicking in an admin panel.

Do this

  1. npm test. Ten tests, no database — can() is a pure function, so it needs none.
  2. Write the test from MISSION.md: can("VIEWER", "task:update") is false.
  3. Call can("ADMINN", "task:read"). It must be false, not an exception.
