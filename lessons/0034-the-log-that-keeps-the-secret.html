Log redaction

You already have a logger. You have had one since lesson 1, and you wrote one log line by hand in lesson 21: request.log.error({ err }, "unhandled error"). It is a good line. I measured what it prints, and it printed a password hash and a full SQL string. Not because you wrote them — because err carries whatever anyone attached to it, and a log line prints the whole object. Your 154 tests cannot see this. They run with the log turned off.

In one minute

  • A log line is an output channel, exactly like a reply. You already know this rule from lesson 30: the response schema guards the wire, not the query. The log is a second wire, and nothing guards it.
  • Measured: { err } prints everything hanging off the error. One line in your app today, and err.user.passwordHash went to stdout in full. A stack trace is the part you wanted; the rest came along.
  • The real rule: log the fields you chose, never a whole object. { userId: user.id }, not { user }. That is an allowlist — you name what may go out.
  • Redaction is the net, not the plan. redact is a denylist — a list of paths you predicted. I applied one. Keep both.
  • Trap, measured: redact paths count levels. *.passwordHash caught user.passwordHash and missed err.user.passwordHash, one level deeper. And **.passwordHash matches nothing at all — no error, no warning, the value prints in full.
  • A log line has no failing state. Nothing turns red when it leaks. So the log gets a stream, and the test reads it.

First: what your log already says

Show the thing before explaining it. This is one request through your app, as Fastify writes it. Three lines, one request:

{"level":30,"time":1789100853784,"pid":8888,"hostname":"sf-cpu-565",
 "reqId":"req-1","req":{"method":"POST","url":"/login",
 "host":"localhost:80","remoteAddress":"127.0.0.1"},"msg":"incoming request"}

{"level":50,...,"reqId":"req-1","err":{...},"msg":"unhandled error"}

{"level":30,...,"reqId":"req-1","res":{"statusCode":500},
 "responseTime":8.15,"msg":"request completed"}

Three things worth naming, because you will use all three.

1. It is JSON, not a sentence. That is what structured logging means — every line is an object with named fields, so a machine can filter it. console.log("user " + id + " failed") is a sentence: to find all the failures for user 7 you need a regular expression. With fields you ask for userId=7. This is the whole reason the library exists, and it is why every deploy platform can search these lines and cannot search yours.

2. level is a number, and it is a dial. 30 is info, 50 is error. Your config.LOG_LEVEL sets the floor: at error the first and third lines vanish and the middle one stays. This is why npm test can run LOG_LEVEL=silent and stay quiet. Remember that fact — it comes back in ten minutes and it is a trap.

3. reqId is the thread. Every line from one request carries the same id, and lesson 21 already puts that id in the 500 reply. So a user reporting “error req-42” hands you a search term that finds every line of their request. You built that. You may not have noticed it working.

Now the bug: { err } is not one field

Here is the line you wrote, in src/app.ts, unchanged since lesson 21:

request.log.error({ err }, "unhandled error");

It looks like it logs an error. It logs an object called err, with every property that object happens to have. Errors in a real app collect properties: Prisma attaches meta, a database driver attaches the failing statement, and your own code attaches whatever was in scope. I built exactly that shape and ran it through your error handler. Measured, before today’s change:

{"level":50,"reqId":"req-1","err":{
  "type":"Error","message":"db down",
  "stack":"Error: db down\n    at Object.<anonymous> ...",
  "user":{"id":7,"email":"jay@example.com",
          "passwordHash":"scrypt$AAAA$BBBB"},
  "query":"SELECT * FROM User WHERE email = 'jay@example.com'"
},"msg":"unhandled error"}

Nothing failed. The request returned its polite 500 with only a request id in it — lesson 21 is still doing its job perfectly on the reply side. And at the same moment the hash went to stdout, which in a deploy means a log file, a log search tool, and a backup of both. Lesson 21 split the audience into “the caller” and “us”. Today’s lesson is that “us” is bigger than you think.

Who reads a log. Not just you. The platform that stores it, everyone with access to that platform, the error tracker you will add in week 13, and whoever gets a copy of a backup. A secret in a log is a secret you have handed to a list of people you did not write down. This is why OWASP treats it as its own failure class, not as a tidiness issue.

Two fixes, and only one of them is the plan

The plan: choose the fields

The fix that always works is the one you already apply to replies. In lesson 30 you learned that TaskPublic guards the wire: the reply contains the fields you named, and a field you never named cannot escape. Do the same at every log call:

Pass the object

req.log.info({ user }, "signed in");

Whatever user holds today, and whatever someone adds to it next year, goes to the log. You will not notice, because nothing fails.

Choose the fields

req.log.info({ userId: user.id }, "signed in");

Two fields can never become three by accident. A new column on User changes nothing here.

That is an allowlist: a list of what is permitted, and everything else is refused by default. It is the same shape as the response schema, the same shape as strict() on your zod bodies, and the same sentence you have heard since lesson 3 — make the safe thing the default and the unsafe thing deliberate.

The net: redaction

An allowlist at every call site is a rule about human behaviour, and humans debug at midnight. So there is a second layer, and I applied it. pino takes a list of paths and replaces those values before writing. In src/app.ts:

export const REDACT_PATHS = [
  "*.password",
  "*.passwordHash",
  "err.user.password",
  "err.user.passwordHash",
  "req.headers.cookie",
  "req.headers.authorization",
];

const app = Fastify({
  logger: {
    level: ...,
    redact: REDACT_PATHS,
  },
  ...
});

Measured against your real buildApp, after the change — same three log lines as before:

"user":{"id":7,"email":"jay@example.com","passwordHash":"[Redacted]"}
"err":{"message":"db down", ... "user":{... "passwordHash":"[Redacted]"}}
"body":{"email":"a@b.c","password":"[Redacted]"}

leaks "scrypt$SALT$HASH"?  false
leaks "hunter2"?           false

Note that the key stays. You can still see that a passwordHash field was there, which is useful when reading a log, and the value is gone. (remove: true deletes the key as well; I did not use it, because “this field existed” is information worth keeping.)

And now the trap, which is the real lesson

A redact path is an exact path counted from the root of the line, and the wildcard is one level. I measured three paths against the same error object:

the line:   { err: { message, user: { passwordHash: "SEKRET" } } }

redact "user.passwordHash"       -> misses.  it is at err.user, not user
redact "*.passwordHash"          -> misses.  one level; this is two
redact "err.*.passwordHash"      -> catches
redact "err.user.passwordHash"   -> catches
redact "**.passwordHash"         -> misses, and does not complain

Read that last line again. ** is not pino’s syntax. It does not throw. It does not warn. It is accepted, it matches nothing, and the hash prints in full — and the config looks more thorough than the version that works. That is the third time in six lessons you have met this exact shape:

  • lesson 29 — dead code has no failing state (six leftovers, 141 tests green with and without them),
  • lesson 33 — a filter missing from the key sends zero requests (no error, no network row),
  • today — a redact path that matches nothing is silence.

This is why the denylist is the net and not the plan. A denylist is a list of things you predicted, written in a syntax that fails quietly. The allowlist at the call site does not need you to predict anything.

How do you test a log line?

You cannot assert on something you never read, and pino writes to stdout. So buildApp now takes an optional stream:

export async function buildApp(logStream?: NodeJS.WritableStream) {
  const app = Fastify({
    logger: {
      level: logStream === undefined ? config.LOG_LEVEL : "info",
      redact: REDACT_PATHS,
      ...(logStream !== undefined && { stream: logStream }),
    },

Three small decisions in there, all of them the point:

The level flips. npm test runs LOG_LEVEL=silent — that is why 154 tests are quiet. A test that wants to read the log would read nothing, pass, and prove nothing. Passing a stream means “I intend to read this”, so the level goes back up. A green test that cannot fail is worse than no test.

The spread is load-bearing, again. stream: logStream does not compile. exactOptionalPropertyTypes refused it with TS2769 — the same flag, and the same shape, as the where clause one lesson ago. Absent and present-but-undefined are different things, and the flag makes you say which. Second time in two lessons that a config flag you never chose caught a real mistake of mine.

Nineteen files call buildApp() with no arguments. An optional parameter changed none of them. 154 tests, still 154.

Check yourself

Your error handler logs { err }. What reaches the log file?

Everything. Measured on your own handler: err.user.passwordHash and a full SQL string, next to the stack you wanted. An error is an ordinary object, and libraries decorate it — Prisma adds meta, drivers add the statement, your code adds what was in scope. Logging a whole object logs its future contents too, and nothing will ever turn red to tell you.

A redact path uses a syntax pino does not support. What happens?

Nothing. Measured: "**.passwordHash" is accepted, matches nothing, and the hash goes to stdout in full — while the config reads as if it were stricter than the version that works. Same family as lesson 29’s dead code and lesson 33’s missing filter: the dangerous bugs in this course are the ones with no failing state. A denylist you cannot test is a hope.

Which is the plan, and which is the net?

Choosing the fields is the plan. { userId: user.id } cannot leak a column added next year, because you named what goes out — the same allowlist shape as TaskPublic in lesson 30 and strict() on your bodies in lesson 3. Redaction is a denylist of paths you predicted, in a syntax that fails silently. Keep it, because people debug at midnight, but never let it be the only layer.

Why does buildApp raise the log level when you hand it a stream?

npm test sets LOG_LEVEL=silent so 154 tests stay quiet. A redaction test under that level reads an empty stream, asserts “the password is not here”, and passes — forever, including on the day redaction breaks. Passing a stream is the signal that you intend to read the log, so the level goes back up. Exercise 3 makes you watch that failure happen.
