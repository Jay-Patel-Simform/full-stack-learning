Lesson 36 · Week 11 · Real world

Audit logs store copies, not pointers

You answered the lesson-34 question yourself, and you went past it: AuditLog.userId must not be a foreign key, because a cascade deletes the evidence with the account. You were right. Today I ran the query that proves it, and then the second query, which is the one that hurts: 72 of your audit rows point at a task that no longer exists, and not one of them can tell you what that task was. Today you fix that in a migration, before the page that reads it exists.

In one minute

  • Measured on your database: 3,428 of 7,201 audit rows have a userId that is gone. The rows survived. That is your no-foreign-key rule already paying.
  • And 72 rows are a successful task delete whose task is gone. The row says DELETE ... 204, {"id": 72493}. It cannot say the title, the team or who owned it.
  • An id is a pointer. A pointer into a deleted row is nothing. An audit log must store copies, not pointers.
  • The word is a snapshot — the values as they were at that moment, written into the audit row itself.
  • The trap is timing, not schema. Your audit hook runs onResponse. By then the handler has already deleted the task. The hook cannot read what it needs to copy.
  • So the capture moves earlier and the write stays where it is. Four new columns, one migration, one decorator, three lines in the delete route.

A pointer and a copy

snapshot — a copy of some values, written down at one moment and never updated again. It shows the past, not the present.

Every column in your AuditLog today is either a fact of the request (method, route, status, ip, time) or a pointer to another table (userId, teamId, params.id). Pointers are cheap and always current — which is exactly what is wrong with them here.

Pointer

userId: 3504
params: {"id": 72493}

Answers “who is user 3504 now”. If the row is gone, it answers nothing. If the row changed, it answers with today’s values and quietly rewrites history.

Snapshot

actorEmail: "ana@x.com"
targetTitle: "Ship the invoice fix"

Answers “who did this, and what did they do it to, at the time”. Correct forever, because nothing else can change it.

In lesson 4 the rule was the other way round: store the pointer, not the copy, so one edit changes the fact everywhere. That rule is still right for normal tables. An audit table is the one place it is inverted, and for the same reason — you do not want one edit to change the fact everywhere.

Keep the pointer and the copy. The pointer is for joining while the target is alive; the copy is for the question asked a year later.

This is not a trick of ours. It is the standard shape for audit logs: OWASP asks every event to carry the actor and the affected item as data in the event, not as a lookup. OWASP — Logging Cheat Sheet, “Which events to log”.

The part that will surprise you

The schema is the easy half. Here is the hard half, and it is about when, not what. Your audit write lives in one onResponse hook in src/app.ts, for a good reason you learned in lesson 18: it is the only place that knows both who asked and what the answer was.

But look at the order of a successful delete:

onRequest   requireAuth              task 72493 exists
preHandler  requirePermission        task 72493 exists
handler     await deleteTask(...)    task 72493 is now gone
            reply.code(204).send()
onResponse  writeAudit(...)          nothing left to copy

So if you put await prisma.task.findUnique(...) inside the hook to build the snapshot, it returns null. Every time. No error, no crash, a green test suite — and a targetTitle column full of NULL on exactly the rows you built the column for.

Your shape again. That is the fifth “bug with no error message” in a row. Dead code (29), a runtime throw past a clean tsc (32), a click that sends nothing (33), a redact path that matches nothing (34), a test file the runner never got (35). Today: a read that is correct, and too late.

The fix: capture early, write late

Split the job in two. The handler is the only code that holds the task while it is still alive, so it captures. The hook still does the writing, so the “one place writes audit rows” rule survives.

Three small pieces. One: a place to put the snapshot, declared once in src/app.ts.

// * A box the handler fills and the audit hook empties. Declared here
// * because the hook owns the contract, not the route.
app.decorateRequest("auditTarget", null);

Two: the store hands back what it deleted instead of only a count.

// src/store/task.store.ts
export async function deleteTask(id: number, teamId: number) {
  // ? deleteMany still returns a count, so a missing id is not a throw --
  // ? but a count cannot be snapshotted. Fetch, then delete, in one transaction.
  const [task] = await prisma.$transaction([
    prisma.task.findFirst({ where: { id, teamId } }),
    prisma.task.deleteMany({ where: { id, teamId } }),
  ]);
  return task ?? undefined;   // ! undefined still means 404, as before
}

Three: the route puts the snapshot in the box.

const task = await deleteTask(id, teamId);
if (!task) return reply.code(404).send({ error: "not found" });
request.auditTarget = {
  type: "task",
  id: task.id,
  snapshot: { title: task.title, status: task.status, teamId: task.teamId },
};
return reply.code(204).send();

And the hook copies the box into the row, if there is one. Routes that never fill it write NULL, which is honest.

The migration

Four columns. Note what is not there: no @relation, no foreign key, on purpose — the same reason as userId, and now for the target too.

model AuditLog {
  // ... everything you already have ...

  // * Snapshots. Copies, not pointers. Nothing else may ever update these.
  // ! No @relation on targetId, for the same reason as userId: a cascade
  // ! deletes the evidence at the moment it becomes evidence.
  actorEmail   String? @db.VarChar(255)
  targetType   String? @db.VarChar(30)
  targetId     Int?
  targetSnapshot Json?
}
npx prisma migrate dev --name audit_snapshot

All four are nullable, and they must be. 7,201 rows already exist and none of them can be given a value now — the facts are gone. A NOT NULL column here would need a backfill with invented data, and invented data in an audit log is worse than an empty column. You met this trade-off from the other side in lesson 10.

append-only — a table that only ever receives INSERT. No UPDATE, no DELETE. Your code already treats AuditLog this way; nothing enforces it yet. Postgres can: REVOKE UPDATE, DELETE ON "AuditLog" FROM tasks; Do not run it today — your tests delete audit rows between fixtures. It goes in week 13 with retention.

Check yourself

Why can the onResponse hook not build the snapshot itself?

onResponse runs after the reply is sent, which is after the handler finished. For a delete, the row it would read is gone, so the read returns null and the column is silently NULL. The hook can still reach the database — that is how it writes the audit row. The problem is the clock, not the connection.

Why is targetId a plain integer and not a relation?

Your own answer from lesson 34. A foreign key with ON DELETE CASCADE removes the audit row at the exact moment somebody deletes the thing the audit row is about. Without the key, the id stays as a number that points nowhere — which is why the snapshot next to it is the part that carries the meaning.

The task title changes next month. What should targetSnapshot.title show?

The old one. An audit row describes one moment. If it followed the live row it would rewrite history: a task renamed from “draft” to “approved” would make every past row read as if it always said “approved”. That is why the copy is stored and never touched again, and why the table is append-only.

See it drawn

One DELETE request, hook by hook. The task is alive for three of them and gone for the last one.

The hook knows who and what answer. The handler knows what was destroyed. Neither one knows all three.

capture early, write once
preHandler who request.userId

Three places collect. One place writes. The rule from lesson 18 survives.
