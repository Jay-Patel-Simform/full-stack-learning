Why this is a real problem and not housekeeping

Four days of your own clicking produced 7,292 rows. That rate is ~1,800 a day. Nothing in your code ever removes one, and since lesson 41 nothing in your code can. So there are exactly two futures:

No retentionRetention
Year one~650,000 rows, hundreds of MB90 days, bounded, ~160,000 rows
How rows leavea human panics and runs TRUNCATEone job, on a schedule, a number in the log
What you can answereverything, until the day you can answer nothing“the last 90 days”, forever

A table with no delete path has a delete path. It is called an emergency. The job you write on a calm day is the one that runs correctly.

The whole change

Two new files and one config line.

// src/config.ts
AUDIT_RETENTION_DAYS: z.coerce.number().int().min(1).default(90),

// src/audit/retention.ts
export async function pruneAuditLog(days = config.AUDIT_RETENTION_DAYS) {
  if (!Number.isInteger(days) || days < 1) throw new Error(...);
  const client = new pg.Client({ connectionString: config.DATABASE_URL });
  await client.connect();
  try {
    const result = await client.query(
      `delete from "AuditLog" where at < now() - ($1 || ' days')::interval`, [days]);
    return result.rowCount ?? 0;
  } finally { await client.end(); }
}

// src/audit/prune.ts   ← four lines, the thing cron calls
const deleted = await pruneAuditLog();
console.log(`audit prune: deleted ${deleted} rows`);

The bold line is the lesson

It connects as DATABASE_URL — the owner — and not through the shared prisma from src/db.ts. Since lesson 42 that shared client is tasks_app outside tests, and tasks_app has no DELETE. Measured on your database just now:

as tasks_app: delete from "AuditLog" where at < now() - interval '3 days'
app role refused: 42501

So the job needs a different login. Say the rule out loud, because the wrong version of it is how people undo a whole lesson: the powerful login is allowed here because nothing on the internet can reach this code path. Not “because it was easier”. A stranger can send bytes to a route. Nobody can send bytes to a cron line.

retention — the rule that says how long you keep a record before deleting it. A number of days, decided once, applied by a machine.

Postgres computes the cutoff, not Node

now() - interval runs inside the database. The same clock that stamped at decides what “old” means. If Node computed the cutoff and the two machines disagreed by an hour, you would delete an hour you meant to keep — and you would never notice, because the evidence is the thing that left.

The default that goes the other way

Since lesson 27 your rule has been: the variables that decide whether production is safe get no default. There are five of them now. AUDIT_RETENTION_DAYS breaks that rule on purpose.

DATABASE_URLAUDIT_RETENTION_DAYS
Missing value meansnothing works, loudlyundefined in a subtraction
Cost of a defaultyou silently point at the wrong databasenone — 90 days is a normal answer
Sorefuse to bootdefault to 90, and min(1)

min(1) is doing more work than it looks. Zero days means “older than right now”, which is every row in the table. The zod schema refuses it at boot, and the function refuses it again at the top, because the function is exported and a caller can pass anything.

The rule underneath both columns: a default is right when the default is a sane answer, and wrong when it hides a decision. “No defaults” was never the rule; it was the shape the rule took for connection strings.

The tests, and how they avoid eating your log

This is the first test in the project that deletes real rows for real. So the fixture dodges your data rather than trusting itself:

const OLD = new Date(Date.now() - 400 * 24 * 60 * 60 * 1000);
...
const deleted = await pruneAuditLog(365);

The planted row is 400 days old, the cutoff is 365 days, and your real log starts four days ago. Nothing real is ever in range. Three tests:

TestAsserts
deletes the old row, keeps the fresh oneboth halves — deleting everything would also pass half a test
a second run deletes nothingreturns 0. The job is safe to run twice.
refuses 0, -1 and NaNthrows before a connection is opened

The second test is the one people skip. A scheduled job runs again whether or not you were watching, so “running it twice changes nothing more” is part of the contract. You met that idea as idempotency in lesson 26; this is the same word, off the request path.

Why does AUDIT_RETENTION_DAYS get a default?

A default is right when the default is a sane answer, and wrong when it hides a decision. 90 days is a normal retention period, so the default costs nothing. Retention absolutely is a safety setting — that is why min(1) is there, since 0 days would delete every row.

The one number that must never be zero

AUDIT_RETENTION_DAYS
90 → at < now() - 90 days deletes old rows
1 → at < now() - 1 day deletes old rows
0 → at < now() deletes every row
und. → at < now() - NaN nothing matches, or everything
 
stopped twice: z.min(1) at boot, and a throw at the top of the function

Least privilege is not about the person. It is about the path. The strong key is fine where no stranger can reach the lock.
