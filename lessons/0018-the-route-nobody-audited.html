Lesson 18 · Week 7–8 · API security

User enumeration

Six lessons hardened POST /auth/login. POST /auth/register sits four lines above it in the same file and got none of it.

In one minute

  • User enumeration: any reply that tells a stranger whether an email has an account here.
  • Three channels leak it: the message, the status code, the clock.
  • Your login is clean on all three — measured, 237 ms vs 236 ms.
  • Register leaks it perfectly: 409 means taken, 201 means free.
  • So it does not hide it — it charges for it. Five free probes, then lesson 11's backoff.

The picture — why register was missed

The three channels

ChannelLeaks howLogin
Message"no such user" vs "wrong password"one message
Status code404 vs 401always 401
Clockfast when no user (no hash was run)DUMMY_HASH

DUMMY_HASH is the subtle one. If no user exists you have nothing to compare against, so the naive code returns instantly — and the timing alone answers the attacker's question. You hash against a fixed dummy value instead, and pay the 252 ms anyway.

"Cheap check first" holds only when the cheap check leaks less. A wasted hash can be load-bearing.

The decision: hide it, or charge for it

Those are the only two moves against an oracle. A public signup form cannot hide it — if two people may not share an address, the form must eventually say so.

Found while measuring: two rows, one person

Jay@x.com and jay@x.com were two accounts. The throttle key was lower-cased back in lesson 11; the database lookup was not. Register in one case, log in in the other, get a permanent 401 — with a green test on top claiming case was handled.

// src/routes/auth.schema.ts — fixed at the door
email: z.string().trim().toLowerCase().pipe(z.email())

Order matters: zod chains run left to right. z.email().trim() would validate the untrimmed string. Normalise first, then .pipe() into the validation. Plus a data-only migration for the rows already saved.

Half a normalisation is worse than none.

Check yourself

How should you test a timing defence?

Asserting the two durations are within a few milliseconds is flaky on a busy laptop, and a flaky security test gets deleted. Assert a floor on each path instead.

Do this

  1. npm test — 109 tests, eight new in src/routes/enumeration.test.ts.
  2. Time both login paths: time curl with a real email, then a nonexistent one. Both ~237 ms.
  3. Probe register six times with different emails. Watch the backoff arrive.

See it drawn

Three pictures. The channels a reply leaks through, the hash you must not optimise, and the normalisation you did half of.

1. One question, three answers

“Does jay@work.com have an account here?” A reply can answer it three separate ways.

  • channelhow it leakshow login shuts it
  • Message “wrong password” vs “no such user” One string for both. Byte-identical.
  • Status 409 vs 201. Or a real email flipping to 429 while a fake one stays 401. 401 either way, and the throttle is keyed on the typed email.
  • Clock No user → skip the hash → 2 ms instead of 237 ms. DUMMY_HASH. Hash against nothing rather than branch.

Your login closes all three. Your register closes the clock and leaks the other two — measured 250 ms / 409 against 242 ms / 201. A perfect timing defence is worth nothing next to a status code that just says it.

2. The hash you must not optimise

Register hashes a password, then finds out the email was taken. 250 ms of work thrown away. Fixing it opens the channel the login closed.

Faster · leaks

Check first

if (await exists(email))
  return 409;          // 2 ms
await hashPassword(pw); // 250 ms
create(...)

Taken → 2 ms. Free → 250 ms.

Now delete the 409 and answer 201 to everybody: the clock still gives the answer back.

Wasteful · silent

Hash first

const hash = await hashPassword(pw);
const user = await create(email, hash);
if (!user) return 409;  // 250 ms
return 201;             // 250 ms

Taken → 250 ms. Free → 242 ms.

One channel already shut, for free, before you decide anything about the status code.

“Cheap check first” (lesson 12) holds only when the cheap check leaks less. On login it did. On register it leaks more — so the wasted hash is load-bearing. A rule has a domain.

3. Half a normalisation

Two lines of the same handler. One lower-cased the address, the other did not.

const key = email.toLowerCase();          // the throttle counter  ->  jay@x.com
const user = await findUserByEmail(email); // the database lookup   ->  Jay@x.com
                       ^^^^^ raw

And this test, from lesson 11, was green the whole time — because it only ever exercised the key, never the lookup:

test("case does not open a side door", ...)   // ok 41

Half a normalisation is worse than none. With none, you find the bug the first time you type a capital letter. With half, a passing test tells you not to look.

The fix has one location

Count the places a raw address can enter: login, register, every route after this one. It has one door, and it is not the query.

// src/schemas/auth.schema.ts
const emailField = z.string().trim().toLowerCase();

export const Register = z.object({
  email: emailField.pipe(z.email().max(254)),   // normalise, THEN validate
  ...
});
Reads right · wrong 
z.email().trim().toLowerCase()
// "  Jay@x.com "  ->  400

.email() judged the string before .trim() touched it.

Correct 
z.string().trim().toLowerCase()
  .pipe(z.email().max(254))
// "  Jay@x.com "  ->  "jay@x.com"

A zod chain runs left to right. Transforms are not preprocessing.
