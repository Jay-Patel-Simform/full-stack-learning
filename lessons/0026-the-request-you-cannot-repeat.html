Double-submit and idempotency

The list can be edited but not grown. Today it gets a form. And a create is the one request you cannot make safe to send twice — so the safety has to move somewhere else.

In one minute

  • A create is not idempotent. Send it twice and you own two rows. Measured below: same body, two 201s, ids 360 and 361.
  • You cannot fix that on the wire, so fix it at the button. disabled={isPending} is not a spinner — it is the duplicate guard.
  • The typed text is yours, so it lives in useState. Yesterday done was a server fact and state was a lie. A draft is not a server fact until you send it.
  • Append the reply when you know where it goes. The list is sort=id&dir=asc and the new id is the biggest, so “last” is not a guess.
  • Invalidate when you do not. Switch that list to sort=title and the server puts the new row first. That is the first honest use of invalidateQueries in this course.

The word pair

idempotent (again) — PATCH { done: true } was. POST /tasks is not, and no amount of care makes it so: each call is a request for a new row, and two calls ask for two.
in flight — sent, not yet answered. The window where a second click does damage. isPending is exactly this window, and it is the only thing you can close.

When you cannot make the request safe to repeat, make it hard to repeat.

Look at the first two lines and compare them with lesson 25. There, the same request twice gave the same row twice. Here it gives two different rows, and both replies say success, because both calls succeeded. Nothing went wrong on the server. The duplicate is not a bug you can catch — it is what you asked for.

Line 8 and line 9 are the same refusal for two different reasons: a Viewer holds no task:create, and a team you are not in gives you no role at all. One answer, so neither tells the caller which (lesson 24). Note there is no 404 on this route — you are not naming a row, you are asking for one.

Where the new row belongs

The reply is the whole task, so you can put it in the cache without asking again. But where in the list? That depends on something the reply never mentions: the sort you asked for. Same four rows, same moment, two orders:

Put the reply in the cache when you know where it goes. Ask again when you do not. That is the whole rule, and today is the first time the second half of it is true.

This is the exception named in lesson 25. The reference card says: invalidate when the write changed something you were not told about. A create changes the list’s membership and its order, and the reply only describes one row. You are appending today only because sort=id makes the order a fact you can compute, not a guess.

Where the typed text lives

Yesterday the rule was “no useState — checked is a server fact”. Today the input is useState, and that is not a contradiction.

That third row is the one to notice. Clearing the input in onSuccess and nowhere else means a 403 or a 400 leaves your sentence on screen. Clearing it in onSubmit would throw the user’s typing away to celebrate a request that had not been answered yet.

The code — type it yourself

1. web/src/features/tasks/tasks.ts — add to the existing file

// …Task, tasksKey, useTasks and useSetTaskDone stay exactly as they are…

export function useCreateTask(teamId: number) {
  const client = useQueryClient();

  return useMutation({
    // No `done`. The server defaults it to false, and a field you do not send
    // is a field you cannot get wrong.
    mutationFn: async (title: string) =>
      (await api.post<Task>(`/teams/${teamId}/tasks`, { title })).data,

    // Append, and only because useTasks asks for sort=id&dir=asc: a new id is
    // the biggest id, so "last" is arithmetic, not a hope. Sort this list by
    // title one day and this line must become invalidateQueries.
    onSuccess: (task) =>
      client.setQueryData<Task[]>(tasksKey(teamId), (tasks) => [...(tasks ?? []), task]),
  });
}

2. web/src/features/tasks/tasks-panel.tsx — the form

A new component in the same file, above TasksPanel:

import { useState } from "react";
import { Button } from "@/components/ui/button";
import { Input } from "@/components/ui/input";
import { useCreateTask } from "@/features/tasks/tasks";

function NewTaskForm({ teamId }: { teamId: number }) {
  const [title, setTitle] = useState("");
  const create = useCreateTask(teamId);

  function onSubmit(event: React.FormEvent<HTMLFormElement>) {
    event.preventDefault();
    create.mutate(title, {
      // Clear ONLY on success. A 403 or a 400 leaves the sentence on screen,
      // because the words are still yours until the server accepts them.
      onSuccess: () => setTitle(""),
    });
  }

  return (
    <form onSubmit={onSubmit} className="flex gap-2">
      <Input
        aria-label="New task"
        placeholder="Add a task…"
        maxLength={200}
        required
        value={title}
        onChange={(e) => setTitle(e.target.value)}
      />
      {/* This is the duplicate guard, not a spinner. A create cannot be
          repeated safely, so the second click must not happen. */}
      <Button type="submit" disabled={create.isPending}>
        {create.isPending ? "Adding…" : "Add"}
      </Button>
    </form>
  );
}

Then render it inside TasksPanel. Careful where: the three early returns each end the function, so a form placed after them disappears exactly when it is most useful.

export function TasksPanel({ teamId }: { teamId: number }) {
  const { data: tasks, isPending, error } = useTasks(teamId);
  const setDone = useSetTaskDone(teamId);

  if (isPending) return <p className="text-muted-foreground text-sm">Asking…</p>;

  if (error !== null)
    return (
      <p className="text-destructive text-sm">
        {errorMessage(error, "Could not load tasks.")}
      </p>
    );

  return (
    <div className="grid gap-3">
      {/* "No tasks yet" is no longer a reason to render nothing: an empty
          list is the moment you most want the form. */}
      {tasks.length === 0 ? (
        <p className="text-muted-foreground text-sm">No tasks yet.</p>
      ) : (
        <ul className="grid gap-1">
          {/* …the <li> with the Checkbox from lesson 25, unchanged… */}
        </ul>
      )}

      {setDone.error !== null ? (
        <p className="text-destructive text-sm">
          {errorMessage(setDone.error, "Could not save that.")}
        </p>
      ) : null}

      <NewTaskForm teamId={teamId} />
    </div>
  );
}
Where is the error line for the form? Inside NewTaskForm, next to its own create.error — that is step 3 of Do this, and it is yours to write. A mutation’s error belongs beside the control that caused it, which is the small thing lesson 25 got wrong on purpose.

Check yourself

Why can a create not be made idempotent the way the PATCH was?

{ done: true } names an end state, so arriving there twice changes nothing. A create names no row — it asks the server to invent one — so two calls are two requests for two rows, and the server is right to make both. Measured above: ids 360 and 361, both 201. (Making it repeatable needs an idempotency key the caller invents, which is week 13.)

Why may onSuccess append the reply to the end of the list?

Because useTasks asks for sort=id&dir=asc and a new id is always the largest, so “last” is computed, not assumed. The same append under sort=title puts “Aardvark” at the bottom while the server puts it at the top — measured above. The order is a property of your request, never of the server.

What does disabled={create.isPending} actually prevent?

It closes the in-flight window. On the checkbox, a double-click was harmless — the same value twice is the same result. Here the second click is a second task. The disabled attribute is doing security-shaped work, not decoration, which is also why a slow network makes this the most important line in the file.

Four tasks, one moment, two sort values. Aardvark is the row just created.
