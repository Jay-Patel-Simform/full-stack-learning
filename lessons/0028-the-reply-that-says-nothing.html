Lesson 28 · Week 10 · Front end

204 responses and cache updates

The page can read tasks, tick them and add them. The last write missing is delete — and it is the only one whose reply carries no state at all. That changes what you may put in the cache, and it changes what “safe to send twice” actually means.

In one minute

  • Your DELETE answers 204: zero bytes, no content-type, no content-length. Measured below.
  • axios still hands you .data, and it is "" — an empty string. api.delete<Task>(…) compiles happily and is a lie at runtime.
  • So you filter by the id you sent, not the id you were told. onSuccess’s second argument is that id.
  • Send it twice: 204, then 404. Same world after both, two different answers. That is what idempotent means — and it is not “the answer repeats”.
  • A Viewer’s can is ["task:read"], so no button is drawn. Draw it anyway and the gate says 403. Measured.

The word pair

idempotent — sending it twice leaves the world where sending it once did. A promise about state.
repeatable answer — sending it twice gets you the same reply. A promise about the response.

DELETE is the first one and not the second. A retry is safe and still looks like a failure — so the second 404 is not a bug to fix, it is a thing your UI has to expect.

The trap in one line. (await api.delete<Task>(url)).data type-checks. TypeScript believes you, because a type parameter is a claim you made, not a fact it checked. At runtime that Task is "", and the crash lands later, in setQueryData, on a line that looks fine. The reply has no type because it has no body — so do not give it one.

Two ids, and only one of them exists

from the reply

mutationFn: async (id: number) =>
  (await api.delete<Task>(
    `/teams/${teamId}/tasks/${id}`)).data,

onSuccess: (task) =>
  setQueryData(key, (tasks) =>
    tasks?.filter((t) => t.id !== task.id)),
//                            ^ "".id
//                            = undefined

Filters nothing. The row stays on screen — and the server already deleted it.

from what you sent

mutationFn: async (id: number) => {
  await api.delete(
    `/teams/${teamId}/tasks/${id}`);
},

onSuccess: (_nothing, id) =>
  setQueryData(key, (tasks) =>
    tasks?.filter((t) => t.id !== id)),
//                            ^ the number
//                            you typed

Filters the right row, with zero extra requests.

onSuccess gets four arguments: (data, variables, context, mutation). Until today you only ever needed the first. When the reply is empty, the second is the whole payload — and it is trustworthy for a different reason than the reply is: the server said 204, which means the thing you named is now gone. You are not guessing. You are being told, in the status line instead of the body.

A 204 is not “no information”. It is the information, moved into the status code.

The code — type it yourself

1. web/src/features/tasks/tasks.ts — append

export function useDeleteTask(teamId: number) {
  const client = useQueryClient();

  return useMutation({
    // 204 means "done, nothing to send back". There is no row to type and
    // nothing to return - `.data` on a 204 is "", an empty string, and
    // api.delete<Task>() would have type-checked that lie without complaint.
    mutationFn: async (id: number) => {
      await api.delete(`/teams/${teamId}/tasks/${id}`);
    },

    // The id comes from what we SENT, not from what came back. That is the
    // only difference between this mutation and the other two - and it is
    // safe precisely because the server answered 204 rather than 404.
    onSuccess: (_nothing, id) =>
      client.setQueryData<Task[]>(tasksKey(teamId), (tasks) =>
        tasks?.filter((t) => t.id !== id),
      ),
  });
}

Note the mutationFn body is a block, not an arrow expression. That is deliberate: an expression body would return the axios response, and then something downstream would try to read it. Returning void makes _nothing honest.

Check yourself

Why not filter using the id from the reply?

A 204 is zero bytes — measured above, no content-type, no content-length. axios hands you "", so task.id is undefined, so t.id !== undefined is true for every row and the filter removes nothing. The row stays on screen while the server has already deleted it, which is the exact drift setQueryData was supposed to prevent. The id you sent is the only id in the building.

Your DELETE answered 204 then 404. Is it idempotent?

Idempotent is a promise about state, not about the response. After one delete the task is gone; after two it is still gone, and nothing else changed. That is the whole definition. The 404 is the server truthfully answering a question about a row that no longer exists — it is not a second effect. This is why a network retry on DELETE is safe and a retry on POST is not, even though the delete is the one that looks like it failed.

A Viewer edits the JS in devtools and makes the bin icon appear. What happens?

Measured above: 403 {"error":"forbidden"}, and the audit table recorded the refusal. can.includes("task:delete") decides whether a button is drawn; requirePermission("task:delete") decides whether anything happens. Same rule as lesson 23, now with the button that actually does something. A hint is not a gate.

3. What a 204 is on the wire

200 with a row   —  the PATCH
  content-type: application/json; charset=utf-8
  content-length: 41
  {"id":399,"title":"probe 28","done":true}

204 with nothing  —  the DELETE
  content-type: (none)
  content-length: (none)
    0 bytes — a 204 must not carry a body

So there is no header saying “JSON”, no length, and nothing to parse. axios does not error — it fills data with the empty string it received, which is the most dangerous possible value: falsy, indexable, and not undefined.

Every write either hands you the new state, or hands you the status line and expects you to have kept your own request. Those are the only two kinds. Invalidate only when it hands you neither.
