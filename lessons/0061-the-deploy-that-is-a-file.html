Lesson 61 · Week 15–16 · Deploy

The deploy that is a file

Lessons 56 and 57 built two Render services by typing into a web form. That worked, and it left nothing behind. Nobody can review a form. Today the same two services become render.yaml — a file in your repo, next to the code it deploys. The trap is the one your instinct will walk into: a file in the repo is a public file, so the eight values you typed cannot simply be copied into it.

In one minute

  • A Blueprint (Render’s word for a render.yaml file) is your deploy written as code. Same two services, same settings, but readable in a diff.
  • Secrets go in with sync: false. That means “this service has this variable, and Render asks me for the value”. The name is in git, the value never is.
  • Non-secrets go in with value:. NODE_ENV, TRUST_PROXY, LOG_LEVEL are decisions, not secrets. A decision belongs in the file, where a reviewer can argue with it.
  • rootDir moves the service; it does not move the paths. dockerfilePath is still written from the repo root. This is the line people get wrong.
  • You get a checker. render blueprints validate reads the file and tells you what is wrong, before any deploy. That is today’s feedback loop.

Configuration you can only click is configuration nobody can review. The last row is the one to hold on to: moving the deploy into git must not move the passwords into git. That is the whole difficulty of this lesson, and it has a one-word answer below.

The file

Write it at the workspace root: render.yaml. Not inside server/ — it describes both services, and Render looks for it at the repo root.

# yaml-language-server: $schema=https://render.com/schema/render.yaml.json
services:
  # ---------- the API: the Dockerfile from lesson 52 ----------
  - type: web
    name: tasks-api
    runtime: docker
    plan: free
    region: oregon                 ← the region you picked in lesson 56
    rootDir: server                ← same as the dashboard's "Root Directory"
    dockerfilePath: ./server/Dockerfile   ← ! from the REPO ROOT, not from rootDir
    healthCheckPath: /health
    envVars:
      # decisions: safe to read, and worth reading
      - key: NODE_ENV
        value: production
      - key: TRUST_PROXY
        value: true
      - key: HOST
        value: 0.0.0.0             ← lesson 56: without this the port scan times out
      - key: LOG_LEVEL
        value: info
      - key: AUDIT_RETENTION_DAYS
        value: 90
      # secrets: the NAME is here, the VALUE is asked for in the dashboard
      - key: DATABASE_URL
        sync: false
      - key: APP_DATABASE_URL
        sync: false
      # not a secret, but it is a URL you cannot know until the site below exists
      - key: ALLOWED_ORIGINS
        sync: false

  # ---------- the page: the static site from lesson 57 ----------
  - type: web
    name: tasks-web
    runtime: static
    rootDir: web
    buildCommand: npm ci && npm run build
    staticPublishPath: ./web/dist
    envVars:
      - key: VITE_API_URL
        value: /api                ← lesson 57. A build-time value, and public by design
    routes:
      # ! Order matters, exactly as in the dashboard. /api/* first, or the
      # ! SPA rule below swallows every API call and answers with index.html.
      - type: rewrite
        source: /api/*
        destination: https://tasks-api.onrender.com/*
      - type: rewrite
        source: /*
        destination: /index.html

Nothing here is new behaviour. Every line is something you already typed once by hand; you are writing it down, not deciding it again. Three lines are worth naming out loud.

Three lines worth naming

1. sync: false is not “do not deploy this”. It means: this service needs a variable with this name, and Render must ask a human for the value. The dashboard prompts you once, stores it, and never writes it back to the file. So the file records the shape of the environment — nine variables, these names — while the values stay where values belong. A reviewer can see that APP_DATABASE_URL is required without seeing your Neon password.

2. rootDir moves the service, not the paths. rootDir: server is what the dashboard called Root Directory. But dockerfilePath and staticPublishPath are described by Render’s own schema as relative to the repo root — so they keep the server/ and web/ prefix that rootDir looks like it already removed. Two fields, two different starting points, in one service block. This is the most common wrong guess in a first Blueprint, and the validator below catches it in one second.

3. PORT is still not here, for the same reason it was not in the dashboard: Render sets it. Your config.ts defaults it to 3000 and Render overrides that. A value you write down that the platform will overwrite is a lie in a file, and one day you will read it and believe it.

Check it before you deploy

The Render CLI reads the file against that same schema:

cd ~/learning/full-stack-learning
render blueprints validate

It answers with the errors, or with nothing. Break a line on purpose and run it again — change runtime: docker to runtime: dokcer, or drop the web/ from staticPublishPath — so you learn what its complaints look like while you are not in a hurry. This is the loop: edit, validate, edit. No deploy, no waiting, no money.

The same schema works in your editor. The comment on the first line of the file (yaml-language-server: $schema=…) is read by the YAML extension in VS Code, and you get completion and red squiggles as you type. A checker you get for free before you run anything is always worth the one line it costs.

Practice — three

What does sync: false put in your git repository?

It records that the service needs a variable with that name, and tells Render to ask you for the value in the dashboard instead of reading one from the file. Nothing is encrypted and nothing is hidden — the value is simply never written down here. That is why DATABASE_URL can be in a public repo as a name and stay a secret as a value.

With rootDir: server, what is dockerfilePath relative to?

Render’s schema says dockerfilePath is “relative to the repo root”, and rootDir does not change that. So the server/ stays. rootDir decides where the service lives and what the build context is; it does not rewrite the other paths in the same block. Two fields in one service, two starting points.

Why must the /api/* route come before /*?

Same rule as the dashboard in lesson 57: rules are tried in order and the first one that matches ends the search. /* matches /api/teams perfectly well, so if it comes first the browser gets index.html where it asked for JSON. The bug looks like a broken API and is really a sorted list.

not measured — do this before you click
Your two services already exist, made by hand. I have not tested whether Render adopts services with matching names or creates a second pair. So: run validate first, then open the Blueprint page in the dashboard and read the plan it shows you before approving it. If it offers to create tasks-api when tasks-api already exists, stop and tell me. Names in the file must match your real service names exactly — check them.

Read this: Render — Blueprint specification. It is a field list, so skim it; read the envVars and static-site sections properly.

Then this: twenty minutes. (1) Write render.yaml at the workspace root, with your real service names and region. (2) render blueprints validate until it is quiet. (3) Break it twice on purpose and read both complaints. (4) Commit it — and before you do, git show --stat and then git diff --cached | grep -i -E "postgres|password|neon". Nothing should match. That grep is the habit, not the file.
