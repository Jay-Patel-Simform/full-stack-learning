Lesson 17 · Week 7–8 · API security

Mass assignment

Your handler does data: { ...input, teamId, ownerId } — the caller's JSON, spread straight into a database write. You are safe today for three reasons, none of which you chose.

In one minute

  • Mass assignment: the caller sends a key you never named, and your code passes it to the database anyway.
  • You are already safe, because z.object strips unknown keys. You did not decide that. It is a default.
  • Stripping is safe but silent. A front-end typo gets a 200 and changes nothing — the worst kind of bug to debug.
  • Fix: four lines in src/app.ts, so every request body rejects an unnamed key with a 400.

The picture

The idea

Count what is actually protecting you right now:

  1. z.object strips keys you did not list. A default you inherited.
  2. Your handler overwrites ownerId and teamId after the spread. Ordering luck.
  3. Prisma rejects columns that do not exist. Someone else's library.

Three protections, zero decisions. That is a fine place to be safe from and a bad place to stay.

strip — silently drop the unknown key. Safe. Says nothing.
reject — answer 400 and name the key. Safe and honest.

The code — one place, not seven

// src/app.ts — the validator compiler, four lines
app.setValidatorCompiler(({ schema, httpPart }) => {
  const s = httpPart === "body" && schema instanceof ZodObject
    ? schema.strict()
    : schema;
  return (data) => s.safeParse(data);
});

The alternative was .strict() on all seven schemas. One place beats seven, and body number eight next month gets it for free.

Bodies only. A query string legitimately collects utm_source, fbclid and cache-busters. Rejecting those would break links, not attacks.

Strip is safe. Reject is safe and honest. The honesty is worth more day to day.

Two rules that came out of this: an as cast is not a check — it is a promise kept by something in another file, so say which file in a comment. And strict checks whether you named a key, never whether naming it was wise: AddMember names role, and lesson 9's rank rule is what refuses escalation.

Check yourself

Stripping already stops the attack. Why switch to rejecting?

Security-wise the two are equivalent here. The win is diagnostic: a front-end field name typo becomes a 400 that names the key, instead of a 200 that quietly changes nothing.

Do this

  1. npm test — 101 tests, eight new in src/routes/mass-assignment.test.ts.
  2. curl -X POST .../tasks -d '{"title":"x","ownerId":99}'. You want a 400 that names ownerId.
  3. Also confirm ?utm_source=x on a GET still works. Bodies only.

See it drawn

Same request, twice. Both refuse the unnamed key. Only one says so.

Strip — zod’s default

z.object({ title })

POST /teams/7/tasks { "title": "x", "ownerId": 999 } → 201 Created

The attacker is stopped. ownerId is gone before the handler sees it.

You are lied to. Send isDone instead of done and you get a 200 with nothing changed. Then you debug your reducer for an hour.

Reject — strict

z.object({ title }).strict()

POST /teams/7/tasks { "title": "x", "ownerId": 999 } → 400 Bad Request Unrecognized key: "ownerId"

The attacker is stopped, identically.

You are told. The reply names the key, so a front-end typo is a ten-second fix instead of an hour.

Where the key dies

One compiler in src/app.ts. Four lines, two of them just deciding whether the rule applies.

  1. 1 Is this the body? httpPart === "body" else pass

    Params and query strings go straight through, unstrict. Dashed = the rule does not apply here.

  2. 2 Is the schema an object? schema instanceof ZodObject else pass

    .strict() only exists on an object schema. An array or string body has no keys to argue about.

  3. 3 schema.strict() once

    Returns a new schema; yours is untouched. Runs at route registration, not per request. Per-request cost: zero.

  4. 4 Any key you never named? 400

    (root): Unrecognized key: "ownerId". The handler never runs, so data: { ...input } never sees it.

  5. 5 A PATCH with zero fields? 400

    The other half of silent success. .partial() made every field optional and allowed none, so {} used to answer 200 and change nothing. One .refine() on UpdateTask.

  6. 6 Handler runs 201

    request.body now holds only keys you named. The as CreateTaskInput cast is finally a true statement.

Why only the body

InputStrictBecause
bodyyesYour client composed every byte of it on purpose. An unnamed key is an attack or a typo, and both deserve a 400.
querystringnoThis is the real reason for the check. Query strings collect keys nobody asked for — ?utm_source=newsletter, ?fbclid=…, a proxy cache-buster. Strict here turns a shared link into a 400.
paramsnoMeasured, not assumed: strict params break nothing in this app today — params hold exactly the URL segments you declared. Left out to match the query, not to avert a disaster.

What was protecting you before, and what you chose. Four things blocked {"ownerId": 999} yesterday: zod’s default strip (a default), ownerId written after the spread (typing order), the output serializer (your decision, lesson 2), and an as cast (not a check at all — it does nothing at runtime). One of four. Free protection you cannot see is protection you delete by accident, on a Tuesday, for an unrelated reason.
