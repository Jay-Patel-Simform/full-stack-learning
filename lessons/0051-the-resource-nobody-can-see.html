The resource nobody can see

You built Project in week 5–6. It has a Prisma model, a migration, a store, two routes, a permission rule and six passing tests. I counted the rows in your database this morning: 0. Not one project has ever existed. Today you find out why, and the reason is a single missing verb. Suite goes 170 → 172.

In one minute

  • You can create a project and delete a project. You cannot read one. There is no GET route and no project:read action. A resource with no read is a resource with no screen, and a resource with no screen gets no rows.
  • The permission table was written from the routes that existed. ACTIONS has project:create and project:delete because those were the two routes you wrote. Nothing has ever compared that list against the resource it is supposed to describe.
  • Not every list route needs the gate — this one does. GET /teams has no requirePermission on purpose. GET /teams/:teamId/projects must have one. The difference is one word: where the scope came from.
  • Widening a role breaks two tests, and that is the tests working. Measured: adding one word to VIEWER turns 170 pass into 168 pass, 2 fail. You will watch that happen before you fix it.
  • Streak intact: no new dependency, 51 lessons.

The thing that has been true for forty lessons

Here is every route that exists for Project, straight out of src/routes/projects.route.ts:

POST   /teams/:teamId/projects              project:create
DELETE /teams/:teamId/projects/:projectId   project:delete

And here is ACTIONS, the complete vocabulary of your permission system:

"task:read", "task:create", "task:update", "task:delete",
"project:create", "project:delete",
"member:invite", "member:remove", "team:delete", "audit:read"

Read those two blocks next to each other. Task has four verbs and the first one is read. Project has two verbs and neither one is read. Nothing in TypeScript, Zod, Prisma or your 170 tests can see that, because every one of them checks the code against itself. The route calls an action that exists. The action is in the table. The test asserts the gate refuses a Viewer. All true, all green, and the feature does not work.

A permission table is a list of the verbs you happened to write, not a list of the verbs the resource has. The gap is invisible to every tool you own. You find it by putting the two lists side by side and reading, which is what you just did.

Why zero rows is the proof

You could have created a project at any point in the last six weeks. The route works — projects.test.ts creates them constantly. But you have never created one from the app, because the app has never had a reason to: there is nothing to look at afterwards. A POST whose result you cannot see is a button nobody presses twice.

So 0 is not neglect. It is the honest output of a resource that is write-only.

The decision: which role gets project:read?

Your roles nest, so the question is only “how far down does it go”. Compare it to the two reads you already placed:

ActionLowest roleWhy there
task:readVIEWERSeeing the work is the whole point of being a Viewer.
audit:readADMINThe rows name who did what. A curious member should not browse them (lesson 38).
project:readVIEWERA project is a name and an id. It is the same class of fact as a task — the work, not who touched it.

So project:read goes next to task:read in VIEWER, and every role inherits it. That is one word in one line, and it is the only real decision in today's lesson. Everything after it is mechanics.

Both failures are correct and both are the same shape. Look at what can.test.ts actually asserts:

assert.equal(can("VIEWER", "task:read"), true);
for (const action of ACTIONS) {
  if (action === "task:read") continue;
  assert.equal(can("VIEWER", action), false, `viewer allowed ${action}`);
}

That loop says “everything except this one name is refused”. It is written against ACTIONS, so every action you ever add is automatically denied to a Viewer unless you come back to this test and say otherwise. And team-list.test.ts does the same job over the wire: assert.deepEqual(mine.can, ["task:read"]) — the exact list, not includes.

A permission test should fail when you widen a role. This is the allowlist from lesson 34 wearing its fourth costume. The fix is never to loosen the loop — it is to name the second thing you meant to allow.

So the fix is to name both reads, and let the loop keep guarding everything else:

// src/auth/can.test.ts
const READS = ["task:read", "project:read"] as const;
for (const action of READS) assert.equal(can("VIEWER", action), true);
for (const action of ACTIONS) {
  if ((READS as readonly string[]).includes(action)) continue;
  assert.equal(can("VIEWER", action), false, `viewer allowed ${action}`);
}

// src/routes/team-list.test.ts
assert.deepEqual(mine.can, ["task:read", "project:read"]);

Back to 170. Note the order matters in that second one: deepEqual on an array compares position by position, and can comes from allowedActions(role), which is your VIEWER tuple in the order you wrote it.

app.get(
  "/teams/:teamId/projects",

No cursor, no take, no nextCursor. Tasks are paged because a team accumulates thousands of them; a team has a handful of projects, and paging a handful is code you would have to keep working forever in exchange for nothing. When a real team hits 200 projects, lesson 30 is still on disk.

The bit worth slowing down for

That preHandler line is the whole lesson in one word. You have a list route with no gate, and you were right to write it that way:

// src/routes/teams.route.ts
app.get("/teams", ..., async (request) => {
  const rows = await listMemberships(request.userId!);
  ...
});

Lesson 23 gave you the rule: a list-shaped route needs no gate when the where clause is the scope. where: { userId } cannot return a row you may not see, because the id came from your session cookie. There is nothing to refuse.

Today's route looks identical — a list, one where, no ids in the body — and the rule does not apply, because of one word:

where did the scope come from?
GET /teams where: { userId }   from your session  → no gate needed
GET /teams/:teamId/projects where: { teamId }   from the URL  → gate required
 
Same query shape. The caller can type any teamId they like.
Without the gate: change one number, read another team's projects. IDOR.

A where clause is a scope only when you chose its value. Scope from the session scopes. Scope from the URL is a request, and a request gets checked. This is the same sentence as the deleteMany({ where: { id, teamId } }) comment you already have in project.store.ts — you wrote it for the delete and it is just as true for the read.

The first proves the where does its job — a project that exists, in a team you are not in, does not appear. The second proves the gate does its job. One test per mistake: with the gate gone, an outsider gets 200 [], and the test fails. With the where gone, the viewer sees hidden-, and the first test fails. Measured here: 172 pass, 0 fail.

And note what the two answers are: an outsider asking GET /teams gets an empty list, an outsider asking GET /teams/:teamId/projects gets 403. Both are correct. The first never says a team exists; the second was asked about a specific team and has to answer.

Why does GET /teams/:teamId/projects need a gate when GET /teams does not?

where: { userId } uses an id from your session — you cannot ask it about someone else. where: { teamId } uses a number typed into the URL, so without the gate, changing that number reads another team's rows. Nesting is a URL convention; it guards nothing by itself.

Adding project:read to VIEWER failed two tests. What does that mean?

Both assert a Viewer's whole permission list, not that one entry is present. That is an allowlist, the same rule as pino's redact in lesson 34 and TaskPublic in lesson 30. A permission test that stays green while a role gets wider is a test that will not notice the day you widen it by accident.

The screen

web/src/features/projects/projects.ts

import { useMutation, useQuery, useQueryClient } from "@tanstack/react-query";
import { api } from "@/lib/api";

export type Project = { id: number; name: string; teamId: number };

// The key mirrors the URL, same as tasksScope. One entry per team.
export const projectsKey = (teamId: number) =>
  ["teams", teamId, "projects"] as const;

export function useProjects(teamId: number) {
  return useQuery({
    queryKey: projectsKey(teamId),
    queryFn: async () =>
      (await api.get<Project[]>(`/teams/${teamId}/projects`)).data,
  });
}

export function useCreateProject(teamId: number) {
  const client = useQueryClient();
  return useMutation({
    mutationFn: async (name: string) =>
      (await api.post<Project>(`/teams/${teamId}/projects`, { name })).data,
    // Not a hand-written cache append. The server orders by id and it is
    // the only thing that knows the new id -- lesson 26's rule, and there is
    // no paging here to make a refetch expensive.
    onSuccess: () => client.invalidateQueries({ queryKey: projectsKey(teamId) }),
  });
}

import { useState } from "react";
import { Button } from "@/components/ui/button";
import { Input } from "@/components/ui/input";
import type { Action } from "@/features/teams/teams";
import { useCreateProject, useProjects } from "./projects";

function ProjectRow({ name }: { name: string }) {
  return <li className="font-mono text-sm">{name}</li>;
}

export function ProjectsPanel({
  teamId,
  can,
}: {
  teamId: number;
  can: Action[];
}) {
  const { data, isPending, error } = useProjects(teamId);
  const createProject = useCreateProject(teamId);
  // The words live in state; the request happens on submit. The form IS
  // the debounce -- lesson 33, and still zero useEffect in the app.
  const [name, setName] = useState("");

  if (isPending) return <p className="text-muted-foreground text-sm">Asking…</p>;
  if (error !== null)
    return <p className="text-muted-foreground text-sm">Could not load projects.</p>;

  return (
    <div className="grid gap-2">
      {data.length === 0 ? (
        <p className="text-muted-foreground text-sm">No projects yet.</p>
      ) : (
        <ul className="grid gap-1">
          {data.map((p) => (
            <ProjectRow key={p.id} name={p.name} />
          ))}
        </ul>
      )}

      {can.includes("project:create") ? (
        <form
          className="flex gap-2"
          onSubmit={(e) => {
            e.preventDefault();
            if (name.trim() === "") return;
            createProject.mutate(name, { onSuccess: () => setName("") });
          }}
        >
          <Input
            value={name}
            onChange={(e) => setName(e.target.value)}
            placeholder="New project"
          />
          <Button size="sm" type="submit" disabled={createProject.isPending}>
            {createProject.isPending ? "Saving…" : "Add"}
          </Button>
        </form>
      ) : null}
    </div>
  );
}

The delete button

You asked for it, so here it is — and it is small because the server did the work already: DELETE /teams/:teamId/projects/:projectId exists, sits behind requirePermission("project:delete"), and is tested. Nothing new on the server. Two edits on the screen.

web/src/features/projects/projects.ts — append

export function useDeleteProject(teamId: number) {
  const client = useQueryClient();
  return useMutation({
    // 204: nothing comes back, so nothing to type. Same shape as useDeleteTask.
    mutationFn: async (id: number) => {
      await api.delete(`/teams/${teamId}/projects/${id}`);
    },
    // useDeleteTask filters the row out of the cache by hand because tasks are
    // paged and a refetch there costs pages. Projects are one unpaged list --
    // invalidate, same as useCreateProject, and let the server be the answer.
    onSuccess: () => client.invalidateQueries({ queryKey: projectsKey(teamId) }),
  });
}
