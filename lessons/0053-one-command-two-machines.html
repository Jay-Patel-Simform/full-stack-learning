Lesson 53 · Week 15–16 · Docker + deploy

One command, two machines

Last lesson your API ran in a box and reached back out to the Postgres on your Mac through host.docker.internal — a Docker Desktop convenience that does not exist on a server. Today Postgres moves into a box of its own, the two boxes get a private network where db is a real hostname, and docker compose up starts the whole stack. Zero TypeScript changes. Suite stays at 172. The interesting part is that your lesson-41 role script is about to fail, and the reason is worth the whole lesson.

In one minute

  • A compose file is the docker run flags you were typing, written down. Ports, env file, build context — same things, in YAML, under version control, for two containers instead of one.
  • Containers on one compose network reach each other by service name. db:5432. No host.docker.internal, no IP, and the same string works on Fly.io.
  • A container is throwaway; a volume is not. That is the only reason a database in a box is not a joke. docker compose down keeps your rows, down -v burns them.
  • The database init script runs exactly once — on an empty volume, before any table exists. Your tasks_app.sql ends with a REVOKE on "AuditLog", which is not there yet. It will crash the init. You will watch it, then split the file.
  • Streak intact: no new dependency, 53 lessons. Compose ships with Docker; you installed it last lesson.

Why the Mac's Postgres cannot come with you

Your container currently says host.docker.internal:5432. That name is invented by Docker Desktop for exactly this case: a container that needs to talk back to the laptop hosting it. On a Fly.io machine, an EC2 box or a colleague's Linux desktop, resolving it gets you nothing. So the address in your config is true in one place only, which is the same failure shape as HOST=127.0.0.1 last lesson: a value that is correct, and correct about the wrong machine.

An address that only resolves where you are standing is a note, not a configuration. Compose fixes it by making the name real: it puts every service on one network and registers each service name in DNS. db resolves on your Mac, on a server, and in CI — because db is a thing you declared, not a thing the host offered you.

The file

One new file, server/compose.yaml. Read it before you run it — every line is a flag you typed by hand last lesson, or a thing you had no way to type at all.

services:
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: tasks
      POSTGRES_PASSWORD: tasks
      POSTGRES_DB: tasks
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./prisma/sql/tasks_app.sql:/docker-entrypoint-initdb.d/10-roles.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U tasks -d tasks"]
      interval: 2s
      retries: 15

  api:
    build: .
    env_file: .env.docker
    ports:
      - "3000:3000"
    depends_on:
      db:
        condition: service_healthy

volumes:
  pgdata:

Four things in there are new ideas rather than new syntax.

LineWhat it actually does
image: vs build:db is pulled from Docker Hub as-is; api is built from your Dockerfile, with . as the build context. You never write a Dockerfile for a database — somebody already did, better.
volumes: pgdata:A named volume, managed by Docker, mounted where Postgres keeps its data directory. Without this line the database is a scratchpad that dies with the container.
docker-entrypoint-initdb.dA convention of the postgres image: every .sql and .sh in that directory runs once, when the data directory is empty. Alphabetical, hence the 10-.
condition: service_healthydepends_on alone only orders starting. Postgres accepts connections several seconds after its container starts, so without the healthcheck your API boots, fails to connect, and exits. Start order is not readiness.

And the env file it reads

Rewrite server/.env.docker — every address in it now points at the other container, not at your Mac:

DATABASE_URL=postgres://tasks:tasks@db:5432/tasks
APP_DATABASE_URL=postgres://tasks_app:tasks_app@db:5432/tasks
NODE_ENV=development
ALLOWED_ORIGINS=http://localhost:5173
TRUST_PROXY=false
HOST=0.0.0.0
PORT=3000

Those passwords are not your Mac's passwords, and that is the point. This is a different database on a different machine that happens to be running on your desk. POSTGRES_PASSWORD: tasks in the compose file and tasks_app in your SQL script are throwaway values for a throwaway database. The day this goes to Fly.io, both come from the platform's secret store and neither is in a file. Your Mac's tasks_app password is still the one from lesson 41's script, still in .env, still unrotated. Fourth ask.

Now watch it fail on your own file

Start the database alone, and read the log:

cd server
docker compose up db

It will not come up. In the flood of init output:

ERROR:  relation "AuditLog" does not exist
STATEMENT:  REVOKE UPDATE, DELETE, TRUNCATE ON "AuditLog" FROM tasks_app;

Open prisma/sql/tasks_app.sql and look at what you wrote in lesson 41. The comment at the top says it: run this once, as the postgres superuser, against the tasks database. Against a database that already had fifteen migrations in it. Every statement in the file assumed tables. Now it is running against an empty one, and two different things go wrong — only one of them loudly.

StatementOn a full databaseOn an empty one
CREATE ROLE tasks_appmakes the loginmakes the login — fine
GRANT … ON ALL TABLESgrants on 8 tablessucceeds, grants nothing. Silent.
ALTER DEFAULT PRIVILEGEScovers future tablescovers all of them — this line is now doing the whole job
REVOKE … ON "AuditLog"the wallerrors, and aborts the init

A grant is a statement about rows that exist; a default privilege is a statement about rows that do not yet. You wrote both in lesson 41 and only needed one of them. On a fresh database the ordering inverts: ON ALL TABLES is the decoration and ALTER DEFAULT PRIVILEGES is the mechanism. The audit revoke is neither — it names one specific table, so it simply cannot run before that table is born.

The half-built volume

Before you fix anything: the init crashed partway. The data directory is not empty any more, so Docker will never run the init scripts again — it will start that half-configured database and act like nothing happened. This is the one moment where the throwaway machine is not a metaphor:

docker compose down -v

-v deletes the named volume. Without it you fix the SQL, run up again, and spend twenty minutes wondering why your change had no effect. Init is once per volume, and the only undo for a bad init is deleting the volume.

The fix: split the file by when it can run

Two files, because there are two moments. Cut the last REVOKE line out of prisma/sql/tasks_app.sql (keep its comment block — it is the best paragraph in your repo) and put it in a new file:

-- prisma/sql/audit-lockdown.sql
-- Lesson 53: split out of tasks_app.sql. This one names a TABLE, so it can
-- only run AFTER migrations. tasks_app.sql names only roles and defaults, so
-- it can run on an empty database -- which is what a container start is.
REVOKE UPDATE, DELETE, TRUNCATE ON "AuditLog" FROM tasks_app;

Then the full sequence, from nothing to a running app:

docker compose down -v                                   # throw the bad volume away
docker compose up -d db                                  # init runs clean now
docker compose run --rm api npx prisma migrate deploy     # 15 migrations, into the box
docker compose run --rm api npx prisma db seed            # users, a team, some tasks
docker compose exec -T db psql -U tasks -d tasks < prisma/sql/audit-lockdown.sql
docker compose up                                         # the whole stack

curl localhost:3000/health. Then log in at user1@example.com / correct horse battery and look at a list of tasks that exist nowhere on your Mac.

CommandWhy that one
migrate deployNot migrate dev. deploy applies pending migrations and nothing else — it never writes a new one, never prompts, never resets. The only migration command that belongs anywhere near a deploy.
run --rm apiA one-off container from the same image and env file, deleted when it exits. It reads DATABASE_URL — the owner role — so migrations keep running as tasks, exactly like lesson 42 decided.
exec -T db psqlexec runs inside the container that is already up. psql is in the Postgres image, so you need no client on your Mac. -T because you are piping a file in, not typing.

Prove the wall survived the move. It is one line, and it is the test lesson 41 taught you to run:

docker compose exec db psql -U tasks_app -d tasks \
  -c 'delete from "AuditLog";'
ERROR:  permission denied for table AuditLog

Why db instead of host.docker.internal?

Compose puts the services on one network and registers each service name in its DNS, so db resolves wherever the compose file runs. host.docker.internal is a Docker Desktop convenience that names the laptop, and there is no laptop on a server.

Why did the REVOKE abort the database init?

Init scripts run once, on an empty data directory, before a single migration. A GRANT ON ALL TABLES over zero tables succeeds silently; a statement naming "AuditLog" cannot. Split by when a statement can run: roles and default privileges at init, anything naming a table afterwards.

Why is condition: service_healthy needed?

Plain depends_on waits for the container to start, and Postgres accepts connections several seconds after that. The healthcheck polls pg_isready until it answers, so the API boots into a database that can talk. The same gap exists at deploy, at scale, and in CI.

See it drawn

Last lesson's diagram had one box inside your Mac reaching back out. Today there are two boxes and a network of their own — and the only thing that outlives down is the cylinder.

What you did not build, on purpose

left out
migrations on start no entrypoint script running migrate deploy before the app. Two containers starting at once would both try. It is a real deploy problem and it gets its own lesson.
the front end a third service, a static build, and the nginx config already sitting in deploy/. Not today.
a web profile for tests npm test still runs against your Mac's Postgres. It works, it is fast, and a second database would only give you two places for the suite to be wrong.
secrets throwaway passwords in a file you can read. Correct for a laptop, wrong for Fly.io, and the fix is the platform's, not yours.

Read this: Docker — Compose, and why, then the official postgres image docs. The second one is the more useful page today: the “Initialization scripts” and “Where to store data” sections are exactly the two things that bit you.

Then this: run docker compose down (no -v), then docker compose up, and log in again. Your seeded tasks are still there. Now do it with -v. That two-minute experiment is the whole idea of a volume, and you should feel it once rather than believe it.

Reference card: Environment — the DATABASE_URL host now has a third correct value (localhost, host.docker.internal, db), and which is right depends entirely on who is asking.
