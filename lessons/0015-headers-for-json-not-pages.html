Lesson 15 · Week 7–8 · API security

Security headers for a JSON API

Install Helmet, get thirteen headers. Your API sends JSON. Four of the thirteen matter, one is set wrong for you, and one can lock your own laptop out of localhost for a year.

In one minute

  • Third dependency: @fastify/helmet. New rule — take the library, then turn it down.
  • Helmet's defaults are written for an HTML page. You serve JSON.
  • Four earn their place: nosniff, a CSP of default-src 'none', X-Frame-Options: DENY, and HSTS in production only.
  • Cache-Control: no-store matters most and no plugin sets it. Six lines by hand.

The picture

The idea

Most Helmet defaults defend a browser rendering HTML: inline scripts, fonts, iframes, plugins. Your API returns application/json. Those headers are not wrong, they are simply about somebody else's problem.

The dangerous one is HSTS. It tells the browser "never use plain HTTP for this host again, for a year." Send it from localhost and you have pinned your own development machine. The fix is manual, per browser.

HSTS is gated on NODE_ENV === "production" and must stay that way.

The code

await app.register(helmet, {
  contentSecurityPolicy: {
    useDefaults: false,
    directives: { "default-src": ["'none'"], "frame-ancestors": ["'none'"] },
  },
  frameguard: { action: "deny" },
  hsts: process.env.NODE_ENV === "production" ? { maxAge: 31536000 } : false,
  // page-only, switched off:
  crossOriginOpenerPolicy: false,
  originAgentCluster: false,
  xDnsPrefetchControl: false,
  xDownloadOptions: false,
  xPermittedCrossDomainPolicies: false,
});

// the one no plugin sets — onSend covers 200s AND 400/403/404/429
app.addHook("onSend", async (_req, reply) => {
  reply.header("Cache-Control", "no-store");
});

onSend is the only hook that also runs for error replies. A 403 that says "forbidden" is still a reply you do not want cached in a shared proxy.

A library can be right about the facts and wrong about your situation. Those are two separate judgements.

Check yourself

Why add Cache-Control in onSend rather than a route hook?

A 401, 403 or 429 never reaches your handler's reply path. onSend is the last stop for every response, successful or not.

Do this

  1. npm test — 82 tests, seven new in src/routes/headers.test.ts.
  2. curl -i localhost:3000/health. Count the headers. Confirm no HSTS.
  3. curl -i localhost:3000/nope. The 404 must also carry Cache-Control: no-store.

See it drawn

app.register(helmet) sends all thirteen. This is what each one does to a reply that is JSON, not a page.

  • ✓X-Content-Type-Options: nosniff
    Stops the browser guessing your JSON is HTML.
  • ✎Content-Security-Policy: default-src 'self' 'none'
    Helmet permits loading from yourself. An API should permit nothing.
  • ✎X-Frame-Options: SAMEORIGIN DENY
    You frame nothing, ever.
  • ✓Strict-Transport-Security — production only
    On localhost it pins your whole host to HTTPS for a year.
  • ✓Cross-Origin-Resource-Policy: same-origin
    Blocks <script src> tricks. Cannot break fetch() — that is CORS mode.
  • ✓Referrer-Policy: no-referrer
    Harmless. Keep it.
  • ·Cross-Origin-Opener-Policy — about window.opener between pages
  • ·Origin-Agent-Cluster — a process-isolation hint for pages
  • ·X-DNS-Prefetch-Control — about links on a page
  • ·X-Download-Options — old Internet Explorer
  • ·X-Permitted-Cross-Domain-Policies — Adobe Flash
  • ·X-XSS-Protection: 0 — disables a filter you do not have
  • ·X-Powered-By removed — Fastify never sent one
  • +Cache-Control: no-store — hand-written
    No plugin sets it. Without it a cache can hand one user's reply to the next.

That is the lesson in one column. Helmet is right about the facts — every string above is spelled correctly and current. It is wrong about your situation, because it assumed you serve pages. Two separate judgements.

Where no-store has to sit

A rule with no exceptions belongs in the last hook, not in each route. Here is why — four of these replies never reach your handler:

request arrives
  onRequest → rate limit —→ 429 leaves here
  onRequest → helmet sets its headers
  routing —→ 404 leaves here
  body parse & zod validate —→ 400 leaves here
  preHandler → requireAuth —→ 401 leaves here
  preHandler → can() —→ 403 leaves here
  your handler — 200
  onSend → cache-control: no-store   ← every arrow above passes through here
bytes go out

Put no-store in a route and you cover the 200. Put it in onSend and you cover all seven. That is what the 404 test in src/routes/headers.test.ts is guarding.
