Lesson 59 · Week 15–16 · Front end + auth

The account nobody can make

Your deployed page has a sign-in form. It has no sign-up form. POST /auth/register has worked since lesson 5, and no browser has ever called it. Today you build the page that does. The trap is one line: register replies with a user, but it does not set a cookie. Believe the reply and the whole app thinks it is signed in when it is not.

In one minute

  • Two replies look the same, and only one carries a session. Login answers 200 + set-cookie. Register answers 201 and no cookie. Both bodies are {id, email}.
  • So never write the register reply into the session cache. useLogin does that on purpose. useRegister must not, or useSession() says “in” while every next request gets 401.
  • The fix is to chain, not to trust. Register succeeds → call login with the same two fields. The cookie comes from the second call, which is the only call that makes one.
  • Your API already hides the interesting failures. 409 means the email is taken; 429 means it was asked too often. The form shows both, in the API’s own words.
  • One new route, one new component, one new hook. No server change. No new dependency, 59 lessons.

Look at the route you are calling

This is already in server/src/routes/auth.route.ts. Read the last line of the handler.

const user = await createUser(email, await hashPassword(password));
if (!user) {
  throttleFail(email);
  return reply.code(409).send({ error: "email already registered" });
}
return reply.code(201).send(user);   ← no reply.header("set-cookie", ...)

Now the same place in /auth/login:

const session = await createSession(user.id);
reply.header("set-cookie", sessionCookie(session.id, session.expiresAt));
return reply.code(200).send(toPublic(user));

A reply that names a user is not a reply that logs one in. The session lives in the cookie, never in the body. Ask “did this response set a cookie?” before you ever write a user into the cache.

Build it — the hook

New file, web/src/features/auth/register.ts:

import { useMutation } from "@tanstack/react-query";
import { api } from "@/lib/api";
import { useLogin } from "@/features/auth/session";
import type { User } from "@/features/auth/session";

/**
 * Two calls, one button. Register makes the row; login makes the session.
 * ! Nothing here touches SESSION_KEY. useLogin's own onSuccess seeds it,
 * ! and it is allowed to, because ITS reply carried the cookie.
 */
export function useRegister() {
  const login = useLogin();

  return useMutation({
    mutationFn: async (credentials: { email: string; password: string }) => {
      await api.post<User>("/auth/register", credentials);   // 201, no cookie
      return login.mutateAsync(credentials);                 // 200, cookie
    },
  });
}

mutateAsync, not mutate: mutate returns nothing and swallows the error, so a failed second call would look like a successful signup. mutateAsync returns a promise, so a rejection travels up and the form shows it.

Build it — the form

New file, web/src/features/auth/register-form.tsx. It is login-form.tsx with four words changed, so copy that file and edit it:

minLength={8} is a hint, not a gate — lesson 23’s rule, and it still holds. The real wall is z.string().min(8) in server/src/schemas/auth.schema.ts. The attribute exists so the person is told before the round trip, not so the server can relax.

Build it — the route

In web/src/App.tsx, one line, inside the block that already exists:

<Route element={<RequireAnon />}>
  <Route path="/login" element={<LoginForm />} />
  <Route path="/signup" element={<RegisterForm />} />
</Route>

Inside RequireAnon, not beside it. A signed-in person opening /signup is bounced to / by the guard you already wrote in lesson 58’s commit — and when the chained login succeeds, that same guard is what moves them off the form. You navigate nothing by hand.

StatusThe form showsWritten by
400zod’s complaint about email or lengthRegister, auth.schema.ts
409“email already registered”the route, after createUser returned nothing
429“too many attempts, try again later”throttleCheck, lesson 11, keyed on the email

You need no new code for any of these. errorMessage(register.error, "Sign up failed") reads data.error already, and /auth/register is already in CREDENTIAL_ROUTES in web/src/lib/api.ts — so a 401 from this form is never mistaken for “your session died”. Past you left the door open for present you.

The 429 is deliberate and it is not rate limiting for its own sake. 409 versus 201 tells a stranger whether an address has an account here. The throttle makes asking that question a thousand times expensive.

Practice — three

Why must useRegister not seed the session cache?

The body is the same shape as login’s: {id, email}. What is missing is set-cookie. Write that user into SESSION_KEY and useSession() reports “in”, the guard lets them to /, and the first real request comes back 401.

Why mutateAsync rather than mutate for the login step?

mutate returns void and handles its error internally. So if register succeeded and login then failed, the outer mutation would still resolve, and the form would report success with nobody signed in. mutateAsync rejects, and the rejection is the outer mutation’s error.

What does minLength={8} on the input actually buy you?

Anyone can delete the attribute, or skip the page entirely and post to the API. The guarantee is z.string().min(8) on the server. The attribute is only a faster, kinder way to say the same thing — a hint, never a gate.
