Lesson 16 · Week 7–8 · API security

CSRF: who may write

An attacker's page does not want to read your reply. It wants your browser to send one DELETE, with your cookie, and it does not care what comes back.

In one minute

  • Reading is CORS. Writing is CSRF. Different attacks, never the same defence.
  • SameSite=Lax blocks the cross-site form POST. It does not block a state-changing GET.
  • New defence: Sec-Fetch-Site. The browser writes it and a page is forbidden to set it.
  • Nine lines in src/auth/csrf.ts, one hook. No token, no store, no new dependency.

The picture

Why CORS cannot help

CORS gates reading a reply. A CSRF attack throws the reply away. And an HTML form has been allowed to POST across sites since 1995, so it gets no preflight — CORS is never even consulted.

Why SameSite=Lax is not enough on its own

Attack shapeSameSite=LaxSec-Fetch-Site
Cross-site form POSTblockedblocked
Clicked link doing a GET writewalks throughblocked
Old browser, no headerblockedallowed †

Lax blocks unsafe methods. A top-level click is exactly how a user navigates, so GET is let through with the cookie attached. Hence the other rule: never write in a GET.

The code

// src/auth/csrf.ts — nine lines, no dependency
const SAFE = new Set(["GET", "HEAD", "OPTIONS"]);

export function allowed(method: string, site?: string, origin?: string) {
  if (SAFE.has(method)) return true;
  if (site) return site === "same-origin";
  if (origin) return ALLOWED_ORIGINS.includes(origin);
  return true;   // ponytail: not a browser, so it carries no victim's cookie
}
// src/app.ts — step 4, before anything that touches Postgres
app.addHook("onRequest", async (req, reply) => {
  if (!allowed(req.method, req.headers["sec-fetch-site"], req.headers.origin))
    return reply.code(403).send({ error: "forbidden" });
});

403, not 401. The cookie was perfectly valid — it is the caller that is wrong.

A library encodes the browser of the year it was written. Ask what year its problem was solved in before installing it.

† @fastify/csrf-protection exists and does the token dance. That pattern is a workaround for a header that has shipped in every major browser since March 2023. We skipped it.

Check yourself

Why can a malicious page not just set Sec-Fetch-Site itself?

Sec- is a forbidden header prefix. Browser code writes it; page JavaScript is not permitted to. That is the entire reason it can be trusted.

Do this

  1. npm test — 93 tests.
  2. curl -X POST -H 'Sec-Fetch-Site: cross-site' localhost:3000/teams. You want 403.
  3. Grep your routes for a GET that writes anything. There must be none.

See it drawn

Two different attacks. They never share a defence.

CORS — reading

“Let me see your reply.”

The attacker wants your data. The browser refuses to hand the body to a page from another origin. Your allow-list decides who gets an exception.

CSRF — writing

“Do this thing for me.”

The attacker wants an effect. They never read the reply, so CORS is irrelevant. Their page just needs your browser to send it, with your cookie.

Four shapes, and what actually stops each

Before lesson 16’s hook existed.

fetch(url, { method: "DELETE", credentials: "include" })
preflight: yes cookie: not sent server: never sees it

The browser stops it. The preflight comes back with no permission, so the real DELETE is never sent. Your server was not defended — it was never attacked.

<form method="POST" action="…"> — auto-submitted
preflight: none cookie: withheld server: 401

SameSite=Lax stops it. A form has POSTed across sites since 1995, so there is no preflight and CORS never sees it. One word in one cookie string is the whole defence.

Same form, if that cookie ever became SameSite=None
preflight: none cookie: SENT server: 415

Fastify stops it — by accident. No form-body parser is installed, so it answers 415. That is a refusal nobody decided on.

<a href> the victim clicks → a GET that changes data
preflight: none cookie: SENT server: 200 OK

Nothing stops it. Lax sends the cookie on a cross-site top-level GET. Only the fact that you have no such route. That rule lives in your head, not your code.

The new hook: allowWrite

First match wins. src/auth/csrf.ts, nine lines.

  1. 1 Method is GET, HEAD or OPTIONS allow

    Nothing to defend — as long as no GET writes. This line trusts you forever. It is shape four above, in code.

  2. 2 Sec-Fetch-Site: same-origin allow

    Our own page. The browser writes this header; Sec- makes it a forbidden header name, so a page cannot set it, change it or delete it.

  3. 3 Origin is in ALLOWED_ORIGINS allow

    The dev front end on :5173 is same-site, not same-origin. So is blog.app.example, which is not you. Trust the list, not the word “site”.

  4. 4 There was some Sec-Fetch-Site 403

    A browser spoke, and it said not-our-page. 403, not 401 — the cookie was perfect, the caller was not. A 401 says “log in again”, which the victim already did.

  5. 5 Neither header at all allow

    Not a browser: curl, Postman, a cron job. Only a browser can carry a victim’s cookie, so blocking buys nothing. OWASP says block. Dashed border = the one judgement call, marked ponytail:, one line to flip.

Where it runs: an app-level onRequest hook, step 4 in src/app.ts — after the rate limiter, before anything that touches Postgres. A forged write pays two string compares, not a session query.
