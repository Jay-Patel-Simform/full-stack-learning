Lesson 24 · Week 10 · Front end

403 vs 404

Tasks go on screen. The moment the page asks about a row, the server gains a second refusal — and the two mean completely different things. Getting the difference wrong is how a list leaks.

In one minute

  • 403 is the gate. It is decided from your role in this team, before anything looks at the row.
  • 404 is the row. where: { id, teamId } found nothing — because the task is in another team, or because it does not exist. Same word for both, on purpose.
  • 403 always wins, because the gate runs first. You can never get a 404 from a team you may not touch.
  • The cache key mirrors the URL: ["teams", teamId, "tasks"]. A key of ["tasks"] is one bucket for every team.
  • The error line on screen says what the server said and nothing more. A helpful message here un-blurs the 404.

The word pair

forbidden — “I know exactly what you asked for, and no.” About you. Answerable without reading a single row.
not found — “there is nothing here under that name.” About the row. Deliberately ambiguous: it covers both “not in this team” and “never existed”.

A refusal is an answer, and every answer teaches the asker something. Choose what it teaches.

Measured, on your API, just now

One account: Owner of Platform (431) and of 174, Viewer of Marketing (432), not in Legacy (11). Task 357 lives in Platform. Same PATCH, same cookie, five URLs:

PATCH /teams/431/tasks/357     own team, own task            200
PATCH /teams/174/tasks/357     team I own, task is elsewhere 404
PATCH /teams/174/tasks/999999  team I own, no such task      404   <-- same as above
PATCH /teams/432/tasks/357     team where I am a Viewer      403
PATCH /teams/11/tasks/1        team I am not in at all       403   <-- same as above

Read the two arrows. Line 2 and line 3 are indistinguishable, so an owner of 174 cannot use 174 to find out which task ids exist elsewhere. Line 4 and line 5 are indistinguishable, so a stranger cannot tell a real team from a made-up one — lesson 18's rule, still holding four lessons later.

Where each answer comes from. The 403 is requirePermission("task:update") in tasks.route.ts, a preHandler. The 404 is if (!task) return reply.code(404) in the handler, after updateTask(id, teamId, …) returned nothing. Two different files, in that order — which is why 403 always wins.

Which refusal you get tells you which question was asked first. The gate asks about you; only then does the query ask about the row.

Why the list route only ever says 403

GET /teams/:teamId/tasks has no row to miss. It answers 200 with [] for a team with no tasks, and 403 for a team that is not yours. An empty list and a forbidden list are different replies — and that is fine, because the 403 already refused to confirm the team.

GET /teams/432/tasks   Viewer, no tasks     200 []
GET /teams/11/tasks    not a member         403 {"error":"forbidden"}

A VIEWER holds task:read and nothing else, so this is the one task route they get — and it is exactly the screen you are about to build.

The code — type it yourself

Three pieces. Nothing here is in your app yet; read it, then write it.

1. web/src/features/tasks/tasks.ts — new file

import { useQuery } from "@tanstack/react-query";
import { api } from "@/lib/api";

export type Task = { id: number; title: string; done: boolean };

// The key mirrors the URL. Every guarded route since lesson 8 carries the team
// in the path, so the cache entry carries it too: one entry per team, never a
// single shared "tasks" bucket that a second team could read out of.
export const tasksKey = (teamId: number) => ["teams", teamId, "tasks"] as const;

export function useTasks(teamId: number) {
  return useQuery({
    queryKey: tasksKey(teamId),
    // sort names a COLUMN, so the server only accepts three strings (lesson 20).
    queryFn: async () =>
      (await api.get<Task[]>(`/teams/${teamId}/tasks`, {
        params: { sort: "id", dir: "asc" },
      })).data,
  });
}

The one line to stare at is the key. Drop the teamId out of it and the first team you open fills the bucket; the second team reads the first team's rows out of the cache and renders them, with no request and no 403 to stop it. The server never leaked. The cache did. A query key is not a name for a request — it is a claim about which answers are interchangeable.

2. web/src/features/tasks/tasks-panel.tsx — new file

import { errorMessage } from "@/lib/api";
import { useTasks } from "@/features/tasks/tasks";

export function TasksPanel({ teamId }: { teamId: number }) {
  const { data: tasks, isPending, error } = useTasks(teamId);

  if (isPending) return <p className="text-muted-foreground text-sm">Asking…</p>;

  // Say what the server said, and no more. A friendlier line here — "that task
  // belongs to another team" — hands back precisely what the 404 blurs.
  if (error !== null)
    return <p className="text-destructive text-sm">{errorMessage(error, "Could not load tasks.")}</p>;

  if (tasks.length === 0)
    return <p className="text-muted-foreground text-sm">No tasks yet.</p>;

  return (
    <ul className="grid gap-1">
      {tasks.map((task) => (
        <li key={task.id} className="flex items-baseline gap-2 text-sm">
          <span className="text-muted-foreground font-mono text-xs">
            {task.done ? "done" : "open"}
          </span>
          <span className={task.done ? "text-muted-foreground line-through" : ""}>
            {task.title}
          </span>
        </li>
      ))}
    </ul>
  );
}

Check yourself

You PATCH a task in a team where your role is Viewer. What comes back?

requirePermission is a preHandler: it refuses before updateTask is ever called, so the row is never looked for. A 404 is only reachable once the gate has already said yes. Measured above, line 4.

Why does a task in another team answer 404 rather than 403?

You passed the gate for this team, so "forbidden" would be a lie about your role and a fact about somebody else's row. 404 covers "elsewhere" and "nowhere" with one word. Nothing throws — updateMany reports zero rows and the handler chooses the code.

What breaks if the query key is ["tasks"] instead?

One key means one cached value. Open Platform, then open Marketing: Marketing reads Platform's tasks straight out of the cache, fresh for 30 seconds, with no request made. The API refused nothing because the API was never asked.

["tasks"]

Nothing was forbidden, because nothing was asked. A query key is not a name for a request — it is a claim about which answers are interchangeable. Leave the scope out of the key and you have told the cache that two teams are the same team.
