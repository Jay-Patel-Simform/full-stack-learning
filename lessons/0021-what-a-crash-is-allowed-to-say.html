Error handling: 4xx vs 5xx

Every wall you have built decides who gets in. This one decides what leaks out when something goes wrong — and until today, the answer was “everything”.

In one minute

  • Fastify's default: when your code throws, it sends err.message to the caller.
  • A Prisma error's message is your file paths, your source lines, and every column of the model.
  • The fix is one hook and one rule: split on the status, not on the error.
  • A 4xx was caused by the caller's input — tell them. A 5xx was caused by your code — tell the log.
  • Send back a requestId so the two halves can be joined.

The word pair

the caller's fault — a 4xx. Bad email, missing field, no session, too many requests. The message describes their input. Telling them is the whole point of the API.
your fault — a 5xx. Something in your code broke. The message describes your internals. The caller cannot act on it, and an attacker very much can.

Status code, not error type. It is the one label already on every error, and it already says whose fault it is.

Why does an error message contain source code at all? Because Prisma is trying to help you, at your terminal. That is correct behaviour for a developer tool. The bug is not Prisma's — it is that a developer-facing message reached a stranger, unchanged, because nobody stood in between.

The picture

What you shipped

Step 9 in src/app.ts, after the audit hook, before the routes:

app.setErrorHandler((err: FastifyError, request, reply) => {
  if ((err.statusCode ?? 500) < 500) return reply.send(err);

  request.log.error({ err }, "unhandled error");

  return reply.code(500).send({
    statusCode: 500,
    error: "Internal Server Error",
    message: "Internal Server Error",
    requestId: request.id,
  });
});

Five lines that matter. Take them one at a time.

LineWhy
err.statusCode ?? 500An error Fastify made carries its status. An error your bug made carries none — so missing means 500. The unsafe case is the default, not the exception.
return reply.send(err)Hand a 4xx straight back to Fastify's own formatting. You are not writing a second error format; you are choosing not to interfere.
request.log.error({ err })The detail moves, it does not vanish. Passing { err } (not err.message) makes the logger serialise the whole thing — type, message, stack.
requestId: request.idThe join. Fastify already puts reqId on every log line for free. Now the caller can say “error req-1” and you can find the exact stack.

The reply is now, every time, for every possible crash:

HTTP 500
{"statusCode":500,"error":"Internal Server Error",
 "message":"Internal Server Error","requestId":"req-1"}

And in your terminal, the same second:

{"level":50,"reqId":"req-1","err":{"type":"PrismaClientValidationError",
 "message":"\nInvalid `prisma.task.findMany()` invocation in\n/Users/...

Same incident, two audiences, one shared id. That is the whole design.

Why not just hide everything

You could reply {"error":"error"} to all of it. Do not. A 400 that will not say which field is broken makes your API unusable, and it protects nothing — the caller already knows what they sent.

too much

The left one is a 500: it names a variable in your code. The right one is a 400: it names a field in their request. Same instinct as lesson 18 — a reply should describe what the caller already knows, and nothing more.

How it sits with the other walls

You now have three hooks and a handler wrapped around every request, and their order is not an accident:

onRequest   rate limit, CSRF, requireAuth      before work happens
handler     the route                          the work
setErrorHandler  what a failure may say        when the work throws
onResponse  audit log                          after, knows the status
onSend      cache-control: no-store            on the way out

The error handler runs before onResponse, so your audit log still records the 500 — with the route, the user and the ip. Nothing you built last lesson stopped working. Check it yourself: npm run log.

Check yourself

Why fork on the status code instead of the error's type?

A 4xx means the caller caused it, a 5xx means you did. That is exactly the line you want to draw. Matching on error types means a new library ships a new class and your handler silently misses it — the status has no such gap.

An error arrives with no statusCode at all. What now?

err.statusCode ?? 500. An error with no status came from your own code, not from Fastify — which is precisely the case whose message you must not send. The default has to be the careful one.

What does requestId in the reply actually buy you?

Hiding the detail is useless if you cannot get it back. Fastify stamps reqId on every log line already, so returning request.id costs nothing and turns “it broke” into one grep. It is not a secret and proves nothing.

What this does NOT fix

GapWhy it is still open
Nothing reads the logsThe stack is in your terminal and dies with the process. An error tracker is week 13–14.
A 4xx can still leakYou pass those through on purpose. If you ever throw a 400 whose message names an internal, this handler will happily send it. That is on the thrower.
No LIMIT on the task listStill open from lesson 20. Week 9–10.
