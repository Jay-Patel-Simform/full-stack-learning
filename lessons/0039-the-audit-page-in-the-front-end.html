Two copies of one promise

The server is the only place that knows what GET /teams/:teamId/audit returns. The browser cannot import audit.schema.ts — different process, different build. So the front end writes down what it expects. That written-down expectation is a copy, and copies go stale.

Today you go stale twice, in two different ways:

Copy one — checked

type Action =
  | "task:read"
  | ...
  | "team:delete";   // no audit:read

can.includes("audit:read")

TS2345: Argument of type '"audit:read"' is not assignable to parameter of type 'Action'.

Red before you run it.

Copy two — believed

type AuditRow = {
  at: Date;          // it is a string
};

row.at.toLocaleString()

No error. Compiles, runs, and prints the raw ISO text on screen.

Green all the way to production.

Both lines are wrong in the same way — a local copy no longer matches the server. The difference is only which direction the value travels.

checked — you hand a value to typed code. The compiler compares what you handed over against the type, and can say no. "audit:read" is an argument, so it is checked.
believed — a value arrives from outside the program: JSON, localStorage, a URL. Nothing compares it to anything. The type is your claim about it, and the compiler takes your word.

A type on data you received is a promise you made, not one the compiler kept. This is record 0034 again, in the browser: a declared type is believed, not checked.

That is why row.at.toLocaleString() is so nasty. It is not even a crash. Date has toLocaleString, and String has toLocaleString as well, and on a string it returns the string. So the method exists, the call succeeds, and the page shows a timestamp nobody can read. Measured, both lines, same input:

const at = "2026-09-11T06:58:31.158Z";

at.toLocaleString()              -> "2026-09-11T06:58:31.158Z"   // wrong, silent
new Date(at).toLocaleString()    -> "9/11/2026, 12:28:31 PM"     // right

Your seventh bug with no error message, and the first one that lives in a type. The fix is to stop lying: type the field string, because that is what comes down the wire, and make the conversion a visible line of code.

Why the server's z.date() is still correct. A response schema describes the value your handler returns, and Prisma hands the handler a real Date. Then JSON.stringify calls Date.prototype.toJSON, which is defined to return ISO text — see MDN, Date.prototype.toJSON. Both types are right about their own side. The wire is where the type changes, and nothing on the wire enforces either one.

Why is at typed string in the browser?

JSON has six value types and none of them is a date. JSON.stringify calls Date.prototype.toJSON, which returns ISO text, so text is what crosses the wire. Prisma is innocent — it hands the handler a real Date, and the serializer is where the type changes.

Why the silent one survives

Date.prototype.toLocaleString exists

A wrong type usually crashes on the first method call. Not here. The method exists on a string, and on a string it hands back the string. So the call succeeds, the page renders, and the only symptom is an ugly timestamp.
