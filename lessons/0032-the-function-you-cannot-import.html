Testing a module you cannot import

Your server has 146 tests. Your front end has zero. That gap has been open for six lessons. Today you close it — and the closing is not about picking a test tool. It is about a smaller, sharper fact: editPages, the helper you wrote last lesson, cannot be imported on its own. Not by a test, not by anything. Fixing that is the lesson. Then the very first test you run will tell you something about React Query that you did not know.

In one minute

  • A test has to import the thing it tests. That is the whole requirement, and it is where this stops being easy.
  • Measured: importing tasks.ts from a test fails. Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@/lib'. The @/ alias is a Vite feature. Node has never heard of it.
  • Two ways out: buy a runner that is Vite, or move the function. Vitest is 34 MB installed. Moving editPages into its own file is 0 MB. You already know which one this workspace picks.
  • Measured: a real QueryClient runs in plain Node. No browser, no jsdom (a fake browser written in JavaScript). React Query’s cache is just an object.
  • And then the test finds a bug in your mental model. Measured: after an edit that changes nothing, setQueryData hands back the exact same object you started with. Your three spreads were thrown away. This is deliberate, it has a name, and lesson 31 did not tell you about it.

Start from the requirement, not from the tool

Every conversation about front-end testing starts with tool names. Ignore all of them for two minutes. A test is a file that does this:

import { theThing } from "somewhere";
// call it, check what came back

That first line is the entire problem. So pick your target and try the import. The target is easy to pick — you want the smallest piece of real logic with no screen in it. That is editPages: it takes a cache and a function, and it walks pages. Nothing to click, nothing to render.

Measured: the import fails

I wrote the smallest possible test file in web/ and ran it with Node’s own test runner, no install:

what I ran

// probe.test.ts
import { tasksKey } from
  "./src/features/tasks/tasks.ts";

$ node --test probe.test.ts

what happened

Error [ERR_MODULE_NOT_FOUND]:
Cannot find package '@/lib'
imported from
  .../features/tasks/tasks.ts

Read the error carefully. It is not complaining about your test. It is not complaining about TypeScript — Node stripped the types without a word. It walked into tasks.ts, hit line 6, import { api } from "@/lib/api", and looked for a package on npm called @/lib.

The @/ alias is a rule you wrote in vite.config.ts. Vite obeys it. tsc obeys it, because you repeated it in tsconfig. Node was never told. Three tools, three separate copies of the same rule, and the test runner has none.

New term: import graph. When you import a file, you also get everything it imports, and everything those import, all the way down. That whole tree is the import graph. You did not ask for axios. You asked for tasksKey, a three-line function that builds an array — and the graph under it reaches @/lib/api, which reaches axios and the session key. You cannot take one leaf without the branch it hangs on.

The choice, and it is only two

Buy a runner that is Vite

Vitest. It reads your vite.config.ts, so @/ just works, and nothing in your source moves. Measured install: 34 MB. Real cost here is lower — you already have Vite — but it is a new dependency, a new config surface, and a second test command in a project that already has one.

Move the function

Give editPages its own file whose import graph contains no @/. Then node --test runs it. Measured install: 0 MB. Cost: one new file, and you have to notice which imports are real.

Take the second one. Not only to keep the no-new-dependency streak — 32 lessons now — but because the first option pays money to avoid noticing something true. The function was hard to import because it was welded to a file full of network code. That is worth knowing about your own code. Vitest would have hidden it.

When to change your mind. This trade flips the day you want to test a component — clicking the “Load more” button, checking the row disappears. That needs a fake browser and React Testing Library, and hand-rolling it is not lazy, it is silly. That day, install Vitest. Today you are testing a function that walks an array, and it needs none of it.

The word pair

runtime import — the file is really loaded when your program runs. import { api } from "@/lib/api". Node must find it or crash.
type-only import — you only wanted the shape, for the compiler. import type { Task } from "./tasks.ts". TypeScript deletes the line before Node ever sees it. It is not in the import graph.

Thirteenth pair, and this one is the mechanism that makes today work. edit-pages.ts mentions Task, TaskPage, InfiniteData and QueryClient — four names from two files, one of which reaches axios. Every one of them is import type. At runtime the new file imports nothing at all. That is why Node can load it.

Your tsconfig.app.json already has verbatimModuleSyntax: true, which is what forces you to write the word type instead of letting the compiler guess. Until today that flag looked like tidiness. It is the flag that made this possible.

Measured: React Query runs in a terminal

The thing people assume is that front-end code needs a browser to test. Here is the measurement that says otherwise — a real QueryClient, the same class your app builds in lib/query-client.ts, under plain node --test:

const c = new QueryClient();
c.setQueryData(["a"], 1);
c.getQueryData(["a"])          => 1

$ node --test    pass 1, fail 0

No browser. No jsdom. A cache is a Map with rules around it, and none of those rules need a document. The parts of a front end that need a browser are the parts that touch the screen. That is a much smaller share of your code than it feels like — and it is the share you should test last, not first.

And now the thing the test told me

I ran four candidate tests against the moved function before writing this. Three passed. The fourth failed, and it failed for a reason that is more interesting than the test:

edit that changes nothing   -> same box back?   true
edit that removes one row   -> same box back?   false
                            -> page 0 replaced? true
                            -> page 1 reused?     true   <- the same object

Lesson 31 told you to build a new box at all three levels, because React compares by reference. That is still true — you must build it. What lesson 31 did not say is what happens next. React Query looks at the box you built, compares it to the old one field by field, and quietly gives the old objects back wherever nothing actually changed.

structural sharing — the new value is compared to the old one deeply. Any part that is unchanged keeps its original object. You get a new reference exactly where there is new data, and nowhere else.

So your three spreads are not wasted, and they are not the last word either. They are a proposal. React Query accepts the parts that differ and rejects the parts that do not. Delete a row from page 0 and page 1 comes back as the identical object — so any component reading page 1 sees no change and does not re-render. That is the point. It is a performance feature you have been getting for free since lesson 22.

The first test you ran on your front end corrected something you believed. Six lessons of “we should have tests” produced a real finding in under a minute. That is the argument for tests, and it is better than any argument I could write.

The trap this sets for your test file. If you write a test whose edit is (items) => items and then assert “the box is a new object”, it will fail — and the code is correct. Assert on contents, not on identity, unless identity is the actual thing you mean to check. This is the number one way a first test suite ends up lying to you.

Check yourself

Why did node --test fail to import tasks.ts?

Node stripped the TypeScript without complaining — that has been built in since Node 22, and your machine runs 22.23.1. The error named '@/lib', and it named it as a package: Node looked in node_modules for something called @/lib and did not find it. The @/ rule lives in vite.config.ts and is repeated in tsconfig.app.json. Two copies, and the test runner reads neither. An alias is a bundler convenience, not a language feature.

Why can edit-pages.ts be imported when tasks.ts cannot?

Not calling the network is true but is not the reason — tasksKey does not call the network either, and importing it still failed. The reason is that every import in edit-pages.ts is import type. TypeScript deletes those lines entirely, so at runtime the file imports nothing and nothing has to be resolved. It mentions Task, which lives in tasks.ts, which imports @/lib/api — and that is fine, because that mention never survives to runtime. Testability here is a property of the import graph, not of what the function does.

Your edit changes nothing. What does setQueryData store?

Measured: true for “same box back”. React Query walks the value you returned against the value it held, and keeps the original object for every part that is deeply equal. This is called structural sharing. Your spreads still have to happen — you must never mutate the cached object — but what you build is a proposal, not the final answer. The payoff is real: delete a row from page 0 and page 1 keeps its identity, so components reading page 1 skip the re-render.

Why test editPages before testing the task list on screen?

You cannot know in advance which code is most likely to be wrong — if you knew, you would fix it instead of testing it. You pick editPages because of what it costs: it is a function in, a function out, no clicking and no rendering, so it runs in Node with zero setup. Testing the panel means a fake browser, React Testing Library and Vitest — three new things at once, before you have written a single passing front-end test. Start where the setup is nothing, get one green line, then buy the heavier tools when the cheap ones genuinely run out.

3. What the cache keeps after a write

You delete task 2 from page one. Your updater spreads all three levels and hands back a brand new box. Here is what is actually stored:

measured — @tanstack/react-query 5.102.8
box                  new object  ← something changed inside
 └─ pages          new array
    ├─ page 0      new object  ← the row left from here
    └─ page 1      SAME object  ← your spread was discarded
edit
box identity
items => items  changes nothing
unchanged
items.filter(...)  removes a row
new

Structural sharing. What you build is a proposal. React Query compares it to what it held and keeps the old object everywhere nothing really changed. New reference where there is new data, and nowhere else — so a component reading page 1 never re-renders.

Both rules from lesson 31 survive, with a footnote: never mutate (mutating skips the comparison entirely and nothing re-renders), and always spread (the spread is what lets the comparison happen). You just do not get to decide the outcome.
