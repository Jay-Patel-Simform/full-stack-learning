Lesson 68 · Week 13–14 · Testing

The first test that needed a browser

Sixty-seven lessons, no new dependency. Today that ends, and it should end loudly — because the streak was never a rule, it was a habit of asking “what would this cost me?” before typing npm install. So: here is the question you cannot test today, here is what it costs to be able to, and here is the argument for paying.

In one minute

  • The streak breaks, on purpose. Four packages. The reasoning is the lesson; the packages are the consequence.
  • Your two front-end tests test functions, not screens. Nothing has ever proved that a button is disabled, because nothing has ever rendered one.
  • Vitest, not Jest, and the reason is one file. vite.config.ts already holds your @/ alias and your React plugin. Vitest reads it. Jest would need a second copy of both.
  • Test what a user can do — type, click, read — never what the component holds in useState.
  • The first test is the trim rule from lesson 26, which has been “still open” and is about to become enforced.

The question you cannot answer today

Here is a line from web/src/features/teams/new-team-form.tsx:

<Button type="submit" disabled={createTeam.isPending || name.trim() === ""}>

Three real decisions live in that one attribute. A box holding only spaces must not submit. A submit already in flight must not start a second one — lesson 26’s double-click guard, measured as ids 360 and 361. And the moment the request settles, the button must come back.

Now look at what your suite can see. web/package.json:

"test": "node --test \"src/**/*.test.ts\""

Note the extension: .test.ts. Your two existing tests — edit-pages.test.ts and audit-row.test.ts — test exported functions with inputs and outputs, and they are good tests. But node --test has no DOM to render into, no JSX transform to read <Button> with, and no idea what @/components/ui/button resolves to. Three separate walls, and any one of them is fatal.

You have been testing the parts of the front end that are not the front end. Pure functions were the cheap half, and taking the cheap half first was right. The half left over is the half users touch.

The argument for spending, in order

Could you avoid it? Honestly, no

The lazy instinct says: shim a DOM yourself, keep node --test, streak intact. Follow that through. You would need a DOM implementation, a JSX transform, module resolution for @/, CSS imports turned into no-ops, and import.meta.env defined. Five pieces of machinery, each a real dependency or a hand-written hack, assembled by you and debugged by you.

Take the library when the problem has no decisions left in it. Lesson 12’s rule, fourth outing. “Render a React component in Node and click a button” is a solved problem with no interesting choices inside it. Writing it yourself buys a worse version and a maintenance job.

Vitest or Jest? One file decides it

This is not a taste question. Look at what your app already depends on to run at all:

// web/vite.config.ts, already on disk
plugins: [react(), tailwindcss()],
resolve: { alias: { "@": path.resolve(import.meta.dirname, "./src") } },

Every component you would test imports @/components/ui/button and is written in JSX. Vitest uses that file — same resolver, same transform, same aliases, because it is Vite. Jest would need its own module mapper and its own transform, configured to agree with Vite’s, forever. Two configs that must not drift is a bug generator; lesson 29 was an entire lesson about exactly that shape.

Your laptop is resource-tight and these are direct packages only; the installed tree will be bigger. Measure it yourself, honestly:

cd web

npm i -D vitest jsdom @testing-library/react @testing-library/user-event

Measured on this machine: 254M → 297M. +43 MB and 69 packages — four times the 10.7 MB the table above adds up to, because those are direct packages and every one of them has its own tree. That gap is the reason to run the command rather than trust the registry.

Say the number before you decide, not after. A cost you did not measure is a cost you will discover at the worst moment. This is the fourth time a dependency has been weighed out loud in this course, and the second time the bigger-but-faster option lost because the speed bought nothing at your scale.

The setup — three small edits

1. web/vite.config.ts

One new key. Nothing else in the file moves:

/// <reference types="vitest/config" />
import path from "node:path";
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import tailwindcss from "@tailwindcss/vite";

export default defineConfig({
  plugins: [react(), tailwindcss()],
  resolve: { alias: { "@": path.resolve(import.meta.dirname, "./src") } },
  server: { port: 5173, strictPort: true },
  // The tests reuse everything above -- the alias and the JSX transform are
  // the whole reason this runner and not another one.
  test: {
    // A DOM, only in tests. The app still builds for a real browser.
    environment: "jsdom",
    setupFiles: ["./src/test-setup.ts"],
    // `test`, `expect` and `vi` without importing them in every file.
    globals: true,
  },
});

2. web/src/test-setup.ts — new file, four lines

// ! Unmount between tests, or the second test finds two forms in the document
// ! and every getBy* throws "found multiple elements". The error names the

3. web/package.json

"test": "vitest run",

One runner, not two. Check it before you believe it: run npm test straight after this edit, before adding a single new test.

it fails here, and this is the correction
Your two existing tests do NOT run unchanged. Measured: both files fail to load, with Cannot bundle Node.js built-in "node:test" imported from src/features/audit/audit-row.test.ts. The jsdom environment is a browser-shaped one, and node:test and node:assert are Node built-ins that cannot be bundled into it. Nine tests, zero of them running.
The fix is to convert them, and it is mechanical. Delete the two node:test / node:assert imports — test and expect are globals now — and turn the assertions into expect calls. If you want to keep the original style readable, six one-line wrappers at the top of the file do it: const expectSame = (a: unknown, b: unknown) => expect(a).toBe(b); and so on for not.toBe, toEqual, not.toEqual, toThrow, toBeTruthy. Then all nine pass.
Why this is the right order anyway. You met this failure with the runner as the only change, which is exactly why the loop says to swap the runner first. Had you written three new tests at the same time, the error would have arrived with four suspects instead of one.

“It will just work” is a prediction, and this one was wrong. One runner is still the right call — two runners means two ways to write a test and two commands to remember — but the price was a fifteen-minute conversion nobody had costed. Write the price down next to the decision, not in your memory of it.

The test

New file web/src/features/teams/new-team-form.test.tsx. Note the extension — .tsx, because it contains JSX.

import { render, screen, waitFor } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { MemoryRouter } from "react-router";
import { api } from "@/lib/api";
import { NewTeamForm } from "./new-team-form";

// * The component needs two providers to exist at all: React Query for the
// * mutation, a router for useNavigate. This helper is the whole reason a
// * component test feels heavier than a function test -- a component is a
// * thing in a tree, not a thing with arguments.
function renderForm() {
  const client = new QueryClient({
    // ! retry: false, or the 403 test waits for three backed-off retries
    // ! and then times out. The default is right for an app and wrong for
    // ! a test, every time.
    defaultOptions: { queries: { retry: false }, mutations: { retry: false } },
  });
  return render(
    <QueryClientProvider client={client}>
      <MemoryRouter>
        <NewTeamForm />
      </MemoryRouter>
    </QueryClientProvider>,
  );
}

// ? Spy on the axios instance, not on fetch and not on the module. One line,
// ? no module mocking, and errorMessage() stays the real one.
const post = () => vi.spyOn(api, "post");

afterEach(() => vi.restoreAllMocks());

test("a name of only spaces cannot be submitted", async () => {
  renderForm();
  const user = userEvent.setup();

  // ! getByRole, not getByTestId. The test asks the same question a screen
  // ! reader asks, so it fails if the button stops being a button.
  const button = screen.getByRole("button", { name: /create team/i });
  expect(button).toBeDisabled();

  await user.type(screen.getByLabelText(/team name/i), "   ");
  // ? the trim rule, finally enforced somewhere. Three spaces is still empty.
  expect(button).toBeDisabled();
});

test("a real name submits the trimmed value", async () => {
  const spy = post().mockResolvedValue({ data: { id: 7, name: "Design" } });
  renderForm();
  const user = userEvent.setup();

  await user.type(screen.getByLabelText(/team name/i), "  Design  ");
  await user.click(screen.getByRole("button", { name: /create team/i }));

  await waitFor(() => expect(spy).toHaveBeenCalledTimes(1));
  // ! The assertion that matters: "Design", not "  Design  ". Asserting only
  // ! that a request happened would pass with the spaces still attached.
  expect(spy.mock.calls[0]?.[1]).toEqual({ name: "Design" });
});

test("a refused create leaves the typed name on screen", async () => {
  post().mockRejectedValue({
    isAxiosError: true,
    response: { status: 403, data: { error: "forbidden" } },
  });
  renderForm();
  const user = userEvent.setup();

  const input = screen.getByLabelText(/team name/i);
  await user.type(input, "Design");
  await user.click(screen.getByRole("button", { name: /create team/i }));

  // * Lesson 26's decision, now a test: clear the box in onSuccess, never in
  // * onSubmit. A 403 that eats the sentence you typed is the rudest thing a
  // * form can do, and nothing has ever stopped this regressing.
  await screen.findByText(/could not create team/i);
  expect(input).toHaveValue("Design");
});
one thing that will trip you
toBeDisabled() and toHaveValue() are not Vitest matchers. Measured, by walking into it: Error: Invalid Chai property: toBeDisabled. They come from @testing-library/jest-dom, a fifth package. You can skip it and write expect((button as HTMLButtonElement).disabled).toBe(true) instead — uglier, zero install. Try the plain version first and see whether the ugliness bothers you across three tests; if it does, that is a measured reason to add the fifth package rather than a guessed one.

What not to test, and why it matters more than what to

The temptation with a new tool is to test everything it can reach. Resist, with a rule:

Test what a user can do; never test what a component knows. “name state equals Design” is a test of your implementation — rename the variable and it fails while the app is fine. “The button is enabled and the request carried Design” is a test of behaviour, and it survives every rewrite that keeps the behaviour.

Which is exactly why every query above is getByRole or getByLabelText rather than a test id. A test that finds the button the way a screen reader finds it fails the day the button stops being reachable — so your accessibility becomes load-bearing instead of decorative.

Practice — three

Why Vitest rather than Jest, specifically?

Both runners are parallel and both are fast enough for three tests, so speed decides nothing here. What decides it is vite.config.ts: it already defines the @/ alias every component imports through, and the React plugin that turns JSX into JavaScript. Vitest is Vite, so it reads that file and agrees with your app by construction. Jest would need its own module mapper and transform, configured to match, and kept matching forever — two configs that must not drift, which is the exact shape lesson 29 spent a whole lesson unpicking.

Why is retry: false needed in the test QueryClient?

React Query retries failed requests with a growing delay, which is good behaviour for a real app on a flaky network. In the 403 test the request is meant to fail, so the default turns a one-line assertion into three backed-off attempts, and the test sits there until the runner gives up — reported as a timeout, which names the wrong problem entirely. A default that is right for an app is frequently wrong for a test, and this is the cheapest example of it you will meet.

Why query by role and label instead of a test id?

A test id is an extra handle attached for the test’s convenience, and it survives changes that would leave a real person stranded — a button that lost its accessible name, an input whose label stopped being associated with it. getByRole and getByLabelText find elements the same way assistive technology does, so the test fails precisely when the interface has become unusable. Accessibility stops being a separate checklist item and becomes something your suite is already checking.

What you did not build, on purpose

left out
MSW, a mock HTTP server the “proper” answer, and a sixth package plus a handlers file plus a server lifecycle. vi.spyOn(api, "post") is one line and tests the same behaviour. Reach for MSW when you are testing several requests interacting — not for one POST.
@testing-library/jest-dom nicer matchers and nothing else. Argued above: try it ugly first, and let the annoyance be the measurement.
tests for the other five screens one form, three tests, done. A suite that arrives all at once is a suite nobody read. Add the next test the next time you change a screen, not today.
end-to-end tests (Playwright) a genuinely different tool answering a genuinely different question — does the whole system work, browser to Postgres. It is also a browser download and a CI story, and you have one user and a working app. The day a deploy breaks something these tests could not see is the day to start that conversation.
