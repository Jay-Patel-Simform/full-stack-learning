Globs and test discovery

You wrote the test I asked for in lesson 34. It is correct. It is a good test — it even has the all.length > 0 assertion, which is the part most people leave out. Then I ran npm test and got 154. Not 155. Your test file is on disk, it passes when I run it by itself, and your test suite has never once executed it. Nothing said so.

In one minute

  • Measured: 22 test files on disk, 21 reached the runner. The missing one is src/log-redact.test.ts — yours.
  • The shell expands the pattern, not the test runner. tsx --test src/**/*.test.ts — by the time tsx starts, the * characters are gone and it has a plain list of 21 file names.
  • ** means “any depth” in zsh and “one level” in sh. Your terminal is zsh. npm run uses sh. Same command string, two different answers: 155 and 154.
  • Why it worked for 34 lessons: every test file was one directory deep, so src/*/*.test.ts happened to match them all. Your new file sits at the top of src/, so it fell out.
  • The fix is two quote marks. Quoted, the shell leaves the pattern alone and the runner globs it itself — with real ** support. Node’s own docs ask for those quotes.
  • The lasting rule: a new test is not trusted until you have watched it fail. A pass can mean “it ran and was fine” or “it never ran at all”, and the two look identical.

Nothing changed except who read the *.

Who expands the star

glob — a pattern that matches file names. *.ts, src/**/*.test.ts. The word comes from the old Unix program that did it.
shell expansion — the shell finds the files that match the pattern and replaces the pattern with their names before starting your program. Your program never sees the pattern.

So this command:

tsx --test src/**/*.test.ts

is not what tsx receives. tsx receives this:

tsx --test src/audit/audit.test.ts src/auth/can.test.ts src/auth/csrf.test.ts
    src/auth/session.test.ts ... src/routes/teams.test.ts
    (21 names, and your file is not one of them)

There is no pattern left to be wrong about. The runner ran every file it was given, and every one passed. 154, green, honest — and blind.

globstar — the name for ** meaning “any number of directories, including none”. zsh has it switched on. sh and bash do not, unless you run shopt -s globstar. Without it, ** is treated as a plain * — one level, no more.

So in sh, your pattern is really src/*/*.test.ts: exactly one directory between src and the file. Count the paths:

src/routes/tasks.test.ts       one directory   matched
src/auth/can.test.ts           one directory   matched
src/log-redact.test.ts         zero directories  missed
src/a/b/deep.test.ts           two directories  would also be missed

This is why the bug waited 34 lessons to appear. Every test file you had ever written lived in src/routes/, src/auth/ or src/audit/. The pattern was wrong the whole time and the mistake had nothing to hit.

Why web does not have the bug

Look at the two scripts next to each other. They differ by two characters:

server/package.json

"test": "LOG_LEVEL=silent tsx
  --test src/**/*.test.ts"

web/package.json

"test": "node
  --test \"src/**/*.test.ts\""

When the pattern is quoted, the shell does not touch it. The runner gets the pattern itself and does its own matching — and Node’s matcher does support ** at any depth. That is why web finds src/features/tasks/edit-pages.test.ts, three levels down, which the sh version could never have matched.

The Node documentation says this in one sentence, and it is the sentence to remember: the glob patterns should be enclosed in double quotes on the command line to prevent shell expansion. Node — running tests from the command line.

The fix, and the one you should not pick

Do this

"test": "LOG_LEVEL=silent tsx
  --test \"src/**/*.test.ts\""

Measured: 155 passing. The scope stays named, so a stray .test.ts in prisma/ or in generated code is not picked up.

Not this

"test": "LOG_LEVEL=silent tsx
  --test"

Also 155 passing — with no argument the runner uses its own default patterns. Shorter, and it works today. But it searches the whole project, and src/generated/prisma/ is regenerated code you do not control.

The rule that outlives this bug

A test you have never seen fail is not a test. It is a file.

You now have three ways a test can report success while proving nothing, and you have met all three in two lessons:

FailureWhat you seeWhere you met it
The file never ranA count that did not go upToday
It ran, but had nothing to readGreen, forever, even when brokenLesson 34, the silent log level
It ran and asserted the obviousGreen whatever the code doesLesson 20, the sort test whose two orders agreed

One habit covers all three, and it costs ten seconds: after writing a test, break the code it tests and watch the test go red. Then put the code back. You did this on purpose in lesson 34 exercise 3. Today it stops being an exercise and becomes the routine.

Check yourself

Who turned src/**/*.test.ts into a list of file names?

The shell. It matched the pattern, replaced it with 21 names, and only then ran tsx. The runner had no pattern to interpret and no way to know a file was missing. This is also why quoting fixes it — a quoted argument is passed through untouched, and then the runner does the matching with its own rules.

Why did the bug stay hidden for 34 lessons?

In sh, ** is just *, so the pattern meant “exactly one directory under src”. Every test file you had ever written was in src/routes/, src/auth/ or src/audit/, so all 21 matched. The pattern was wrong from lesson 6 and had nothing to lose until you put a file at the top of src/.

Your suite prints 154 passing and 0 failing. What has it proved?

Only the second. A runner reports on what it was handed. Files it never received are not failures and not skips — they are invisible. That is why the number itself is the signal: you expected 155, you got 154, and the gap was the whole bug. Write the expected count down every session, as these lessons do.
