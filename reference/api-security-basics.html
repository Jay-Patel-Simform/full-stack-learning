API security basics

Quick-reference sheet. Print it. Lines get added as lessons land.

The one rule

Never trust input. Never trust the caller's identity claim. Check both, on the server, every request.

Status codes you will actually use

CodeMeaningUse when
200OKRead or update worked.
201CreatedYou made a new row.
204No contentDelete worked; nothing to return.
400Bad requestInput failed validation.
401UnauthenticatedWho are you? No or bad credentials.
403UnauthorizedI know you, you may not. Role lacks permission.
404Not foundNo such row — or hiding a 403 on purpose.
409ConflictDuplicate email, version clash.
429Too many requestsRate limit tripped. Send Retry-After in seconds.

401 vs 403 in one line: 401 is about identity, 403 is about permission.

Validation snippets

// Params are input too

Zod + Fastify wiring (declare, do not remember)

// once, at app setup
app.setValidatorCompiler(({ schema }) => (data) => {
  const r = (schema as ZodType).safeParse(data);
  if (r.success) return { value: r.data };
  return { error: new Error(
    r.error.issues.map((i) => `${i.path.join(".") || "(root)"}: ${i.message}`).join("; ")
  ) };
});
app.setSerializerCompiler(({ schema }) => (data) =>
  JSON.stringify((schema as ZodType).parse(data)));

// per route
app.post("/tasks", { schema: {
  body: CreateTask,            // input wall
  params: TaskParams,          // path text is input too
  querystring: TaskFilter,     // so is the query string
  response: { 201: TaskPublic } // output whitelist: unlisted fields dropped
}}, handler);

Rules: a compiler returns { value } or { error } and never throws. A failed input schema means the handler never runs (400). A response schema is a whitelist — the only reliable stop for leaked fields.

Rate limiting login (lesson 11)

Count the thing the attacker has only one of. That is the account, never the IP.

Limits to remember: an in-memory Map dies on restart and is per-process. It also has to be size-capped, because anything keyed on caller input is a store the caller can fill. Real answer to patient guessing: MFA.

Rate limiting the whole API (lesson 12)

Two layers, two keys. The account stops guessing; the connection stops volume. Neither covers the other.

// src/app.ts -- BEFORE the routes. 100 requests per IP per minute.
await app.register(rateLimit, {
  global: false,                 // see the warning below
  max: 100, timeWindow: "1 minute", cache: 5_000,
});
app.addHook("onRequest", app.rateLimit());   // app hooks run before route hooks

Why not global: true? The plugin's global mode attaches its check per route, after that route's own onRequest. So a route behind requireAuth would run the session query and answer 401 before counting — a blocked request still costs a query. One app-level hook runs first. The cheap check goes in front of the expensive work, every time.

QuestionAnswerBecause
What is the key?request.ip.An unauthenticated flood has no account in it. Volume is what one address cannot spread away.
Write it or install it?Install.Reject a library when its defaults are wrong. Take it when the problem has no decisions left.
Headers you getx-ratelimit-limit / -remaining / -reset, plus retry-after on a 429.A client can slow down before it is pushed.
Turn it off for one routeconfig: { rateLimit: false }Only with a reason written next to it.
Behind a proxy?trustProxy — at deploy, not before.Believe a header only when something you control writes it.
What to testThe wiring, not the counting.Test what you decided, not what you installed.

Limits to remember: in-process counters (restart forgets, two processes double the limit — the plugin takes a redis option); 100 requests can still be 100 huge bodies (bodyLimit) or 100 unpaginated queries; a real botnet is a layer above your app.

CORS (lesson 13)

CORS is advice to a browser. It does not stop curl, a script, or another server. Access control is requireAuth + can().

await app.register(cors, {
  origin: ALLOWED_ORIGINS,   // exact strings, from env. Never true, never an unanchored regex.
  credentials: true,         // needed for the session cookie
  methods: ["GET", "POST", "PATCH", "DELETE"],
});
  • origin: true reflects the caller's Origin. With credentials: true that is an account-data leak.
  • origin: "*" is safe only because the browser refuses to send cookies to a wildcard.
  • Preflight = an OPTIONS the browser sends first for writes. No preflight answer, no real request.
  • A denied origin still gets 200 — just no access-control-allow-origin header.
curl -si -H 'Origin: https://evil.example' localhost:3000/health | head -8

Security headers for a JSON API (lesson 15)

Headers are advice to a browser, same as CORS. They stop nobody with curl. Helmet's defaults are written for an HTML page — four of thirteen apply to JSON.

HeaderValue we sendWhat it stops
X-Content-Type-OptionsnosniffBrowser guessing your JSON is HTML and running script in it.
Content-Security-Policydefault-src 'none';frame-ancestors 'none'Anything loading, if the reply is ever rendered. And framing.
X-Frame-OptionsDENYFraming, for old browsers. Helmet's default is SAMEORIGIN.
Cross-Origin-Resource-Policysame-origin<script src> / <img> tricks. Not your front end's fetch() — that is CORS mode.
Strict-Transport-Securitymax-age=31536000; includeSubDomains, production onlyA downgrade to plain http.
Cache-Controlno-store — hand-written, no plugin sets itA cache keeping one user's private reply and serving the next person.
await app.register(helmet, {
  contentSecurityPolicy: {
    useDefaults: false,          // without this, default-src stays 'self'
    directives: { "default-src": ["'none'"], "frame-ancestors": ["'none'"] },
  },
  xFrameOptions: { action: "deny" },
  hsts: process.env.NODE_ENV === "production"
    ? { maxAge: 31_536_000, includeSubDomains: true }
    : false,                     // NEVER from localhost
  crossOriginOpenerPolicy: false, originAgentCluster: false,
  xDnsPrefetchControl: false, xDownloadOptions: false,
  xPermittedCrossDomainPolicies: false,
});

app.addHook("onSend", async (_req, reply) => {
  reply.header("cache-control", "no-store");   // onSend = every reply, incl. 400/403/404/429
});
  • HSTS on localhost is hard to undo. The browser writes it down per host and stops asking. You clear it by hand, per browser.
  • Switched off, all page-only: Cross-Origin-Opener-Policy, Origin-Agent-Cluster, X-DNS-Prefetch-Control, X-Download-Options, X-Permitted-Cross-Domain-Policies. Helmet's X-XSS-Protection: 0 and X-Powered-By removal are no-ops here.
  • Your React page needs its own CSP, from nginx. This one only covers API replies.

CSRF — who asked for this write (lesson 16)

Reading is CORS. Writing is CSRF. Different attacks, never the same defence. CSRF = another site's page makes your browser send a write with your cookie, and never reads the reply.

Decision, src/auth/csrf.ts, in order:

CheckResultWhy
Method is GET/HEAD/OPTIONSAllowNothing to defend — as long as no GET writes. This line trusts you.
Sec-Fetch-Site: same-originAllowOur own page. Browser-written, page cannot forge it (Sec- = forbidden header name).
Origin in ALLOWED_ORIGINSAllowDev front end on another port: same-site but not same-origin. A sibling subdomain is same-site too, so trust the list, not the word.
Any Sec-Fetch-Site at all403A browser spoke and it was not our page. 403 not 401 — the cookie was fine, the caller was not.
Neither headerAllow (our call)Not a browser: curl, Postman, cron. No victim cookie exists. OWASP recommends blocking; one-line switch, marked ponytail:.

Sec-Fetch-Site values: same-origin / same-site / cross-site / none (user typed it, bookmark). Baseline in all browsers since March 2023.

  • SameSite=Lax is defence in depth, not the defence. It blocks unsafe methods only, so a state-changing GET walks through. And one word changed to None removes it silently.
  • When Lax is a browser default it is looser: cookies also ride a cross-site POST for two minutes after being set. Write SameSite=Lax explicitly and that grace does not apply.
  • An HTML form has POSTed cross-site since 1995. No preflight. Preflight only happens for non-simple requests, so CORS never sees the classic attack.
  • Hook lives at app level in onRequest, before requireAuth: a forged write pays two string compares, not a session query.
# refused
curl -si -X POST localhost:3000/auth/logout \
  -H 'Sec-Fetch-Site: cross-site' -H 'Origin: https://evil.example' | head -1
# allowed
curl -si -X POST localhost:3000/auth/logout -H 'Sec-Fetch-Site: same-origin' | head -1

Mass assignment — the key you did not name (lesson 17)

Strip is safe. Reject is safe and honest. Both refuse an unnamed key; only one tells you it happened. Also called autobinding (Spring), object injection (PHP). CWE-915; merged into API3:2023 Broken Object Property Level Authorization.

The rule, src/app.ts, inside the validator compiler:

app.setValidatorCompiler(({ schema, httpPart }) => {
  const s = httpPart === "body" && schema instanceof ZodObject
    ? schema.strict()
    : (schema as ZodType);
  return (data) => { /* safeParse as before */ };
});
InputStrict?Why
Request bodyYesThe client composed it on purpose. An unnamed key is an attack or a typo, and both deserve a 400.
Request querystringNoCollects keys nobody asked for: utm_source, fbclid, proxy cache-busters. Strict here turns a shared link into a 400.
Request paramsNoMeasured: strict params break nothing today — params hold exactly the declared URL segments. Left out for consistency with the query.

Zod behaviour worth memorising (docs):

FormUnknown key
z.object({...})Stripped, silently. The default. Safe, mute.
z.strictObject({...}) / .strict()Rejected: Unrecognized key: "x"
z.looseObject({...})Passed through. This is the hole.
  • .partial() makes every field optional and allows none. Add .refine((p) => Object.keys(p).length > 0) or an empty PATCH answers 200 and changes nothing.
  • schema.strict() returns a new schema and runs once at route registration. Zero per-request cost.
  • An as cast is not a check. patch as {title?: string} is true only because bodies are strict. Say which rule keeps the promise, in a comment.
  • Strict checks whether you named a key, never whether naming it was wise. AddMember names role on purpose; what stops escalation is the rank rule in can().
  • Your zod schema is the allow-list and TaskPublic is the DTO — two of OWASP's three mitigations, since lesson 2.
# refused, and it names the key
curl -sb /tmp/c.txt -X POST localhost:3000/teams/1/tasks \
  -H 'content-type: application/json' -d '{"title":"forged","ownerId":1}'
# {"statusCode":400,...,"message":"(root): Unrecognized key: \"ownerId\""}

User enumeration — the reply that says who exists (lesson 18)

Hide it, or charge for it. Those are the only two moves. An oracle is any reply that tells a stranger whether an account exists. OWASP WSTG-IDNT-04.

Three channels. Check all three, every time.

ChannelThe leakThe close
Message“wrong password” vs “no such user”One string for both. Byte-identical.
Status code409 vs 201; 404 vs 403; a real email flipping to 429 while a fake one stays 401Same code for both, and key the throttle on the typed email so an unknown address throttles too.
ClockNo user → skip the hash → answer in 2 ms instead of 237 msHash anyway, against DUMMY_HASH.
// auth/password.ts -- a hash of nothing, with the real settings
export const DUMMY_HASH =
  `scrypt$${N}$${r}$${p}$${Buffer.alloc(16).toString("base64")}$${Buffer.alloc(64).toString("base64")}`;

// auth.route.ts -- no branch on `user` before the hash
const user = await findUserByEmail(email);
const ok = await verifyPassword(password, user?.passwordHash ?? DUMMY_HASH);
if (!user || !ok) { throttleFail(key); return reply.code(401).send({ error: "invalid email or password" }); }

Where enumeration survives: login is the route everyone hardens. Register, forgot-password, and invite-by-email are the ones that leak. Audit a new route against the rules you already wrote — and note that rules living in an app-level hook (CSRF, strict bodies) are inherited for free, while rules living in a handler (one message, throttle) are not.

The two designs, and there are only two:

ReplyLeakCost
A — hide it202 "check your email", alwaysNoneNeeds a mailer, a token table, unverified accounts
B — charge for it201 / 409, throttled per emailFull, but slow and loggedNine lines. Bulk attacks die; five probes stay free.

Timing rule that reads backwards: “cheap check first” (lesson 12) holds only when the cheap check leaks less. On register, checking the email before hashing would be faster and would open a timing oracle. A wasted hash can be load-bearing.

One address, one account. Normalise at the door, never at the query:

// schemas/auth.schema.ts -- validation goes on the RIGHT of .pipe()
const emailField = z.string().trim().toLowerCase();
export const Register = z.object({ email: emailField.pipe(z.email().max(254)), ... });
  • Zod chains run left to right. z.email().trim() validates the untrimmed string, so a pasted " a@b.com " is a 400. Clean first, then .pipe() into the check.
  • Half a normalisation is worse than none. Lower-casing the throttle key but not the lookup gave two accounts for one person and a green test claiming case was handled.
  • Backfill old rows in a data-only migration: UPDATE "User" SET email = lower(email) WHERE email <> lower(email);. Let it hit the @unique and roll back if duplicates exist — only a human can pick which row is the real person. Find them with SELECT lower(email), count(*) FROM "User" GROUP BY 1 HAVING count(*) > 1;.
  • toLowerCase() is not a Unicode normaliser. jаy@x.com (Cyrillic а) stays a separate row.

Testing a timing defence: assert both paths are slow (> 100 ms), never that the two times are close. A loaded laptop makes identical paths differ by 200 ms; it cannot make scrypt free. A flaky security test gets deleted, which leaves no test at all.

Audit log — who did what, when (lesson 19)

A request log is about the server. An audit log is about a person. Neither replaces the other. OWASP Logging Cheat Sheet, A09:2021.

Request log (logger: true)Audit log (a table)
Knows whoNo — the line is written before auth resolvesYes — request.userId
Queryablegrepwhere "userId" = 7 order by at desc
KeptDays, then rotatedAs long as you decide

Write it in one onResponse hook, never in a handler. It is the only hook that knows both halves of the row — who asked (requireAuth set request.userId upstream) and what the answer was (reply.statusCode). A 401 or 403 never reaches a handler, so a log line in a handler records only the requests that were allowed. That is the opposite of an audit log.

// audit/audit.ts -- the decision, three lines, its own test file
const SAFE_METHODS = new Set(["GET", "HEAD", "OPTIONS"]);
const REFUSALS = new Set([401, 403, 429]);
export function shouldAudit(method: string, status: number): boolean {
  return !SAFE_METHODS.has(method) || REFUSALS.has(status);
}

// app.ts -- step 9, after everything
app.addHook("onResponse", async (request, reply) => {
  if (!shouldAudit(request.method, reply.statusCode)) return;
  await writeAudit({
    userId: request.userId,                              // undefined on a 401
    route: request.routeOptions.url ?? "(no route)",     // the PATTERN, not request.url
    status: reply.statusCode, method: request.method, ip: request.ip,
    params: request.params,
  });
});
  • Every write, plus every refusal — never every read. A refused GET is not a read, it is an attempt: a walk through /teams/1..500 makes no writes at all. But one row per successful GET is 40 million rows of nothing a month, so the table gets truncated and then there is no audit log at all. Third use of a store keyed on caller input is a store the caller can fill.
  • Store the route pattern, never request.url. /teams/:teamId/tasks is one of a short fixed list. A URL is caller input: 8 KB long if they like, and it may carry a token somebody pasted into a query string. Put the ids in their own JSON column.
  • No @relation to User. The one model that must not cascade — onDelete: Cascade would delete the evidence the moment the account it accuses is deleted. Nullable too, because a 401 has no user and is still a row worth having.
    userId Int? // a plain Int. No relation, so no cascade.
  • The write is free to the caller. onResponse fires after the reply is flushed. Measured: a 401 answered in 1.3 ms and still left a row.
  • Testing it: app.inject() resolves before onResponse finishes, so poll for the row — never sleep. The polling is the proof the caller does not wait.
  • Gotcha: request.params holds raw strings until zod coerces them. A 401 row records {"teamId":"249"}; a 403 row records {"teamId":999999}. Same column, two JSON types.
  • Still not solved: nobody reads it. A log with no alert is archaeology. And nothing prunes it — the table only grows.
