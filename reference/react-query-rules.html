React Query, the rules so far

Every rule the front end has earned across lessons 22–31, on one page. Print it and keep it next to web/src.

The one-line rules

Server state lives in the cache. No useState copy, no useEffect sync.A copy drifts, and the copy that drifts is the one with no test.22, 25
Three session states, not two: undefined asking, null out, User in.Booting into “signed out” flashes a login form at someone signed in.22

Read: the shape of a query

export const tasksKey = (teamId: number) => ["teams", teamId, "tasks"] as const;

export function useTasks(teamId: number) {
  return useQuery({
    queryKey: tasksKey(teamId),
    queryFn: async () => (await api.get<Task[]>(`/teams/${teamId}/tasks`)).data,
  });
}

isPending = no answer yet. error !== null = the server said no. data = the answer. Handle all three, in that order, before the happy path.

Write: the shape of a mutation

export function useSetTaskDone(teamId: number) {
  const client = useQueryClient();
  return useMutation({
    mutationFn: async ({ id, done }: { id: number; done: boolean }) =>
      (await api.patch<Task>(`/teams/${teamId}/tasks/${id}`, { done })).data,
    onSuccess: (task) =>
      client.setQueryData<Task[]>(tasksKey(teamId), (tasks) =>
        tasks?.map((t) => (t.id === task.id ? task : t)),
      ),
  });
}

And the same shape when the reply is empty. Two differences, both forced by the 204: no type parameter, and the id comes from the second argument.

export function useDeleteTask(teamId: number) {
  const client = useQueryClient();
  return useMutation({
    mutationFn: async (id: number) => {
      await api.delete(`/teams/${teamId}/tasks/${id}`);   // no <Task>, no .data
    },
    onSuccess: (_nothing, id) =>
      client.setQueryData<Task[]>(tasksKey(teamId), (tasks) =>
        tasks?.filter((t) => t.id !== id),
      ),
  });
}

Useful fields on the returned object: mutate, isPending, error, and variables — the payload currently in flight, which is how one row knows to disable itself while the others stay live.

After a write: which move?

The reply is…DoCost
the whole changed rowsetQueryData, map it over the old one0 extra requests
a bare 204 (a delete)setQueryData, filter out the id from variables0 extra requests
a new row, an unpaged list sorted id&ascsetQueryData, append it0 extra requests
a new row, and the list is paged (lesson 31)invalidateQueries — the row may belong to a page you never fetched1 request per page held
a deleted row, paged, any number of filters cachededitPages on the prefix — setQueriesData drops it from all of them0 extra requests
a changed row, and the list is filtered (lesson 33)invalidateQueries on the prefix — the change may move the row out of the list1 request per page held, mounted keys only
a new row that must be sorted ininvalidateQueries1 extra request, correct order
a change that touched other queries tooinvalidateQueries on each key1 request each, and honest

Invalidate when the write changed something you were not told about. Otherwise you are asking a question you have already been answered.

Paging: useInfiniteQuery

One key, an ordered list of replies. The recipe, from lesson 31:

useInfiniteQuery({
  queryKey: tasksKey(teamId),
  queryFn: async ({ pageParam }) =>
    (await api.get<TaskPage>(url, {
      params: { sort: "id", dir: "asc", cursor: pageParam },
    })).data,                      // the WHOLE page, not .items
  initialPageParam: undefined as number | undefined,
  getNextPageParam: (last) => last.nextCursor ?? undefined,
});

// in the component
const tasks = data.pages.flatMap((page) => page.items);
{hasNextPage && <Button disabled={isFetchingNextPage}

query = one key, one answer. infinite query = one key, a growing list of answers. Everything that reads or writes that key has to know which — and the type checker will only tell you about the reads.

Editing a paged cache

function editPages(client, teamId, edit: (items: Task[]) => Task[]) {
  client.setQueryData<InfiniteData<TaskPage>>(tasksKey(teamId), (data) =>
    data === undefined ? data : {
      ...data,                                   // new box
      pages: data.pages.map((page) => ({         // new array
        ...page, items: edit(page.items),        // new page
      })),
    },
  );
}

Three spreads, on purpose: the box, the array, the page. The undefined branch is required — the updater runs even when the entry was collected while the write was in flight.

Filters: the key is the question

export type TaskFilter = { done?: boolean; q?: string };

// the PREFIX - every mutation talks to this
export const tasksScope = (teamId: number) => ["teams", teamId, "tasks"] as const;

// the WHOLE key - every read talks to this
export const tasksKey = (teamId: number, filter: TaskFilter) =>
  [...tasksScope(teamId), filter] as const;

useInfiniteQuery({
  queryKey: tasksKey(teamId, filter),
  queryFn: ({ pageParam }) => api.get(url, {
    params: { sort: "id", dir: "asc", cursor: pageParam, ...filter },
  }),
  placeholderData: keepPreviousData,   // the key changes; do not blank the screen
  ...
})
The filter is…Change it and…Then “Load more” sends…
not in the key0 requests. Same entry, still fresh. The screen does not react.the new filter with the old cursor — measured 1 row where 4 belong, and the pages of two questions land in one array
in the keya new entry, so a request with no cursorthe right cursor for the right list

A cursor is a bookmark in one list. Hand it to a different list and it is still a valid number pointing at the wrong place — the server cannot tell, and answers.

Two notes on hashing keys. React Query drops undefined values when it hashes, so { done: undefined } and {} are the same entry — which is why clearing a filter to undefined is safe. And axios drops an undefined param, so an absent filter sends no query string at all. Verified: {sort:"id",dir:"asc",cursor:undefined,done:false} → ?sort=id&dir=asc&done=false.

Structural sharing: what actually gets stored

You return a new box. React Query does not store it as-is. It deep-compares your value against the one it held and keeps the original object for every part that did not change. Measured on 5.102.8, deleting one row from a two-page cache:

LevelAfter the writeEffect
the boxnew objectsubscribers re-run
pages arraynew arraythe list is rebuilt
page 0 — the row left herenew objectre-renders
page 1 — untouchedthe same objectdoes not re-render
any edit that changes nothingthe same boxnothing re-renders at all

So the three spreads are still required — mutating in place skips the comparison entirely and the screen never updates. You just do not get to decide the outcome. New reference where there is new data, and nowhere else.

Testing this without a browser

A real QueryClient runs under plain node --test. No jsdom, no Vitest. The blocker is never the browser — it is the @/ alias, which Vite and tsc know and Node does not.

The rule: a function is testable when its runtime import graph
has no @/ in it. Type-only imports are erased, so they cost nothing.

// web/src/features/tasks/edit-pages.ts
import type { InfiniteData, QueryClient } from "@tanstack/react-query";
import type { Task, TaskPage } from "./tasks.ts";
// -> at runtime this file imports NOTHING. node --test can load it.

// web/package.json
"test": "node --test \"src/**/*.test.ts\""

Install Vitest the day you test a component — a click, a rendered row. That needs a fake browser, and hand-rolling one is not worth it. Until then: 0 MB.

The reply is not the type you wrote

The browser cannot import the server's zod schemas, so every reply type in web/ is a hand-kept copy. Copies go stale. Which staleness you hear about depends only on the direction the value travels.

The cure for a believed type is a runtime check — parse the reply with a schema in queryFn — and it costs a copy of zod in the bundle. Not paid yet, on purpose. Until it is, the honest move is to declare the type the wire really carries.

Glossary

TermMeaning here
query keyThe identity of a cached answer. Same key = the app claims the answers are interchangeable.
key prefixThe first part of a key. Not an entry itself — it matches every entry starting with it. What invalidateQueries and setQueriesData take.
whole keyOne exact entry, filter included. What a useQuery reads and setQueryData writes.
membershipWhether a row still answers the question a list is asking. Contents come in the reply; membership does not.
setQueriesDataSame updater, run over every entry matching a prefix. One call, all filters.
keepPreviousDataShow the last key's answer while the new key loads. isPending stays false, isPlaceholderData is true.
staleTimeHow long a cached answer is used without asking again. Zero for anything that decides what screen you get.
idempotentSending it twice lands where sending it once did. {done:true} is; toggle is not.
authoritative replyA response that is the new state, not a receipt. It is what makes setQueryData honest.
in flightSent, not yet answered. The window a second click does damage in. isPending is exactly this window.
idempotency keyA value the caller invents so the server can recognise a repeat of the same create and return the first reply. Week 13.
204 No ContentSuccess with no body, and it must not have one. The answer moved into the status line.
variablesThe payload of the mutation currently in flight, and the payload onSuccess gets as its second argument. The only copy of your request you still hold.
soft deleteA deletedAt column instead of a removed row. What real undo needs. Not built.
optimistic updateWriting the cache in onMutate, before the server answers, with a rollback in onError. Not used yet, on purpose.
infinite queryOne key holding an ordered list of replies. data.pages plus the pageParams each was fetched with.
pageParamThe value queryFn receives to fetch one page. Here it is the cursor. undefined means the first page.
getNextPageParamThe only function that reads nextCursor. Its return becomes the next pageParam; undefined means there is no next page.
InfiniteData<T>The cache shape: { pages: T[]; pageParams: unknown[] }. Not an array, and it has no .map.
flatMapThe one line that turns pages back into the flat list the UI wanted. Placed after the loading and error returns, never before.
structural sharingReact Query deep-compares your new value to the old one and reuses the old objects wherever nothing changed. Free render skipping.
import graphEverything a file pulls in, and everything those pull in. What decides whether a test can load your function.
type-only importimport type. Deleted before the code runs, so it is not in the import graph. verbatimModuleSyntax makes you write the word.
checkedA value you hand to typed code. The compiler compares it to the type and can refuse it.
believedA value arriving from outside the program. The type is your claim about it; nothing verifies it.
ISO string"2026-09-11T06:58:31.158Z". What every Date becomes in JSON, via Date.prototype.toJSON.
controlled inputAn input whose value comes from React on every render. The reason a refused write un-ticks the box for free.
runtime guardA function that checks a believed value's actual shape before anything trusts it, e.g. assertAuditPage. Turns believed into checked without a validator library.
type predicate(v: unknown) => v is T. Narrows the type only if the function's body actually checked it — the check and the claim are the same code.
