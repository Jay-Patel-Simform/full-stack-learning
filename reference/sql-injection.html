SQL injection and allowlists

Quick-reference sheet. Print it. The decision at the top answers every case below.

The one question

Is the caller's input a value or an identifier? A value can be a parameter. An identifier cannot — so it needs a list.

KindExamplesDefence
valuea title to match, an id, a date, a page sizeparameter — free, automatic
identifiercolumn in ORDER BY / GROUP BY, table name, ASC/DESCallowlist you wrote

Prisma: which call is safe

CallValuesInjectable?
prisma.task.findMany({ where })parameterisedno
$queryRaw`... = ${v}` (tagged template)parameterisedno
$queryRawUnsafe(`... = '${v}'`)glued into the textyes
$queryRawUnsafe(sql, v)parameterisedno — values only

The rule: a tagged template gets the fixed text and the ${} values as two separate arrays. It cannot mix them. Backticks safe, Unsafe( + ${ not.

The two failure modes, both silent

# 1. a parameter in an identifier slot: accepted, then IGNORED
ORDER BY ${"title"}       -> unsorted
ORDER BY ${"nonsense!!"}  -> unsorted, identical

# 2. a Fastify route with no querystring schema: validation SKIPPED
schema: { params: X }             -> ?sort=anything answers 200
schema: { params: X, querystring: Y }  -> ?sort=anything answers 400

Neither throws. Test for them by asserting a reordering, never just a 200.

The allowlist, in this codebase

// src/schemas/task.schema.ts -- the enum IS the allowlist
export const TaskQuery = z.object({
  sort: z.enum(["id", "title", "createdAt"]).default("id"),
  dir: z.enum(["asc", "desc"]).default("asc"),
});

// src/routes/tasks.route.ts -- without this line the schema does nothing
schema: { params: TeamParams, querystring: TaskQuery, response: { ... } }

// src/store/task.store.ts -- sort is a KEY, so it is only ever safe upstream
orderBy: { [sort]: dir }

Allowlist, not denylist. ownerId is a real column and still refused. Not-on-the-list beats does-it-exist.

Writing a sort test that cannot lie

// titles chosen so id order and title order DISAGREE
const TITLES = ["cherry", "apple", "banana"];
// then assert the ORDER, not the status code
assert.deepEqual(titles(res), ["apple", "banana", "cherry"]);

Do not declare a response schema for a framework reply

// WRONG -- the serializer drops `message`, every 400 becomes {"error":"Bad Request"}
response: { 200: z.array(TaskPublic), 400: ErrorReply, 403: ErrorReply }

// RIGHT -- 403/404 are replies WE write; 400 is Fastify's, shaped
//          { statusCode, error, message }. Leave it alone.
response: { 200: z.array(TaskPublic), 403: ErrorReply }

A validation message describes the caller's input, so it is safe to send. "sort: Invalid option: expected one of \"id\"|\"title\"|\"createdAt\"" is the API contract.

What an allowlist does not fix

  • The 500 body. Prisma's error message carries absolute file paths, line numbers and your source comments. Fastify sends it. The allowlist stops one route reaching that; only an error handler stops the rest.
  • Identifiers built from input at all. If you ever need a dynamic table name, the list is still the only answer — quote_ident makes it valid SQL, not authorised SQL.
  • Volume. A sortable list with no LIMIT is a free full-table read.
