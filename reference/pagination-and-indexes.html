Pagination and indexes

Quick-reference sheet. Print it. Every list route in this API should pass the four checks at the top.

The four checks for any list route

#CheckWhat it costs if you skip it
1Is there a default limit?The caller decides how much memory one request uses.
2Is there a maximum limit??limit=999999999 puts you back at zero.
3Is the sort order unique?A cursor into an unstable order skips rows, silently.
4Does the query select only what the response sends?Wasted query, and secrets in memory for nothing.

The one question

Is the caller asking you to count to a place, or to look up a place? Counting gets slower every page. A look-up does not.

offset / skipcursor / keyset
SQLOFFSET 4980 LIMIT 20WHERE id >= 4980 LIMIT 20
Rows read for page 2505,00020
Cost as pages go deepergrowsflat
Jump to “page 7”yesno — next/prev only
Row inserted mid-readshifts every later pageunaffected
Use it foradmin tables with page numbersfeeds, infinite scroll, APIs

Offset is not forbidden. It is fine when the list is small and the user wants page numbers. It is wrong for anything that grows.

The store recipe

export async function listTasks(
  teamId: number,
  { sort, dir, limit, cursor }: TaskQueryInput,
): Promise<{ items: Task[]; nextCursor: number | null }> {
  const rows = await prisma.task.findMany({
    where: { teamId },
    orderBy: [{ [sort]: dir }, { id: dir }],   // 3. tiebreak makes it unique
    take: limit + 1,                            // 1. one extra = "is there more?"
    ...(cursor ? { cursor: { id: cursor }, skip: 1 } : {}),
  });
  const items = rows.slice(0, limit);
  return { items, nextCursor: rows.length > limit ? items.at(-1)!.id : null };
}
LineWhy
take: limit + 1Answers “is there a next page?” without a second COUNT(*). The extra row is already in the index you are walking.
orderBy: [..., { id: dir }]Not optional. A non-unique sort key leaves ties in an order Postgres never promised, and may answer differently next time. A cursor is a position in that order.
skip: 1Steps over the cursor row itself. Without it, every page repeats its first row.
.slice(0, limit)The extra row is for you, not for the caller. Never send it.
nextCursor: nullMeans “that was the last page”. The front end stops asking.

The schema half

export const TaskQuery = z.object({
  sort: z.enum(["id", "title", "createdAt"]).default("id"),
  dir: z.enum(["asc", "desc"]).default("asc"),
  limit: z.coerce.number().int().min(1).max(100).default(20),
  cursor: z.coerce.number().int().positive().optional(),
  done: z.stringbool().optional(),              // NOT z.coerce.boolean()
  q: z.string().trim().min(1).max(100).optional(),
});

export const TaskPage = z.object({
  items: z.array(TaskPublic),
  nextCursor: z.number().nullable(),
});

z.coerce because query strings are text. .max(100) because a limit the caller can raise without a ceiling is not a limit. And the reply is an object, not an array — an array has nowhere to put “there is more”.

Filters, and the two traps in them

where: {
  teamId,
  ...(done === undefined ? {} : { done }),
  ...(q === undefined ? {} : { title: { contains: q, mode: "insensitive" } }),
},
TrapMeasuredFix
z.coerce.boolean() on "false"true — it is JavaScript's Boolean(), and a non-empty string is truthy. ?done=false would filter for done.z.stringbool(): knows true/1/yes/on and false/0/no/off, 400 for anything else
Prisma containsfound 2 of 4 rows a person would call a match — Postgres LIKE reads capital lettersmode: "insensitive" → ILIKE, seen as ~~* in the plan
...(done && { done })silently drops done: false — the filter people use mosttest === undefined, always
where: { teamId, done }TS2375 under exactOptionalPropertyTypes: an optional prop may be absent or a boolean, never present-and-undefinedthe spread is load-bearing, not tidiness

Coercion converts; parsing decides. coerce.number() is fine — Number("abc") is NaN and zod still refuses it. Boolean() can never fail, and a conversion with no failing state is not a check.

A cursor is a bookmark in one list. The moment a list takes filters, a cursor is only valid for the filter it came from. Measured: ?done=true&cursor=103, where 103 came from the unfiltered list, returned 1 row where 4 belong — no error, because on the server it is a perfectly ordinary request. This is why the filter belongs in the front end's query key: a new key has no cursor.

A leading % ends index help. title ILIKE '%buy%' uses the teamId index to find the team's rows, then filters every one of them (Rows Removed by Filter: 8). Free at 12 rows. At a million rows per team the answer is a trigram index (pg_trgm) — measure before you reach for it.

Changing an array reply into an object is a breaking change. Budget for it: measured on this codebase, 4 tests and 1 front-end line. If nothing breaks when you change a response shape, nothing was checking it.

Reading a query plan in four lines

EXPLAIN ANALYZE SELECT * FROM "Task"
  WHERE "teamId" = 7 ORDER BY "createdAt" DESC LIMIT 20;
What you seeWhat it means
Seq ScanRead the whole table. Correct and fast on a tiny table — Postgres ignores indexes below a few hundred rows. Bad news on a big one.
Index Scan using XUsed index X to find rows. Read the Index Cond: line to see which part of your WHERE the index actually answered.
Sort under a LimitThe smell. Everything matching had to be collected and sorted before the LIMIT could apply. A compound index on (filter, sortkey) removes it.
rows= at the bottom vs the topRows read vs rows returned. rows=5000 in and rows=20 out is work you paid for and threw away.

Measured on this project, 5,000 rows in one team

QueryIndexPlanTime
ORDER BY createdAt DESC LIMIT 20(teamId)Sort, rows=5000 in0.814 ms
same(teamId, createdAt)Index Scan Backward, rows=200.025 ms
ORDER BY id ASC LIMIT 21(teamId)Index Scan on Task_pkey, no sort0.017 ms
same(teamId, id)Index Scan, no sort0.025 ms
whole list + include: { owner: true }—2 queries, 5000 rows20 ms
take: 20, no include—1 query, 20 rows3 ms

Add an index for a Sort you measured, not for a column that looks important. Every index also slows down every INSERT.

A plan is about your data, not about databases. The Task_pkey row above is fast partly because that team owned 5,000 of the 5,005 rows, so almost nothing was filtered out. The same query for a 30-row team in a 50,000-row table chose a different plan. Re-run EXPLAIN when the shape of your data changes.

Overfetching: the query the response schema cannot fix

include: { owner: true }   ->  SELECT "User"."id", "email", "passwordHash", ...

The response schema (TaskPublic, three fields) drops the owner before anything reaches the wire. It cannot un-run the query. The hashes were already decoded into JavaScript objects in your process.

A field the response schema drops is a field you should not have selected. The schema is the last wall, not the first one.

Is an index earning its space? (lesson 46)

-- every index, worst first: never used, biggest
select relname tbl, indexrelname idx, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) size
from pg_stat_user_indexes
order by idx_scan, pg_relation_size(indexrelid) desc;

-- ALWAYS read this before trusting an idx_scan of 0
select stats_reset from pg_stat_database where datname = current_database();

-- shrink a bloated index. VACUUM does not do this.
REINDEX TABLE "Task";              -- locks writes; fine when small
REINDEX TABLE CONCURRENTLY "Task"; -- slower, does not block writers
  • idx_scan = 0 over a long stats window → drop it. It costs disk and a write on every insert/update/delete.
  • idx_scan = 0 over a short window → no information. stats_reset is the denominator.
  • Index much bigger than the rows it indexes → bloat, not a schema mistake. REINDEX. Measured here: 4,408 kB → 32 kB.
  • After any retention/delete job, reindex. Otherwise the indexes keep the space the rows gave back.
  • REINDEX needs table ownership — DATABASE_URL, not APP_DATABASE_URL.
  • High seq_scan on a tiny table is correct. Never read a scan ratio without the row count.

Should this index exist at all? (lesson 47)

An index is a bet that the query wants a small slice. If the query matches a large fraction of the table, Postgres ignores the index and scans the table — correctly. Measured on 200,000 rows, same index on at:

Rows matchedPlan chosenPages read
75%Seq Scan — index untouched1,082
1.8%Bitmap Index Scan13

The fold sits somewhere under a tenth of the table and moves with row width and physical order. Check, do not guess:

EXPLAIN (ANALYZE, COSTS OFF, BUFFERS) <your query>;
  • A plan from a small table is not evidence. Build the rows first — 414 rows fit in two pages and every plan looks fine.
  • Run ANALYZE after a bulk insert, or the planner is reading stale statistics.
  • An index with no query is pure cost: disk, plus work on every insert, update and delete.

Adding an index properly (lesson 47)

Never CREATE INDEX by hand in psql. Prisma will not know about it and the next reset loses it. The schema file is the truth.

// 1. schema.prisma, inside the model
@@index([at])

// 2. write the SQL, do not run it
npx prisma migrate dev --create-only --name audit_log_at_index

// 3. read migration.sql, add CONCURRENTLY if the table is live
CREATE INDEX CONCURRENTLY "AuditLog_at_idx" ON "AuditLog"("at");

// 4. apply, then confirm both sides agree
npx prisma migrate dev
psql "$DATABASE_URL" -c '\d "AuditLog"'
npx prisma migrate status
  • Plain CREATE INDEX takes ShareLock: reads pass, every write waits. On a big table that is an outage.
  • CONCURRENTLY cannot run inside a transaction. Prisma opens one only when the migration file holds more than one statement — so put a concurrent index alone in its own migration file.
  • If a concurrent build fails halfway it leaves an invalid index behind. Drop it by hand and retry.

Where the planner's row estimate comes from (lesson 48)

Postgres never counts rows to plan a query. It reads a stored guess, written by ANALYZE from a sample of 30,000 rows (default_statistics_target 100 × 300), and kept in pg_stats — one row per column.

psql "$DATABASE_URL" -c "select attname, null_frac, n_distinct from pg_stats where tablename = 'AuditLog';"
psql "$DATABASE_URL" -c "select relname, last_analyze, last_autoanalyze, n_mod_since_analyze from pg_stat_user_tables order by relname;"
Column of pg_statsMeaningUsed for
null_fracfraction of rows that are NULLIS NULL estimates
n_distinctcount of different values; negative = ratio to row count (−0.99 ≈ unique)col = X: rows ÷ distinct
most_common_vals / _freqsthe popular values and their real frequencycol = X when values are skewed
histogram_bounds101 values cutting the column into 100 equal-row bucketscol < X, ranges, BETWEEN
  • A range estimate is bucket counting. Cut-off near boundary 76 → ~75% of rows. That is where lesson 47's rows=150677 came from.
  • Measured: same query, truth 3,852 rows. No statistics → estimate 72,193 (19× out). After one ANALYZE → 3,737.
  • Stale statistics pick the wrong plan. 200,000 rows inserted unseen: estimate 5,811 → index scan over nearly the whole table. After ANALYZE: 201,208 → Seq Scan.
  • Autovacuum analyses after 50 + 10% of rows change. Under that, a small table can sit with no statistics for a long time.
  • Run ANALYZE by hand after a bulk load or bulk delete, and after a migration that adds an index. Milliseconds, no write lock.

Slow query after a data change? ANALYZE → EXPLAIN again → only then consider an index. The free fix comes before the permanent one.

Equality estimates: the three cases (lesson 49)

psql "$DATABASE_URL" -c "select attname, n_distinct, most_common_vals, most_common_freqs from pg_stats where tablename = 'Task' and attname = 'teamId';"
Case for WHERE col = XArithmeticMeasured example
X is in most_common_valsits most_common_freqs entry × rows0.96374 × 524 = 505, truth 505
X is not in the list(1 − sum of freqs) ÷ (unlisted distinct values) × rows0.00191 ÷ 1 × 524 = 1
No MCV list (no value is common)rows ÷ n_distinct524 ÷ 4 = 131, wrong for all 4 teams
  • The list holds up to 100 values (default_statistics_target), paired positionally with the frequencies.
  • An estimate is never 0. A value the list covers but the table lacks estimates as 1 row.
  • Selectivity is per value, not per column. Same table, same index: teamId = 652 (96%) → Seq Scan; teamId = 11 (1%) → Index Scan. Both correct.
  • Find your skew: select tablename, attname, most_common_freqs[1], (most_common_vals::text::text[])[1] from pg_stats where schemaname='public' and most_common_freqs[1] > 0.3 order by 3 desc; — most_common_vals is anyarray and must be cast before subscripting.
  • The knob, for one symptom only: ALTER TABLE t ALTER COLUMN c SET STATISTICS 500; then ANALYZE t; — for thousands of distinct values where a mid-sized one misses the top 100.
