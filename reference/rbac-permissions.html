Roles & permissions

The permission table for the Team Task Tracker, and the rules around it. Print this and keep it next to the code.

The two words

WordQuestionFails withWhere it lives
AuthenticationWho are you?401src/auth/require-auth.ts
AuthorizationMay you do this?403src/auth/can.ts

401 = come back with a name. 404 = you may not know this row exists (use it instead of 403 when the id itself is a secret). 403 = I know exactly who you are, and no.

Roles are data. Permissions are code.

  • A role is a row: this person, this team, this role. It changes at runtime.
  • A permission is a line in can.ts. It changes only when you deploy.
  • So nobody grants themselves a new power by editing a row — the powers are not in rows.
  • Move the map into the database only when users must build their own roles. Oso: "the map from a role to a list of permissions needs to be dynamic" — at that point, not before.

The shape

import type { Role } from "../generated/prisma/enums.ts";   // the Postgres enum
export const ROLES = ["VIEWER", "MEMBER", "ADMIN", "OWNER"] as const satisfies readonly Role[];
export type Action = (typeof ACTIONS)[number];

export type Resource = { targetRole?: Role | undefined };   // the thing acted on
const rank = (role: Role): number => ROLES.indexOf(role);   // derived, never retyped

export function can(role: Role | undefined, action: Action, resource?: Resource): boolean {
  if (role === undefined) return false;                     // 1. deny by default
  if (!(PERMISSIONS[role]?.includes(action) ?? false)) return false;  // 2. the table

  const target = resource?.targetRole;                      // 3. the rank rule
  if (target !== undefined && rank(role) <= rank(target)) return false;

  return true;
}

Six rules

  1. Deny by default. Unknown role, missing action, no membership → false. Never true, never a throw.
  2. One function. No if (role === "ADMIN") anywhere else. A scattered check is a check somebody forgets.
  3. Check on every request. OWASP: "permission should be validated correctly on every request, regardless of… source".
  4. Server side only. Hiding a button is not security. The front end may hide; the server must refuse.
  5. Every rule gets a test. It is a pure function — a test costs two lines.
  6. Fetch the target in the gate, never the handler. A handler only runs after the gate said yes, so a check there is a gate you can forget.

Naming

  • resource:verb, lower case, always. task:delete, not deleteTask or DELETE_TASK.
  • Name the action, never the role. can(role, "member:invite"), never isAdmin(user). When Admin loses inviting next year, you change one line, not forty.
  • Roles are SCREAMING_CASE because they will become a Postgres enum.

Where the role lives

Not on User. One column holds one answer, and a person has a different role in each team. The role belongs to the pair, so it is a join row.

enum Role { VIEWER MEMBER ADMIN OWNER }   // -> CREATE TYPE "Role" AS ENUM (...)

model Membership {
  role   Role @default(MEMBER)
  team   Team @relation(fields: [teamId], references: [id], onDelete: Cascade)
  teamId Int
  user   User @relation(fields: [userId], references: [id], onDelete: Cascade)
  userId Int
  @@id([teamId, userId])        // one membership per person per team
}
PieceWhat it buys
enum RolePostgres refuses a typo: invalid input value for enum Role: "ADMINN".
@@id([teamId, userId])Composite primary key. A duplicate membership cannot exist — the route turns the refusal into 409.
onDelete: CascadeNo orphan role in a deleted team, or for a deleted user.
Explicit join modelPrisma: use it whenever the join carries a field of its own.
Import the enum typeOne source of truth for the names. A new role breaks the build until PERMISSIONS covers it.

Creating a team makes the creator OWNER in the same transaction. A team with no owner is a team nobody can delete or invite into.

Enforcing it in a route

export function requirePermission(action: Action) {
  return async function gate(request, reply) {
    const { teamId } = request.params as { teamId: number };
    const role = await getRole(teamId, request.userId!);
    if (!can(role, action)) return reply.code(403).send({ error: "forbidden" });
    request.role = role;
  };
}

Reply codes. 401 = I do not know you. 403 = I know you, and no. Give the same 403 to a wrong role and to a total stranger — a 404 would confirm the team exists, and ids can be walked.

Testing the enforcing. Unit tests prove the decision; route tests prove the enforcing. Assert the status and the state — a 403 after the row was already deleted still reads as a pass.

The third argument

A role→action table only knows about the person asking. Some rules depend on the thing being acted on. Pass it as a third argument, and keep the table as the first question.

You may only act on somebody strictly below you. Equal rank is a no.

The gate does the fetching. A Load function says where the target lives, and the factory takes it as an optional second argument.

export type Load = (request: FastifyRequest) => Promise<Resource>;

// target named in the URL       DELETE /teams/:teamId/members/:userId
export const targetMember: Load = async (request) => {
  const { teamId, userId } = request.params as { teamId: number; userId: number };
  return { targetRole: await getRole(teamId, userId) };
};

// target named in the body      POST /teams/:teamId/members { role }
export const grantedRole: Load = async (request) => {
  const { role } = request.body as { role: Role };
  return { targetRole: role };
};

preHandler: requirePermission("member:remove", targetMember)
preHandler: requirePermission("member:invite", grantedRole)

Still not expressible: "you may edit a task you own." That is a fact about a row, not a role. Oso's stage three. It is no longer hiding in the store — lesson 10 took it out. If you ever want it back, it is a new field on Resource and a new comparison in can(), never a where clause.

Scope: the fact before the fact

A role is held in a team, so a permission question with no team in it has no answer. That is why every guarded URL names one.

PATCH /tasks/5                 ← no scope, no role, no answer
PATCH /teams/7/tasks/5         ← the gate can look up a role

The gate reads :teamId from the params, so the scope must be in the URL, not the body. A body can be changed after routing; a path cannot.

LayerQuestionWrong answer
GateMay a MEMBER of team 7 update tasks?403
StoreIs task 999 one of team 7's rows?404

Both refusals, two different codes, on purpose. 403 is about the person. 404 is about the row. Answering 403 for the second one would tell an attacker that the id exists somewhere else — which is the leak IDOR is made of.

Telling the UI, without moving the decision

A front end has to draw a screen before the user clicks anything, so it needs to know roughly what this person may do. Send it the answer; never send it the policy.

  • Hide, do not disable. A greyed-out Delete team still tells a Viewer the power exists here.
  • The list is approximate even when fresh. An Admin's can holds member:remove, and removing the Owner is still a 403 — the rank rule needs a target.
  • A list-shaped route needs no gate if the where clause is the scope: where: { userId } cannot return a row you may not see. An outsider gets [] and a 200, never a 403.

  • Ambiguity is the feature. Two situations sharing one status code is what stops a caller enumerating team ids or task ids.
  • The error line on screen must not out-explain the server. "That task belongs to another team" hands back exactly what the 404 blurred.
  • A list route only says 403. No row to miss: an empty team is 200 [].
  • The cache key mirrors the URL — ["teams", teamId, "tasks"]. Drop the scope from the key and one team renders another's rows with no request made and no refusal possible.

Glossary

TermPlain words
RBACRole-Based Access Control. Powers come from your role.
ABACAttribute-Based. Powers come from facts (time, department, amount).
ReBACRelationship-Based. Powers come from links ("owner of", "parent folder of").
Least privilegeGive the smallest set of powers that still lets the job get done.
Privilege creepPowers pile up over years and nobody takes them away.
IDOR / BOLASwap an id in the URL and read someone else's row. Number 1 on the OWASP API Top 10.
Decision vs enforcementcan() decides. The route enforces. Keep them apart.
Join rowA row about two things. Membership joins a user to a team and carries the role.
Composite primary keyThe key is two columns together: @@id([teamId, userId]).
Scoped roleA role that only counts inside one team. Oso's stage two, cross-organization roles.
Rank ruleYou may only act on somebody strictly below you on the role ladder.
Subject / operation / objectNIST's three parts of an access decision. can(role, action, resource).
LoaderThe small function that fetches the target so the gate can judge it.
401 vs 403I do not know you / I know you and no. Authn vs authz.
ScopeThe where of a permission. Which team the role is held in.
Scoping (a query)Narrowing which rows a permitted action can see. Not a permission.
403 vs 404Forbidden is about you and is decided first; not found is about the row and covers "elsewhere" as well as "nowhere".
Hint vs gateThe can list draws buttons; can() in the gate decides. Only the second one is security.
Expand / backfill / contractAdd nullable, fill it, then lock it. How a required column lands on a table with rows.
