Schema field cheatsheet

model Task {
  id         Int      @id @default(autoincrement())
  title      String   @db.VarChar(200)   // length rule in the table
  done       Boolean  @default(false)
  email      String   @unique            // no two rows alike
  ownerId    Int
  owner      User     @relation(fields: [ownerId], references: [id])
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt         // set on every write
  @@index([ownerId])                     // fast lookup by owner
}

Adding a required foreign key to a table that already has rows takes three migrations in production: add it nullable, backfill with UPDATE, then make it required. Only reset the database when the data is throwaway.

Adding a required column to a table with rows

Postgres will refuse. It cannot invent a value for the rows already there. Three steps, in this order — on a live server, three separate deploys.

npx prisma migrate dev --create-only --name <change>   # write the file, do not run it
# edit prisma/migrations/<stamp>_<change>/migration.sql
npx prisma migrate dev                                  # now run it
-- 1. EXPAND   nullable, so old rows may be empty for now
ALTER TABLE "Task" ADD COLUMN "teamId" INTEGER;

-- 2. BACKFILL  give every empty row a real value
UPDATE "Task" SET "teamId" = 1 WHERE "teamId" IS NULL;

-- 3. CONTRACT  nothing is empty, so the wall goes up
ALTER TABLE "Task" ALTER COLUMN "teamId" SET NOT NULL;
Way outCost
Make it nullableThe rule leaves the database. Every reader now needs a null branch, forever.
Delete the rowsFine on a laptop. Data loss anywhere else, and not undoable.
Expand / backfill / contractThree statements, and you must decide what the old rows meant. Take this one.

The backfill is not a technical step. It is you writing an assumption about the past into SQL, permanently. Say it in a comment.

Scoping vs permission in a where

These look identical and are not.

where: { id, ownerId }where: { id, teamId }
asksmay you?which rows?
decided bythis query, alone, untestedthe gate, already, upstream
remove it andanyone edits anythingyou leak across teams (IDOR)

A permission rule inside a query is a rule nobody can find. Move it to can(). Keep the scope.

Two kinds of nothing in a Json column

Postgres jsonb can be empty, or it can hold the JSON literal null. They are different values and only one of them matches IS NULL.

You writeColumn becomesIS NULLjsonb_typeof
undefinedSQL NULLtrueNULL
Prisma.DbNullSQL NULLtrueNULL
Prisma.JsonNullJSON nullfalse'null'
nullJSON nullfalse'null'

Prisma reads both back as JavaScript null, so the client cannot tell them apart. Only SQL can. Count them:

select count(*) filter (where col is null)             as sql_null,
       count(*) filter (where col = 'null'::jsonb)     as json_null,
       count(*) filter (where jsonb_typeof(col) = 'object') as real
from "Table";

Default to ?? undefined for a Json? field. Use Prisma.JsonNull only when a stored null is a fact you mean. And an as never on a Prisma write is a promise to the compiler — this is the bug it hides.

Database roles and privileges

Two permission systems sit under this app. can() decides what a person may do. A role (a database login) decides what the app may do. Today the app owns every table, so the second one grants everything.

NeedSQL
See the privileges on one table\dp "AuditLog" in psql, or select relacl from pg_class where relname = 'AuditLog';
Take a power awayREVOKE UPDATE, DELETE, TRUNCATE ON "AuditLog" FROM tasks_app;
Give a powerGRANT SELECT, INSERT ON "AuditLog" TO tasks_app;
A whole schema at onceGRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO tasks_app; — existing tables only
Cover future tables tooALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ... TO tasks_app;
Auto-increment ids need thisGRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO tasks_app;

Reading relacl. NULL means nothing is written down, so the owner holds everything. Otherwise the form is grantee=letters/grantor:

rawdDxt
SELECTINSERTUPDATEDELETETRUNCATEREFERENCESTRIGGER

Measured, lesson 41. An append-only AuditLog is {tasks=arxtm/tasks} — r and a, no w, no d, no D.

  • TRUNCATE is a separate privilege. Revoking DELETE leaves one word that empties the table.
  • A revoke on the owner works, and the owner can grant it back. Against your own role it guards mistakes, not attackers. The wall needs a second role that owns nothing.
  • Split the jobs, not the code. Serving requests, running migrations and deleting old rows are three jobs. Only the first faces the internet, and it is the one that needs least.
  • A role that owns nothing cannot grant itself anything. Measured in lesson 42: GRANT DELETE ON "AuditLog" TO tasks_app; run as tasks_app answers WARNING: no privileges were granted. Not an error — a warning, and nothing changes.
  • Assert the code, not the message. 42501 is the SQLSTATE for insufficient privilege. The English text can change between versions; the five characters cannot.

How big is it? (lesson 45)

pg_database_size('tasks')whole database, including the ~7.4 MB catalog floor
pg_total_relation_size('"AuditLog"')one table: heap + indexes + TOAST — the default answer
pg_relation_size('"AuditLog"')the rows only
pg_indexes_size('"AuditLog"')the indexes only
pg_size_pretty(...)wrap any of them: bytes → 3152 kB

Prisma table names are capitalised, so they need SQL double quotes inside shell single quotes: '"AuditLog"'. Unquoted AuditLog folds to auditlog and does not exist.

Every table, biggest first — the query to run when a disk alert fires:

select relname,
       pg_size_pretty(pg_total_relation_size(c.oid)) as total,
       pg_size_pretty(pg_relation_size(c.oid))       as heap,
       pg_size_pretty(pg_indexes_size(c.oid))        as idx
from pg_class c join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relkind = 'r'
order by pg_total_relation_size(c.oid) desc;

Measure growth per table, never with pg_database_size — an empty database is already 7.4 MB, which buries the change. The app login may read all of these; size is not privileged.

Rules that keep you out of trouble

  • Never edit a migration that has already run. Add a new one.
  • Commit prisma/migrations/. Never commit .env.
  • One role and one database per project. Never develop as the postgres superuser.
  • The role needs CREATEDB, because migrate dev makes a temporary shadow database.
  • One PrismaClient for the whole app, exported from src/db.ts.
  • Put the rule in the table too, not only in Zod. Zod guards one door.
  • Use the query API, not string-built SQL. That is what stops SQL injection.
  • Reading a list? Add take and skip before the table gets big.
  • Index every column you filter a list on: @@index([teamId]).
  • A required column on a table with rows is three steps, never one.
  • A where that decides may you is a permission rule in hiding. Move it out.
  • Json? field with no value? Write undefined, not null. null stores the word.
  • A privilege nothing in the app uses is a privilege to revoke. Check before you assume it is needed.
