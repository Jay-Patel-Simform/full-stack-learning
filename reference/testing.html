Tests in this project

How the suite is run, what each kind of test is for, and the four ways a test can pass without proving anything. Open this before you add a test file. From lessons 6, 34 and 35.

The rule

A test you have never seen fail is not a test. It is a file.

The commands

CommandWhereWhat it does
npm testserver/All server tests. Hits the real Postgres. Expect 155.
npm testweb/Pure front-end logic only, no browser. Expect 5.
npx tsx --test src/x.test.tsserver/One file, while you are writing it. Add LOG_LEVEL=silent in front to keep it quiet.
npm run typecheckserver/tsc --noEmit. Not a test. It cannot see a wrong value, only a wrong type.
npx tsc -bweb/Same job on the front end.

On the server: no Jest, no Vitest, no test framework installed. The runner is node:test, which ships inside Node, driven through tsx so it reads TypeScript. Decided in lesson 6 and still the right call. On the front end that changed in lesson 68 — the first component test needed a DOM, a JSX transform and the @/ alias, so web/ now runs Vitest. See Front-end testing.

Globs: quote them, always

"test": "LOG_LEVEL=silent tsx --test \"src/**/*.test.ts\""
shell expansion — the shell replaces the pattern with matching file names before your program starts. Quoted, it does not touch the pattern, and the runner does the matching itself.
globstar — ** meaning “any number of directories”. On in zsh. Off in sh and bash, where ** is an ordinary * — one level only.

npm run uses sh, your terminal uses zsh. Unquoted, the same script gives different suites in the two places. Measured in lesson 35: 154 through npm test, 155 pasted into the terminal.

The check, any project, any runner:

find src -name '*.test.ts' | wc -l        22   files on disk
sh -c 'set -- src/**/*.test.ts; echo $#'  21   files the runner gets

When those two numbers disagree, some test file is never running and nothing will tell you.

The four silent passes

FailureCauseHow to catch it
The file never ranA glob the shell ateExpect a number. A new file must move it.
It ran with nothing to readLOG_LEVEL=silent, an empty stream, an empty listassert.ok(all.length > 0) first, before any “is not present” check.
It asserted the obviousBoth branches give the same answer on your dataUse data where the right and wrong answers differ.
The type checker passedtsc believes a declared type; it does not check a valuetsc is not a test. Run the code.

One habit covers all four: break the code, watch the test go red, put the code back.

Two kinds of test, and which to write

decision test

can("VIEWER", "task:update")
// false

Pure function, no app, no database. Fast, and it can cover every role and action. Use it for the rule.

enforcement test

await app.inject({
  method: "PATCH", url: "...",
  cookies: { sid } })
// 403

app.inject() runs a real request through the real pipeline — hooks, CSRF, zod, Postgres — with no port and no network. Use it for the wiring.

A passing decision test with no enforcement test means the rule is correct and possibly not called. Seventeen test files use app.inject(); that is the shape to copy.

Fixtures: every file is its own process

The runner starts one process per file and runs up to 8 of them at once on this machine. So two files that seed rows with the same key will delete each other’s data, and the failure looks like a random 401. This cost an afternoon in lesson 10.

RuleWhy
Each file makes its own fixtureNo shared setup file to depend on, and no order between files.
Make every key unique per fileconst stamp = Date.now() is not enough on its own — add the file’s own prefix.
Never share state between filesThere is no order and no lock. Two files are genuinely concurrent.
Clean up rows you seededThe dev database is also the app’s database.

Reading a log line in a test

const out: string[] = [];
const sink = new Writable({
  write(chunk, _enc, cb) { out.push(chunk.toString()); cb(); },
});
const app = await buildApp(sink);        // a stream raises the level too
// ... make it log ...
const all = out.join("");
assert.ok(all.length > 0, "the log wrote nothing - check the level");

buildApp(logStream?) exists because a log line has no failing state — the only way to test one is to read it. Passing a stream is the signal that you intend to read the log, so buildApp raises the level above LOG_LEVEL=silent. Without that, the test reads nothing and passes forever.
