Sessions & cookies

Quick-reference sheet. Print it. Rules come from The Copenhagen Book, checked 2026-09-02.

The one rule

The browser holds a long random id. The database holds only its SHA-256. Every request looks the id up. Delete the row and the login is over, instantly.

Session vs JWT

Server-side sessionJWT
Browser holdsRandom id, means nothing aloneSigned user data
Cost per requestOne indexed row readSignature check, no I/O
Instant logoutYes — delete the rowNo — valid until it expires
Ban a user nowYesNo
Change a role nowYesNo, stale until refresh
Pick it whenOne app, one database. Default.Many services that must not share a database

A "refresh token stored in a database table" is a session with extra steps. If you need revocation, you need a lookup. Decide that once, up front.

Generating the id

RuleValueWhy
Entropy≥ 112 bits (120–256 is the good range)Guessing one must be impossible
SourcerandomBytes() — never Math.random()Must be cryptographically secure
Encodingbase64url or base32; case sensitiveSafe in a cookie with no escaping
Stored assha256(id)A stolen dump holds no live logins
const id = randomBytes(15).toString("base64url");        // 120 bits
const idHash = createHash("sha256").update(id).digest("base64url");

Which hash, where

SecretHash withBecause
Password (human, short)scrypt / argon2idLow entropy. Slowness is the only defence.
Session id (random, 120 bits)sha256Nothing to guess. Speed costs you nothing.
Password reset tokensha256Same — it is a random token, not a password.

The rule to remember: slow hashing protects guessable secrets. Not "always slow".

Cookie flags

Set-Cookie: session=<id>; HttpOnly; SameSite=Lax; Path=/; Secure; Expires=<utc>
FlagStopsNote
HttpOnlyXSS reading the cookieAlways. No exceptions.
SameSite=LaxBasic CSRF from another siteNot Strict: Strict logs users out when they arrive from an external link.
SecureThe cookie crossing plain httpRequired in production. Omit on localhost or it is never stored.
Path=/—So every route receives it.
Expires / Max-AgeCookies outliving the rowMatch the session's expiresAt.

SameSite is not full CSRF protection. Add a real check for state-changing routes. Copenhagen — CSRF.

Expiry

  • Sliding window (normal apps): 30 days, pushed back to 30 on each use. Rewrite the row only past the halfway point, so you are not writing on every request.
  • Absolute cap (banking, admin): also expire N hours after creation, no matter how active the user is.
  • Check expiry in code on every read. The row may still be in the table.
  • Expired rows only die when someone touches them. A periodic sweep is still needed.

Login route checklist

  1. One error message for every failure: "invalid email or password".
  2. Hash even when the user does not exist (a dummy hash), so both paths take the same time.
  3. No .min(8) on the login schema. That is a register rule, and here it is a free hint.
  4. New session id on every login. Never reuse one.
  5. Reply carries no hash, no session id in the body — only the cookie.
  6. Missing today: rate limit. Weeks 7–8.

Ownership: the where clause rule

// wrong -- any logged-in user can hit any row (IDOR)
prisma.task.updateMany({ where: { id }, data });

// right -- the owner is part of the lookup
prisma.task.updateMany({ where: { id, ownerId }, data });
Updated in lesson 10. Once tasks belong to a team, the where carries teamId, not ownerId — and the permission itself moves out of the query into requirePermission. See lesson 10 for the difference between a fence and a hidden permission.

Authentication answers who. Authorization answers allowed. Passing the first never grants the second. OWASP API Top 10 #1.
