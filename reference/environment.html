Environment and config

Every variable the server reads, what it decides, and what a wrong value costs. Open this during a deploy. From lesson 27 and lesson 29.

The rule

A .default() is a place a typo can hide. Give one only where being wrong is visible in a second.

fail fast — refuse to start when the setup is wrong. The error lands in the deploy log.
fail quiet — start with a fallback. The error lands in an incident report.

And the second rule, from lesson 29: one fact, one reader. config.ts is the only file that may touch process.env. Everywhere else imports config.

snapshot — a copy taken once. config is one: read at import, never re-read.
live read — going back to the source each time. process.env.X is one, and process.env is mutable, so the two can disagree inside a single running process.

The shape

// src/config.ts - parsed once, at boot, before anything else runs.
try { process.loadEnvFile(); } catch { /* no file in production */ }

const Env = z.object({ /* … */ });
const parsed = Env.safeParse(process.env);

if (!parsed.success) {
  console.error("Bad environment:\n" + z.prettifyError(parsed.error));
  process.exit(1);          // the exit code is what the host reads
}

export const config = parsed.data;   // typed. Never read process.env again.

The leftovers checklist

Adding a validated config is two jobs, and the second is easy to skip. Run these four after any config refactor:

Look forCommandWhy it is wrong
A second readergrep -rn "process\.env" src/ --include="*.ts" | grep -v generatedOnly config.ts and tests may appear. A snapshot and a live read of one fact will drift.
A second defaultgrep -n "config\.[A-Z_]* ??" src/?? on a value zod already defaulted is dead code that reads like a safety net. It also lies about the type.
A second loadEnvFilegrep -rn "loadEnvFile" src/One call, in config.ts. A module’s imports all finish before its own body runs, so importing config is enough.
A missing examplediff <(grep -oE "^[A-Z_]+" .env | sort) <(grep -oE "^[A-Z_]+" .env.example | sort)No output means the committed file lists every name. .env is gitignored, so this file is the only documentation.

None of the four is visible to tsc or to a passing test suite. The program behaves identically with and without them. There is no green light that will ever turn red — so these are found by grep, then locked down by a test.

Hosted Postgres: which URL goes where (lesson 55)

A managed Postgres such as Neon hands you two connection strings for one database. They differ only by -pooler in the host name, and they are not interchangeable.

VariableRoleEndpointWhy that one
DATABASE_URLownerdirect (no -pooler)prisma migrate deploy takes an advisory lock, and a lock belongs to one connection. A pooler may put the next statement on a different one, so the lock stops protecting you — silently, and only when two containers start at once.
APP_DATABASE_URLtasks_app-poolerEvery request, short-lived. Postgres holds only a few hundred connections and each costs memory; PgBouncer lends a small set out per query.

The owner/app split from lesson 42 was made for security. It turns out to be exactly the split pooling needs. One decision, paid twice.

A role password on a hosted database needs real entropy — Neon requires about 60 bits and refuses anything weaker at CREATE ROLE. Generate one with openssl rand -base64 18.

.env.example, the shape

# Copy to .env and fill in. The first five have NO default: no value, no boot.
# Values here are placeholders, never real secrets.

# The owner. Migrations, seeds, npm test.
DATABASE_URL=postgres://tasks:CHANGEME@localhost:5432/tasks
# The login the running server uses. Owns nothing, cannot delete an audit row.
APP_DATABASE_URL=postgres://tasks_app:CHANGEME@localhost:5432/tasks
NODE_ENV=development                      # development | test | production
ALLOWED_ORIGINS=http://localhost:5173     # comma separated
TRUST_PROXY=false                         # true/1/yes/on or false/0/no/off

# Optional - config.ts has a default for each of these three.
# PORT=3000
# HOST=127.0.0.1
# LOG_LEVEL=info

Keep the required block and the commented-out optional block visually apart. That split is the lesson-27 rule, made readable by someone who never opens config.ts.

Two logins, one app

New in lesson 42. The login is chosen by the job, not by the file. One line in src/db.ts:

const connectionString =
  config.NODE_ENV === "test" ? config.DATABASE_URL : config.APP_DATABASE_URL;
JobLoginWhy

Measured, lesson 42. A shell variable beats .env. process.loadEnvFile() only fills in what is missing, so NODE_ENV=test npm test works even though .env says development. Same reason LOG_LEVEL=silent has worked since lesson 6.

Least privilege applies to the exposed path, not to your terminal. Locking down your own commands costs an hour a week and buys nothing.

The cookie-flag trap

sessionCookie() and clearCookie() both decide on Secure from NODE_ENV. If they read it from different places they can disagree:

set-cookie   : session=abc; HttpOnly; SameSite=Lax; Path=/; Expires=...
clear-cookie : session=;    HttpOnly; SameSite=Lax; Path=/; Max-Age=0; Secure
                                                                  ^ mismatch

An http: site cannot set a Secure cookie at all, so the browser drops that whole header. Logout answers 200, the server row is gone, and the browser still holds a cookie. The flags on a clearing cookie must match the cookie being cleared, Secure included. The regression test lives in src/auth/session.test.ts.

Deploy checklist

  1. .env is in .gitignore. .env.example is committed and lists every name.
  2. Production sets all four required names. No file — the host’s secret store.
  3. NODE_ENV=production, lowercase. Check the reply carries strict-transport-security.
  4. TRUST_PROXY=true only where a proxy you control is the only way in.
  5. HOST=127.0.0.1 when nginx fronts it. 0.0.0.0 only where the platform terminates TLS for you.
  6. ALLOWED_ORIGINS can be empty of foreign origins when the front end is same-origin (lesson 14) — but the variable itself must still be set.
  7. Boot once with a deliberately wrong value and confirm the deploy fails. A safety net you have never tested is a decoration.

What config cannot check

  • A misspelled optional name. process.env holds hundreds of keys, so the schema must ignore unknown ones. Removing the default is the defence, not the schema.
  • Whether the values are true. z.url() says “shaped like a URL”, not “a database answers there”. That is a health check.
  • Whether a secret leaked. That is .gitignore and rotation.
  • That the rest of the app actually uses it. A validated schema plus a ?? "default" somewhere else is worse than no schema, because it looks finished. A written rule in CLAUDE.md is not enforcement either; the two things that enforce are refusing to boot, and a failing test.
