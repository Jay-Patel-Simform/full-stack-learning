Logging and redaction

What a log line may carry, what it may never carry, and how to prove it. Open this before you add a log call. From lesson 34.

The rule

Log the fields you chose. Never a whole object.

structured log — every line is JSON with named fields, not a sentence. You filter on userId=7; you do not write a regular expression.
allowlist — you name what is permitted. Everything else is refused by default. { userId: user.id }, TaskPublic, strict().
denylist — you name what is forbidden. Everything else passes. redact is one, and it only covers what you predicted.
redaction — replacing a value with "[Redacted]" before it is written. The key stays, so you can still see the field existed.
log stream — where the lines are written. Default stdout. Point it at memory and a test can read them.

The second rule, and the one that costs money when it is broken: a log is a second wire out of your process. The reply has a schema. The log does not. Same catch block, same secrets in scope.

Path syntax, and the trap

A path is exact, counted from the root of the log line. The wildcard is one level.

PathAgainst { err: { user: { passwordHash } } }
"user.passwordHash"misses — wrong root
"*.passwordHash"misses — * is one level, this is two
"err.*.passwordHash"catches
"err.user.passwordHash"catches
"**.passwordHash"misses, and says nothing. Not pino syntax. No throw, no warning, value printed in full.

Third member of a family you now know: dead code has no failing state (lesson 29), a filter missing from the key sends zero requests (lesson 33), a redact path that matches nothing is silence (lesson 34).

remove: true deletes the key instead of the value. Not used here — “this field was present” is worth keeping while reading a log.

Levels

NameNumberUse it for
error50Our code broke. Someone should look.
warn40Recovered, but suspicious. Rate limit hit, bad login burst.
info30The default. One line in, one line out, per request.
debug20Turned on while hunting something. Off in production.
silent—npm test. Nothing is written at all.

LOG_LEVEL sets the floor: lines below it are never written. See environment and config.

Testing a log line

A log line has no failing state, so give it a stream and read it.

const out: string[] = [];
const sink = new Writable({
  write(chunk, _enc, cb) { out.push(chunk.toString()); cb(); },
});
const app = await buildApp(sink);          // a stream also raises the level

app.log.error({ err }, "unhandled error");
await app.close();

const all = out.join("");
assert.ok(all.length > 0, "the log wrote nothing - check the level");
assert.ok(!all.includes("scrypt$SALT$HASH"));

Assert the log is not empty first. An empty string passes every “does not include” check, so without that line the test is green on the day redaction breaks.

Audit rows: pointer and copy (lesson 36)

An id is a pointer. A pointer into a deleted row is nothing. An audit row stores copies.

ColumnKindStill true after the target is deleted?
userId, teamId, params.idPointerNo — measured: 3,428 of 7,201 rows point at a user that is gone
actorEmail, targetType, targetSnapshotCopyYes, forever

Rules that go with it:

  • No @relation on userId or targetId. A cascade deletes the evidence at the moment it becomes evidence.
  • Snapshot columns are nullable. Old rows cannot be backfilled, and invented data in an audit log is worse than an empty column.
  • Never update a snapshot. If it followed the live row, a rename would rewrite history.
  • Append-only. Enforced in code today; REVOKE UPDATE, DELETE in the database is the week-13 version.

When to capture (lesson 36)

The audit write lives in one onResponse hook. That hook runs after the handler, so on a delete there is nothing left to read — the snapshot read returns null, silently.

onRequest   requireAuth        target alive
preHandler  requirePermission  target alive
handler     deleteTask(...)    target gone from here on
onResponse  writeAudit(...)    too late to copy anything

Capture early, write once. The handler fills request.auditTarget; the hook is still the only code that inserts a row.

Retention: how rows leave (lesson 43)

The app cannot delete an audit row — tasks_app has no DELETE. One job does it, and it is the second job that needs the owner login (migrations were the first).

npm run audit:prune              # uses AUDIT_RETENTION_DAYS, default 90
AUDIT_RETENTION_DAYS=3 npm run audit:prune   # one run, different cutoff

0 3 * * * cd /path/to/server && /usr/local/bin/npm run audit:prune >> /tmp/audit-prune.log 2>&1

Space: DELETE does not shrink the table (lesson 44)

A DELETE marks a row version dead and leaves the bytes in the file. Retention bounds the table; it does not make it smaller.

on a log tablethis is the answeronly after a one-off huge delete, off-hours
# is it happening? one query, changes nothing
select n_live_tup, n_dead_tup, vacuum_count, autovacuum_count, last_autovacuum
from pg_stat_user_tables where relname='AuditLog';

select pg_size_pretty(pg_total_relation_size('"AuditLog"'));   # total
select pg_size_pretty(pg_relation_size('"AuditLog"'));         # heap only
select pg_size_pretty(pg_indexes_size('"AuditLog"'));          # indexes — often bigger

The silent failure. VACUUM as a non-owner prints WARNING: permission denied to vacuum ... skipping it, then reports VACUUM and exits 0. DELETE under the same login is a hard ERROR. A maintenance job must report a number it measured — the way pruneAuditLog() returns a row count — not just finish.

Before you add a log call

  1. Is it an object? Replace it with the two or three fields you actually want.
  2. Could any of those fields ever hold a secret? Then it is an id, not the thing.
  3. Is it inside a loop or a hot path? A log line per row is how you fill a disk.
  4. grep -rnE "\.log\.(info|error|warn)|console\." server/src — keep this number small enough to read.
