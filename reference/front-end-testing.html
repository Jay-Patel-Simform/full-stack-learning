Front-end testing

The setup, the three queries that matter, and the defaults that are right for an app and wrong for a test. From lesson 68. For the server suite see Tests in this project.

The two rules

Test what a user can do; never test what a component knows.

A test you have never seen fail is not a test. It is a file.

One runner, and the conversion it cost

node:test cannot be bundled into the jsdom environment: Cannot bundle Node.js built-in "node:test", and the file does not load at all. Converting a pure-function file is mechanical — drop the node:test and node:assert imports (test and expect are globals) and rewrite the assertions. To keep the old reading style, six wrappers at the top of the file:

const expectSame = (a: unknown, b: unknown) => expect(a).toBe(b);
const expectNotSame = (a: unknown, b: unknown) => expect(a).not.toBe(b);
const expectEqual = (a: unknown, b: unknown) => expect(a).toEqual(b);
const expectNotEqual = (a: unknown, b: unknown) => expect(a).not.toEqual(b);
const expectThrows = (fn: () => unknown) => expect(fn).toThrow();
const expectTruthy = (v: unknown) => expect(v).toBeTruthy();

Swap the runner before writing new tests, so this failure arrives with one suspect instead of four.

The setup, in three files

// vite.config.ts — one new key, nothing else moves
test: {
  environment: "jsdom",
  setupFiles: ["./src/test-setup.ts"],
  globals: true,
}
// src/test-setup.ts
import { afterEach } from "vitest";
import { cleanup } from "@testing-library/react";
// ! or the second test finds two forms and every getBy* throws
// ! "found multiple elements" -- an error naming the wrong problem.
afterEach(cleanup);
// package.json
"test": "vitest run"

Which query? In this order

Reach forWhenWhy it is first
getByRole(role, {name})buttons, links, headings, inputsFails exactly when a user could not find it. Accessibility becomes load-bearing.
getByLabelTextform fieldsProves the label is actually associated with the input, which is the bug you would otherwise ship.
getByTextmessages, static copyFine for content, useless for controls.
getByTestIdlast resortA handle added for the test’s convenience. Survives changes that leave a real person stranded.

findBy* not getBy* for anything async. getBy* throws immediately; findBy* retries until it appears or times out. A message that arrives after a request needs findBy.

Defaults that are right for an app and wrong for a test

DefaultWhat it does in a testSet
React Query retriesA failing request is retried with backoff, so the test waits and then reports a timeout — naming the wrong problem.retry: false on queries and mutations
A shared QueryClientCache from test one leaks into test two.A fresh new QueryClient() per render
No cleanupMounted trees pile up in the document.afterEach(cleanup)
Live spiesA mock from one test answers in the next.afterEach(() => vi.restoreAllMocks())

The wrapper every component test needs

function renderForm() {
  const client = new QueryClient({
    defaultOptions: { queries: { retry: false }, mutations: { retry: false } },
  });
  return render(
    <QueryClientProvider client={client}>
      <MemoryRouter><NewTeamForm /></MemoryRouter>
    </QueryClientProvider>,
  );
}

A component is a thing in a tree, not a thing with arguments. That is the whole reason a component test feels heavier than a function test, and the wrapper is where the weight lives.

Faking the network

const spy = vi.spyOn(api, "post").mockResolvedValue({ data: { id: 7, name: "Design" } });
// a refusal:
vi.spyOn(api, "post").mockRejectedValue({
  isAxiosError: true,
  response: { status: 403, data: { error: "forbidden" } },
});

One line, on the axios instance. MSW (a mock HTTP server) is the heavier, more faithful answer — reach for it when several requests interact, not for one POST.

Assert the value, not the call

expect(spy).toHaveBeenCalledTimes(1);          // weak: passes with untrimmed input
expect(spy.mock.calls[0]?.[1]).toEqual({ name: "Design" });  // the real assertion

Same family as the server rule from lesson 20: a sort test whose two orders agree cannot fail. Pick fixtures and assertions that can tell the right answer from the nearly-right one.
